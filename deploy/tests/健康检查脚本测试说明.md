# 单服务器健康检查脚本测试说明

## 目的

验证 `deploy/xupan-healthcheck.sh` 能够只读检查 Spring Boot 的
`/actuator/health`，只有 HTTP 200 且 JSON 中的 `status` 为 `UP` 时返回 0。
网络错误、非 200 响应、响应状态不是 `UP` 或响应不是预期 JSON 时，脚本必须向
标准错误输出不含敏感信息的失败摘要并返回非 0。

脚本只负责发现并记录失败，不执行 `systemctl restart`，服务恢复由
`xupan-server.service` 的 `Restart=on-failure` 负责。

## 本地静态检查

在 Linux、WSL 或安装了 Bash 的环境执行：

```bash
bash -n deploy/xupan-healthcheck.sh
git diff --check
```

预期：两个命令均返回 0。Windows PowerShell 本身不能执行 `bash -n` 时，只记录为
“待 Linux/WSL 执行”，不能把 PowerShell 语法检查结果当作 Bash 验证。

## 受控动态检查

动态检查需要在具有 Bash、curl、systemd 和本地 Spring Boot 服务的 Linux 环境执行，
不应在本机脚本测试中连接真实生产服务器。可使用本地测试 HTTP 服务，或在授权的
维护窗口使用 `XUPAN_HEALTHCHECK_URL` 指向本机健康端点：

```bash
XUPAN_HEALTHCHECK_URL=http://127.0.0.1:8080/actuator/health bash deploy/xupan-healthcheck.sh
```

应覆盖以下结果：

| 场景 | 预期退出码 | 预期证据 |
| --- | ---: | --- |
| HTTP 200 且 `{"status":"UP"}` | 0 | 标准输出包含 `result=UP` |
| 服务未监听或连接超时 | 非 0 | 标准错误包含 `curl_exit`，不包含环境变量或凭据 |
| HTTP 500/503 | 非 0 | 标准错误包含 `http_status` |
| HTTP 200 但状态为 `DOWN` | 非 0 | 标准错误包含 `health_status_not_UP` |
| HTTP 200 但响应不是健康 JSON | 非 0 | 标准错误包含 `health_status_not_UP` |

检查日志时执行：

```bash
journalctl -t xupan-healthcheck -n 50 --no-pager
systemctl status xupan-healthcheck.timer --no-pager
systemctl status xupan-server --no-pager
```

## systemd 配置检查

安装到服务器前，管理员应先使用 `systemd-analyze verify` 检查 unit 文件，再按维护
窗口启用 timer。此步骤不应通过应用启动过程自动安装或覆盖系统配置：

```bash
systemd-analyze verify deploy/xupan-server.service deploy/xupan-healthcheck.service deploy/xupan-healthcheck.timer
```

确认 `xupan-server.service` 的日志标识为 `xupan-server`，健康检查日志标识为
`xupan-healthcheck`，JVM fatal error 文件写入 `/opt/xupan-platform/logs/hs_err_pid%p.log`。
启用 timer 后，健康检查失败只产生 journal 记录，不会直接重启应用。

部署前必须由管理员预创建日志目录，并确认服务用户可写、其他普通用户不可读：

```bash
install -d -o xupan -g xupan -m 0750 /opt/xupan-platform/logs
```

该命令只作为部署前置说明，本任务没有在真实服务器执行。
