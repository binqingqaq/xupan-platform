# 阶段二：玩家链接登录与聊天室权限实施计划

> **给实施者：** 本阶段在身份字段完成后执行。核心验收是“链接玩家能进入聊天室，但不能获得后台、下注、钱包或开奖权限”。

**目标：** 为普通玩家建立可撤销、可过期的链接登录机制，并将其认证主体限制为 `CHAT_ONLY`；管理员仍使用密码登录，托继续由服务端行为链路运行。

**架构：** 增加玩家访问链接表，数据库只保存链接哈希；访问链接兑换为现有会话体系中的普通访问 token，并在认证上下文附带 `CHAT_ONLY` 范围。后端按路径和范围双重校验，聊天 REST 与 WebSocket ticket 允许该范围，其他业务 API 明确拒绝。

**技术栈：** Java 21、Spring Security、JDBC、Flyway、MySQL 8.4 LTS、H2、Vue 3、TypeScript、Vitest、现有 WebSocket。

## 全局约束

- 不把链接明文、访问 token、刷新 token 写入数据库、日志或前端持久化存储。
- 链接登录只能绑定 `player_kind=NORMAL` 的 ACTIVE 玩家；`BOT` 使用服务端身份，不生成玩家链接。
- `CHAT_ONLY` 不能调用 `/api/admin/**`、`/api/demo/game/**`、钱包接口、用户管理接口和机器人管理接口。
- 余额、下注、开奖、中奖、流水和结算继续只表示虚拟积分；本阶段不新增现实资金能力。
- 登录链接必须有过期时间、主动撤销、重新生成和所有会话失效能力。
- 现有管理员登录、刷新、退出、WebSocket ticket 和 `/room` 不得回归。
- 不能只靠 Vue 路由隐藏页面；接口和 WebSocket ticket 都必须验证范围。

## 任务 1：定义认证模式和访问链接表

- [ ] **步骤 1：写迁移测试。** 断言 `sys_user.auth_mode` 默认兼容现有密码用户；普通玩家可标记为 `PLAYER_LINK`；托为 `BOT_SERVICE`；访问链接表包含 user、token hash、范围、过期、撤销、创建人和时间字段。
- [ ] **步骤 2：新增 `V19__建立玩家访问链接与认证模式.sql`。** 建议字段：

```sql
ALTER TABLE sys_user ADD COLUMN auth_mode VARCHAR(24) NOT NULL DEFAULT 'PASSWORD';
ALTER TABLE sys_user ADD CONSTRAINT ck_sys_user_auth_mode
  CHECK (auth_mode IN ('PASSWORD', 'PLAYER_LINK', 'BOT_SERVICE'));

CREATE TABLE player_access_link (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    token_hash CHAR(64) NOT NULL,
    scope VARCHAR(32) NOT NULL,
    expires_at TIMESTAMP NOT NULL,
    revoked_at TIMESTAMP NULL,
    last_used_at TIMESTAMP NULL,
    created_by BIGINT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_player_access_link_hash UNIQUE (token_hash),
    CONSTRAINT fk_player_access_link_user FOREIGN KEY (user_id) REFERENCES sys_user(id),
    CONSTRAINT ck_player_access_link_scope CHECK (scope = 'CHAT_ONLY')
);
```

- [ ] **步骤 3：编写模式迁移规则。** 现有管理员保持 `PASSWORD`；已有普通玩家切换为 `PLAYER_LINK` 前必须先生成有效链接；托切换为 `BOT_SERVICE` 并撤销所有链接。
- [ ] **步骤 4：运行 H2 迁移测试。**

运行：`.\mvnw.cmd -pl server/xupan-server -Dtest=FlywayAuthMigrationTest test`

预期：字段、约束、外键、索引和默认值通过。

## 任务 2：实现链接签发、兑换和撤销

**接口契约：**

```text
POST /api/admin/player-desk/players/{userId}/access-links
POST /api/player-auth/exchange
POST /api/admin/player-desk/players/{userId}/access-links/{linkId}/revoke
POST /api/admin/player-desk/players/{userId}/access-links/rotate
```

- [ ] **步骤 1：实现 `PlayerAccessLinkRepository`。** 只按 `SHA-256(rawToken)` 查询；兑换时使用数据库行锁或原子条件更新 `last_used_at`，检查玩家状态、链接状态、范围和过期时间。
- [ ] **步骤 2：实现 `PlayerLinkAuthenticationService.issue`。** 生成足够长度的随机原始 token，只返回一次；写入哈希、`CHAT_ONLY`、过期时间和后台操作人；日志仅写 link ID、user ID 和结果。
- [ ] **步骤 3：实现 `exchange`。** 验证原始 token，确认 `auth_mode=PLAYER_LINK`、用户和账户 ACTIVE，然后调用现有会话/token 服务创建受限会话。兑换失败统一返回不可枚举的错误，不暴露用户是否存在。
- [ ] **步骤 4：实现撤销和轮换。** 撤销当前用户的所有旧链接和玩家会话，轮换后只返回新的完整链接；托和删除状态不可签发。
- [ ] **步骤 5：为 Controller 写 MockMvc 测试。** 覆盖成功、过期、撤销、重复兑换、停用玩家、托玩家、无权限管理员和 token 不落日志。
- [ ] **步骤 6：运行后端专项测试。**

运行：`.\mvnw.cmd -pl server/xupan-server -Dtest=PlayerLinkAuthControllerTest,PlayerLinkAuthenticationServiceTest test`

预期：链接生命周期和错误边界全部通过。

## 任务 3：把 CHAT_ONLY 接入统一认证和聊天室

- [ ] **步骤 2：扩展 Bearer token 过滤器。** 从数据库恢复玩家范围，构造 `AuthenticatedUser` 时不注入任何管理员权限；失效、撤销、软删除和 security version 变化立即拒绝。
- [ ] **步骤 3：修改 `SecurityConfig`。** 聊天 GET/POST/read-cursor 和 `/api/auth/ws-ticket` 可接受 `CHAT_ONLY`；后台、游戏、钱包和机器人路径继续要求管理员/业务权限。
- [ ] **步骤 4：修改 `AuthController.wsTicket` 和 WebSocket 校验。** ticket 绑定 user ID、room code 和 scope；`CHAT_ONLY` 只能绑定聊天室，不能复用到游戏或后台通道。
- [ ] **步骤 5：修改 `ChatController`。** 继续使用当前认证主体写入消息和游标，确保链接玩家的昵称、member code 和 internal code 来源于服务端身份，不接受客户端覆盖。
- [ ] **步骤 6：写权限矩阵测试。** 至少断言：

## 阶段验收标准

- 管理员必须密码登录，原权限和后台路由不变。
- 普通玩家通过有效链接进入聊天室，能读取和发送消息。
- 普通玩家不能访问后台、下注、钱包、开奖和机器人管理接口。
- 托不生成玩家链接，不因 `BOT_SERVICE` 变更而影响自动/手动行为。
- 链接过期、撤销、轮换和玩家停用后均不能建立新会话。
- H2 测试和本地浏览器聊天运行态通过；服务器验证在阶段四完成前不能宣称完成。
