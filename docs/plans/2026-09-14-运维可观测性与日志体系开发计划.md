# 运维可观测性与日志体系实施计划

> 给实施者：按任务顺序执行本计划。步骤使用复选框（- [ ]）跟踪进度。本计划已进入实施后复核阶段；代码、配置、本地自动化测试和维护文档已完成，真实服务器安装、故障演练、日志保留现场检查和外部告警仍未执行。未执行项不能按完成处理。

> 当前状态（2026-09-14）：后端全量 H2 195/195、前端 Vitest 21/21、typecheck 和 build 已通过；请求关联、异常日志、滚动日志、Actuator 权限、业务指标和部署模板已落地。详细证据见 [运维可观测性与日志体系验收记录](../验收记录/2026-09-14-运维可观测性与日志体系验收记录.md)。

目标：为当前单服务器、单 Spring Boot 实例建立可以定位请求、查看异常、判断服务健康、确认服务崩溃原因并执行故障恢复的基础运维体系。

架构：应用层使用统一的 request ID、MDC 上下文和访问日志；业务异常继续通过现有 HTTP 错误响应返回，但服务端必须同步记录可检索的异常上下文。运行层以 Spring Boot Actuator 提供健康和 JVM/HTTP/数据库指标，以 systemd 管理进程，以 journald 作为服务器控制台日志来源，并按生产配置选择性保留应用滚动日志文件。业务审计、机器人派发失败记录和基础设施日志分开管理，不能互相替代。

技术栈：Java 21、Spring Boot 4.0.8、Spring MVC、Spring Security、Spring Boot Actuator、Micrometer、Logback、systemd、journald、MySQL 8.4 LTS、Flyway、H2 测试数据库。

## 全局约束

- 当前部署目标是一台 Ubuntu 服务器上的一个 Spring Boot 实例，不引入 Redis、MQ、ELK、Prometheus、Grafana 或多节点协调作为本阶段前置条件。
- Java 版本固定为 21；应用版本和 Spring Boot 版本以当前 server/xupan-server/pom.xml 为准。
- 生产数据库固定按 MySQL 8.4 LTS 验证，自动化测试继续使用 H2；H2 通过不能替代 MySQL 运行态验证。
- /actuator/health 可以作为反向代理健康检查；详细指标和运行信息必须受认证与权限保护，不能公开给互联网用户。
- 日志不得记录密码、Access Token、Refresh Token、Cookie、WebSocket ticket、完整请求体、投注敏感内容或外部凭据。WebSocket 日志只能使用连接 ID、房间编码和结果状态等必要字段。
- 日志中的 request ID 必须能够与 HTTP 错误响应中的 requestId 对应；不能只返回 ID 而不在服务端记录它。
- 预期的业务失败和参数错误使用低级别日志或结构化审计记录；未预期的 5xx 异常必须记录异常类型、请求路径、request ID 和完整堆栈。
- 不新增后台日志查看页面作为第一版目标。单服务器维护优先通过 SSH、journalctl、受保护的 Actuator 和数据库查询完成。
- 当前工作区存在用户已有的前端、首页静态资源、文档和后端改动。实施前必须重新执行 git status --short 和 git diff --check，只提交本计划涉及的文件。
- 每个任务都必须完成自己的测试或人工验证后再进入下一个任务；不能把应用启动当作日志、指标和故障恢复均已验收。

## 现状与本计划边界

当前已经存在：

- Spring Boot 默认控制台日志和若干机器人、聊天室、WebSocket 失败日志。
- sys_login_audit、sys_operation_log 等业务审计表。
- chat_robot_dispatch.last_error、消息状态和 outbox 状态等业务故障记录。
- /actuator/health 和 deploy/xupan-server.service 中的 Restart=on-failure。

当前尚未形成闭环：

- 没有统一请求日志和 request ID 传播。
- 通用 500 响应返回 request ID，但异常没有按 request ID 记录。
- 没有正式的 Logback 文件输出、滚动和保留策略。
- 没有受保护的 JVM、HTTP、数据库连接池、WebSocket 和机器人积压指标。
- 没有崩溃证据文件、日志保留检查和正式单服务器故障演练。
- 没有外部通知渠道配置，因此本计划第一版只建立本地可发现、可查询和可恢复能力，不伪造已经接入告警通知。

- [ ] 步骤 1：记录日志字段契约

### 任务 2：实现 HTTP request ID 和访问日志

文件：
- 新建：server/xupan-server/src/main/java/com/xupan/server/web/RequestObservabilityFilter.java
- 测试：server/xupan-server/src/test/java/com/xupan/server/web/RequestObservabilityFilterTest.java

接口：
- 消费：HTTP 请求、响应状态码和 Spring Security 上下文。
- 产出：X-Request-Id 响应头、MDC key requestId、不包含请求体和敏感参数的访问日志。

- [ ] 步骤 1：编写失败测试

  测试至少覆盖：没有请求 ID 时生成 UUID；传入合法 UUID 时沿用；非法或过长的请求 ID 被替换；响应包含相同 X-Request-Id；请求结束后 MDC 被清理；访问日志包含方法、路径、状态、耗时和 request ID，但不包含 Authorization、Cookie、query string 或请求体。

- [ ] 步骤 2：运行过滤器测试确认失败

  运行：./mvnw.cmd -Dtest=RequestObservabilityFilterTest test

  预期：测试在过滤器不存在或行为未实现时失败，失败原因应指向缺少的 request ID 或日志契约行为。

- [ ] 步骤 3：实现最小过滤器

  RequestObservabilityFilter 使用 OncePerRequestFilter：

  1. 从 X-Request-Id 读取值，仅接受 UUID 格式；其他值生成新的 UUID。
  2. 写入 request attribute、MDC.put("requestId", value) 和响应头。
  3. 调用下游过滤器，使用 System.nanoTime() 计算耗时。
  4. 在 finally 中按状态码记录访问日志，然后执行 MDC.remove("requestId")。
  5. 日志只记录结构化键值，不记录 query string、headers、body、Token 或 ticket。
  6. /actuator/health 的成功探测使用 DEBUG 或低噪声日志；健康检查失败使用 WARN，避免健康探测刷满生产日志。

- [ ] 步骤 4：运行过滤器测试确认通过

  运行：./mvnw.cmd -Dtest=RequestObservabilityFilterTest test

  预期：全部通过；MDC 清理测试必须通过，避免线程池复用造成用户请求信息串线。

- [ ] 步骤 5：运行现有认证和 Web 测试

- [ ] 步骤 1：修改 systemd 服务元数据

  在部署说明中规定 /opt/xupan-platform/logs 由 xupan:xupan 持有、目录权限为 0750、日志文件不允许普通用户读取。ReadWritePaths=/opt/xupan-platform 必须保留，不能把日志路径放到受保护的临时目录。

- [ ] 步骤 1：编写故障排查手册

  至少覆盖以下症状和命令：

  - 页面打不开：systemctl status xupan-server、journalctl -u xupan-server -n 200 --no-pager、curl -fsS http://127.0.0.1:8080/actuator/health。
  - 页面返回 500：先把响应中的 UUID 保存为 PowerShell 变量 requestId，再执行 journalctl -u xupan-server | Select-String -Pattern $requestId；服务器上使用 journalctl -u xupan-server | grep -F "$requestId"，再按异常堆栈定位。

## 维护人员最终可见能力

完成本计划后，维护人员应能形成以下闭环：

浏览器错误响应 requestId
    -> journalctl / 滚动日志定位请求、路径、状态和异常堆栈
    -> Actuator health/metrics 判断进程、JVM、数据库、WebSocket、机器人状态
    -> 数据库审计和业务失败记录确认具体业务影响
    -> systemd 重启记录和 hs_err 文件判断是否发生进程/JVM 级崩溃
    -> 按故障手册执行恢复并填写验收记录

## 明确不在本阶段的内容

- 不建设 ELK、Loki、Prometheus、Grafana 等集中式监控平台。
- 不建设面向业务管理员的日志查询 UI。
- 不接入未确认的短信、邮件、钉钉、企业微信或 webhook 通知渠道。
- 不引入 Redis、MQ、多实例任务租约、跨节点 WebSocket 广播或高可用架构。
- 不把日志表当作所有基础设施日志的替代品，也不把 Actuator 健康为 UP 写成业务功能完全正常。

## 实施完成判定

只有同时满足以下条件，才能把本阶段标记为完成：

1. HTTP 错误响应的 requestId 能在应用日志中定位到同一次请求。
2. 未登录、普通用户和监控权限管理员访问 Actuator 的结果符合权限设计。
3. 机器人和聊天室指标能反映测试数据变化，数据库查询失败不会静默成正常值。
4. 生产日志具备可验证的滚动和保留策略，且不包含敏感信息。
5. systemd 崩溃自动恢复、journald 查询、JVM fatal error 路径和健康检查均已在真实运行环境验证。
6. 后端、前端、MySQL 8.4 运行态和服务器故障演练均有独立证据。
7. README.md、docs/项目方案.md、docs/项目记忆.md、docs/部署运行说明.md 与实际实现一致，未把计划或未执行内容写成事实。
