# AU8 七球全链路开发、迁移与验收计划

> 状态：2026-10-31 已完成代码、V102–V104 和本机 `xupan_platform` 七球切换；首个七球期 3014739 已生成，当前 3014740 为七球。核心隔离 MySQL 8.4 与前端专项通过，中心/代理完整回归仍有失败项；生产切换及玩家真实浏览器人工验收未完成，当前浏览器的玩家会话已失效。实际证据见[本机验收记录](../验收记录/2026-10-31-AU8七球全链路本机验收记录.md)。需求与数据兼容规则以[七球全链路改造方案](2026-10-31-AU8七球全链路改造与历史八球兼容方案.md)为准。使用者已确认：首个七球期正式开始后，玩家、代理、平台的正常界面和聊天/历史只能看到七个球；旧八球数据仅在内部核账、补结算和受限审计中保留。
>
> 本计划中的 SQL 和命令是实施/验收清单，不表示已经在本机或服务器执行。正式迁移号、生产库状态和实际验证结果在开工时重新核对，不能引用本计划代替验收记录。

## 1. 完成定义与边界

完成不是隐藏第 8 球，而是新 AU8 期次从接单到开奖、结算、机器人、中心订单均只有第 1–7 球。技术键 `AU8` 保留，不改旧期号和旧账本；历史八球记录在数据库中仍按原八个号码解释和结算，正常产品页面从切换点起不展示八球盘面，也不重放旧八球聊天卡片。新期结果摘要以第 7 球作为末球计算番/单双/大小；旧期内部核账仍以原第 8 球为末球。虚拟积分、赔率、限额、返水、300 秒期长、180 秒投注窗口和审批时点均不变。

| 项目 | 范围 | 明确不做 |
| --- | --- | --- |
| 正式业务 | `/room`、`/console`、`/platform-admin`；聊天、直连接单、托、自动/人工开奖、旧期补结算、内部中心、报网快照 | 不接真实外部资金或上游；不把第 8 球旧单改算第 7 球 |
| 历史数据 | 已确认/未确认旧八球期、第 8 球旧注单、中心订单、账本、审计与消息原文保留 | 不批量改写已确认开奖结果，不清理旧虚拟积分流水 |
| 展示 | 首个七球期开始后，正常页面的当前球条、上期参考、历史、走势、开奖卡片、选球控件均为七球 | `/display/mobile` 外部七球卡片不是 AU8 数据源；`/hby019-demo` 原版静态参考资产不改写 |

## 2. 开工前的只读盘点与停工条件

先记录 `git status`/当前提交，保留已有未提交改动与生成资源；读取 `docs/文档索引.md`、本方案、`03` 和 `07` 模块基线、BY220 `application/common.php` 与玩家页面对应分支。源码当前最高 Flyway 为 V101，实施前用文件列表和实际 `flyway_schema_history` 重核；不能占用已存在版本。

只读检查本机目标 MySQL 8.4 与拟发布环境的期次和未结单。下列 SQL 只用于盘点，实施时在**明确指定的隔离库或目标库**运行并将行数/期号脱敏写入验收记录：

```sql
SELECT version, success FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 5;
SELECT game_code, issue_number, phase, draw_confirmed_at, number_8
  FROM game_issue WHERE game_code = 'AU8' ORDER BY id DESC LIMIT 10;
SELECT issue_number, settlement_status, COUNT(*) AS n
  FROM game_bet WHERE game_code = 'AU8' AND ball_number = 8
  GROUP BY issue_number, settlement_status;
SELECT issue_number, status, COUNT(*) AS n
  FROM center_order WHERE game_code = 'AU8' AND ball_number = 8
  GROUP BY issue_number, status;
SELECT game_code, display_name, ball_indexes, version
  FROM game_definition WHERE game_code = 'AU8';
```

盘点时还需核对开奖草稿、旧期本地/中心未结订单、`report_upstream_order` 中结果未知/重试项、机器人 `DRAW_RESULT` 待派发、当前在线玩家页面版本。若发现**已确认结果缺第 8 球、七球样式旧数据、同一期球数不一致、迁移失败记录或无法确认真实数据库版本**，暂停切换，先形成专项修复记录；不能用覆盖历史数据“修好”盘点结果。

## 3. 开发与迁移阶段

### D1. 双规则数据层与 Flyway

| 步骤 | 文件/动作 | 完成条件 |
| --- | --- | --- |
| D1-1 | 以开工时下一个空闲 Flyway 版本新增 `game_issue.ball_count`、`game_definition.next_issue_ball_count`，默认 8；现有期次回填 8，不改任何旧号码或余额。新增只追加的 `game_ball_rule_change`，记录 AU8 首个七球期号、操作人、时间和原因，并对期号切换键建唯一约束。 | 旧八球样本行前后字段、确认时间、注单/钱包/中心订单数量一致；旧应用读取新库仍按 8 运行。 |
| D1-2 | 在后续前向迁移中替换 `V93` 的“八球完整”CHECK 为按每期 `ball_count` 判断；为七球行约束 `number_8 IS NULL`；将球数加入 `V95` 确认结果不可变触发器。保持旧 1–8 注单/改单/中心 CHECK 以容纳历史。 | MySQL 8.4 上七球确认完整、八球历史完整、已确认结果不可改/不可删，迁移途中不暴露无保护写入窗口。 |
| D1-3 | 读期次/历史/中心结果统一带 `ballCount`；七球读七位、八球读八位，空位读取使用可空 API。新增面向写入的该期球位校验。 | `number_8=NULL` 不会被当作 0；旧第 8 球单的结算查询仍能读到原值。 |

迁移脚本只前向新增/替换约束，绝不编辑 V1/V45/V92/V93/V95。MySQL DDL 可能隐式提交；每个脚本在隔离 MySQL 8.4 空库与已有 V101 的数据库副本各跑一遍，并验证失败后前向修复路径。V95 含触发器；隔离库迁移成功之后，还需核对正式迁移账号对触发器的权限。未经服务器操作授权，本阶段只做本机隔离验证。

### D2. 接单与后台改注单

| 入口 | 具体修改 | 必验结果 |
| --- | --- | --- |
| 玩家文本与 REST | `PlaceBetRequest` 保留历史 1–8 协议上限，`BetTextParser` 不把 8 直接改为 7；`DemoGameService` 锁定期次后按 `issue.ballCount` 拒绝越界，`ChatMessageService` 以真实期次反馈。 | 新七球期的“第8球/…”和 `ballNumber=8` 返回明确错误；无注单、预扣、机器池或中心订单半笔。旧八球活跃期仍按原范围执行直到切换点。 |
| 批量/快捷/托 | 同批校验在任何钱包操作前完成；托沿正式玩家下注入口；前端选球默认合法且每次期次切换重校。 | 批次含非法第 8 球时整体拒绝；同一幂等键重试不重复接单，旧客户端不可绕过 UI。 |
| 平台改单与游戏设置 | `PlatformOrderCorrectionService` 按目标注单所属期次而非全局常量校验；`GameSettingsService` 保持未来球数与 `ball_indexes` 一致且不因编辑其他字段回退为 8。 | 新期改单不能选第 8 球，旧八球记录的原球位在内部核账仍保留；设置更新的乐观锁冲突可识别。 |

数据层可加入针对**新插单/球位改变**的 MySQL 防线；先核对现有下注、改单、结算锁顺序，避免在每次状态更新时再锁期次造成死锁。`center_order` 历史允许原有 `NULL`/8 球值，新增已受理中心单须关联真实期次并校验球位范围。

### D3. 自动、人工与补期结算

1. `自动轮期服务` 从本期 `ballCount` 生成预览和正式号码；已有草稿只有数量、范围与本期一致才可使用。结算每笔本地注单前显式检查球号 <= 本期球数，保留 `settleBetOnce` 和钱包积分幂等键。旧八球当前期在预设七球后仍按八球结束；下一期读取 `next_issue_ball_count=7`。
2. `DemoGameService.draw`、`PlatformDrawHistoryService` 的草稿、确认、补期、强制结算、分页历史和结果事件改为按期球数判断。旧期即使在七球切换后走内部补结算仍用八个原号码；缺失历史期的补录根据 `game_ball_rule_change` 的生效期号判 7/8，不能按请求数组长度猜规则。
3. `CenterOrderRepository.findConfirmedDrawNumbers` 和 `CenterSettlementService` 严格读取、比较锁定的 7/8 个正式号码；中心风险快照和结算球位范围按关联期次判断，旧中心第 8 球单仍可恢复结算。`draw_numbers` 只写该期正式结果，历史快照不回写。
4. 已确认开奖、中心订单和本地账务在**原有事务边界**内一次完成；任一球位越界或中心未结阻断时整体回滚，不得发布“结算成功”的机器人消息。失败恢复从期号/注单状态和幂等键继续，而不是重新随机生成一套结果。

### D4. 机器人、聊天室及七球展示

- `RobotDispatchService`、历史/走势指令、`robotDrawMessage.ts`、`robotDrawImage.ts`、`gameHistory.ts` 按当前七球数据渲染；新结果摘要与番/单双/大小取第 7 球。旧八球 payload 和原聊天内容保持数据库原文，不做数据删除或替换。
- 正常聊天室 **REST 初次加载、向上分页、WebSocket 新消息、断线补偿** 共用切换生效过滤：首个七球期创建时记录服务端可复现的可见时间/序号边界；其后按该边界及来源期次 `ball_count` 排除旧八球开奖卡片和旧球位消息。缺少来源期次的历史开奖类消息须保守隐藏，不能凭正文猜成七球。历史查询只取七球期；切换时清理客户端在内存里的旧八球卡片，服务端保留持久化消息供内部审计。过滤后游标仍单调推进，不能因被跳过的旧消息反复补发或卡死。
- `/room` 顶部、下注选球、七条同步滚动动画、历史和上期区域始终七球；首个七球期不能把 `previousBalls` 的旧八球直接顶替当前七球占位。`/console` 下注榜、`/platform-admin` 开奖历史/草稿/改单/游戏设置都不提供第 8 球入口或八球盘面。历史第 8 球旧单在正常流水只显示真实积分和状态，原始球位仅受限审计可查。
- 正式页面文案用“七球”口径，内部 `AU8` 键不直接当界面标题。`/hby019-demo` 的静态参考样例保持原样；若正式页面依赖其桥接动态字段，须在正式路径替换为七球数据。`/display/mobile` 外部开奖卡片单独验证未受影响。

## 4. 切换步骤与故障处理

1. **准备**：完成代码和迁移的隔离验收，备份目标库与应用包，记录校验和、当前期号、数据库版本、未结单和机器人待派发数量；发布后确认所有应用实例均运行能同时处理七/八球的新版本。先禁止旧进程再次接单或开奖，确认调度锁归属；期间 `next_issue_ball_count` 仍为 8。
2. **预设**：在同一事务/锁顺序下计算首个尚未创建的七球期号，写唯一规则记录，并将 AU8 `next_issue_ball_count`、`ball_indexes` 设为 7 和 1–7。已有八球期按原球数完成。预设成功不等于对外切换完成，页面此时仍可能显示当前八球期。
3. **生效**：旧八球期结算事务创建首个七球期时，`game_issue.ball_count=7` 且 `number_8=NULL`，同时持久化聊天室的七球可见边界；从此刻起正常页面、聊天室、历史和后台只呈现七球。验证事件顺序、前端缓存/长连接重连、服务器 `game_definition` 与期次行一致。若期号已经由并发任务提前创建为八球，停止切换并核对，不覆写该期球数。
4. **失败处理**：未产生七球期之前，可撤销预设并维持旧规则，同时保留审计记录；产生七球期之后不回滚到旧八球代码或生成新的八球期，按故障范围以前向修复处理。若数据库迁移部分完成，依据 Flyway 历史及备份恢复/补迁移，不手动修改已确认 `number_1..number_8`、积分或中心账本。

本计划不自行执行服务器安装、迁移、上传或重启。若后续实施任务只授权本机开发，则第 4 节的服务器步骤保持“未执行”；本机隔离验收不得写成现场切换成功。
