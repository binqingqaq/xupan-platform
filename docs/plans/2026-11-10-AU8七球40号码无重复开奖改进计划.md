# AU8 七球 40 号码无重复开奖改进计划

> 制定日期：2026-11-10
> 状态：代码已实施，验收未完成。
> 范围：AU8 内部业务开奖的全链路；不改动其他彩种、外部展示源、历史已确认结果或虚拟积分合规边界。

## 1. 目标与已确认规则

把 AU8 每期开奖号码从“7 个球位、各球 1～20、允许重复”调整为：

1. 每期固定 7 个球位，球位编号为 1～7，不增加或减少球位。
2. 每个球位从 1～40 中开出一个整数；同一期 7 个号码必须互不相同。
3. 每个球位仍分别承载该球位的下注结果；注单按自身球位对应的开奖号码结算。
4. 番规则不变：号码对 4 取余，余数 0 记为 4 番，其余分别为 1～3 番。
5. 大小改为 1～20 为小、21～40 为大；单双继续按号码奇偶判断。
6. 特玩法的可选号码扩大到 01～40。玩家快捷下注面板应能选择 01～40 特；所有特号码共用现有统一特码赔率配置，不为每个号码新增单独赔率。
7. 特玩法仍按注单指定球位的开奖号是否包含在所选特号码中判定命中；开奖不重复与特玩法选码不重复是两个独立校验。
8. 历史已确认开奖结果、历史注单及其赔率快照保持不变；新规则只用于切换后创建的新期和新订单。
9. 本次只调整 AU8。其他游戏代码、其球数、开奖范围和历史不受影响。
10. 后续时长决定：下注保持 180 秒，开奖阶段由 120 秒缩短为 60 秒，总期长变为 240 秒；已有期次的 `draw_ends_at` 持久化快照不回写。

“全项目适配”在本计划中指 AU8 规则必须贯穿当前仓库内玩家前台、代理后台、超级管理后台、开奖历史、报表、机器人/聊天展示、服务端 API、中心订单闭环、数据库与迁移；不表示把外部参考站静态快照或非 AU8 外部彩种改成 1～40。

## 3. 当前实现缺口盘点

静态源码检查确认以下硬编码和规则缺口需要在实施时逐一消除：

- `BallResult.fromNumber()` 限制 1～20，大小以 11 为界；虽番和单双计算可复用，但大小边界必须改为 20。
- 自动轮期和预览号码使用 1～20 随机值；最终号码当前允许重复。期次预设与 `PlatformBettingPlayStatsService` 也校验 1～20。
- `GameDataRepository.validateDrawNumbers()`、`PlatformDrawHistoryService.validateNumbers()` 限制 1～20，但当前只检查数量/范围，不拒绝同一期重复号码。
- 手工开奖控制 `AdminPanel.vue`（旧路由 `/platform-admin/operations`）、逐球预设 `PlatformAdminBettingPlayStats.vue`、补期 `PlatformAdminDrawHistory.vue` 使用 1～20 输入边界或校验提示；旧运营路由实施前须核对是否仍可达/可写，不能漏掉有效兼容入口。
- 玩家 `betText.ts`、服务端 `BetTextParser`、`SettlementService` 对特码选择范围均为 1～20。
- `quickBet.ts` 固定生成 01～20 特快捷项；`QuickBetPanel.vue` 另有 21～40 的 display-only 项，但当前这些后 20 项不可提交，需接入真实 option/指令生成，避免只显示不下单。
- `game_issue` 与中心订单采用固定 `number_1`…`number_8` 字段及 `ball_count`；此结构可存 1～40，且 AU8 已固定七球，但已有 MySQL CHECK、触发器及中心仓储查询按 1～20 验证。
- `game_bet_selection.number_value` 等下注号码检查也存在 1～20 约束，需要判断其是否承载当前特码明细并同步放宽 AU8 适用路径。
- 机器人开奖图/聊天文本包含“大”按 `>=11` 的派生显示；移动开奖、玩家结果、开奖记录、下注统计及代理开奖表格需搜索并验证不存在 1～20 的残留显示或校验。
- 既有开奖结果不可变约束必须保留；不可通过直接更新历史开奖来伪造符合新规则的历史。

数据库 `TINYINT` 足以保存 1～40，固定 8 列在 AU8 七球下继续使用 `number_1`…`number_7`，`number_8` 仍为空；本次不需要把表扩成 40 列。

## 4. 关键设计要求

### 4.1 无重复随机生成及预设合并

- 随机生成必须从 1～40 无放回抽取 7 个号码，而非生成 7 次后重抽碰撞不受限；使用服务端安全随机源，输出顺序即球位顺序。
- 若本期含管理员预设号码，预设值必须在 1～40 且彼此不同。自动补齐时从未被预设的号码集合无放回抽取，最终仍恰好 7 个唯一号码。
- 单球预设更新时检查该期其他球位已有的预设值，重复时拒绝并给出明确错误；并发预设以期次行锁/版本条件更新保证不会产生重复预设。
- 最终保存、确认、开奖历史补录、手工开奖和中心结算入口都执行完整结果校验：恰好 7 个、每个 1～40、集合大小为 7。
- 失败必须在任何注单结算、钱包积分流水、中心订单结算或开奖事件写入前拒绝；整个开奖闭环仍由原有事务和幂等约束保护。

### 4.2 规则版本与历史数据

- 新约束不能把既有重复号码的历史开奖判成非法，也不能改写其号码、时间、结算或账本事实。
- 实施前读取本机 MySQL 8.4 的迁移状态、现存 AU8 期次、中心订单和开奖数据，统计旧数据范围、重复值和未完成订单；只读盘点，不清理或重建数据。
- 迁移采用可追溯的切换标记/规则版本区分旧期开奖规则与新规则，或采用经 MySQL 8.4 验证的等价约束方案。新规则对切换后期次强制范围 1～40 和七球唯一；历史期次保留原值和原解释。
- 期次创建时持久化规则快照或等价版本标识，确保重启、并发开奖、补期、强制结算和审计均能判断适用规则；已确认开奖继续不可变。
- 迁移不得删除、重建生产库或清空开发数据。需要回滚时优先前向修复；若新期已按 1～40 开奖，不得用降级代码把这些结果解释为非法 1～20 数据。

### 4.3 特玩法与赔率

- 1～40 特号码映射到统一玩法键 `SPECIAL` 和现有机器级 `tePeilv`/报价来源，不创建 40 个赔率字段，也不让 21～40 显示成不可下注的占位项。
- 选中一个或多个特号码时，按现有规则校验号码不重复、金额按单号金额和号码个数计算、保存统一赔率快照并按指定球位结算。
- 用户确认统一赔率配置，不代表赔率数值应由代码自动翻倍；实施保持现有赔率配置形式和值，除非用户另行确认调整。计划验收应明确展示 1～40 共用同一个报价及历史注单快照不变。
- 特号码额度、限额分桶、机器人自动投注可选号码范围、赔率面板文本、机器人下注解析及报表显示都要支持 21～40，并保持机器隔离和原有下注限额语义。

## 5. 分阶段实施

### P0：基线和数据前置检查

1. 复核最新需求、当前 Git 提交/工作区、迁移版本和现有 AU8/中心期次数据；不把计划或旧验收代替当前事实。
2. 检查所有开奖读写入口和调用者：自动轮期、演示/管理 API、逐球预设、草稿、确认、补期、强制结算、批量强制结算、内部中心结算、机器人和测试夹具。
3. 按玩家、代理、超级后台、公开展示、机器人/聊天、报表、数据库七类建立真实实现映射；核验每个玩家特号码选项的生成、文本解析、服务端接单、额度、赔率快照、结算回显链路。
4. 形成迁移前只读数据盘点和规则版本策略，确认历史结果保留且新旧规则可区分。

### P1：领域规则和后端服务

1. 增加或统一 AU8 开奖规则定义，避免范围、球数、大小边界散落在多个常量中；其他彩种保持各自配置。
2. 修改号码到 `BallResult` 的转换：1～40、番 `% 4`、奇偶、大小 `number >= 21`；完善空值/边界校验。
3. 实现 7 个号码无放回抽取及预设号码去重补齐；保证同一期规则下恰好七个唯一值。
4. 统一开奖输入校验用于自动开奖、管理员手工开奖、草稿确认、历史补录、单期强制结算读取和中心订单结算；错误响应明确指出球数、范围或重复号码问题。
5. 扩展玩家文本解析、服务端下注校验和特码结算参数范围到 1～40；赔率保持统一快照路径和原下注金额计算。
6. 审查随机展示动画：只作展示、不写开奖事实；其号码应取 1～40 且展示不应被误认为已确认开奖结果。

### P2：数据库与迁移

1. 新建中文 Flyway 迁移，按当前真实结构修改开奖结果、确认、中心订单、下注选码/明细和相关触发器或 CHECK 约束中的 1～20 上限。
2. 为新规则和旧期次建立可审计版本/切换标记；数据库级规则对新规则 AU8 结果实施范围和七值互异约束，同时兼容既有历史行。
3. 对每个写入面覆盖 `INSERT` 和 `UPDATE`，防止应用以外的直接 SQL 或并发写入绕过七球唯一性、1～40 范围和 `number_8 IS NULL`。
4. 保留 `ball_count=7`、球数快照不可变和已确认结果不可变；中心订单结果快照与本地开奖结果必须一致。
5. 在独立 MySQL 8.4.11 空库和带旧历史数据的副本上验证迁移；检查迁移可重复部署、约束拒绝条件、历史保留、回滚/前向修复策略及索引影响。
6. 若目标 MySQL 开启 binary logging 且 `log_bin_trust_function_creators=OFF`，应用账号创建触发器会被 MySQL 拒绝。迁移窗口需由 DBA 临时开启该全局变量或使用经批准的迁移身份，迁移后恢复原值；服务器/生产部署另行审批。

### P3：玩家、代理和超级后台

1. 玩家快捷面板将 01～40 全部作为真实可选特项；21～40 可选择、显示统一赔率、生成合法下注文本并完成提交，选项不得只展示不可下注。
2. 玩家文本下注支持 21～40 的号码格式、组合特号码、前导零、重复号码拒绝与金额规则；前后端错误提示一致。
3. `/console` 代理机器配置继续只维护统一特赔率；代理报价与其名下玩家的特码下注使用该机器赔率和限额，不跨机器读取或写入。
4. 超级后台“下注玩法统计”逐球预设控件支持 01～40；提交重复预设时在前端提示、后端拒绝；开奖随机补齐避开所有预设号码。
5. 超级后台开奖控制手填/随机按钮限制七球和无重复，最大号码 40；不得让随机按钮输出重复值。
6. 开奖历史草稿、确认、补期、强制结算和批量操作页面按 7 个不重复号码验证 1～40，并显示对应服务端错误。
7. 保持 `/console`、`/platform-admin` 两套入口和各自角色权限，不以本次号码规则重组菜单或扩大权限。

### P4：机器人、展示、报表和中心闭环

1. 机器人自动投注涉及 `SPECIAL` 的选号和号码格式扩展到 40；随机投注（若存在）禁止重复选同一号码并遵守统一赔率/限额。
2. 机器人开奖摘要、开奖记录图片、聊天室消息、玩家上期开奖栏、代理开奖表格、管理期次详情和所有本地展示面改为显示 01～40。
3. 所有派生摘要统一使用大小分界 20/21，番规则和单双规则统一调用领域映射，避免 UI 自行保留 11 的旧边界。
4. 中心订单接收和中心结算完整传递七个 1～40 唯一号码；一个中心订单无法结算时保留原有原子回滚和可重试状态，不出现本地成功而中心部分成功。
5. 审查未结订单、订单修改、导出、玩家积分流水、开奖历史投注明细、统计报表及搜索/排序所用的号码范围校验；这些视图不应截断、丢弃或把 21～40 格式化为错误数据。
6. 非 AU8 外部开奖展示（例如静态快照或其他彩种数据）保持原映射；明确测试证明 AU8 规则不会污染这些页面。

### P5：文档、验收和发布准备

1. 更新业务模块 03、06、07、中心模块及必要的机器配置/机器人模块规则；将本计划继续作为当前活动事项，直到验收闭环完成。
2. 更新产品方案和项目索引；记录迁移版本、规则生效边界、历史兼容方式及未执行验证。
3. 先运行静态检查、相关后端/前端测试、类型检查和构建，再执行 MySQL 8.4 迁移与业务验收；最终按授权范围评估服务器/生产迁移，不因本计划直接部署。

## 8. 风险与控制

- **历史数据与约束冲突：**旧结果可能含重复值。规则版本标记必须在强制唯一性约束之前设计；禁止为通过迁移而修改历史开奖号。
- **开奖公平性：**无放回抽取改变每球间的统计相关性。生成必须使用安全随机源；手工预设与随机补齐不得产生偏置或重复。
- **号码范围遗漏：**仅修改 API 不足以覆盖 Vue、聊天解析、HBY019 桥、机器人、报表、图像生成、SQL CHECK/触发器和中心仓储；按验收矩阵逐个扫尾。
- **赔率解释：**40 个可能特号码下单号命中概率为 1/40。用户确认统一赔率设置，不应擅自为号码分层或自动乘二；继续使用现有机器统一赔率配置并保留订单快照。
- **历史图像/消息：**历史消息按旧规则生成的派生大小可能与新规则不同。不要重写已发布历史消息；新增开奖按新规则生成，查询历史应以其实际开奖时的规则版本解释。
- **其他彩种误改：**AU8 专属边界必须由 `game_code`/规则快照控制，不可把全局 `1..20` 替换成 `1..40` 后污染外部或其他游戏。
- **直接数据库绕过：**应用层唯一性检查须配合 MySQL 8.4 数据库级约束或触发器，并测试插入与更新两种路径。
- **MySQL binlog 触发器权限：**V112 包含数据库触发器。开启 binlog 且 `log_bin_trust_function_creators=OFF` 时，`xupan_app` 无 `SUPER` 将无法创建触发器；仅在授权迁移窗口临时开启该设置并在完成后恢复，或由 DBA 执行等效迁移。不得在代码中授予应用账号全局管理权限。
