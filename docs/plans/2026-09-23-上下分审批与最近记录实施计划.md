# 上下分审批与最近记录实施计划

> 状态：本机实施完成，服务器与生产待验收
>
> 规划日期：2026-09-23
>
> 当前代码基线：`3f7d7e4` + 当前未提交的 V27 聊天指令与积分申请改动
>
> 所属模块：虚拟积分与钱包、聊天室与实时消息、运营后台与报表

**目标：** 在统一管理后台的 `/console` 页面中，将“期号与开奖区域”“聊天与上下分记录”两个占位块替换为“上下分确认”和“最近上下分记录”，让玩家或托从聊天室提交的上下分申请能够由管理员确认、拒绝、即时提示，并与手动上下分共同形成当天可核对的记录。旧 `/admin` 仅保留自动跳转兼容。

**架构：** 继续复用 `player_point_request` 作为待审批申请事实源，复用 `demo_balance_ledger` 作为所有实际积分变化事实源，不新增第二套余额、申请或统计表。后台待处理队列通过 `GET /api/admin/player-desk/point-requests` 读取；同意和拒绝继续调用现有审批服务；最近记录新增只读查询接口，从钱包流水筛选当天管理员上分和下调记录。前端由统一后台挂载两个独立 Vue 模块，审批成功后刷新待处理队列和最近记录。

**技术栈：** Java 21、Spring Boot 4.0.8、Spring Security、JDBC、Flyway、MySQL 8.4 LTS、Vue 3、TypeScript、Vite、Vitest、单实例轮询。

## 1. 已确认规则

### 1.1 后台布局

- 统一后台 `/console` 中原“期号与开奖区域”和“聊天与上下分记录”两个占位块由本次模块替换。
- 左侧区域为“上下分确认”，右侧区域为“最近上下分记录”，保持截图中的双栏结构。
- 顶部当前期号、阶段和系统状态摘要继续保留；本次不顺带实现期号、封盘或开奖控制。
- 桌面端使用左右双栏；窄屏下按“上下分确认”在上、“最近上下分记录”在下折叠，不产生页面级横向滚动。

### 1.2 上下分确认

- 玩家或托在聊天室发送 `上100`、`上1000`、`下100` 等指令后，服务端创建 `PENDING` 积分申请。
- 申请创建时不改变余额，只写入 `player_point_request` 和对全员可见的机器人反馈。
- 后台待处理项显示方向、金额和玩家昵称：

```text
上分 +100（用户昵称）
下分 -100（用户昵称）
```

- 未处理申请必须持久化，刷新页面、重新登录或服务重启后仍存在。
- 点击“同意”后先显示二次确认弹窗，例如“是否确认上分 +100（用户昵称）”。
- 确认后才调用审批接口，在同一事务中更新钱包、写不可变流水并标记申请为 `APPROVED`。
- 点击“取消”表示拒绝该申请，不改变余额；申请标记为 `REJECTED`，从待处理列表消失。
- 二次确认弹窗自身的“取消”只关闭弹窗并保留待处理申请；列表行上的“取消”才表示拒绝申请。
- 同一申请只能处理一次。并发管理员同时处理时，只允许一个请求产生钱包变化，其他请求必须返回已处理状态或明确冲突。
- 查询和审批继续使用 `USER_MANAGE` 权限，所有成功和拒绝动作保留操作审计。

### 1.3 提示音

- 后台提供“声音1”和“声音2”两个单选选项，以及“测试提示音”按钮。
- 声音选择和测试音只属于管理员浏览器交互偏好，不写入钱包或申请业务表。
- 默认选择“声音1”；选择结果使用 `localStorage` 保存，键名建议为 `xupan.admin.point-request-sound`。
- 初始加载已有待处理申请时不播放提示音，避免刷新页面重复响铃。
- 轮询发现新的 `PENDING` 申请 ID 时播放当前选择的声音。
- 浏览器尚未允许播放音频时，不能静默失败；应保留待处理数量和视觉提示，并允许管理员点击“测试提示音”解锁音频。
- 两个声音使用本地资源或本地 Web Audio 合成，不请求外部音频地址。

### 1.4 最近上下分记录

- 右侧默认显示“玩家”，通过“玩家/托”分段按钮切换。
- 只展示当天实际生效的管理员上分和下调记录。
- 列表格式：

```text
09-23 16:57 昵称：+100
09-23 16:57 昵称：-100
```

- 正数使用绿色，负数使用红色；按时间倒序，最新记录在上方。
- 审批通过的前台申请和玩家工作台手动上分、下分都必须进入同一列表。
- `REJECTED`、`PENDING` 申请不进入最近记录。
- `ADMIN_RESET`、下注扣分、结算派彩、撤单返还等流水不属于上下分记录，不进入本列表。
- 列表只读取现有钱包流水，不由前端根据申请状态本地拼接。
- 当天口径默认复用项目现有业务日规则：`Asia/Shanghai` 每天 06:00 切换。实施前若用户明确要求自然日 00:00，再单独修改为自然日。

## 2. 当前事实和复用边界

### 2.1 已存在的后端能力

- `player_point_request` 保存申请用户、上下分类型、金额、状态、来源聊天消息、审批人和审批时间。
- `ChatCommandParser` 已识别 `查`、`玩法`、`取消`、`流水`、`上金额`、`下金额`。
- `ChatMessageService` 已能把上下分指令写入待审批申请并向聊天室发布反馈。
- `PlayerDeskAdminController` 已提供待处理列表、同意和拒绝接口。
- `PlayerPointRequestService` 已使用事务、行锁和稳定幂等键执行审批。
- `demo_balance_ledger` 已保存管理员上下分、操作人、原因、前后余额和幂等键。
- 玩家工作台手动上下分已经通过钱包服务写 `ADMIN_GRANT` 或 `ADMIN_ADJUST` 流水。

### 2.2 本阶段不重复建设

- 不新增申请表、余额表或上下分记录表。
- 不把待处理状态保存在浏览器、内存队列或消息正文里。
- 不让前端直接修改钱包余额。
- 不通过删除申请记录表示拒绝；拒绝必须保留可审计状态。
- 不把申请创建时的余额快照当作审批后的真实余额。
- 不新增充值、支付、提现、转账、代理分成或现实资金语义。

## 3. 用户可见行为

### 3.1 待处理队列

```text
加载 /console
  -> 获取待处理申请
  -> 标记当前已有 ID，不播放声音
  -> 每 3 秒轮询
  -> 发现新 PENDING ID
  -> 播放当前选择的声音
  -> 新申请出现在左侧列表
```

- 待处理列表按申请时间从旧到新排列，先提交先处理。
- 每行保留“同意”和“取消”按钮。
- 同意时打开自定义确认弹窗，确认按钮处理期间禁用，防止重复点击。
- 关闭二次确认弹窗不改变申请状态，原申请继续保留在待处理列表。
- 取消后立即刷新列表，并显示“已取消该申请”Toast。
- 同意成功后显示“上分成功”或“下分成功”Toast，并刷新最近记录。
- 申请已被其他管理员处理时，显示状态冲突提示并刷新队列。
- 列表为空时显示“暂无待处理的上下分申请”。

### 3.2 最近记录

- 首次进入页面加载默认“玩家”当天记录。
- 切换“玩家/托”时重新请求服务端，不在前端混合两份数据。
- 手动上下分成功后，最近记录立即刷新。
- 审批成功后，最近记录立即刷新。
- 页面每隔 5 至 10 秒进行一次轻量刷新，避免其他管理员操作后长期不更新。
- 加载失败时显示可重试状态，不展示旧数据冒充最新结果。

## 4. 接口和数据设计

### 4.1 现有接口

```text
GET  /api/admin/player-desk/point-requests?limit=100
POST /api/admin/player-desk/point-requests/{requestId}/approve
POST /api/admin/player-desk/point-requests/{requestId}/reject
```

审批请求体保持可选原因：

```json
{
  "reason": "后台聊天上下分申请批准"
}
```

### 4.2 新增最近上下分记录接口

```text
GET /api/admin/player-desk/point-operations/recent?kind=NORMAL|BOT&beforeId=&limit=50
```

响应建议：

```json
{
  "kind": "NORMAL",
  "businessDate": "2026-09-23",
  "fromInclusive": "2026-09-22T22:00:00Z",
  "toExclusive": "2026-09-23T22:00:00Z",
  "items": [
    {
      "ledgerId": 1001,
      "userId": 12,
      "memberCode": "v1001",
      "displayName": "玩家昵称",
      "playerKind": "NORMAL",
      "operationType": "ADMIN_GRANT",
      "direction": "TOP_UP",
      "amount": 100.00,
      "balanceAfter": 500.00,
      "reason": "聊天上下分申请批准",
      "createdAt": "2026-09-23T08:57:00Z"
    }
  ],
  "nextBeforeId": null,
  "hasMore": false
}
```

实现规则：

- 只查询 `ADMIN_GRANT` 和 `ADMIN_ADJUST`。
- `amount > 0` 映射为 `TOP_UP`，`amount < 0` 映射为 `DOWN`。
- 继续使用 `USER_MANAGE` 权限。
- 默认查询当前业务日，不允许普通玩家调用。
- `limit` 限制在 1 至 200，默认 50。
- 使用 `created_at DESC, id DESC` 排序。
- 需要继续分页时使用 `beforeId`，返回 `nextBeforeId` 和 `hasMore`。

### 4.3 数据约束和索引

- 复用 V27 的 `player_point_request` 唯一键 `(user_id, client_message_id)`。
- 审批继续使用稳定幂等键 `POINT-REQUEST:{requestId}`。
- 最近记录查询需要确认现有索引是否覆盖玩家类型、操作类型、时间倒序和游标分页。
- 如现有索引不足，只在有 MySQL 8.4 执行计划证据后增加 Flyway 迁移。
- 不允许修改已执行迁移文件；新增结构调整必须使用后续版本。

## 8. 验收标准

- `/console` 中原两个占位区域替换为“上下分确认”和“最近上下分记录”。
- 前台或托发送上下分申请后，后台在持久化列表中显示该申请。
- 未处理申请不会因刷新、重新登录或服务重启消失。
- 同意后余额和 `demo_balance_ledger` 只变化一次。
- 取消后余额不变，申请从待处理列表消失并保留 `REJECTED` 审计状态。
- 声音1、声音2可以被选择、试听并在出现新申请时播放。
- 最近记录只显示当天实际生效的管理员上下分，玩家和托可以切换查看。
- 手动上下分和审批通过进入同一最近记录。
- 拒绝申请、待处理申请、下注扣分和结算派发不进入最近上下分记录。
- 所有接口继续受 `USER_MANAGE` 权限保护。
- H2、本机 MySQL、浏览器、服务器和生产证据分层记录，不以 H2 代替生产验证。

- “当天”当前建议复用 `Asia/Shanghai` 06:00 业务日；若产品要求自然日，必须实施前确认。

- 当前单实例轮询方案不提供跨实例推送；若未来多实例部署，需要另行设计共享事件通道。
- 如果待处理申请量长期较大，需要增加分页、筛选和批量处理，但首阶段不做批量审批。
- `REJECTED` 申请保留审计事实，但当前不提供拒绝历史查看页面。
- V27 和审批后端仍属于当前未提交范围，实施新面板前必须先完成基线收口。

## 10. 非目标

- 不实现充值、支付、提现、转账、代理分成或现实资金能力。
- 不实现期号、封盘、开奖和结算控制。
- 不实现聊天治理后台。
- 不实现批量审批、审批理由模板和审批工作流引擎。
- 不在本阶段引入 Redis、MQ 或多实例广播。
