## 0. 一句话结论

30 个代理的规模**不需要** Redis、消息队列、独立服务或分库分表。

需要的是三组工作，按顺序做完即可上线：

1. **P0 —— 修 5 处并发与进程边界缺陷**（单实例也能咬人，必须先修）；
2. **P1 —— 补齐中心上游阶段 C 业务能力**（可运营）；
3. **P2 —— 完成上线门禁**（服务器、生产 MySQL、真实浏览器、备份恢复、安全与可观测性）。

阶段 D 的清单里，**只有"定时任务互斥"一项随上线强制**，其余（独立进程、独立数据库、Redis、MQ、分布式锁、多租户）全部按触发条件后置。

### 1.1 上线形态已定：**不拆进程，单实例单进程部署**（用户 2026-10-03 确认）

用户 2026-10-03 明确确认：**本项目部署一套，中心上游逻辑就在这一套进程内运行，不拆成独立进程、不对外提供 HTTP 接单入口。**

理由（用户口径）：中心逻辑在自己这套系统里能跑通、账算得对、代理能报回来就已经达到目标；为"身份语义"去拆进程，换来的是部署面、跨网络超时查证、双进程定时任务互斥、迁移归属等一堆新问题，收益不划算。

**必须区分"意义问题"与"功能缺口"**（避免后续误判）：

| 说法 | 是否成立 |
| --- | --- |
| 同进程下中心逻辑也能用 | **成立**：功能完整、账算得对、端到端闭环已验收 |
| 同进程下"没任何区别" | **不成立**：跨进程独有的失败路径（网络超时、超时后查证上游状态、跨网络重试）**从未被实现、也从未被验证** |
| 同进程下"只是身份不符" | **一半成立**：身份语义确实立不住（中心无独立对外入口、非独立部署单元、无真实多代理接入形态），此外还有上述未覆盖的失败路径 |

**两条由此产生的结论**：

1. **`TIMEOUT` 查证（P0-4）不再是上线前置**：同进程调用永不产生网络超时，该场景在当前架构下**不会发生**（注意：是"不产生"，不是"未做"）。保留为条件性待办，触发条件见 §7。
2. **定时任务互斥（P0-1）仍然必须做**：与拆不拆进程无关——单实例滚动重启（新旧进程并存数十秒）同样会重复开奖。只是不再涉及"常态双跑"。

### 1.2 "拆成独立服务"的准确含义（保留供将来评估）

**拆服务 = 跨进程边界，不等于分服务器部署。** 一台服务器上跑两个进程同样是拆分。真正带来新问题的是"调用要过网络"这件事本身，而不是"有没有两台机器"。若将来改变决定，前置条件是：超时语义、超时后查询中心订单状态、幂等重试、不允许"超时即退款"。

## 2. 规模测算与架构结论

### 2.1 测算（按 30 个代理）

| 假设档 | 玩家总数 | 每期下注单 | 封盘前 60 秒峰值 | 单次下注写入行数 |
| --- | --- | --- | --- | --- |
| 保守（每代理 200 玩家） | 6,000 | 约 600 | 约 5 单/秒 | 注单 + 玩家流水 + 上报单 ≈ 3~4 行 |
| 激进（每代理 1,000 玩家） | 30,000 | 约 9,000 | 约 150 单/秒 | 同上 ≈ 600 写/秒 |

单实例 MySQL 8.4 在索引齐备的前提下，简单带索引插入可达**数千写/秒**。30 个代理对应的是 **10~50 倍余量**。

### 2.2 结论

- **单实例 + 单 MySQL 是当前正确的工程选择**，不是妥协；
- 余额读写的行锁竞争被代理数天然限制（最多 30 个热点行），不构成瓶颈；
- 真正的风险不在吞吐，而在 §4 的 5 处缺陷——它们会在 **5 单/秒**就发作。

### 2.3 触发阈值（什么时候才需要上更重的东西）

| 触发条件 | 需要补的能力 | 是否需要 Redis/MQ |
| --- | --- | --- |
| 需要跑第二个应用实例 | 定时任务互斥（`GET_LOCK` / 锁表 / 主节点选举） | **不需要**，MySQL 足够 |
| `game_bet` 累计超过约 5,000 万行 | 时间分区 + 冷数据归档 | 不需要 |
| 峰值超过约 1,000 写/秒（约 200+ 代理） | 读写分离 + 热点行拆分 | 可能需要（限流/去重） |
| 需要跨实例实时推送 | — | 需要（Redis Pub/Sub 或 MQ） |

按 30 个代理测算，**前三行两年内都碰不到**。

## 4. P0：上线前必修的并发与进程边界缺陷

> 这一组的共同特征：**与规模无关**，在 5 单/秒就会发作，且都不会在 H2 单测里暴露。

### P0-1 五个定时任务全部无互斥

| 项 | 内容 |
| --- | --- |
| 现象 | `@EnableScheduling` 已开启，5 个 `@Scheduled` 任务各自独立运行 |
| 证据 | [自动轮期服务.java:85](../../server/xupan-server/src/main/java/com/xupan/server/game/service/自动轮期服务.java#L85)（1 秒）、[RobotDispatchScheduler.java:31](../../server/xupan-server/src/main/java/com/xupan/server/robot/service/RobotDispatchScheduler.java#L31)（1 秒）、[ReportDispatchScheduler.java:42](../../server/xupan-server/src/main/java/com/xupan/server/report/service/ReportDispatchScheduler.java#L42)（2.4 秒）、[TestPlayerBehaviorScheduler.java:25](../../server/xupan-server/src/main/java/com/xupan/server/system/service/TestPlayerBehaviorScheduler.java#L25)（1 秒）、[ChatHeartbeatScheduler.java:17](../../server/xupan-server/src/main/java/com/xupan/server/chat/realtime/ChatHeartbeatScheduler.java#L17)（20 秒）；全仓无 `ShedLock`、无 `GET_LOCK` |
| 影响 | **滚动重启或双实例时重复开奖、重复派发托行为。** 即使只跑单实例，第一次滚动重启（新旧进程并存数十秒）就会触发 |
| 修法 | 引入 MySQL 命名锁（`GET_LOCK`）或任务锁表，任务执行前抢占、结束释放；`自动轮期` 与 `RobotDispatch` 必须最先覆盖 |
| 验收标准 | 双进程并行启动的集成测试：同一期内开奖只发生一次、托派发不重复；本机 MySQL 实测双实例并存 |
| 迁移 | 需要一个任务锁表或复用现有表；若用 `GET_LOCK` 则无需迁移 |

### P0-2 上报重报的头部阻塞（**新发现，本组最严重**）

| 项 | 内容 |
| --- | --- |
| 现象 | 重报扫描 `ORDER BY b.id LIMIT ?`，且状态集合包含 `REJECTED`/`TIMEOUT` |
| 证据 | [ReportUpstreamOrderRepository.java:207-223](../../server/xupan-server/src/main/java/com/xupan/server/report/repository/ReportUpstreamOrderRepository.java#L207-L223)（`ORDER BY b.id` + `LIMIT`）、[ReportService.java:349-353](../../server/xupan-server/src/main/java/com/xupan/server/report/service/ReportService.java#L349-L353)（`includeRetry=true` → `PENDING`/`REJECTED`/`TIMEOUT`）、[ReportDispatchScheduler.java:28,45](../../server/xupan-server/src/main/java/com/xupan/server/report/service/ReportDispatchScheduler.java#L28)（batch=50、每 2.4 秒） |
| 影响 | 注单按 `b.id` 升序取，**最老的 50 笔一旦长期停留在 `REJECTED`/`TIMEOUT`，批次会被它们永久占满，此后新注单永远排不上上报**。累积到 50 笔坏单，整条上报链路静默停摆。`report_upstream_order` 无 `next_retry_at` 列（`V58:17-47`），没有退避也没有重试上限 |
| 修法 | ① 加 `next_retry_at` 与 `attempt_count`；② 扫描改为 `WHERE next_retry_at <= NOW()` + `ORDER BY next_retry_at`；③ 分级退避（如 1s / 5s / 30s / 5min）；④ 设重试上限，超限转人工待处置状态 |
| 验收标准 | 构造 60 笔永久失败单 + 后续正常单，验证正常单仍能在下一轮报到；本机 MySQL 实测 |
| 迁移 | `V65`：`report_upstream_order` 增列 + `(status, next_retry_at, id)` 索引 |
| 待确认 | BY220 原实现（`flyers_status = 3` 轮询）很可能有同样问题。**加退避与上限属于对 BY220 的偏离，需用户确认**，并按规则单独记录 |

| 对账差异自动修复 | 差异应先人工确认再自动化 | 差异量稳定且规则明确后 |
