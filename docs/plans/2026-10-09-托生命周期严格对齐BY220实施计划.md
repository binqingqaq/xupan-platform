# 托生命周期严格对齐 BY220 实施计划

> 状态：本地实现、定向验证及托下注故障修复完成（2026-10-09）；V80 已应用本机 MySQL 8.4，指定托已实测生成正式注单与机器隔离聊天消息。未跑全量测试；服务器/生产与 BY220 运行态未验证。
> 需求基线：[托生命周期严格对齐 BY220 确认](../需求基线/2026-10-09-托生命周期严格对齐BY220确认.md)。
> 范围限制：保留 Xupan 托的会员资料、拉黑、换名与链接有效期；托积分完全不进入机器积分池；清除此前自造的托行为设定，严格按 BY220 有源码证据的规则实现。

## 1. 目标与验收边界

在 `/console` 的机器托管理中，保留当前托玩家账号/链接/昵称/拉黑/换名/有效期体验；把自动托生命周期收敛为 BY220：创建默认自动、固定五档下注金额、按 BY220 自动下注池选取、自动上下分、机器级追单权限与托级状态、BY220 可证的飞单状态。托手工或自动上下分仅记托钱包虚拟积分账，不触碰机器积分池。

工程实现继续使用 Xupan 的 Spring Boot、MySQL、Flyway、虚拟钱包事务/账本、幂等任务与审计，不复制 BY220 PHP、数据库或外部报网运行配置。

## 2. BY220 候选池与 Xupan 比较

BY220 `application/console/Websocket.php` 的托下注候选池按游戏行 `hasKey/hasTe` 分支：

| 游戏标记 | BY220 源码池 | 槽位数 | 唯一基础项 | 执行语义 |
| --- | --- | ---: | ---: | --- |
| `hasKey=0` | 五个位置各自的大/小、单/双、尾大/尾小，再加龙虎及全局大小单双尾项 | 38 | 38 | 按候选池均匀抽取 |
| `hasKey=1, hasTe=0` | 番/角/正/无/严/单双/大小/车等，含重复权重和“特”占位 | 80 | 53 | 24 个“特”槽因 `hasTe=0` 被跳过；其余有效候选 56 槽、52 个不同基础文本 |
| `hasKey=1, hasTe=1` | 同类带权重池，含“特” | 80 | 53 | 24 个“特”槽各再随机 1–20 号码 |

BY220 本地 `local/seed-base.sql` 将“澳8番摊” `gameType=132` 设为 `hasKey=0, hasTe=0`，所以该本地种子使用 38 项分支。生产/服务器实际机器库未在本次静态核对中读取；实施验收须把实际游戏标记映射到 Xupan 目标彩种，不能把本地 fixture 写成生产事实。

Xupan 当前后端有 11 个 `PlayType` 类别；其中 `ODD_EVEN` 由参数拆成单/双、`BIG_SMALL` 拆成大/小，所以现有玩家端实际支持 13 个叶子玩法。玩家聊天室键盘已列出单、双、大、小独立输入；下注解析器、赔率模型和结算服务均已有对应的 11 个类型及二值参数。托自动生成器目前按 11 个类型抽取，再随机二值参数，并允许白名单配置。

### 2.1 用户确认的唯一托玩法池

- 单池固定包含 **13 个叶子玩法**：`番`、`角`、`加`、`车`、`念`、`正`、`通`、`无`、`单`、`双`、`大`、`小`、`特`。
- `单/双` 与 `大/小` 分别作为四个可独立抽取/下注的玩法结果；`特` 始终参加自动候选抽取，不受 BY220 历史 `hasTe` 跳过逻辑影响。
- `加`、`通`沿用 Xupan 当前生成器；其余 11 个结果映射 BY220 AU8 的语法和玩法参数。仍通过现有 `BetTextParser`、赔率和结算链路，不允许仅生成聊天文本却没有正式 `game_bet`。
- 不建立三个 `hasKey/hasTe` 自动池，不保留托级玩法白名单。13 个叶子玩法在同一个池中抽取，“特”始终作为候选项。选中后再按玩法合法范围随机参数；`加/通`沿用现有 Xupan 参数生成器。抽样权重按使用者 2026-10-09 确认的 §2.2 执行。
- **可行性核对**：`UserRoom.vue` 键盘包含 13 个独立 token；`BetTextParser`、`SettlementService` 对应 11 个类别并支持单双/大小二值参数；`QUICK_BET_OPTIONS` 已有单、双、大、小快捷项。Xupan 当前玩家端与正式下注/结算链路已具备承载能力；本计划需保证托自动入口使用同一解析/结算路径。
### 2.2 已确认的单池抽样权重

按使用者确认，以 BY220 `hasKey=1, hasTe=1` 的 80 槽完整池作为共同玩法权重底稿：`特` 24 槽（30%）、`无` 24 槽（30%）、`车` 8 槽（10%）、`严/念` 8 槽（10%）、`角`/`番`/`正`各 4 槽（各 5%）、`单`/`双`/`大`/`小`各 1 槽（各 1.25%）。

为将 Xupan 扩展的`加`、`通`纳入同一池，使用者确认分别分配 5%，其余 BY220 权重按 90% 等比例缩放：

| 玩法 | 已批准概率 |
| --- | ---: |
| 特 | 27% |
| 无 | 27% |
| 车 | 9% |
| 念（BY220 源码命令使用“严”） | 9% |
| 角、番、正 | 各 4.5% |
| 单、双、大、小 | 各 1.125% |
| 加、通 | 各 5% |

合计 100%；选中特后，再在 01–20 中均匀选号码。作为对照，13 项完全等概率会使`特`、`无`各从 BY220 完整池的 30% 降到约 7.69%。上表权重已经使用者确认。BY220 实际运行 AU8 标记不再作为前置条件；依据为 BY220 源码候选数组与本地种子，Xupan 使用用户指定的统一池，不按 `hasKey/hasTe` 分支跳过。

## 3. BY220 → Xupan 实施映射

| BY220 页面/规则 | Xupan 当前实现 | 收敛实现 |
| --- | --- | --- |
| 创建托时 `isauto=1`；默认 `tuoMin=30, tuoMax=300` | 新托 `MANUAL`，每期单数默认 0 | 新托行为行由数据库和全部创建入口默认 `AUTOMATIC`；默认金额档为 30–300。已有托的手动/自动开关保留；新旧托均不保留其他 Xupan 私有参数 |
| `SetAuto` 切换 `isauto` | `AUTOMATIC/MANUAL` 模式已存在，但旁挂大量参数 | 保留此开关；自动状态驱动 BY220 风格服务端行为 |
| `tuoMinMax` 固定五档；`rand(tuoMin,tuoMax)` | 六档含 `RANDOM`，并整十/20% 余额压降 | 仅五档，按整数区间随机；删除额外压降和整十规则 |
| BY220 根据 `hasKey/hasTe` 分支生成带权托玩法；用户确认采用单一 13 叶子池及 §2.2 权重 | Xupan 原来按 11 个 `PlayType` 类别抽取且受白名单/活跃比例/每期单数影响 | 使用固定 13 个叶子玩法单池并按已批准权重抽取；`加/通`沿用 Xupan 当前生成器，其余按 BY220 AU8 语义；不做 `hasKey/hasTe` 分支，`特`始终参与；去除白名单/活跃比例/每期单数配置，保留持久化幂等动作 |
| 余额不足时按 `tuoMin` 自动上分；阈值与下注下限共用；自动下分按 BY220 条件 | 概率上分，写 `PENDING` 申请；无自动下分 | 自动上/下分直接写托钱包虚拟账本，不扣机器池、不审批；来源动作有独立幂等键与原因码 |
| 15 秒行为循环可能发布下注、上下分、查余额/流水/历史消息 | 自动模式不发闲聊，只有托下注消息/反馈 | 按 BY220 行为类别生成并持久化托操作消息；每种消息仍按当前机器聊天室隔离规则投递 |
| 超管机器 `zhui` 权限 + 托 `zhui` 开关 | `agent.chase_enabled` 字段存在；无托级值/校验链 | 增加托级开关，机器权限为后端门禁；BY220 代码只证明字段保存和界面/门禁，不自行新增没有源代码依据的追号投注规则 |
| 托 `isFeidan` 按钮/玩家级字段 | 只有机器级报网设置，无托级字段 | 增加托级开关/状态；BY220 自动托单排除在自动飞单队列外，不能因 UI 字段而把托下注送到真实上游 |
| 托余额独立于机器积分池 | Xupan 手工 BOT 上下分已不联动机器池；新的自动上分申请也是 BOT 钱包操作 | 所有托人工/自动加减分使用托钱包及流水，确认不调用机器池账本 |
| 玩家链接有效期、黑名单 | Xupan 链接体系与有效期 | 保持当前实现；链接过期行为沿用当前 Xupan 登录访问规则，不修改链接/身份模型 |

| 截图中的现有控件 | 计划处理 | BY220 对应控件/行为 |
