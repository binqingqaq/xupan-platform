# Xupan 机器人回复格式与场景补齐开发计划

> 状态：2026-10-30 已按本计划实施 P1–P6 的代码、迁移和自动化验收；本机 MySQL 8.4、前端定向测试、类型检查与生产构建通过。BY220 运行界面、Xupan 真实角色浏览器、服务器和生产未验收，范围见[本机验收记录](../验收记录/2026-10-30-Xupan机器人回复格式与场景补齐本机验收记录.md)。使用者明确要求按 BY220 和当前 Xupan 事实确定口径，不设置文案审核前置步骤。当前差异见 [Xupan 机器人回复格式与场景对齐草案](../需求基线/2026-10-30-Xupan机器人回复格式与场景对齐草案.md)；BY220 第一参考见[机器人回复消息格式与场景样例](../参考资料/BY220机器人回复消息格式与场景样例.md)。

## 1. 目标与已定边界

把每一期的开期、提醒、封盘、核对、开奖、结算消息，以及下注、查询、取消、上下分、托和失败退单的机器人反馈补成一条可测试的业务链。消息由服务端根据已提交的期号、注单、钱包和申请事实生成，玩家前端只负责展示。BY220 的触发场景与可见文本是第一参考；底层继续使用 Xupan 的 Java、MySQL、结构化开奖卡片、唯一机器人和消息 outbox。

- **既有决定保持**：唯一机器人显示名“机器人”和固定头像；同机消息隔离，公共开奖共享；全部为虚拟积分、最多两位小数；下分申请创建即扣、驳回才退；`玩法/说明` 由发送者本机弹层，不新增机器人图片；托自动下注走正式玩家注单，不伪造闲聊或成功结果；中心结果未知不当作退单。
- **统一显示词**：保留 BY220 和当前 Xupan 均使用的“攻击成功”，但把“粮草”“元”“¥”改为“积分”；期号显示完整期号，金额显示两位小数。历史旧消息不回写。系统/机器人身份和图片渲染不得靠前端拼接假事实。
- **不改变账务**：机器人文案调整不得改变下注、撤单、报网、钱包、结算的事务和余额时点。当前聊天“流水”是业务日内 `SUM(stake)`，输出明确称“今日累计下注积分”，不把它误标为单边/双边流水。机器报表的 `rebate_mode` 与该聊天查询不是同一已证明算法，本批不移植 BY220 的单/双边统计。
- **BY220 页面映射**：`application/common.php` 的 `addMsg*`/`addDan*` 和期次播报对应 Xupan `ChatMessageService`/`RobotDispatchService`；BY220 `chat/controller/Index.php` 指令对应 `ChatCommandParser` 与玩家聊天链；BY220 `rbt/controller/Index.php` 审批与人工上下分对应 `PlayerPointRequestService`/`AgentConsoleService`；BY220 报网失败撤单对应 `ReportService`。参考项目实际运行页须在实施阶段用本地授权环境核对，静态源码不能充当运行证据。

## 2. 按场景确定的实现结果

以下 ID 与草案一致。“保持”是明确决定，不是待确认。固定展示模板用于下一轮开发和测试；业务异常只能选与真实状态匹配的分支。

| 场景 | 本次决定 | 数据与可见范围 |
| --- | --- | --- |
| L01 开期 | 保留 `{完整期号}期开始，欢迎进入聊天室。`，一期开一次 | `game_issue_event` → `PUBLIC` |
| L02 封盘前提醒 | AU8 改为每台机器在**实际有效封盘时刻前 60 秒**提醒一次；按真实剩余秒数输出 `距离{期号}期本机封盘还剩{秒}秒！`，不能迟到时仍说 60 秒。切换后不再为 AU8 新写全局 30 秒提醒；其他彩种先维持原规则 | `MACHINE`；有效封盘取全局投注截止与机器提前封盘时点中较早者。机器已手动关闭时不发倒计时 |
| L03/L04 停止与核对 | 全局投注期停止仍发 `{期号}期停止` 公告；机器有效封盘时发该机器核对列表，保留真实注额合计、昵称分组、空列表及“开奖前已公告退单”有效性说明。机器提前封盘时先发本机停止提示再发核对；默认封盘与全局停止同刻时避免重复停止提示 | 停止公告 `PUBLIC`；提前停止和核对 `MACHINE`。核对名单只读该机器正式未取消注单 |
| L05 开奖中 | 保持无随机号码机器人消息；顶部滚动球只是前端动画 | 无新机器人消息 |
| L06–L08 正式开奖三段 | 保留 `DRAW_SUMMARY`、`DRAW_HISTORY`、`WINNER_LIST`，补八球、番、适用的球位属性、时间、真实下注积分/净盈积分及空状态；历史继续最近 15 期与至多 60 期番路。后台确认开奖结果之前绝不派发 | 前两段 `PUBLIC`，获胜名单 `MACHINE`，结构化 payload 而非任意 HTML |
| L09 当期总榜 | 增加机器范围内的“本期积分榜”组件，按该机器已结注单计算玩家当期下注积分合计和净盈，固定排序与并列规则；**不展示实时钱包余额**，避免跨结算时点误导 | 新组件 `MACHINE`；无注单时显示空态，不生成假排名 |
| L10 开奖走势 | 自动开奖继续在 `DRAW_HISTORY` 网格内展示番路，不再额外发一张重复走势图；玩家主动输入“走势”时返回单独同机查询卡片 | 查询 `MACHINE`，由已确认历史结果生成 |
| C01/C09/C14/C16 | 普通聊天仍回复既有格式错误；幂等重发不重复回复；`玩法/说明` 仍本机弹层；取消的三类禁止/空窗口分支保持 | 维持当前权限与机器范围 |
| C02–C04 下注成功、部分成功、全限额拒绝 | 成功为 `@{昵称}，第{期号}期攻击成功，使用积分{本次已受理合计}，剩余积分{余额}。`；部分成功在同一回复追加每个被拒子项和剩余可下额；全拒绝只发失败及逐项原因，不写成功注单 | 同机反馈；只使用正式受理/拒绝项及提交后的钱包余额 |
| C05–C08 余额、封盘和玩法拒绝 | 余额不足写需要的积分数，不写竞争后可能已变动的“当前余额”；区分全局封盘、开奖中、机器手动封盘、机器提前封盘、玩法关闭和参数错误。仅使用稳定服务端错误码/安全文案，不拼接 SQL/异常类名 | 同机反馈；拒绝后无扣分或成功注单 |
| C10/C11/C12/C13 查询 | `查` 输出 `剩余积分：X.XX`；`历史` 返回最近 15 期已确认结果的同机结构化卡片；新增 `走势` 指令，复用最多 60 期已确认番路，历史为空时明确空态；`流水` 保留 06:00 起算的今日业务日，输出今日累计下注积分、已结盈亏和下注期数 | 来源输入和回复均 `MACHINE`；不读取其他机器玩家账务 |
| C15 取消成功 | 保持一条幂等机器人消息，先列每笔取消的原注单文本、返还积分和当次余额，最后列“{秒}秒内有效指令已全部取消”；不为同一次取消另造第二条总结 | 同机；仅已成功删除/取消并完成退款的注单 |
| P01–P03 申请 | 上分提交后说“待审批”；下分提交后明确“已扣除 X 积分，待审批，剩余 Y”；零额/超精度等指令格式错误给上/下分专属失败文案，相同客户端消息 ID 幂等重放 | 同机；申请与下分预扣事实一致 |
| P04 下分余额不足 | 申请、预扣失败时回滚业务事务；另在新事务安全记录来源文本及一条“下分申请未提交：积分不足”回复，**不留下申请或预扣行** | 同机；需复用下注拒绝的事务后反馈模型 |
| P05–P07 审批 | 同意上分可显示审批后钱包快照；同意下分只告知审批通过，不再次扣分；拒绝上分告知未通过；拒绝下分仅在存在原预扣且已成功退款时写“已退回 X”，历史无预扣申请绝不写已退款 | 同机；批准/驳回与申请状态、机器池、钱包流水一致 |
| P08–P11 代理人工与托 | 代理在 `/console` 对名下玩家/托人工上下分成功后发一条同机机器人结果；托自动下注与自动上下分继续复用正式业务链，成功用“积分”格式，跳过/失败不伪报成功 | 不给其他机器广播；普通玩家的机器池划拨与托钱包规则保持原状 |
| P12/P13 上报失败/未知 | 明确失败且开启自动退单、退款提交后，改用持久化昵称与注单玩法快照回复 `@昵称，第{期号}期“{原下注文本}”因上报失败已取消，返还积分X.XX。`；`PENDING/TIMEOUT` 保持无退款/取消消息 | 同机；`BetRow` 需补快照字段，不使用 `@betId`，不猜测已删除玩家信息 |
| P14 中心人工结论 | `REFUND_CANCEL_LOCAL` 真正完成本地取消退款后发一条同机消息；`KEEP_LOCAL` 只在代理操作页显示处理结果，不发玩家聊天室消息 | 不改中心订单/额度；同一结论重放不重复通知 |
| 单笔结算反馈 | WIN/LOSE/DRAW 使用“积分”；LOSE 表述为“本注已扣积分”而非“结算时再扣”；余额采用**该笔结算提交时的账本快照**，不在发送时重新读取可能已变化的钱包。CANCELED 与主动取消/自动退单通知按同一注单事件去重 | 同机；开奖卡片与单笔反馈分别幂等，暂不要求跨异步派发器的绝对到达顺序 |

统一金额展示为 `0.00`、`10.50` 等两位小数；原始用户输入和玩法文本按当前安全文本策略处理。原有 `chat_message` 历史内容不批量改写。上述范围不新增充值、提现或真实外部上游能力。

## 3. 消息契约与持久化设计

### 3.1 共用消息出口

保留 `ChatMessageService.publishRobotMessage` 作为唯一写 `chat_message`、分配房间序号和写 `chat_outbox` 的出口。为新业务结果引入内部“机器人通知意图”持久化表（实施时使用 V99 之后的**下一个空闲 Flyway 版本**，不得修改旧迁移）：

- 字段至少包含 `id`、`event_code`、`source_type`、`source_id`、`game_code`、`issue_number`、`visibility`、`agent_id`、必要且脱敏的业务快照 JSON、稳定唯一 `idempotency_key`、`status`、`attempt_count`、`next_attempt_at`、`lease_until`、`message_id`、`created_at/updated_at`；对 `status`、`visibility`、金额精度和键长度加约束，并建立到期扫描和来源查询索引。
- 钱包/申请/报网退款事务只在同一事务追加通知意图；派发器随后读取快照生成文字，通过现有机器人消息出口写消息和 outbox，再把意图标为已发布。重复执行命中唯一键和既有消息，不能重复扣分、退款或发同义消息。失败保留原因、退避重试，处理中租约过期可恢复。
- 已完成意图按现有聊天保留期分批清理；待处理、处理中、失败的不因到期被删。快照不保存密码、Token、真实外部地址或无关个人信息。`message_id` 可随聊天保留清理解除引用；操作审计独立保留。
- **用户直接聊天反馈**继续在来源消息事务内写机器人消息；C05/P04 的业务拒绝需在原交易回滚后由独立事务写“用户原文 + 失败反馈”，不留下失败业务事实。**期次四类既有事件**继续使用 `game_issue_event/chat_robot_dispatch`；新机器级提示和非聊天业务通知使用通知意图，避免强行塞进全局唯一 `(game_code, issue_number, event_type)` 的事件表。

### 3.2 数据来源与回执快照

| 输出字段 | 事实来源与实现约束 |
| --- | --- |
| 期号与开奖 | `game_issue` 的正式期次/已确认八球；未确认和前端滚动预览不得写入机器人结果。人工确认、自动开奖和补期共用同一事件幂等键 |
| 机器封盘时点 | 当前 `betting_ends_at` 与 `draw_ends_at - close_seconds` 取较早者；`close_seconds<=0` 时只用全局截止。机器手动关闭单独决定能否下注，不生成假“本期结束”事件 |
| 玩家称呼 | `demo_user_account` / `game_bet` 的发送时昵称快照；失败退单查询需给 `ReportUpstreamOrderRepository.BetRow` 增补 `player_name_snapshot` 与可还原的原始下注文本/球位，快照缺失时不得用数字 ID 冒充昵称 |
| 下注金额和余额 | 成功批次实际落库注额合计、钱包/流水前后值；限额拒绝使用逐项 `BetLimitExceededException` 的剩余额度，不能凭前端估算 |
| 结算余额 | `BetSettlementCompletedEvent` 增加事务内确认的 `balance_after` 或账本流水 ID；WIN/DRAW/LOSE 都保存同一时点快照。监听器只读快照，不重新计算或改写钱包 |
| 审批结果 | `player_point_request.status`、本次钱包/机器账本和预扣/退款幂等流水。旧 DOWN 请求没有预扣行时只说“未通过”，不发“已退回” |
| 当期总榜 | 仅聚合本机同一期已结注单，按净盈降序、同分按稳定玩家标识排序；不读取跨机器余额，也不把未结注单算进榜 |
| 主动历史/走势 | 与自动开奖卡片共用已确认期号查询和结构化渲染；用户主动查询的消息加来源消息关联且限定 `MACHINE` |
| 今日流水 | `PlayerBetSummaryRepository.findBetDayStatistics` 当前 `SUM(stake)`、已结 `net_profit` 与 `countBetIssues`；Asia/Shanghai 06:00 业务日，不借 `rebate_mode` 标签冒充单/双边流水 |

### 3.3 结构化消息兼容

开奖卡片继续用受校验的结构化 payload；`RobotDrawMessage.vue` / `robotDrawImage.ts` 只做无脚本渲染。新增总榜及主动走势图要扩展 `RobotDrawComponent`、`RobotDrawComponentRepository`、前端 `robotDrawMessage.ts` 解析和渲染，并通过新迁移扩展组件 CHECK/默认配置；旧 `xupan.chat-payload.v1` 的三种历史组件仍必须可读。金额图片不再显示 `¥`，空态和屏幕阅读文字也使用积分。不要把 BY220 HTML 直接塞入 `v-html`。

## 5. 必须通过的验收场景

1. **一期完整闭环**：正常开期 → 机器实际封盘前提醒 → 全局停止与每机器核对 → DRAWING 不发假号码 → 正式结果/历史/机器中奖名单/本期总榜 → 下一期开期。零注单、无赢家及缺结果均给真实空态或保持未发布，不出现占位数据。
2. **机器时间和范围**：两台机器 `close_seconds` 不同、一台手动封盘；只在各自有效时点收到一次提醒/核对。公共开奖结果两机可见，名单、榜单、玩家反馈只在所属机器可见。下注、机器关盘和核对生成共享必要行锁，避免核对遗漏正在提交的注单。
3. **玩家操作矩阵**：单笔成功、同批部分成功/全拒、余额不足、总额和玩法限额、机器手动/提前封盘、全局封盘、开奖中、格式错误、相同请求重发、不同正文复用幂等键；逐条核对注单、钱包、消息、outbox 和提示文本。
4. **查询与取消**：查余额；历史 0/1/15+ 期；走势 0/60+ 期；跨 06:00 的今日流水；玩法说明只给发送者弹层；取消 0/1/多笔、禁止取消和窗口超时，验证退款金额、剩余余额及消息不重复。
5. **积分申请**：上分和下分提交、下分不足、并发下注耗尽余额、同意/拒绝、旧无预扣 DOWN、重复审批；普通玩家与托人工/自动上下分分别按实际钱包与机器池规则回复，不出现“已退款但无退款流水”。
6. **报网和结算**：明确失败自动退单发昵称/原注单文本/实际退回积分；`PENDING/TIMEOUT` 不发取消；中心退款后 `KEEP_LOCAL` 静默、`REFUND_CANCEL_LOCAL` 一次通知。WIN/LOSE/DRAW 的余额来自结算快照，消息失败/重试不再次结算。
7. **交付与恢复**：事务回滚无成功消息；重启、并发扫描、投递租约过期与 outbox 重放只各发一次；旧 `xupan.chat-payload.v1` 能显示；聊天保留五天与待处理通知意图不丢；主机时间、时区、精度和字符安全校验均通过。

验证层级：源码/单测 → 隔离 H2（可运行部分）→ 隔离 MySQL 8.4 LTS 迁移与集成 → 本机真实角色浏览器 → 服务器/生产现场。项目既有 V83 MySQL `UPDATE ... JOIN` 会阻断某些 H2 全上下文测试，不能用 H2 失败替代 MySQL 验收，也不能把本机 200/测试通过写成服务器上线。真实账号、完整 URL、密码、Token 不进入测试输出或文档。

## 6. 风险与回退

- **提醒错时**：机器提前封盘和全局截止同时存在，按较早时点判断；若任务延迟进入不足 60 秒窗口，只写真实剩余秒数，封盘后不补过期提醒。模板切换前后同一期用稳定键避免新旧提醒重复。
- **消息与账务分叉**：业务事务只生成通知意图，消息派发失败重试；退款、批准和结算的金额快照不可由重试时的当前余额重算。取消与自动退单之间按注单状态和事件键互斥。
- **旧聊天与迁移**：不重写旧 `chat_message` 内容；新结构化组件兼容旧 payload。Flyway 只前向新增或调整约束；若失败，保留已提交的账务和消息，按迁移与派发状态前向修复，不手工删除历史。
- **大卡片与信息泄露**：核对、历史、走势、榜单按长度/条数上限分页或截断并标明“仅展示前 N 条”；榜单不展示跨机玩家或实时余额。前端固定宽度图片要在窄屏可读且不遮挡聊天室输入。
- **偏离 BY220 的已确认规则**：虚拟积分、机器隔离、唯一机器人、玩法说明本机弹层、积分非负与两位小数、下分创建即时扣除均优先保留；不因照搬旧文案引入现实资金语义或覆盖现行账务事实。
