## 2. 开发阶段重构原则

本次可直接重构现有类、服务、接口DTO、表结构和索引。以最终 BY220 业务流程清晰、数据一致为目标，不要求沿用当前 `DemoGameService`、`PlayType → 单一赔率` 或全局限额的结构。

1. **允许重建开发数据。** 为消除旧赔率、旧限额、旧返点来源的语义冲突，可清理并重建本地开发库中的关联业务数据；不要求保持旧账单结果或迁移全部历史注单。
2. **统一处理关联数据。** 清理订单时同步处理关联钱包流水、结算记录、批次幂等、报表明细、机器人／聊天事件及中心上游引用，先梳理外键和逻辑引用。不能只删注单后让余额、流水或引用悬空。
3. **交付可重复初始化。** 表结构仍由 Flyway 管理；新库从零初始化和现有开发库重建都应可重复执行。优先新增迁移重构，不直接改已执行迁移的校验值；若确需重做迁移基线，必须提供明确的开发库重建步骤，不能把旧库校验失败当成正常状态。
4. **不建设旧数据双轨。** 无须为旧开发注单保留第二套结算器、旧规则回退或兼容接口。旧数据清理后以新模型为唯一正常链路。
5. **保留运行期快照。** 重建完成后，新订单仍须固定接单时的规则和P/T/F/R。运营中修改配置不改变已接订单；这是业务正确性，与是否保留开发历史数据是两回事。
6. **环境范围明确。** 本计划实施默认针对本地开发环境；本次清理授权不自动意味着现在清理服务器。需要发布时另按实际发布任务执行。

## 5. 目标实现结构

以下类名为建议命名，可在实现时结合现有结构调整，职责与业务契约必须保留。

```text
机器表单／顶部保存
  → MachineBettingConfigService（授权、校验、版本、审计）
  → agent及玩家配置

文本／快捷／API／托
  → BetTextParser或结构化请求
  → BetRuleCatalog（合法名称、规范参数、赔率规则、额度分组）
  → BetPricingService（机器参数、展示值、结算公式）
  → BetPlacementService（批次幂等、期号、限额、钱包、落单事务）
  → SettlementService（快照结算）
  → BetFlowMetricsCalculator（单／双边流水、返水）
```

### 5.1 规则目录与赔率

- 规则目录同时保存结算规则键和限额组键；二者不强制相同。NONE两参数与三参数必须可以区分；念／无的方向参数不能随意排序；仅对BY220允许交换的别名归一化。
- 目录提供明确参数长度、号码范围、重复限制、可用游戏和 `hasTe` 条件。`132456番`、无号码“特”等不能靠字符串包含关系通过校验。
- 统一从目录取得展示倍率与结算公式。P=95时番3.850、念2.900、正／角／单双／大小／加／两号码无1.950、通／三号码无1.475；车显示1.316，结算保留1/3公式；T=18时特码显示18.00。
- 车和返水不能由已格式化字符串反推精度；存储原参数或有理数系数，在规定步骤截断或舍入，最终虚拟积分以2位持久化。
- 全量224名称、52普通规则、20特号码与74快捷格共用目录事实；前端不能再独立维护第二套赔率公式。

### 5.2 机器配置与保存

- 复用已有 `agent` 参数列，统一超管编辑与代理保存的字段校验；当前登录机器由服务端确定。
- 将13项限额纳入接单配置；配置读取得到一次完整版本，避免同一批订单混用更新前后的P/T和限额。
- 顶部失焦保存与弹窗确认按BY220操作顺序实现。采用仅提交变更字段或携带版本的更新方式，避免整表单旧数据覆盖其他操作者的新值。
- `xiugai` 对应编辑权限必须在服务端落实；超管权限与机器本人权限按原入口区分，不能把超管API当作机器登录的替代入口。
- 机器0值／缺项按取证结果返回相应状态，不再静默读取全局值兜底。保存失败显示原因并恢复已保存值。

### 5.3 单笔、批次和特码组合

- 保留“用户指令”“拆分后的明细”和“批次”三个层次。`1/2特100` 的指令总额是200，每号100；最高／最低注额检查该指令总额，号码限额按100检查。
- 普通多条指令逐条校验最高／最低注额，同时对整批总额与相同额度组累计待接金额；相同别名不能绕过批内额度。
- BY220常规预检查失败应不进入扣分阶段。目标采用整批业务原子性：任一指令校验失败则整批不扣分、不占额、不生成成功订单；失败回执可指出具体项目。
- 批次幂等键绑定玩家、游戏、期号和规范化请求摘要；同键同请求返回原结果，同键不同内容拒绝。消息重发跨期时不得误变成新下注。
- 成功响应返回各明细实际倍率与快照信息；所有消息／机器人反馈在事务成功后发布。拒绝反馈不意味着成功订单存在。

### 5.4 限额与并发

1. 服务端解析所属机器、玩家、游戏和当前期，检查玩法启用、开盘／封盘及指令合法性。
2. 固定锁顺序读取期号、机器配置和玩家余额／额度；接单与撤单必须使用相同数据库锁规则。
3. 从有效订单明细累计本玩家本期额度；保留BY220游戏及非托条件，球位不默认加入分组。模板展示的剩余额不是接单依据。
4. 按每指令最小／最大、具体玩法桶、具体特码号码桶及整批总额校验；恰好达到限额允许，再多最小单位拒绝。
5. 同一事务内写批次、明细、快照和钱包流水；提交前再次确保所使用期号仍可接单。不得仅依赖JVM进程内锁或先查后写。

首选锁定现有玩家账户行后重查订单累计，减少新增可漂移的计数表；MySQL一致性读与锁定读需显式设计，避免等待锁后仍读旧快照。若压测表明需要额度表，再新增带唯一键的事务性额度记录及对账修复机制。具体锁顺序在实现前写入代码设计并覆盖死锁／重试测试。

撤单退分、物理删除或历史取消状态排除均应同步释放额度。数据库重试由唯一键与幂等保证不重复扣分；配置下调不回写既有订单，已用额度超过新上限时新增订单拒绝。
