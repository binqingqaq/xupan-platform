# 玩家身份模型与聊天室链接登录总体实施计划

> **给实施者：** 本计划负责全局统筹。按阶段顺序执行对应详细计划；每个阶段完成代码、测试、迁移和验收后，才能进入下一阶段。

**目标：** 在现有统一管理后台和玩家工作台基础上，建立稳定的 `wxid` 内部编号、`v数字` 会员 ID、昵称展示体系，并为普通玩家提供只能访问聊天室的链接登录能力，同时保持管理员密码登录、托行为和虚拟积分流水的既有边界。

**架构：** 保留 `sys_user.id` 作为数据库技术主键，新增不可变的 `internal_code` 作为 `wxid_...` 业务内部编号；保留 `demo_user_account.user_code` 作为旧接口兼容字段，同时增加面向业务的会员 ID映射，不直接改写现有注单和流水关联。管理员继续使用密码认证，普通玩家使用受控链接认证，托使用服务端行为身份，不向托发放人工登录链接。

**技术栈：** Java 21、Spring Boot 4.0.8、Spring Security、JDBC、Flyway、MySQL 8.4 LTS、H2、Vue 3、TypeScript、Vite、Vitest、现有单实例 WebSocket。

## 全局约束

- 生产业务事实必须持久化到 MySQL 8.4 LTS；H2 只用于测试，不代表生产验证。
- 所有余额、下注、流水、中奖和结算仍然是虚拟积分，不新增充值、支付、提现、转账或现实资金能力。
- 不把 `wxid` 直接替换 `sys_user.id` 或 `sys_user.username`；数据库主键和旧登录字段保持兼容。
- `wxid_...` 必须不可变且唯一；会员 ID 必须唯一；昵称允许变更但不能承担身份唯一性。
- 链接登录必须使用哈希后的访问凭据，支持过期、撤销、重新生成和会话失效；完整链接只在创建或重新生成时返回给管理员，不写入日志。
- `CHAT_ONLY` 是后端授权边界，不以隐藏前端按钮作为权限控制。
- 管理员后台必须继续使用密码登录并要求现有权限；链接玩家不能访问 `/api/admin/**`、钱包管理、玩家管理、下注和开奖控制接口。
- `chat_robot` 服务端机器人与 `player_kind=BOT` 托玩家保持身份、权限、行为和数据隔离。
- 删除采用软删除和会话/链接撤销，保留下注、流水、聊天和审计记录。
- 每个阶段都必须补充对应测试；未执行的本机 MySQL、服务器和生产验证必须明确记录为未验证。

## 已确认的当前事实

- 统一后台主模块已有独立计划：[2026-09-20-统一管理后台与玩家工作台主模块实施计划.md](2026-09-20-统一管理后台与玩家工作台主模块实施计划.md)。该计划是本计划的阶段 0 前置，不在本计划重复实现。
- `sys_user` 当前有 `id`、`username`、`display_name`、`password_hash`、状态和用户类型。
- `demo_user_account` 当前有 `user_code`、`display_name`、余额、状态、身份类型和玩家分类。
- 普通玩家创建接口仍接受密码；托创建接口不要求密码，但服务端会生成随机密码。
- 当前 `/api/auth/login` 是用户名密码登录；`/api/auth/ws-ticket` 基于当前统一认证主体签发 WebSocket ticket。
- 当前 `/room` 前端路由要求统一认证，聊天 REST 接口也依赖当前认证主体。
- 当前玩家工作台没有删除接口；截图中的 `wxid_xxx（昵称）` 删除确认属于目标交互，不是现有实现事实。

## 目标身份关系

```text
sys_user.id                         数据库技术主键，不向用户承诺
sys_user.internal_code              wxid_atM9Rz1V8q3CF，内部稳定编号
demo_user_account.member_code      v1982，对外业务会员 ID
sys_user.display_name              拔胜侠454，昵称
展示                              @v1982.拔胜侠454
```

现有 `demo_user_account.user_code` 暂时保留为兼容字段。阶段一需要评估并确定它与 `member_code` 的映射方式，默认不直接批量改写已有 `user_code`，避免影响历史下注、流水和旧接口路径。

## 总体统筹任务

### 任务 1：冻结阶段边界和依赖

- [ ] **步骤 1：** 先完成阶段 0 统一后台计划中尚未完成的测试和运行态验收，不在身份改造阶段重新维护第二套玩家工作台。
- [ ] **步骤 2：** 阶段 1 只允许新增身份字段和展示契约；阶段 2 之前不得返回可登录链接；阶段 3 之前不得提供删除操作。
- [ ] **步骤 3：** 每个阶段结束时检查对应验收标准和 Git 范围，未通过则停止推进后续阶段。

### 任务 2：维护跨阶段接口兼容

- [ ] **步骤 1：** 保留 `userId`、`userCode`、`username` 旧字段和旧路由，同时增加 `internalCode`、`memberCode`、`authMode`、`scope`。
- [ ] **步骤 2：** 确认阶段 2 的 `CHAT_ONLY` 会话不能被阶段 3 的删除流程绕过；删除和链接轮换必须共享同一用户状态和安全版本校验。
- [ ] **步骤 3：** 每次数据库迁移后运行旧钱包、下注、聊天和机器人测试，确保身份改造不改变虚拟积分事实源。

### 任务 3：统一验收证据和发布门禁

- [ ] **步骤 1：** 阶段 1 至 3 使用 H2 完成自动化测试；阶段 4 使用本机 MySQL 8.4 完成真实迁移和 API 检查。
- [ ] **步骤 2：** 将浏览器、服务器和生产验证分别记录，不把计划、截图或 H2 结果写成生产结论。
- [ ] **步骤 3：** 所有阶段提交前运行 `git diff --check`、敏感信息扫描、前端构建和后端测试，并保留与本阶段相关的提交范围。

## 跨阶段接口契约

后台玩家接口最终返回以下身份字段，旧字段在迁移完成前继续返回：

```json
{
  "userId": 12,
  "internalCode": "wxid_atM9Rz1V8q3CF",
  "memberCode": "v1982",
  "userCode": "legacy-player-12",
  "displayName": "拔胜侠454",
  "playerKind": "NORMAL",
  "authMode": "PLAYER_LINK"
}
```

玩家链接认证返回普通访问 token 和最小用户视图，但不返回管理员权限：

```json
{
  "accessToken": "<一次性响应中的访问令牌>",
  "user": {
    "internalCode": "wxid_atM9Rz1V8q3CF",
    "memberCode": "v1982",
    "displayName": "拔胜侠454",
    "scope": "CHAT_ONLY"
  }
}
```

## 总体验收顺序

1. 先执行阶段 0 计划中尚未完成的统一后台测试和窄屏验证。
2. 执行阶段 1 的 Flyway、Repository、Controller、前端类型和展示测试。
3. 使用 H2 跑认证和聊天权限测试，再用本机 MySQL 8.4 执行迁移与真实 API 检查。
4. 通过阶段 2 后再开放链接生成入口，不在阶段 1 提前返回可登录链接。
5. 执行阶段 3 删除、撤销、重新生成、历史查询和并发重复请求测试。
6. 阶段 4 记录服务器验证、未执行项、备份/回滚方案和最终 Git 范围。

## 阶段验收标准

- 总计划和四份阶段计划的文件路径、阶段依赖、数据库版本和认证范围保持一致。
- 阶段 0 的统一后台能力不被身份改造破坏；阶段 1 至 3 各自具备可独立执行的测试和验收门槛。
- 普通玩家、托、管理员和链接会话的身份边界清晰，`CHAT_ONLY` 不能越权访问后台、下注、钱包或机器人管理。
- 所有玩家都能关联 `wxid`、会员 ID 和昵称，历史业务记录仍能追溯到同一用户。
- 只有经过 H2、本机 MySQL 8.4 和对应运行态证据的内容，才能在交付记录中标记为已验证。

## 非目标

- 不实现现实资金能力。
- 不复制参考项目的密码、Token、支付配置、外部地址或未经确认的业务规则。
- 不把普通玩家链接直接扩展为后台、下注、钱包或机器人控制权限。
- 不删除现有 `/admin/test-players`、`/admin/users`、`/admin/robots` 兼容入口。
- 不把 `chat_robot` 改造成玩家身份，也不让链接玩家参与服务端托调度。
