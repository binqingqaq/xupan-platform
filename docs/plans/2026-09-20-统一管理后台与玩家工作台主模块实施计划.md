# 统一管理后台与玩家工作台主模块实施计划

> **给实施者：** 按任务顺序执行本计划。步骤使用复选框（`- [ ]`）语法跟踪进度。本计划已进入实施，未勾选步骤表示本轮尚未执行或仍需现场验收。

**目标：** 建立统一的 `/admin` 管理后台壳体，并将现有玩家工作台作为第一块真实业务模块嵌入其中，其他管理区域保留清晰、无业务副作用的空白占位。

**架构：** 新的 `/admin` 负责统一后台布局、导航、模块选中状态和预留区域；玩家工作台拆成可嵌入的 Vue 业务模块，继续复用现有 `PlayerDeskAdminController`、`PlayerDeskAdminService` 和 `/api/admin/player-desk/**` 接口。旧运营页、用户管理页、测试玩家直达页和服务端机器人管理页保留兼容入口，避免统一壳体改造造成已有能力丢失。

**技术栈：** Java 21、Spring Boot 4.0.8、Spring Security、JDBC、Flyway、MySQL 8.4 LTS、Vue 3、TypeScript、Vite、Vitest。

## 全局约束

- 本阶段只改后台前端路由、布局、组件和对应前端测试；不新增数据库迁移，不修改玩家、钱包、注单、托动作和机器人领域规则。
- 所有余额、下注、开奖、结算和盈亏均为虚拟积分；不得新增充值、支付、提现、转账、代理分成或现实资金语义。
- 普通玩家继续通过现有 `UserAdminService.createUser` 和 `/api/admin/player-desk/players/normal` 创建；托继续通过现有测试玩家创建链路和 `/api/admin/player-desk/players/bot` 创建。
- `player_kind=BOT` 的测试玩家与独立 `chat_robot` 服务端机器人保持数据、权限、钱包和下注链路隔离。
- `/admin` 统一壳体中未实现区域只能显示占位标题和空状态，不显示可点击的伪按钮、不生成假数据、不调用未实现接口。
- `/admin/test-players`、`/admin/users`、`/admin/robots` 和现有旧运营能力必须保留可访问性；迁移统一页面时不得删除兼容入口。
- 桌面端参考截图的紧凑分区结构，移动端必须纵向折叠，不能产生页面级横向滚动；表单必须保留可见标签、加载状态、错误提示和键盘可访问焦点。
- 新增文档、组件和测试文件使用中文或中英文结合文件名；代码标识、路径、命令和 API 名称保留原始英文形式。

## 当前事实与边界

已存在的业务入口和事实：

- `web/src/main.ts` 已注册 `/admin`、`/admin/users`、`/admin/test-players`、`/admin/robots` 四个管理员路由。
- `web/src/views/TestPlayerManagement.vue` 已实现普通玩家/托创建、筛选列表、详情、积分操作、托自动/手动模式、动作记录和注单展示。
- `web/src/api.ts` 已提供 `getPlayerDeskSummary`、`getPlayerDeskPlayers`、`getPlayerDeskPlayer`、`createNormalPlayer`、`createBotPlayer`、积分操作、行为配置、立即执行、消息和动作查询接口。
- `server/xupan-server/src/main/java/com/xupan/server/system/web/PlayerDeskAdminController.java` 已提供 `/api/admin/player-desk/**` 接口，统一受 `USER_MANAGE` 权限保护。
- `web/src/views/AdminPanel.vue` 当前仍承载旧的赔率、虚拟钱包、开奖和本期注单操作；本阶段不能直接删除这些能力。
- `web/src/views/RobotManagement.vue` 管理的是独立 `chat_robot`，不等同于玩家工作台中的测试托。

本阶段明确不做：

- 不把开奖、赔率、钱包、注单、用户管理和服务端机器人真正迁入统一主壳体。
- 不改变现有接口路径、数据库表、权限编码或自动托调度行为。
- 不实现截图中未确认的第三方业务语义，不复制参考系统的支付、代理或现实资金能力。

## 目标页面结构

统一 `/admin` 页面采用以下稳定结构：

```text
统一管理后台
├── 顶部状态栏：平台名称、管理员、系统状态、退出登录
├── 左侧功能区：玩家工作台选中项 + 期号/开奖等后续入口占位
└── 右侧主工作区
    ├── 当前期号/状态摘要：只展示已有游戏状态
    ├── 期号开奖区域：空白占位，不提供操作
    ├── 聊天与上下分区域：空白占位，不提供操作
    └── 玩家工作台：本阶段唯一完整业务模块
        ├── 总积分、普通玩家数、托数
        ├── 搜索、类型/状态筛选、刷新
        ├── 创建普通玩家、创建托
        ├── 玩家列表
        └── 玩家详情、积分、托行为、动作和注单
```

玩家工作台必须保持“左列表、右详情”的核心关系。创建入口放在工作台标题区或列表区，不再在页面外另设一套创建方式。普通玩家选择后只显示普通玩家相关信息；托玩家选择后显示 `AUTOMATIC/MANUAL`、每期下注、聊天消息和“立即执行”等托行为设置。

## 验收标准

- `/admin` 成为统一后台入口，页面结构包含顶部状态、左侧导航/预留区、主工作区和玩家工作台。
- 只有玩家工作台具备真实业务操作；其他区域是明确、无副作用的空白占位。
- 普通玩家和托的创建入口、列表、详情、积分、下注统计、动作记录和托自动/手动行为都集中在玩家工作台。
- 玩家工作台复用现有 `/api/admin/player-desk/**`，不新增重复业务 API 或数据库事实源。
- `/admin/test-players`、`/admin/users`、`/admin/robots` 和旧运营能力继续可访问，权限边界不变。
- `chat_robot` 服务端机器人与 `player_kind=BOT` 测试玩家在界面文案、API、数据和权限上保持隔离。
- 桌面端接近参考图的密集分区结构，移动端无页面级横向滚动，关键控件具备清晰标签、焦点和反馈。
- 前端测试、类型检查、构建和后端回归测试通过；运行态验收证据按环境分层记录。

## 后续阶段

本计划完成后，才分别为以下模块制定独立计划并接入统一壳体：

1. 期号、封盘、开奖和结算控制。
2. 注单查询、中奖流水和虚拟积分流水。
3. 聊天运营和上下分记录。
4. 服务端机器人、模板和投递记录。
5. 系统参数、权限和操作审计。

每个后续模块必须在自身接口、数据权限、审计、测试和运行态验收完成后，才从占位区域切换为可操作区域。
