## 2. 目标（用户已描述部分）

1. 托要先插入和普通玩家同一套逻辑：自动有效期 7 天的登录链接，链接可以进下注室。
2. 链接过期 → 进不去，且托的任何行为都停止；拉黑同理，托不执行任何操作。**链接是托能否工作的前提。**
3. 托没打开自动时与普通玩家没区别；打开自动才自动干活。
4. 托行为约束项（截图圈出部分）：
   - 下注范围：`随机 / 30-300 / 300-1000 / 1000-3000 / 3000-10000 / 10000-30000`
   - 下注金额整十：`随机 / 关 / 开`
   - 下注指定玩法：弹窗多选（截图含 角/正/番/车/单/双/大/小），再增加`随机`（等于全选）
   - 活跃比例（%）与每期注单（单）
5. 自动模式下**不发送聊天消息**（你好、吃了吗这类闲聊不再自动发）。
6. 不在一期开始瞬间所有托一起下注，而是在倒计时内随机时间下注。
7. 余额不够也要下（尽力下注，而不是直接失败）。
8. 还要覆盖上下分后台审核等场景，行为尽量贴近真实玩家。

## 3. 当前托已具备的能力（源码证据）

### 3.1 身份与入口

| 能力 | 现状 | 代码位置 |
| --- | --- | --- |
| 创建托 | 走测试玩家创建，然后 `player_kind='BOT'`、`auth_mode='BOT_SERVICE'`，创建时自动签发链接并建立行为行（默认未启用自动） | `PlayerDeskAdminService.createBot` |
| 登录链接 | 与普通玩家同一张 `player_access_link`、同一套 7 天默认有效期、拉黑/拉白/刷新/改有效期 | `PlayerLinkAuthenticationService` |
| 链接进下注室 | 可以。兑换要求 `scope=PLAYER_FULL`、`revoked_at IS NULL`、`expires_at > now`、用户与账户 ACTIVE、`player_kind IN ('NORMAL','BOT')` | `PlayerAccessLinkRepository.findUsableByHashForUpdate` |
| 账号状态 | 与普通玩家一致：ACTIVE / DISABLED / DELETED；停用或删除会撤销会话，删除还会撤销链接并停用行为 | `PlayerDeskAdminService`、`UserAdminService` |

### 3.2 行为配置（`test_player_behavior`）

- 字段：`run_mode(AUTOMATIC/MANUAL)`、`enabled`、`bets_per_issue(0-20)`、`stake_min/stake_max`、`chat_enabled`、`messages_per_issue(0-20)`、`next_run_at`、`last_issue_number`、`last_error_*`、`version`。
- 约束：`bets_per_issue`、`messages_per_issue` 各 0-20；`stake_min > 0`、`stake_max >= stake_min`；`enabled` 与 `run_mode` 联动（`AUTOMATIC` 才为 true）。
- 后台现状（工作台）：执行模式（自动/手动）、每期下注单数、最低积分、最高积分、发送聊天消息、每期消息数、保存、立即执行、手动发送测试消息。

### 3.3 调度与执行

- `TestPlayerBehaviorScheduler` 每 1 秒扫描一次 `player_kind='BOT'` 且用户/账户 ACTIVE 的玩家，逐个调用 `dispatch`。
- `xupan.test-player.behavior-enabled` 默认 **true**，`dispatch-interval-ms` 默认 1000。
- `dispatch` 条件：`BOT` + 行为配置存在 + （非 force 时）`AUTOMATIC` + 当前期处于 `BETTING`。
- **动作一次性创建并立即执行**：新一期开始后的第一次扫描就会把本期全部注单和聊天动作建好并执行完 → 所有托在同一时刻集中下注（与目标 6 冲突）。

### 3.4 下注内容与金额

- 文本固定为 `1番<金额>`：永远是第 1 球、永远是`番`玩法，参数固定为 `1`。
- 金额在 `stake_min..stake_max` 之间随机，保留 2 位小数（`randomStake`），例如 `1番217.43`。
- 没有"指定玩法"、没有"整十"、没有"活跃比例"、没有档位范围的概念。

### 3.5 聊天

- `chat_enabled` 打开时按 `messages_per_issue` 发送**固定文本**「大家好，托玩家测试消息」。
- 手动模式可由管理员在工作台发任意测试消息。

### 3.6 幂等、失败与审计

- `test_player_action` 每个动作有稳定幂等键 `TEST-PLAYER-{userId}-{issue}-{type}-{no}`，唯一约束 `(behavior_id, issue_number, action_no, action_type)`。
- 状态机 `PENDING/PROCESSING/SUCCEEDED/FAILED/SKIPPED`，带 `attempts`、30 秒租约、`error_code/error_message`、`message_id`、`bet_id`。
- 动作复用正式链路：`ChatMessageService` → 下注/扣分/注单/限额校验/机器人反馈。重复扫描不会重复下注。
- 执行前置检查只有账号状态（`isActiveBot`），**不看链接** → 拉黑或链接过期时，托的自动下注仍会继续（与目标 2 冲突）。

### 3.7 资金与审核

- 托有独立虚拟钱包，余额不足时 `placeBet` 抛 `WALLET_INSUFFICIENT_BALANCE`，动作记 `FAILED`，**不会降额重试**（与目标 7 冲突）。
- 托可以走聊天指令 `上100/下100` 进入后台审批队列；工作台也可人工上分/下分。
- 托的动作被限额拒绝时不会抛异常，动作会记 `SUCCEEDED` 但没有 `bet_id`（统计上"看起来成功"）。

### 3.8 当前能力的缺口汇总

1. 链接不是工作前提（拉黑/过期不影响自动行为）。
2. 自动模式会发闲聊消息。
3. 一期开始瞬间集中下注，没有随机时间分布。
4. 只有`番`、只有单参数、金额带小数，没有范围档位/整十/多玩法。
5. 没有活跃比例、没有每期注单与实际执行的关系控制。
6. 余额不足直接失败，不会尽力下注。

## 4. 逐项分析

### 4.1 链接作为工作前提

建议把"托可工作"定义为四要素同时成立：

```text
用户状态 ACTIVE + 账户状态 ACTIVE + player_kind = BOT + 存在可用链接
可用链接 = scope PLAYER_FULL 且 revoked_at IS NULL 且 expires_at > now
```

含义：拉黑、链接过期、刷新链接（旧链接撤销到新链接签发之间）、停用、删除都会让托停下来；重新拉白或刷新链接后自动恢复。这与"链接是托能不能工作的前提"一致。

注意点：

- 行为调度是后台任务，不依赖登录会话；因此"能工作"按"链接可用"判断，而不是"当前有在线会话"。若要求必须有活跃会话，需要额外定义"离线多久算不活跃"，成本更高，建议不做。
- 已经排好时间的待执行动作，在链接失效后应按 `SKIPPED(LINK_INVALID)` 收尾，而不是继续执行。

### 4.2 下注范围

6 个选项：`随机 / 30-300 / 300-1000 / 1000-3000 / 3000-10000 / 10000-30000`。

- 固定档位语义清楚：本期每笔在档位区间内随机取值。
- `随机`有两种解释，需要确认：
  - A. 每次从全部档位里随机挑一档，再在档内随机取值（波动大，更像"什么都下"）。
  - B. 在系统允许的最小值到最大值之间直接随机（等价于全局区间）。
  - 我倾向 A，因为和"下注范围 = 档位"的 UI 语义一致。
- **与现有额度规则的冲突（必须先定）**：当前全局配置为`玩家最高注额 5001`、`单场总限额 5000`、`番限额 20000`、`角限额 1000`、`特码限额 200`。若托选 `10000-30000` 或 `3000-10000`，单笔会被限额直接拒绝。三种处理方式：
  - 建议：托同样受限额约束，实际下注金额 = min(档位随机值, 该玩家当前期剩余额度, 该玩法剩余额度)；不足最小值（默认 1）时本期不下注并记录原因。
  - 备选：托不受限额约束（需要单独开关，风险是他们能下出超过限额的注）。
  - 备选：为托单独配置额度（新增一套配置，复杂度最高）。

### 4.3 下注金额整十

`随机 / 关 / 开`：

- `开`：金额向下取到 10 的倍数（100、200…）；取整后低于最小值（或取整后为 0）时按规则处理。
- `关`：金额可以是 217、147 这类非整十数，但仍应为整数（当前系统最小注额是整数 1）。
- `随机`：每笔独立随机决定是否整十。

需要确认：`关` 时是否允许小数（现状允许 2 位小数，如 `1番217.43`）？我建议**只允许整数**，与`玩家最小注额=1`的整数校验一致。

### 4.4 下注指定玩法

参考截图的弹窗标题是「当前托允许下注的玩法」，勾选项为`角 正 番 车 / 单 双 大 小`，按钮为`全选 / 清空 / 确定 / 取消`；用户要求再增加`随机`（等于全选）。

本项目解析器支持的玩法比截图多，可选集合如下（括号内为随机参数空间）：

| 弹窗项 | PlayType | 文本形式 | 随机参数空间 |
| --- | --- | --- | --- |
| 番 | FAN | `1番100` | 4（番值 1-4） |
| 角 | ANGLE | `12角100` | 6（2 个不同番值组合） |
| 车 | CAR | `1车100` | 4（缺哪个番值） |
| 念 | STRICT | `1念2/100` | 12（有序不同番值对） |
| 加 | ADD | `1加23/100` | 24（首位 + 两个不同番值） |
| 正 | POSITIVE | `1正100` | 4 |
| 通 | TONG | `1通23/100` | 24 |
| 无 | NONE | `2无3/100`、`12无3/100` | 12 + 24 |
| 单双 | ODD_EVEN | `单100`、`双100` | 2 |
| 大小 | BIG_SMALL | `大100`、`小100` | 2 |
| 特 | SPECIAL | `01特100`、`01/02特100` | 20 + 组合 |

需要确认：本次托的弹窗是否只做截图里的 8 项（角/正/番/车/单/双/大/小），还是把`念/加/通/无/特`也放进去。放进去能力更全，但`特`玩法受`特码限额 200`限制，和常见的 30-300 档位会冲突。

### 4.5 活跃比例（我的理解）

UI 把`活跃比例 100 %`和`每期注单 1 单`放在同一行，说明它们共同决定"这个托看起来有多活跃"。三种可能语义：

| 语义 | 含义 | 100% 与 30% 的表现 |
| --- | --- | --- |
| A. 参与概率（推荐） | 每期按比例随机决定本期是否参与；参与就按`每期注单`下满 | 100% 每期都下；30% 大约三成期数在下，其余期数完全安静 |
| B. 注单折扣 | 本期实际注单数 = 每期注单 × 比例 | 每期 4 单、50% → 平均每期 2 单，期期都有动作 |
| C. 金额折扣 | 金额 = 档位随机值 × 比例 | 会让金额偏离配置档位，语义与"下注范围"打架 |

我的建议：**采用 A**，理由是"活跃比例"字面就是"有多少期在活动"，而且自然制造"这个玩家不是每期都玩"的间歇感，比每期都下但少几单更接近真实玩家。如果希望同一期内也平滑，可以采用 A+B：先按比例决定参与，参与时把本期注单数按比例做一次上限收缩。

请确认选 A、B 还是 A+B。

### 4.6 每期注单

- 现状字段 `bets_per_issue(0-20)`，语义是"本期最多执行多少张注单"。
- 结合 4.5 与随机时间：一期内的 N 单应各自落在投注窗口内的随机时刻，而不是同一时刻。
- 需要确认上限（继续 20 单？）以及是否要限制"所有托合计每期总注单/总积分"。

### 4.7 自动模式不发聊天消息

- 关闭自动闲聊（删除"大家好，托玩家测试消息"的生成），`chat_enabled/messages_per_issue` 不再参与自动行为。
- **需要确认**：托下注成功后，系统机器人会按现有链路发一条 `@托名 攻击成功，使用粮草X，剩余粮草：Y` 反馈。我的理解是这条要**保留**（它是下注痕迹，真实玩家下注也会产生同样的反馈），只去掉"你好、吃了吗"这类主动闲聊。如果这条也要去掉，托的下注在聊天室里就只剩玩家自己的注单消息。
- 后台工作台的"手动发送测试消息"建议保留，用于人工验证。

### 4.8 随机时间下单

建议做法：不再在扫描到新期时立刻执行，而是：

1. 新期开始时，为该托本期生成 N 个**计划执行时刻**（`scheduled_at`），在投注窗口内随机分布（例如均匀随机或避开最后 30 秒）。
2. 调度器每秒只执行 `scheduled_at <= now` 且状态为待执行的动作。
3. 时刻持久化，服务重启后继续按计划执行，不会重复也不会丢。
4. 期结束（封盘/开奖中）仍未执行的动作按 `SKIPPED(ISSUE_CLOSED)` 收尾。

需要确认：时间分布偏好（完全均匀 / 偏向中段 / 避免最后 30 秒），以及同一托的多单之间是否要求最小间隔。

### 4.9 余额不足也要下

现状：余额不足 → 动作 FAILED，没有下注。

建议：实际下注金额 = min(档位随机值, 当前可用余额, 该玩法剩余额度, 单场剩余额度, 玩家最高注额剩余)，再按整十规则取整。

- 取整后 ≥ 玩家最小注额 → 正常下注（金额降级）。
- 取整后 < 玩家最小注额或余额不足最小值 → 本期该单跳过，记录 `SKIPPED(INSUFFICIENT_BALANCE)`，并在工作台动作列表可见。
- 是否在余额不足时自动发起`上分申请`进后台审核队列，需要确认；若要做，必须限制频率（例如同一托只允许一条待审批申请、N 分钟内不重复提交），否则会刷屏审批队列。

### 4.10 上下分与后台审核等真实玩家场景

托已经具备：聊天指令上下分申请、后台审批、工作台人工上下分、软删除与停用联动。改造后需要额外对齐的场景：

| 场景 | 现状 | 建议 |
| --- | --- | --- |
| 余额不足 | 下注失败 | 降额下注；可选自动上分申请（需确认） |
| 链接过期/拉黑 | 自动行为继续 | 停止并 `SKIPPED(LINK_INVALID)` |
| 删除/停用 | 行为停用、会话撤销 | 保持；补 `SKIPPED(PLAYER_INACTIVE)` 收尾 |
| 封盘/开奖中 | 不生成新动作 | 保持；待执行动作按期结束收尾 |
| 限额拒绝 | 动作记 SUCCEEDED 但无注单 | 改为 `SKIPPED(LIMIT_EXCEEDED)` 并记录原因 |
| 服务重启 | 幂等键保证不重复 | 配合 `scheduled_at` 支持续跑 |
| 跨期 | 每期独立幂等键 | 保持；清理过期 PENDING 动作 |
| 手动模式 | 只有点"立即执行"才动 | 保持（后台测试入口） |
| 托的链接本身 | 与普通玩家一致 | 保持；作为工作前提 |

## 5. 需要你确认的问题

### 5.1 用户确认结果（2026-09-24）

1. 活跃比例：**A+B**（先按比例决定本期是否参与，参与时再按比例收缩本期注单数）。
2. `下注范围=随机`：**全局最小到最大之间随机**，但单笔不超过当前积分余额的 **20%**，并偏向较小金额，避免梭哈。
3. 玩法弹窗：**包含 `念/加/通/无/特`**，共 11 类玩法全部可选，`随机`=全选。
4. 托**受现有全局限额约束**，按剩余额度降额。
5. 增加**所有托每期总注单与总积分上限**。
6. 余额不足**只降额**；上分申请是**随机**发生的，不因余额不足强制触发。
7. 保留下注成功后的机器人「攻击成功，使用粮草…」反馈。
8. 随机时间**不避开最后 30 秒**，封盘前仍属正常活动范围。
9. 保留工作台「立即执行」。
10. 金额**不出现小数**。

### 5.2 原始问题清单（已全部回答）

3. 玩法弹窗只放截图的 8 项，还是把`念/加/通/无/特`也放进去（推荐全部放出，但`特`需要放宽特码限额）？
4. 托是否受现有全局限额（玩家最高注额/单场总限额/玩法限额）约束？推荐受约束并按剩余额度降额。
5. 每期注单上限是否继续 20 单？是否需要"所有托每期总量/总积分"上限？

8. 随机时间的分布偏好：全程均匀、避开最后 30 秒，还是其它？
9. 手动模式是否保留工作台"立即执行"按钮（推荐保留，作为测试入口）？
10. `下注金额整十=关`时是否允许小数（推荐不允许，保持整数）？

## 6. 建议的实施顺序

## 9. 已实施内容（阶段一至阶段三，2026-09-24）

### 9.1 阶段一：基础行为

1. **链接成为工作前提**：`workabilityFailure` 要求用户/账户 ACTIVE 且存在 `PLAYER_FULL`、未拉黑、未过期的链接；不满足时不创建动作，已有待执行动作按 `SKIPPED(LINK_INVALID)` / `SKIPPED(PLAYER_INACTIVE)` 收尾。
2. **期内随机时间下注**：Flyway `V31` 为 `test_player_action` 增加 `scheduled_at`；计划时刻在投注窗口内均匀随机、按序递增，只保留期初 3 秒缓冲，**封盘前最后时段同样参与**；调度器只执行到期动作，「立即执行」忽略计划时间；计划持久化，重启后继续。
3. **自动模式不再发聊天消息**：`dispatch` 不再生成 `CHAT_TEXT`；工作台移除「发送聊天消息」「每期消息数」控件，固定写 `chatEnabled=false`、`messagesPerIssue=0`；手动发送测试消息保留。
4. **余额不足也要下**：执行前按「计划金额 → 可用余额 → 剩余额度」逐级压降；压降后低于最小注额才记 `SKIPPED(INSUFFICIENT_BALANCE)`。
5. **假成功修正**：被限额或封盘拦掉、没有生成注单时记 `SKIPPED(LIMIT_EXCEEDED)`；封盘/开奖或跨期后未执行动作记 `SKIPPED(ISSUE_CLOSED)`。

### 9.2 阶段二：行为约束与随机上分

6. **下注范围档位**：Flyway `V32` 为 `test_player_behavior` 增加 `stake_range_code`，可选 `随机 / 30-300 / 300-1000 / 1000-3000 / 3000-10000 / 10000-30000`；`随机`在全局 30-30000 之间取值，取两次随机中的较小值（偏向小额），并额外受**当前余额 20%** 上限约束。
7. **下注金额整十**：`stake_round_ten` 支持 `随机 / 关 / 开`；`开`向下取到 10 的倍数，`随机`每单独立决定；所有金额为整数，不再出现小数。
8. **下注指定玩法**：新增 `test_player_behavior_play_type` 子表与工作台玩法弹窗，支持 11 类玩法（角/正/番/车/念/加/通/无/单双/大小/特）、`随机`（=全选）、全选、清空、确定、取消；参数由 `BotBetTextGenerator` 随机生成且保证能被解析器接受。
9. **活跃比例（A+B）**：`activity_percent` 先按概率决定本期是否参与，参与时本期注单数按比例收缩（至少 1 单，不超过配置值）；`slotCount` 单独可测。
10. **随机上分申请**：`topup_probability_percent`、`topup_min`、`topup_max` 控制；命中且当前没有待审批申请时，直接写入后台审批队列（`TOP_UP_REQUEST` 动作，不在聊天室发消息）。
11. **全局托风控**：`game_betting_config` 增加 `bot_issue_total_bets`、`bot_issue_total_stake`（所有托每期总注单/总积分上限）与 `bot_night_activity_override_percent`（深夜 00:00-06:00 统一覆盖活跃比例，留空表示不覆盖），全部可在后台限额弹窗配置。

### 9.3 阶段三：真实感与运营

12. 多托错峰：每个托独立生成计划时刻，同一托多单按序递增，不再期初集中下注。
13. 动作可观测：跳过/失败均记录原因码（`LINK_INVALID`、`INSUFFICIENT_BALANCE`、`BOT_ISSUE_CAP`、`LIMIT_EXCEEDED`、`ISSUE_CLOSED`、`TOPUP_PENDING` 等），工作台动作列表可查。
14. 报表联动：托的注单与积分走正式链路，进入既有下注榜与积分记录统计口径。
