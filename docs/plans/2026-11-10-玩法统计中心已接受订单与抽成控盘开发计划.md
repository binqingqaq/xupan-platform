## 1. 目标与边界

### 1.1 交付目标

1. 玩法排行、单数、总积分和抽成目标只来源于当前期已被中心接受的普通玩家订单。
2. 托单、未上报、被拒绝、待核/超时以及身份未知的订单不出现在玩法统计，也不参与抽成计算。
3. 删除页面现有“托开关”及 `includeBots` 请求参数和浏览器本地偏好。
4. 提供抽成比例选择与自定义数字输入。目标中心净赢按符合条件的中心订单下注总积分乘抽成比例计算。
5. 服务端按注单实际结算规则和赔率快照，求出中心净赢达到或超过目标的合法七球结果，直接写入现有七张球位预设卡片。
6. 计算和七球写入为一个完整操作。开奖前最后 10 秒（含第 10 秒）由服务端拒绝操作；结果不能在请求中途留下部分更新。
7. 继续由原开奖调度在既定开奖时间确认开奖结果并运行原本地/中心结算；本功能不提前开奖或结算。

### 1.2 明确边界

- 金额都是虚拟积分；不新增真实资金、代理分成、充值/提现、外部网络调用或中心上游业务规则。
- 不调整机器报网设置、中心账号绑定、上报调度、中心额度、中心订单接单与结算事务。
- 不改变托单创建、托单本地下注/结算或中心上报隔离；只从玩法统计中完全排除托单。
- 不改变历史已确认期次或历史中心订单。
- 不把未结算的本地普通玩家注单自动视为中心已接受单；统计与计算都必须以已持久化的中心接单事实为准。

## 3. 统计与订单资格口径

### 3.1 普通玩家有效中心订单

查询以当前期 `(game_code, issue_number)` 为边界，候选行同时满足：

1. `game_bet` 玩家身份快照明确为 `NORMAL`；托单、未知身份一律排除。涉及玩家物理删除时以不可变快照判型，不允许将未知默认解释为普通玩家。
2. `center_order.local_bet_id` 唯一对应该 `game_bet`，中心订单彩种、期号和投注数据与本地下注快照一致。
3. 本地 `report_upstream_order` 存在对应中心上报记录，最新相关尝试状态为 `ACCEPTED`，并能关联到同一中心订单/幂等单。
4. `center_order.status = 'ACCEPTED'`，即尚未开奖结算的已接受中心订单。`PENDING`、`TIMEOUT`、`REJECTED`、`CANCELLED`、`REFUNDED`、`SETTLED` 不参与当前期活动统计。
5. 注单属于当前活动期并仍可结算；取消/撤销或已处理的本地单不得进入。

同一注单可能有多次追加的上报尝试。查询必须按业务规定的同一上报类型及 `bet_id` 找最新尝试，不能因为历史上曾出现 `ACCEPTED` 就把后续已拒绝/处置的记录重新计入。中心订单应以本地注单 ID/幂等关联键防止重复计数。

### 3.2 聚合字段

- 玩法排行仍按球位和标准化后的具体结算指令聚合，保留 `1正` 与 `2正` 分开、语义等价别名合并的现有规则。
- 单数为符合资格的中心订单数；总积分为同一订单本金之和，使用中心订单金额与本地投注快照核对后统计。
- 返回页端的仅是球位/玩法汇总、订单数和积分，不包含玩家、机器、中心账号、订单 ID 或原始投注明细。
- 每期总下注积分只汇总一次，不能因中心订单/上报尝试连接造成重复计数。
- 无符合条件订单时总基数为 0；控盘按钮禁用并说明当前期没有中心已接受普通玩家订单，不允许以 0 目标生成无业务意义的号码。

## 4. 抽成目标及中心净赢计算

### 4.1 输入与目标

- 前端提供常用比例选择和自定义数字输入；自定义输入按百分比显示，例如 `20` 表示 `20%`，不得将 `20` 当作 `0.2%` 或 `2000%`。
- 服务端再次校验比例格式、精度和允许范围。允许的最小/最大比例、步进和小数位数目前未由使用者明确，进入实现前需在接口契约中确认；不得只用前端校验。
- 基数 `B = SUM(center_order.amount)`，仅限本节 3.1 资格订单。
- `target = round(B × ratio / 100, 2)`，舍入方式采用明确的十进制货币精度规则；技术设计需与项目积分/结算既有精度一致并补边界测试。
- 页面在执行前展示期号、中心已接受订单笔数、总下注积分、比例和目标中心净赢，让用户确认控盘基数。

### 4.2 单笔中心收益

对候选完整开奖结果逐笔调用与正式开奖相同的玩法结算语义：

| 本地玩家结算 | 中心净收益 |
| --- | --- |
| `LOSE` | `+center_order.amount`，中心收取下注本金 |
| `WIN` | `-玩家净赢额`，其中净赢额按正式结算使用的赔率、特码单位本金及机器赔率快照等规则计算 |
| `DRAW` | `0`，中心释放风险，不产生中心输赢 |
| 撤单/退款/流局 | 不作为有效活动中心接受单参加控盘；如期次内出现此状态，按正式中心结算结果排除或整次拒绝并提示，不得当作普通输单计入 |

一期总中心净赢 `P(draw) = Σ 单笔中心净收益`。中心净赢必须沿用 `CenterSettlementService` 实际中心账务方向；不能将玩家本金返还、玩家净赢、中心冻结额度或风险预留额混为一项。

## 5. 七球计算方案

### 5.1 计算模型

当前一笔注单落在一个球位，七球开奖按球位分别判定玩法结果；AU8 v2 的额外约束是 7 个球位的号码互不重复。可将全部有效订单转换为每个 `(ball_number, number)` 的中心净收益矩阵：

```text
收益矩阵 score[球位][号码] = 该球位所有符合资格订单在此号码下的中心净收益之和
目标：选择 7 个合法号码，使 Σ score[球位][所选号码] >= target
AU8 v2 附加约束：七个球位所选号码两两不同
```

不能枚举所有 AU8 组合（`40P7` 规模过大）。首选用 7 行、号码为列的最大权二分匹配/指派算法，在 `DrawRule` 规则允许的号码集合内求中心净赢最大值及对应完整号码：

1. 对每笔有效中心订单及每个可能命中号码，调用/复用 `SettlementService` 对应结算规则，传入持久化赔率快照、单位下注与机器赔率快照；通过中心结算语义转换为中心收益分。
2. 按球位累加为 7×N 收益矩阵；非法号码、期次未开放球位不能进入矩阵。
3. 对要求号码不重复的规则求最大权指派；允许重复的规则则按每球独立最大值求解。必须由 `DrawRule` 选择规则，不能依据彩种名字在 UI 中猜测。
4. 最大可达净赢低于目标时返回“当前订单结构下没有可达到该目标的合法开奖结果”，保留当前预设不变。
5. 最大可达净赢达到目标时，返回一组完整合法开奖结果及实际预测中心净赢。按已确认业务口径，“至少达到目标”是硬条件；多个可行结果之间的选择规则在实现设计中固定、可重复并写入审计。首版最大权解会倾向中心净赢最高，可能超过目标较多，页面必须同时展示目标与预测结果，避免把目标误报为精确收益。

最大权指派可证明是否存在任何 `P(draw) >= target` 的结果，但实现前仍须用所有现行玩法类型、赔率路径和 AU8 不重复约束验证矩阵可加性。若某玩法存在跨球耦合或 `SettlementService` 调用上下文不同，必须先补模型或停止控盘，不允许退化为不完整猜测。

### 5.2 手工预设与号码结果

- 控盘操作输出完整七球结果并覆盖当前七个球位预设；操作前、操作后号码都写审计。
- 手工预设会被这次明确的控盘写入覆盖；UI 提交前显示覆盖提示和本次结果摘要。若用户最终要求保留某些手工固定球，则算法需作为固定列约束重新求解，另行补充业务确认后再实施。
- AU8 v2 的选中七号必须唯一且位于 1～40；既有规则按 `DrawRule` 验证上限、球数和重复策略。
- 写预设仅更新期次预设号码及结果版本，不调用开奖确认、派奖、中心结算或创建下一期逻辑。

## 6. 后端接口、事务、并发和审计

### 6.1 接口建议

- 保留 `GET /api/admin/betting-play-stats/current?gameCode=...`，移除 `includeBots`；响应统计只包括合格中心订单。
- 新增整组控盘写入接口，例如 `POST /api/admin/betting-play-stats/current/control`。请求至少含 `gameCode`、`issueNumber`、期次 `draw_result_version` 快照、抽成比例、幂等键；服务端自行读取订单、求解并写入七球，不接受前端提交计算出的号码或订单明细。
- 响应含彩种/期号、合格订单数、下注基数、比例、目标净赢、完整号码、预测中心净赢、当前开奖结果版本和操作结果 ID；不含身份字段或逐单数据。
- 计算失败使用稳定错误码区分：无当前期、期号过期、无中心已接受订单、目标不可达、距开奖不足 10 秒、权限不足、订单/期次快照变化、数据不一致及幂等重放。

### 6.2 事务步骤

1. 鉴权并校验 `BETTING_DRAW_PRESET_MANAGE`；验证百分比和幂等键。
2. 开启事务后按既有锁顺序锁定当前 `game_issue`；确认期号、彩种、球数、规则版本、`draw_confirmed_at IS NULL`、阶段可修改，并重新检查 `drawEndsAt - now > 10 秒`。
3. 在同一事务读取符合条件的最新中心上报/中心订单与下注快照；验证没有重复关联或状态不一致。固定订单 ID 集合及投注/赔率快照摘要供本次计算使用。
4. 计算目标和合法号码组合；再确认订单集合与关键状态未变化（或用锁/版本条件保证其在开奖截止前不会被并发处置）。
5. 使用期次行锁一次更新所有有效号码列、`draw_result_version` 和 `updated_at`；按期号与旧版本做 CAS 条件。更新行数不为 1 则整次回滚。
6. 在同一事务写入操作审计/幂等结果。审计记录比例、基数、目标、合格订单数、输入摘要哈希、计算结果、预测净赢、旧/新预设、操作人和时间，不记录用户名、Token、密码或完整订单文本。
7. 提交后返回结果。事务任何一步失败均不得留下部分号码、版本递增或成功审计。

### 6.3 截止与竞态

- 服务端使用数据库期次快照的 `draw_ends_at` 与服务端当前时间计算，边界为 `remaining <= 10 seconds` 拒绝。
- 与自动开奖共享 `game_issue` 行锁及稳定锁顺序。开奖结果一旦确认，控制接口不允许改写；自动开奖只会在该操作提交后读取完整预设或在此前先完成开奖，不能产生半套号码。
- 重复提交同一个幂等键返回同一成功结果，不重复增加版本或写第二次操作事实；同键不同请求体应冲突。
- 长时间求解期间临近 10 秒时，提交前再次检查截止时间；若已经进入保护窗口，回滚整次操作。
- 计划性并发包括开奖、期次切换、重新上报、中心订单取消/退款处置及重复控盘请求。

### 6.4 持久化与迁移

- 不新增或改写下注、报网上报订单、中心订单、余额和结算事实表。
- 建议新增控盘操作记录表，用于保留比例、目标、预测结果、输入摘要、版本、操作人、幂等键及结果；实现前确认现有 `sys_operation_log.request_summary` 容量、留存和成功/失败审计要求是否足够。若采用独立表，应以 Flyway 新迁移创建约束、索引和幂等唯一键，按 MySQL 8.4 验证。
- 审计保留策略及个人数据最小化按项目基线执行；不将逐单玩家明细复制到控盘日志。

## 8. 实施阶段

### P0：结算公式与计算可行性验证

- 对照 `SettlementService`、正式本地结算调用、`CenterSettlementService` 和 `CenterOrderRepository`，列出所有玩法的赔率/单位本金/机器赔率输入，以及对应中心净收益。
- 用已确认规则构造小型可枚举测试夹具，对比“逐球收益矩阵 + 匹配”与正式逐单结算结果，验证加和性和 7×N 最大权结果。
- 记录最大权解“至少达到目标”但可能高于目标的产品展示语义；校验所有已启用游戏当前规则都可由计算器表达。

## 9. 验收矩阵

| 场景 | 预期 |
| --- | --- |

| 手工预设已存在 | 用户确认后整组被计算结果覆盖；操作记录包含前后七球 |
| 剩余 10 秒或更少 | 服务端拒绝且预设、结果版本不变 |

| 重复相同幂等请求 | 返回相同结果，不重复写预设版本和控盘成功记录 |

## 10. 实施收敛项

1. 自定义抽成比例采用 `0.01%–100.00%`，最多两位小数；常用选项为 5%、10%、15%、20%、25%、30%、50%、100%，0% 不允许。

4. 新增 V114 `betting_play_control_operation` 保存成功结果及幂等键；`sys_operation_log` 另写操作摘要。
