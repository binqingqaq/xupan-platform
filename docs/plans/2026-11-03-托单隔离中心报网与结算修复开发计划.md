# 托单隔离中心报网与结算修复开发计划

> 制定日期：2026-11-03
> 状态：实现与本机 MySQL 8.4 空库迁移已完成；自动化测试、浏览器验收及服务器/生产均未执行。过程记录见 §6。
> 最新决定：托不参与飞单、报网、中心接单、额度占用和中心第二层结算；中心上游只处理普通玩家注单。开发阶段允许重建本机开发数据，不做旧托中心单兼容。全部积分仅为虚拟积分，中心是 Xupan 同进程内部服务，不接真实外部上游。

## 1. 结论与边界

1. `NORMAL` 玩家下注保留现有本地钱包结算；符合机器报网配置时才可上报内部中心，产生中心订单、风险占用和第二层结算。
2. `BOT` 托下注保留 BY220 式本地注单、虚拟钱包扣分、开奖输赢和聊天室反馈，但无论自动/手动、托级旧“飞单”值、机器报网开关或中心会话状态如何，都不得产生上报尝试、中心订单、中心额度或机器风险补足流水。托上下分仍只改变托钱包。
3. 托下注榜继续显示托的本地注单和开奖状态；托单没有“未报/失败/重新飞单”状态和入口。中心报网订单列表、待报/失败/超时计数及中心对账只统计普通玩家报单。
4. 旧版 BY220 代理页面保存托级 `isFeidan` 状态，但正常自动托下注、自动重试和页面手动重报均不报托。其 `reFeidan` 后端缺少托身份校验，存在绕过页面的例外；本次按用户明确决定在 Xupan 服务端封死该例外，并删除 Xupan 托级无效飞单配置。这一处是明确收紧，不保留旧接口兼容。
5. “托不需要真实结算”在本项目落实为**不进行中心第二层结算**，不取消托的本地虚拟积分开奖结算。BY220 的 `openKj()` 对所有未结算本地注单调用 `jiesuan()`，没有排除托。

## 3. 当前冲突与影响

- `ReportUpstreamOrderRepository.findSubmittableBets()`、`isReportableBet()` 没有托过滤，自动扫描选中托；`findPendingAttempts()` 又可恢复已有托尝试。
- `ReportService.submitForBet()`、`doResubmit()`、`recoverPendingAttempt()` 未验证注单身份；`CenterOrderRepository.findLocalBetSnapshot()` / `CenterOrderService.accept()` 不拒绝托。中心 `findAcceptedByIssue()` 按订单状态结算，不区分托。
- `ReportUpstreamOrderRepository.counts()`、`findOrders()` / `countOrders()` 将托的无上报行派生为 `PENDING`，污染“未报”数字和报网订单列表。`BetBoardRepository.findBets()` 对托也返回可重报的上报状态；Vue 下注榜和 HBY019 桥允许误导或误点。
- `test_player_behavior.player_feidan_enabled` 只保存托开关，不参与当前报单资格判定；托配置 UI/API 暴露无效“飞单”能力。2026-10-09 旧需求基线保留追溯，本次决定替代其中“保留托级飞单状态”的条款。
- 本机开发库重建前的 2026-11-03 22:50:52 一致性快照：有 27 笔托注单、27 条上报尝试、27 笔中心订单（24 笔已结算、3 笔待结算），中心冻结余额 1330.05，并存在托单对应的机器风险预留/释放账本。此为开发库时间点数据，已随授权的全库重建清除；不代表服务器或生产数据。

## 4. 实施步骤

### P0. 收敛执行窗口与数据

1. 开始修改运行态前，确认目标是**本机开发库**及对应应用进程；停托自动派发和报网扫描，并记录起止时间、当前 Flyway 版本、账号/普通玩家/托/注单/中心订单、两侧账本及余额的聚合盘点。禁止把本计划用于服务器/生产库清理。
2. 在隔离 MySQL 8.4 库验证新 Flyway 迁移和全链路后，重建本机开发库并重新初始化必要的本地测试账号、机器和中心额度。用户已授权开发阶段删改重建数据，本方案**不做旧托中心订单的逆向兼容或静默冲销**；重建会删除该开发库原有业务数据、账号会话和历史流水，应在执行记录中列明实际删除范围。
3. 若本机仍需保留其它开发数据，先改用新的隔离开发库完成验证和切换，不在混有普单、托单与共享中心账本的原库里只删托中心订单或只改中心余额。现有 `SETTLED` 托单已影响可用/冻结/机器积分；局部删单无法还原账本。

### P1. 固定身份事实与数据库门禁

1. 以 `game_bet.player_kind_snapshot` 作为报单资格来源；下注时写 `NORMAL`/`BOT` 快照，并防止已有非空快照被改写。身份未知（NULL）的记录一律不具备报单资格；服务层和 MySQL 触发器都拒绝它们进入中心，不从可变账号类型猜补为普通玩家。
2. 在中心订单写入边界加 MySQL 8.4 触发器或等效数据库约束：`center_order.local_bet_id` 必须指向 `NORMAL` 注单；拒绝直接 SQL 插入/改指向 BOT。Flyway 编号以开工时最新版本为准（当前源码最新 V106，候选 V107）；对照现有 V95/V104 触发器顺序和 MySQL 迁移权限验证。
3. `report_upstream_order` 的新写入也加数据库级普通玩家门禁；正常新单和重试共享同一约束。数据库不采用“托单已报但标记不适用”的兼容状态。

### P2. 后端报单与结算边界

1. 自动候选查询只取 `NORMAL`，同时在 `isReportableBet()`、`submitForBet()` 做事务内资格复核，避免筛选后注单或账号状态变化的竞争。
2. 普通重报、人工重报、未决尝试恢复均验证同一快照；BOT 直接返回稳定业务错误或跳过，不写尝试、不调用中心网关、不冻结额度。明确区分“BOT 不适用”与普单的“期号已封盘”。
3. `CenterOrderService.accept()` 在任何幂等回放、风险计算、账本变动之前拒绝 BOT；`CenterOrderRepository.findLocalBetSnapshot()` 只取普通注单。中心结算入口保持对普通中心订单的正常结算，数据库门禁保证新托中心订单不可存在；针对直接旧行/伪造行补拒绝或异常保护，不让托单走 `ACCEPTED → SETTLED`。
4. 报网订单列表/总数/状态计数限定普通玩家；本地下注榜仍保留托注单，并返回明确的“报网不适用”展示状态，不将无尝试行误写成 `PENDING`。普通玩家无尝试仍按现有报网状态机处理。
5. 检查中心账号删除、子账号删除、玩家物理删除、对账、人工本地处置和保留清理的联表查询，确保普通中心单继续完整运转，托本地注单不被中心引用而阻滞清理。

### P3. 前端与托配置收敛

1. Vue `BetBoardPanel` 及 HBY019 下注榜保留普/托两个分类、下注数和本地结算结果；托行显示本地状态，不显示“已报/未报/失败”或重报按钮。服务端拒绝仍是最终门禁。
2. HBY019 `refeidan` 桥只处理普通玩家注单，避免绕过 Vue；托行即使被伪造点击也由后端拒绝。
3. 删除托级“飞单”按钮、`feidanEnabled` 请求/响应字段、验证和 `test_player_behavior.player_feidan_enabled` 列及关联测试。保留机器级自动报网配置，且只作用于普通玩家。明确修订 2026-10-09 旧口径，不保留无效开关。
4. 中心管理页/代理报网栏的可用额度、未结算押注和订单状态继续展示普通玩家中心业务真实值；不把托本地下注积分计入“网盘下注”。

## 5. 验证矩阵与完成标准

| 场景 | 必须证明的结果 |
| --- | --- |
| 托自动下注、托手动下注、托上下分 | 本地钱包、注单、聊天室和开奖按原规则运行；`report_upstream_order`、`center_order`、中心账本及 `CENTER_RISK_*` 机器账本均无新增 |
| 机器自动上报开启、中心在线，迁移前托旧飞单标志分别为开/关 | 两类迁移样本都不能产生托中心单；删除旧字段后托不占中心可用/冻结额度，不参与第二层结算 |
| 托订单普通重报、人工重报、HBY019 桥直调、服务直调、数据库直写 | 稳定拒绝，订单/余额/流水不变；前端不提供托重报入口 |
| 普通玩家下注、重报/恢复、中心拒绝/受理、失败退单、开奖结算 | 原有幂等、限额、风险冻结、机器补足、释放和输赢分录保持正确；中心只出现普通玩家注单 |
| 普托同机同期开、封盘、取消及并发 | 普通玩家正常报单；托只本地结算；报网计数和订单列表无托，下注榜普/托数量不丢失 |
| 玩家删除、中心账号删除、子账号删除、对账和保留清理 | 普单关联和账本继续一致；托历史不被误识别为未报或需中心处置 |

执行顺序：源码/迁移静态检查 → 隔离 MySQL 8.4 Flyway 空库迁移和直接 DML 拒绝测试 → 后端报单/中心/托行为定向集成及并发测试 → 前端专项、类型检查与构建 → 本机服务和开发库重建后的真实机器账号浏览器流程 → 余额/两层账本重算与零托中心单 SQL 断言。H2 若仍被既有 V83 方言问题阻断，单独记录，不能代替 MySQL 验证。BY220 运行态、服务器和生产未执行时均明确标注。

验收结束必须满足：新库中 `center_order` 与 `report_upstream_order` 关联 BOT 数均为 0；托动作前后中心账号可用/冻结/未结算三层与机器风险账本变化均为 0；普通玩家至少覆盖一赢一输和拒绝/重报；所有中心订单均可追溯到 `NORMAL` 快照；对账无未解释差异。届时同步更新 `docs/项目方案.md`、业务模块 03/05/09/11、文档索引与本机验收记录，才可写“本机已修复”。

## 6. 本机实施进度

- 2026-11-03 已完成代码修改：自动候选、报单恢复、手工/人工重报、报网订单列表/计数和积压计数限制为 `NORMAL`；中心接单先校验快照身份；中心开奖结算只取并接受普通玩家中心订单。`NOT_APPLICABLE` 是托下注榜的非报网状态，Vue 与 HBY019 均不提供托重报按钮。
