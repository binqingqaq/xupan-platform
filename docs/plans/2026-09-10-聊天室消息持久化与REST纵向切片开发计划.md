# 聊天室消息持久化与 REST 纵向切片实施计划

> **给实施者：** 按任务顺序执行本计划。步骤使用复选框（`- [ ]`）跟踪进度；本计划只覆盖聊天室消息持久化、REST 发送/历史查询和前端 REST 轮询纵向切片，不提前实施 WebSocket、常驻机器人或 Redis 多实例能力。

**目标：** 在现有认证、权限和虚拟余额钱包已经完成的基础上，建立服务端可信的聊天室房间、消息、顺序、幂等和禁言校验，并让两个正式用户通过 REST 发送、查询和刷新后继续读取真实消息。

**架构：** 使用 Flyway `V9` 创建房间和消息表，使用 `V10` 创建 outbox、禁言和已读游标表；使用 Spring JDBC 以事务锁维护房间内单调 `sequence_no`，由服务端从 `AuthenticatedUser` 确定发送者和展示名称。REST 阶段先使用前端短轮询读取 `afterSequence`，下一阶段再复用相同的持久化消息模型接入一次性 WebSocket 票据和实时广播。

**技术栈：** Java 21、Spring Boot 4.0.8、Spring Security、Spring JDBC、Flyway、MySQL 8.4 LTS、H2 测试、JUnit、MockMvc、Jackson、Vue 3、TypeScript、Vite。

## 全局约束

- 当前事实以源代码、配置、Flyway 迁移和测试结果为准；本计划完成前的内容都是计划，不代表功能已经实现。
- 数据库版本固定为 MySQL 8.4 LTS；数据库变更只通过 Flyway，不能手工建表、修改共享库或重写已执行的 `V1` 至 `V8`。
- 聊天迁移固定使用 `V9` 和 `V10`；机器人表从 `V11` 开始，不能把机器人字段提前写入聊天表来绕过后续设计。
- 聊天消息不能写入 `game_issue_event`；该表仍只表示轮期领域事件。聊天可以保存可选的 `issue_number`，但游戏服务不能解析聊天文本来下注、扣款或结算。
- 当前虚拟余额不是支付系统；聊天室不能增加充值、提现、转账、代理分成、支付回调或真实资金清算入口。
- 未认证、禁用、撤销会话或没有 `CHAT_ROOM_READ`/`CHAT_MESSAGE_SEND` 权限的请求必须被服务端拒绝；前端隐藏按钮不能替代后端权限检查。
- `sender_id`、`sender_name`、`sender_type`、`message_type`、`room_id`、`sequence_no`、`issue_number` 和 `payload_json` 不能由普通客户端请求体直接决定。
- 普通用户消息使用 `(room_id, sender_id, client_message_id)` 幂等；系统、机器人和结果消息使用独立 `idempotency_key`，本阶段只实现普通用户消息写入，机器人消息留给阶段 5。
- 消息正文只保存纯文本，最大长度为 500 个 Unicode code point；拒绝空消息、HTML 标签、NUL 和不可接受的控制字符。前端使用文本插值，不使用 `v-html`。
- REST 历史接口单页默认 50 条，最大 100 条；不得通过任意 `limit` 查询全表，不得用数据库主键代替房间顺序游标。
- `chat_outbox` 本阶段只负责可靠落库，不启动 WebSocket 发布消费者；发布失败恢复、广播和 Redis 锁属于后续阶段。
- 生产配置不得写入密码、Token、数据库凭据、Redis 凭据或带访问作用的完整 URL；测试数据使用测试代码生成。
- 参考 `caipiaowan-main`、汇博盈页面和若依只用于概念与交互边界，不能复制 PHP/Workerman、浏览器触发机器人、HTML 拼接、余额旁路或默认密码。

## 2. 固定设计决策

### 2.1 房间

- 首期房间编码固定为 `main`，展示名称为“公开大厅”，由 `V9` 幂等种子创建；业务代码通过 `room_code` 查找，不在每个 Controller 中硬编码数据库 ID。
- `chat_room.status` 使用 `OPEN`、`CLOSED`；只有 `OPEN` 房间接受普通消息，历史读取仍允许读取 `CLOSED` 房间。
- `next_sequence_no` 保存该房间已经分配的最大序号，第一条消息从 `1` 开始。事务内先 `SELECT ... FOR UPDATE` 锁房间，再加一并写回。

### 2.2 消息身份和字段来源

| 字段 | 普通用户 REST 消息的来源 |
| --- | --- |
| `room_id` | 服务端按路径 `roomCode` 查询 |
| `sender_id` | `AuthenticatedUser.getUserId()` |
| `sender_type` | 服务端固定为 `USER` |
| `message_type` | 服务端固定为 `USER_CHAT` |
| `sender_name` | 服务端读取当前用户 `display_name` 并保存快照 |
| `sequence_no` | 房间行锁内生成 |
| `created_at` | 服务端 `Instant.now()` |
| `client_message_id` | 请求体必填，长度 1 至 128 |
| `content` | 请求体正文，经服务端 Unicode/HTML/控制字符校验 |
| `payload_json` | 普通聊天为 `NULL`；不接受客户端扩展对象 |
| `issue_number` | 本阶段普通聊天为 `NULL`，不从客户端接受 |

消息历史展示使用 `sender_name` 快照，但权限、禁言和操作人始终使用 `sender_id` 对应的正式用户，不使用昵称做身份判断。

### 2.3 游标和幂等

- `beforeSequence` 用于向上翻页：只返回 `sequence_no < beforeSequence` 的消息；不传时返回最新一页。
- `afterSequence` 用于 REST 短轮询：只返回 `sequence_no > afterSequence` 的消息，最多返回 100 条；与 `beforeSequence` 不能同时传。
- 响应按 `sequence_no` 升序返回；向上翻页查询数据库时可倒序取 `limit + 1`，返回前在服务层反转。
- 同一 `(room_id, sender_id, client_message_id)` 再次请求时，正文相同返回原消息，正文不同返回 `CHAT_IDEMPOTENCY_CONFLICT`。
- `chat_outbox` 使用 `message_id + event_type` 的唯一业务键；本阶段所有用户消息使用 `MESSAGE_CREATED`。

### 2.4 错误码

| 错误码 | HTTP | 条件 |
| --- | --- | --- |
| `CHAT_ROOM_NOT_FOUND` | `404` | 房间不存在 |
| `CHAT_ROOM_CLOSED` | `409` | 房间不接受新消息 |
| `CHAT_MESSAGE_EMPTY` | `400` | 正文为空或只包含空白 |
| `CHAT_MESSAGE_TOO_LONG` | `400` | Unicode code point 超过 500 |
| `CHAT_MESSAGE_HTML_FORBIDDEN` | `400` | 检测到 HTML 标签或脚本标记 |
| `CHAT_MESSAGE_CONTROL_CHAR` | `400` | 包含 NUL 或不允许的控制字符 |
| `CHAT_IDEMPOTENCY_CONFLICT` | `409` | 幂等键已存在但正文不同 |
| `CHAT_USER_MUTED` | `403` | 当前用户处于有效禁言区间 |
| `CHAT_CURSOR_INVALID` | `400` | 游标格式无效、超过房间当前最大序号或同时传 before/after |
| `CHAT_MESSAGE_LIMIT_INVALID` | `400` | `limit` 不在 1 至 100 |
| `AUTH_PERMISSION_DENIED` | `403` | 缺少聊天室权限 |

    CONSTRAINT ck_chat_message_sender_type CHECK (sender_type IN ('USER', 'ROBOT', 'SYSTEM', 'ADMIN')),

CREATE INDEX idx_chat_message_room_created ON chat_message (room_id, created_at, id);

INSERT INTO chat_room (room_code, display_name, status, message_retention_days, next_sequence_no)

实施时必须保留以下事实：`sender_id` 不能统一做外键，因为系统/机器人消息的身份来自后续独立表；普通用户消息在 Service 层确认用户存在且状态为 `ACTIVE`。`client_message_id` 和 `idempotency_key` 对非对应消息类型允许为 `NULL`，不能依赖单个 `NULL` 唯一规则实现幂等。

### 3.2 `V10__创建聊天治理和消息投递表.sql`

新建 `server/xupan-server/src/main/resources/db/migration/V10__创建聊天治理和消息投递表.sql`：

```sql
CREATE TABLE chat_outbox (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    message_id BIGINT NOT NULL,
    event_type VARCHAR(32) NOT NULL,
    payload_json JSON NOT NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'PENDING',
    attempt_count INT NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMP NULL,
    published_at TIMESTAMP NULL,
    last_error VARCHAR(1000) NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT uk_chat_outbox_message_event UNIQUE (message_id, event_type),
    CONSTRAINT ck_chat_outbox_status CHECK (status IN ('PENDING', 'PUBLISHED', 'FAILED')),
    CONSTRAINT ck_chat_outbox_attempt CHECK (attempt_count >= 0)
);

CREATE INDEX idx_chat_outbox_pending ON chat_outbox (status, next_attempt_at, id);

CREATE TABLE chat_user_mute (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    room_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    start_at TIMESTAMP NOT NULL,
    end_at TIMESTAMP NULL,
    reason VARCHAR(255) NOT NULL,
    operator_user_id BIGINT NOT NULL,
    revoked_at TIMESTAMP NULL,
    revoked_by BIGINT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_chat_mute_room FOREIGN KEY (room_id) REFERENCES chat_room(id),
    CONSTRAINT fk_chat_mute_user FOREIGN KEY (user_id) REFERENCES sys_user(id),
    CONSTRAINT fk_chat_mute_operator FOREIGN KEY (operator_user_id) REFERENCES sys_user(id),
    CONSTRAINT fk_chat_mute_revoked_by FOREIGN KEY (revoked_by) REFERENCES sys_user(id)
);

CREATE INDEX idx_chat_mute_active ON chat_user_mute (room_id, user_id, start_at, end_at, revoked_at);

CREATE TABLE chat_read_cursor (
    room_id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    last_read_sequence BIGINT NOT NULL DEFAULT 0,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (room_id, user_id),
    CONSTRAINT fk_chat_cursor_room FOREIGN KEY (room_id) REFERENCES chat_room(id),
    CONSTRAINT fk_chat_cursor_user FOREIGN KEY (user_id) REFERENCES sys_user(id),
    CONSTRAINT ck_chat_cursor_sequence CHECK (last_read_sequence >= 0)
);
```

`chat_outbox.payload_json` 由服务端生成 `messageId`、`roomCode`、`sequenceNo` 和消息摘要；本阶段不放完整 Token、密码或未脱敏请求体。禁言记录只追加，解除禁言通过 `revoked_at/revoked_by` 表达，不能删除历史治理事实。

```java
private int tableCount(String tableName) {
    return jdbcTemplate.queryForObject(
            "SELECT COUNT(*) FROM information_schema.tables "
                    + "WHERE UPPER(table_schema) = UPPER(?) "
                    + "AND UPPER(table_name) = UPPER(?)",
            Integer.class, currentSchema(), tableName);
}

private int columnCount(String tableName, String columnName) {
    return jdbcTemplate.queryForObject(
            "SELECT COUNT(*) FROM information_schema.columns "
                    + "WHERE UPPER(table_schema) = UPPER(?) "
                    + "AND UPPER(table_name) = UPPER(?) AND UPPER(column_name) = UPPER(?)",
            Integer.class, currentSchema(), tableName, columnName);
}

private int constraintCount(String tableName, String constraintName) {
    return jdbcTemplate.queryForObject(
            "SELECT COUNT(DISTINCT constraint_name) FROM information_schema.table_constraints "
                    + "WHERE UPPER(table_schema) = UPPER(?) "
                    + "AND UPPER(table_name) = UPPER(?) AND UPPER(constraint_name) = UPPER(?)",
            Integer.class, currentSchema(), tableName, constraintName);
}

    jdbcTemplate.update("INSERT INTO chat_room "
            + "(room_code, display_name, status) "
            + "SELECT 'main', '公开大厅', 'OPEN' "
            + "WHERE NOT EXISTS (SELECT 1 FROM chat_room WHERE room_code = 'main')");
    int after = jdbcTemplate.queryForObject(
            "SELECT COUNT(*) FROM chat_room WHERE room_code = 'main'", Integer.class);
    return before == 1 && after == before;
}

private String currentSchema() {
    try (Connection connection = jdbcTemplate.getDataSource().getConnection()) {
        String schema = connection.getSchema();
        return schema == null || schema.isBlank() ? connection.getCatalog() : schema;
    } catch (SQLException exception) {
        throw new IllegalStateException("无法读取当前数据库 schema", exception);
    }
}
```

代码片段需要补齐 `java.sql.Connection`、`java.sql.SQLException` 导入；`currentSchema()` 按测试连接返回当前 schema，H2 通常为 `PUBLIC`，MySQL 返回当前 catalog/schema。MySQL 8.4 专项必须保留相同约束验证，不能因为 H2 与 MySQL 的元数据大小写差异而删除断言。

测试查询必须限定当前 JDBC schema；MySQL 使用连接 `getSchema()`，H2 使用 `PUBLIC`，不能跨库查询 `information_schema` 造成误判。V9/V10 在 H2 和 MySQL 8.4 都成功时，才允许进入 Repository 实现。

## 5. REST 接口契约

### 5.1 房间摘要

`GET /api/chat/rooms/{roomCode}`，权限 `CHAT_ROOM_READ`。

响应 `200`：

```json
{
  "roomCode": "main",
  "displayName": "公开大厅",
  "status": "OPEN",
  "messageRetentionDays": 30,
  "nextSequenceNo": 12,
  "currentIssueNumber": "3000000",
  "serverNow": "2026-09-10T15:00:00Z"
}
```

`currentIssueNumber` 只作为展示摘要，读取现有游戏 Service 的只读结果；聊天室 Service 不写入或解析游戏事件。

### 5.2 历史和增量消息

`GET /api/chat/rooms/{roomCode}/messages?beforeSequence=&afterSequence=&limit=`，权限 `CHAT_ROOM_READ`。

- `beforeSequence` 和 `afterSequence` 最多传一个；两者都为空时返回最新一页。
- `limit` 缺省 50，允许 1 至 100。
- 历史响应按 `sequenceNo` 升序；增量响应也按升序。

响应 `200`：

```json
{
  "roomCode": "main",
  "items": [
    {
      "id": 12,
      "sequenceNo": 12,
      "messageType": "USER_CHAT",
      "senderType": "USER",
      "senderId": 7,
      "senderName": "用户甲",
      "content": "大家好",
      "payloadJson": null,
      "status": "ACTIVE",
      "createdAt": "2026-09-10T15:00:00Z"
    }
  ],
  "nextBeforeSequence": 12,
  "nextAfterSequence": 12,
  "hasMore": false
}
```

响应不返回密码、Token、内部数据库错误、完整请求体或未脱敏操作日志。

### 5.3 发送消息

`POST /api/chat/rooms/{roomCode}/messages`，权限 `CHAT_MESSAGE_SEND`。

请求只允许：

```json
{
  "clientMessageId": "web-2f4a6d4c-01",
  "content": "大家好"
}
```

服务端忽略或拒绝其他身份字段；成功响应 `201` 返回完整 `ChatMessageResponse`。相同用户、房间和 `clientMessageId` 正文一致时返回原消息，HTTP 可使用 `200`；正文不一致返回 `409 CHAT_IDEMPOTENCY_CONFLICT`。

### 5.4 已读游标

`POST /api/chat/rooms/{roomCode}/read-cursor`，要求已认证。

请求：

```json
{"lastReadSequence": 12}
```

服务端拒绝大于房间当前 `nextSequenceNo` 的游标；重复提交更大的游标幂等成功，较小游标不能覆盖较大游标。已读游标只用于用户体验，不作为消息投递或可靠性证明。

## 8. 完成标准和交接

本计划的代码实现和自动化验收只有在以下条件全部满足后才算完成；真实浏览器双用户手工联调另列为交接前人工验收，不得把未执行写成已完成：

- Flyway 当前版本为 `V10`，V9/V10 在 H2 和 MySQL 8.4 迁移成功。
- `main` 房间存在且种子可重复执行；消息房间序号没有重复或倒退。
- 两个认证用户通过 REST 可以发送和读取同一房间消息；刷新后消息从数据库恢复。
- 普通消息的用户、名称、类型、序号、时间和房间均由服务端确定；客户端字段污染无效。
- 重复 `clientMessageId` 不重复写入；不同正文冲突；消息和 outbox 在同一事务中提交或回滚。
- 空消息、超长消息、HTML、控制字符、关闭房间和有效禁言均有稳定错误码。
- 当前前台不再把固定演示用户、固定机器人或本地假回复当作聊天事实来源。
- 后端全量测试、聊天专项 H2、独立 MySQL 8.4 专项、前端类型检查和生产构建均通过。
- 文档清楚记录：REST 轮询已完成；WebSocket、机器人、Redis、治理后台和正式生产运营仍未完成。

当前代码与自动化验收已达到上述标准；交接前仍需在真实运行页面完成一次双浏览器消息发送、刷新恢复和错误状态人工验收。

交接给阶段 4 时只允许依赖以下稳定能力：

1. `ChatMessageService.sendUserMessage(...)` 是唯一普通用户消息写入口。
2. `ChatMessageService.history(...)` 提供 before/after 游标和去重所需的 `sequenceNo`。
3. `chat_outbox` 已持久化 `MESSAGE_CREATED` 事件，但本阶段没有消费者；WebSocket 阶段负责实现发布、重试和连接广播。
4. WebSocket 必须复用 `/api/auth/ws-ticket` 和 `ChatMessage`，不能再造一套本地消息模型或把 Token 放入 URL。
5. 机器人阶段只能通过独立 `chat_robot` 和 `chat_robot_dispatch` 写 `ROBOT` 消息，不能复用普通用户发送接口或钱包账户。

## 9. 风险和处理顺序

1. **房间序号竞争：** 先锁房间行再分配序号；不能用 Java `AtomicLong`，否则多实例或重启会重复。
2. **幂等键为空：** 普通用户消息必须校验 `clientMessageId` 非空；数据库允许系统消息使用 `NULL`，业务层不能把空键当成幂等成功。
3. **消息与广播脱节：** 本阶段先同事务写 outbox，WebSocket 阶段再消费；不能在 Controller 里直接广播后写数据库。
4. **前端假消息残留：** 接入 REST 后删除固定消息和本地机器人回复；任何演示数据必须来自服务端数据库或明确的测试夹具。
5. **HTML/XSS：** 服务端拒绝 HTML，前端使用文本插值；不能只依赖正则或只依赖前端过滤。
6. **游戏领域耦合：** 聊天消息可以携带期号摘要，但消息正文和机器人文本不能成为下注/结算输入。
7. **H2 与 MySQL 差异：** 迁移、JSON、时间精度、唯一 NULL 行为和复合索引必须在独立 MySQL 8.4 中复验。
8. **认证存储边界：** 当前 `web/src/api.ts` 使用 `sessionStorage` 保存访问令牌；本阶段切换为内存变量并继续使用 HttpOnly 刷新 Cookie，避免新聊天功能继续扩大持久化 Token 范围。
