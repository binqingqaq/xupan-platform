# 当前期下注玩法统计与逐球开奖结果预设开发计划

> 日期：2026-11-04
> 状态：基础玩法统计/逐球预设已实施；2026-11-10 中心已接受订单筛选与抽成控盘代码已实施，隔离 MySQL 和专项测试通过，共享库/浏览器/服务器/生产验收未完成。新增实施记录见[详细开发计划 §12](2026-11-10-玩法统计中心已接受订单与抽成控盘开发计划.md)；需求基线见[玩法统计中心已接受订单与抽成控盘需求](../需求基线/2026-11-10-玩法统计中心已接受订单与抽成控盘需求.md)。
> 范围：超级管理后台新增当前期下注玩法统计页，并将当前期逐球手动预设入口从开奖历史移入新页；历史补期流程另行保留。

## 1. 需求基线

使用者确认：

1. 菜单新增“下注玩法统计”，位置为“开奖历史”和“报表统计”之间。
2. 展示当前期 7 个球位的下注玩法分布，按有效下注单数由多到少排序。
3. 统计范围为所有机器账号名下普通玩家的下注，不按具体机器账号、子账号或玩家拆分；排除托和未绑定机器账号的其他注单。页面和接口不得展示这些身份信息。
4. 每种玩法除下单笔数外，同时显示对应下注总积分，供判断下单数量相同时的规模差异。
5. 管理员可针对球位单独预设开奖号码。每球初始为空；仅手动填入并保存的球位固定该号码，其余空球在开奖时随机生成。
6. 预设号码只在本期规定开奖时间到达后参与正式开奖；保存时不立即开奖、不结算、不提前进入下一期。

### BY220 映射与有意扩展

BY220 `admin.php` 有开奖历史和订单操作菜单，但未发现“按球位聚合所有机器下注玩法，并据此预设部分开奖球号”的对应页面或流程。该菜单、统计 API 和部分球位预设行为属于 Xupan 自有扩展，按使用者本次明确需求实现。不得将 BY220 的玩家、机器、子账号明细或其他菜单行为引入本页面。

## 2. 页面与交互方案

### 2.1 菜单及页面头部

- 在 `PlatformAdminNav.vue` 中将开奖相关菜单顺序调整为：`开奖历史 → 下注玩法统计 → 报表统计`。当前源码顺序是`报表统计 → 开奖历史`，因此为满足使用者指定位置，需要交换这两个现有菜单项的相对顺序。
- 页面标题：“下注玩法统计”。
- 页面头部展示当前彩种、期号、期次阶段、开奖倒计时、最近刷新时间和手动刷新按钮。
- 统计限定在同一 `(game_code, issue_number)`，多彩种数据不得跨彩种混合；使用该期快照球数。AU8 当前固定 7 球。
- 页面在当前期切换后自动加载新期统计，将选中球位恢复为第 1 球，并清除前一期结果预设视图状态。

### 2.2 球位总览与玩法排行

- 顶部以 7 个可选择的球位卡片横向呈现。桌面端单行显示；窄屏允许横向滚动，卡片尺寸保持稳定。
- 每个球位卡片只显示球位编号、该球有效下注单数和下注总积分；当前球的号码预设状态在下方号码输入区体现，不在球卡重复展示玩法/随机摘要。
- 点击某球位后，下方以横向排行条显示具体下注指令；每行同时展示玩法指令、下单数和总积分。条长表示相对下单量，第一名轻度突出；不显示表格网格或单独百分比列。
- 按下单笔数降序；笔数相同时按下注总积分降序；仍相同时按固定玩法顺序，保证刷新前后稳定。
- 按标准化后的具体结算指令聚合，不只按 `play_type` 大类合并。例如 `1正` 与 `2正` 结算条件不同，分别统计；同规则别名如 `1堂` 与 `1正`、车玩法数字排列与 `N车` 合并。同参数下注笔数和金额累加，不展示订单、玩家、机器、代理子账号或中心账号。
- 使用 Element Plus 基础组件加轻量 CSS 横向排行条；条长以最高下单数为基准，单数和总积分保留准确数值。不新增 ECharts 等依赖。
- 下注统计数据由初次进入、手动刷新、切换托开关及保存预设时加载，不在后台自动轮询；倒计时使用接口服务器时间校准后本地每秒更新，投注截止时自动切换到开奖阶段。加载和错误状态需明确。

### 2.3 每球开奖结果预设

- 在球位卡片上或选中球位面板内提供 1–20 的号码选择和“保存预设”操作；允许清空该球预设以恢复开奖随机。
- 七球初始均为空。保存一球只写该球的预设值，不要求其它球填满。
- 预设状态明确显示“已固定：NN”；空值显示“开奖随机”。页面禁止提供“确认并立即结算”操作。
- 只允许对当前未确认期次预设号码。请求锁定期次后校验球位范围、号码范围、`game_code + issue_number`、期次阶段及开奖结果未确认状态；与自动开奖并发时由同一数据库行锁串行化。
- 每次新增、改号、清空都写操作审计，包含操作者、期次、球位、变更前后值和时间。开奖结果确认后依靠已有数据库不可变约束拒绝任何预设修改。
- 当前“开奖历史”里的“编辑开奖草稿”属于当前期逐球预设能力，搬到新页面并从历史页移除。历史页仍显示最终结果。历史“补期并确认”是补录过去缺失开奖记录的独立功能，本计划不搬移、不删除。

## 3. 统计口径

- 数据事实：`game_bet` 已受理注单，按当前彩种和当前期号限定；机器归属通过 `COALESCE(demo_user_account.agent_id, game_bet.agent_id_snapshot)` 判定。
- 聚合维度：`ball_number + normalized_settlement_rule_key`；规则键区分实际输赢/和局条件，同时只合并语义等价别名。
- 下单笔数：有效注单行数，不是不同玩家人数；同一玩家多笔下单按多笔计。
- 下注总积分：该分组下注本金 `SUM(stake)`。
- 仅纳入所有机器账号名下普通玩家的有效注单：机器归属优先读取玩家账号当前 `agent_id`，玩家物理删除导致 `user_id` 置空时回退 `agent_id_snapshot`；玩家类型优先读取当前 `player_kind`，玩家物理删除后回退 `player_kind_snapshot`，只统计 `NORMAL`。托单 `BOT`、类型未知、未绑定机器归属、取消/已撤销订单都排除；不按具体机器账号、子账号或玩家拆分统计。
- API 仅返回按球、标准化结算指令聚合后的数字与具体中文指令名。不得返回订单 ID、用户 ID、昵称、机器名、代理账号或原始下注内容。
- SQL 对 `demo_user_account` 左联结，以归属/类型快照过滤普通玩家及可选托单；再按期次、球位、`play_type`、`parameters_text` 预聚合，服务层标准化语义等价别名后汇总到具体结算指令。不得按机器/玩家分组或返回身份字段，不得将订单明细下载到前端再聚合。

## 4. 开奖与结算行为

当前实现 `自动轮期服务.finalizeIssue` 只在 7 个保存号码全部有效时整体采用草稿，否则会为所有球重新随机。本功能需改成逐球合并：

1. 到达本期期次 `drawEndsAt` 后，自动开奖锁定期次并读取 7 个预设字段。
2. 每个已预设且有效的球保留其号码；每个空球单独生成随机号码，允许号码重复的规则保持当前玩法规则。
3. 完整 7 球结果、`draw_confirmed_at`、结果事件、本地玩家结算及中心订单结算在现有事务边界内提交。
4. 任一开奖或结算失败时整体回滚，当前期保留未确认状态，由现有自动轮期重试；不能提前跳期、只提交部分球或重复结算。
5. 开奖历史只读展示最终号码和结算状态；正常日常流程不依赖人工点“确认并结算”。

现有 `game_issue.number_1..number_7` 可空，已确认结果约束仍要求 7 个号码完整且有效；预设阶段允许部分号码为空。初步方案复用期次号码列保存预设值，不新增开奖结果表；实现前需复核最新迁移约束、当前草稿写入路径及手工开奖结果兼容。最终开奖必须将空位补齐后才设置 `draw_confirmed_at`。

## 5. 后端接口、权限与审计

- 新增只读聚合接口（建议）：`GET /api/admin/betting-play-stats/current?gameCode=AU8`。返回当前期概要、7 球预设状态及各球玩法排行，不含任何身份和注单明细。

- 新增独立读取权限 `BETTING_PLAY_STATS_READ` 和预设权限 `BETTING_DRAW_PRESET_MANAGE`；按超级后台现有开奖信息/历史授权规则授予适用角色。读统计不应隐式授予改开奖结果权限。

## 8. 验收标准

- 同一期所有机器账号下普通玩家的相同球位/具体结算指令汇总到一行；不同参数且输赢条件不同的指令分行，语义等价别名归并；托单和类型未知单排除；物理删除玩家后的注单通过归属/类型快照判定；不返回任何账号或玩家身份。
- 下单数为普通玩家订单数；总积分与普通玩家有效注单本金合计一致；托单、类型未知单和取消单排除。
- 每球独立排序，名次与笔数、总积分并列规则一致；7 球为空时正确显示无预设。
- 设置第 7 球为 `08` 后，仅本期第 7 球固定为 `08`，其余 6 球各自随机生成；不出现旧全有/全无草稿行为。
- 预设保存不会提前开奖、结算或创建下一期；开奖时间到达后一次性确认并结算。跨期迟到请求因 `gameCode + issueNumber` 快照不一致而拒绝，不会写入下一期。
- 清空预设后，该球在开奖时改为随机；开奖确认后设置/清空都被服务端拒绝。
- 下注、预设保存、自动开奖并发时结果可预测且无覆盖；开奖/中心结算失败不留下半期结果或重复账务。
- 页面能正确处理无下注、一个玩法、并列名次、加载/错误、当前期切换和窄屏显示。

## 9. 实施前风险与边界

- 这项能力会基于下注热度人工固定部分开奖号码，直接改变随机开奖结果和玩家积分盈亏。所有金额仍是虚拟积分；预设号码必须完整审计，开奖后不可改。
- 预设必须在截止时间前写入，并与自动轮期共用期次锁。不能用前端倒计时作为唯一截止校验。
- 当前菜单的 BY220 原始顺序是“报表统计 → 开奖历史”；本计划为实现“开奖历史 → 新菜单 → 报表统计”需要调整既有两个菜单顺序。
- 本功能不删历史补期，也不改变投注或结算公式；已实施范围与尚未完成的验证见 §10。

### 10.5 中心已接受订单统计与抽成控盘需求（2026-11-10，本机代码已实施，验收未完）

使用者确认：

1. 普通玩家统计只纳入当前期中心已接受的订单。必须按该注单最新一次上报尝试及中心接受状态判定；填写网盘账号但未上报、被拒绝或仍待核的订单均不纳入。
2. 托单完全不进入玩法统计、抽成基数或开奖结果计算；删除现有“托开关”，不再提供包含托单的统计模式。
3. 新增抽成比例下拉选项和手动输入百分比。目标中心净赢按中心已接受普通玩家订单下注总积分乘抽成比例计算。例如 10,000 积分、20% 对应目标 2,000 积分。
4. 服务端根据已接受订单、各球玩法、玩法参数、下注积分及赔率快照计算合法的七球结果；结果须使中心净赢至少达到目标。多个结果可行时的优选/平局策略在技术方案中确定，不改变“至少达到目标”的业务条件。
5. 计算成功后直接写入现有七个球位卡片的预设，不另建结果建议流程；不提前开奖或结算。距离本期开奖时间不足或等于 10 秒时，服务端拒绝计算/写入。
6. 没有任何合法结果达到目标时明确失败，不降低目标、不写入部分预设，原预设保持不变。计算和写入作为一个完整操作并记录操作审计。

实现前需继续核对中心订单与注单的关联、最新上报尝试状态、赔率快照结算公式、当前期锁与开奖锁的事务边界，并评估七球合法开奖结果空间下计算方案的可行性。页面不得加载订单明细后在浏览器计算。所有金额仍为虚拟积分，不改变中心上报、接单、额度和结算业务规则。
