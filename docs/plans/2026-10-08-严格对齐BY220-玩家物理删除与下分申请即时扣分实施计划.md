## 1. BY220 依据（源码级，逐行核过）

### 1.1 删玩家：**物理删除 + 余额退回机器**

`application/rbt/controller/Index.php:235-243`：

```php
public function DelMember() {
    $data = $this->request->param();
    $user = db('rbuser')->where('wxid', $data['wxid'])->where('uid', USER_ID)->find();
    db('robot')->where('UserName', $user['uid'])->setInc('score', $user['score']);  // ① 玩家余额退回机器
    db('rbuser')->where('wxid', $data['wxid'])->where('uid', USER_ID)->delete();    // ② 物理删除玩家行
    setCount(USER_ID);                                                             // ③ 重算机器统计
    return 0;
}
```

**精确语义**：①把该玩家**当前余额**加到机器 `x_robot.score`；②**物理删除** `x_rbuser` 行；③重算统计。**只删玩家行——注单（`x_record`）、资金流水（`x_money_log`）等历史全部保留**（BY220 无外键，所以能这样删）。

### 1.2 上下分申请：**下分创建即扣、拒绝退回**

| 环节 | 上分（type=0） | 下分（type=1） |
| --- | --- | --- |
| 申请创建 `application/common.php:1874-1876` | 不动余额 | **`setDec('score', $last)` 立即扣玩家余额** |
| 同意 `application/rbt/controller/Index.php:268-286` | 玩家 `setInc`；**普（`isTuo==0`）才 `robot.score -=`**；池不足且非托返回 `-2` | **普才 `robot.score +=`**；**玩家余额不再变动**（创建时已扣） |
| 拒绝 `application/rbt/controller/Index.php:307-315` | 不动 | **`setInc('score', $res['score'])` 退回玩家** |

即：**下分的"钱"在申请创建时就离开玩家余额**，同意后被机器池收走，拒绝则原路退回。上分流程与我们现状**已经一致**（创建不动、同意时普才扣池、池不足拒绝）。

## 2. 现状差异（我方）

| 项 | 我方现状 | 与 BY220 的差异 |
| --- | --- | --- |
| 删玩家 | **软删除**（`status='DELETED'`，历史全留，余额**不退回机器池**） | ①玩家仍在库里（只是状态变了）②**余额没有退回机器** |
| 下分申请 | 申请**不动余额**；同意时才 `玩家 -= amount` 且 `机器池 += amount`；拒绝不动 | **最终态相同**，但**中间态不同**：BY220 在创建时就扣、拒绝才退回；且流水时间点不同 |

## 3. 目标设计

### 3.1 删玩家（工作包 DEL）

**行为**：`agent.score += 玩家当前余额` → **物理删除**该玩家（身份 + 账号）→ 重算统计；**注单与流水历史保留**。

**必须解决的工程约束（BY220 没有的问题）**：实测外键（本机 MySQL `information_schema`）：

| 引用方 | 列 | ON DELETE |
| --- | --- | --- |
| `game_bet` | `user_id` → `demo_user_account` | **NO ACTION**（有注单就删不掉） |
| `demo_balance_ledger` | `user_id` → `demo_user_account` | **NO ACTION** |
| `game_bet_edit_record` | `account_id` → `demo_user_account` | NO ACTION |
| `test_player_action` / `test_player_behavior` | `account_id` → `demo_user_account` | NO ACTION |
| `demo_user_account` | `sys_user_id` → `sys_user` | NO ACTION |
| 身份域一批（`sys_user_role`、`player_access_link`、`player_point_request`、`player_name_change_record`、`player_quick_bet_preference`、`player_link_expiration_config`、`chat_read_cursor`、`chat_user_mute`、`auth_session`、`auth_ws_ticket`…） | 各自 `user_id` → `sys_user` | NO ACTION |

**设计方案（本计划定稿，实施 lane 不得擅自改向）**：

1. **保留历史**：把 `game_bet.user_id`、`demo_balance_ledger.user_id`、`game_bet_edit_record.account_id` 改为**可空 + `ON DELETE SET NULL`**；
   **并要求**：这些表必须已有**可用于展示的快照**（玩家编号/昵称）。**实施前先核实**：若某表只有 `user_id` 而没有玩家可读标识，则**该表补一个快照列**（迁移内 `ADD COLUMN`，并在删除前把当前值写入）——**不得**因为"删了看不到"而放弃保留历史。
2. **身份域子行**：按语义分两类处理——
   - **应当随身份消失的**（`sys_user_role`、`auth_session`、`auth_ws_ticket`、`player_access_link`、`player_quick_bet_preference`、`chat_read_cursor`、`chat_user_mute`、`player_link_expiration_config`）→ **物理删除**；
   - **属于业务历史的**（`player_point_request`、`player_name_change_record`）→ 优先**改可空 + SET NULL**（与注单同口径）；若技术上不可行则在报告里说明并**停下请示**，不得静默删除。
3. **删除顺序**：`test_player_*` → 身份域子行 → 历史表（SET NULL）→ `demo_user_account` → `sys_user`；**全程一个事务**。
4. **退回机器池**：用现有机器池入账服务写一条 `agent_ledger`（BY220 不记流水，我们为审计必须记——**这是超集，须在文档登记**），`amount = 删除时玩家余额`，`reason` 写明"玩家删除退回余额"。
5. **幂等**：同一玩家重复删除 → 幂等成功（第二次目标已不存在，不得重复退款）。**并发**：删除与"上下分"并发时，以事务 + 行锁保证只退一次。
6. **权限**：仍只允许**机器账号**删除**自己名下**的玩家（`scope = MACHINE`）；超管/子账号 403（阶段 3 已收紧）。
7. **文案/返回**：对齐 BY220 的 `return 0`（成功标志）；前端提示按现有文案风格，不新造业务名词。

### 3.2 下分申请即时扣分（工作包 REQ）

**行为**：
- **创建下分申请**（`type = 下分`）：**立即扣玩家余额**（写钱包流水，语义 = 下分预扣），申请置 `PENDING`。
- **同意**：**不再动玩家余额**；**普**才 `机器池 += amount`（托不联动，沿用现值）；写相应流水。
- **拒绝**：`玩家余额 += amount`（退回）+ 写退回流水；**重复拒绝幂等**（只退一次）。
- **上分申请**：**保持现状**（创建不动、同意时普才扣池、池不足拒绝）。

**本计划定死的一个偏离（需使用者知悉）**：BY220 创建下分申请时**不校验余额**（可以扣成负数）。我方**拒绝创建**（余额不足 → 400，复用现有余额不足文案），因为允许负余额会破坏我们的钱包口径与报表。**这是有意偏离，须登记到缺口表 §4**；若使用者要求连负余额也一致，需另开一次评审。

## 5. 验收矩阵（两条都必须有运行态证据）

| 层 | 用例 | 断言 |
| --- | --- | --- |
| H2 | 删玩家（有注单/流水） | 玩家行**已不存在**；注单/流水**仍在且可读**（`user_id` 为 NULL 或快照可读）；机器池**增加额 = 删除时余额**；统计正确 |
| H2 | 删玩家（无注单/流水） | 同上；无外键报错 |
| H2 | 重复删除 | 幂等；**不重复退款** |
| H2 | 超管/子账号删除 | 403（阶段 3 口径） |
| H2 | 下分申请创建 | 玩家余额**立即减少**；产生预扣流水；状态 `PENDING` |
| H2 | 下分申请创建（余额不足） | 400，**余额不变**（我方刻意偏离，登记） |
| H2 | 下分同意 | 玩家余额**不再二次减少**；**普**机器池 `+= amount`；**托不联动** |
| H2 | 下分拒绝 | 玩家余额**退回**；产生退回流水；**重复拒绝不重复退回** |
| H2 | 上分申请 | **与改动前逐项一致**（回归） |
| 本机 MySQL | 全链路 | 建玩家 → 上分 → 下分申请（余额立即减少）→ 拒绝（退回）→ 再申请 → 同意（池增加）→ 删玩家（余额退回池、历史保留）。**清理测试数据到基线**（`agent 6 / sys_user 8`、机器池与 `agent_ledger` 复原） |
| 前端 | 类型检查 + 构建 + 相关组件测试 | 通过；若有"删除玩家"确认文案需与后端语义一致（物理删除不可恢复） |

## 6. 风险与边界

- **不可逆**：物理删除后玩家无法恢复（BY220 亦如此）。前端删除确认文案必须明确"不可恢复"，且**必须二次确认**（BY220 前端已有确认流程，实施时核对其模板 `rbt/view/index/admin_list.html`）。
- **历史可读性**：SET NULL 后若界面依赖 `user_id` 展示玩家名，需改为读快照列，否则历史会显示为空——**这是本计划最容易漏的地方，实施 lane 必须逐表确认**。
- **不得**用"CASCADE"简化为一次删除（会毁掉注单/流水历史，与 BY220 相反）。
- 本批**不改**上分流程（已对齐）；**不改** `PlayerDeskScopeService`。
- 未验证内容一律如实标注；每处改动须给 BY220 `file:line` 依据与验证方式。
