> **给实施者：** 按任务顺序执行本计划。步骤使用复选框（`- [ ]`）语法跟踪进度。

> **执行状态（2026-09-14）：** 本计划已完成代码实施和本轮验收。后端全量 H2 测试 `176/176` 通过；独立 MySQL `8.4.11` 临时验收库从 V1 到 V12 迁移成功，真实 Spring Boot 在独立端口启动，调度器实际扫描 `ISSUE_STARTED` 并生成 `PUBLISHED` 机器人消息、聊天室消息和 outbox。专项证据见 [服务端常驻机器人基础能力验收记录](../验收记录/2026-09-14-服务端常驻机器人基础能力验收记录.md)。
>
> 本次仍未实现：机器人后台前端页面、历史事件批量补发、消息归档和真实支付。Redis/MQ 多实例、跨节点 WebSocket 广播和专门监控告警平台不属于当前单服务器目标，只有正式上线后出现明确容量或故障需求时才另行评估。计划中的细粒度复选框保留为设计追踪清单，最终判断以本执行状态和验收记录为准。

**目标：** 在现有单实例聊天室基础上，实现一个不依赖浏览器在线、不占用真实用户身份、不接入用户钱包和下注链路的服务端常驻机器人基础能力。机器人读取 `game_issue_event`，根据已配置的机器人和模板生成 `ROBOT` 消息，持久化到聊天室，进入现有 outbox 和 WebSocket 广播链路，并通过后台接口完成启停、权重、延时、模板和投递记录管理。

**架构：** 机器人作为 `game` 的只读事件适配器和 `chat` 的消息生产者存在。游戏模块继续只负责轮期和游戏事件；机器人调度器独立扫描已提交的游戏事件，创建可恢复的投递任务；机器人消息通过现有聊天室消息表、outbox 和提交后广播机制发布。单实例阶段使用数据库事务、唯一约束和任务状态恢复保证一致性，不引入 Redis、Quartz 或多实例锁。

**技术栈：** Java 21、Spring Boot 4.0.8、Spring JDBC、MySQL 8.4 LTS、Flyway、H2 测试配置、现有 Spring Security/JWT 认证、现有聊天室 WebSocket 和 outbox 机制。

## 全局约束

- 本计划只覆盖服务端常驻机器人基础能力，不改变已经完成的用户认证、聊天室用户发言、轮期推进、开奖结果和虚拟钱包规则。
- 机器人不是 `sys_user`，不创建后台登录账号，不进入 `sys_user`、`sys_user_role`、`demo_user_account`、`wallet_account`、`wallet_ledger` 或 `game_bet`。
- 机器人消息固定使用 `message_type=ROBOT`、`sender_type=ROBOT`，`sender_id` 保存 `chat_robot.id`。当前多态发送者表结构不新增到 `sys_user` 的外键。
- 机器人不能调用下注服务、扣减钱包、增加钱包、代替真实用户发言或写入真实用户的 `client_message_id`。
- 游戏事件表 `game_issue_event` 仍是游戏模块的事实来源。机器人只能读取事件，不修改事件内容，不改变事件唯一键和轮期推进事务语义。
- 机器人消息必须先写入 `chat_message` 和 `chat_outbox`，再由现有 `ChatMessageCreatedListener` 在事务提交后广播；机器人服务不得直接绕过持久化向 WebSocket 推送。
- 同一 `game_issue_event` 在本阶段最多生成一条机器人消息。相同扫描、服务重启、浏览器重连和重复请求都不能产生重复机器人消息。
- 没有浏览器连接时仍必须完成数据库持久化；连接数为零不能被当作发送失败。
- 失败任务可以重试；机器人被管理员禁用时，历史事件标记为 `SKIPPED`，不因重新启用而补发已经跳过的历史消息。
- 模板只允许白名单变量和纯文本，禁止 HTML、脚本、函数调用、表达式、远程资源和动态 SQL。
- 新增数据库结构只允许通过 Flyway 迁移；不得要求实施者手工执行建表 SQL。
- 测试中的 H2 结果只能证明测试配置下的行为；MySQL 8.4 LTS 迁移和 SQL 兼容性必须单独验证。
- 当前工作区实施基线为 `f726e40 fix: 完善聊天室断网重连验收` 加本计划范围内的未提交变更；本文件的执行状态和验收记录分别区分代码完成、测试完成与未实现边界。

## 一、范围与完成定义

### 1.1 本阶段包含

- 一个独立的机器人身份模型：编码、显示名、头像标识、启停状态、权重、延时和审计字段。
- 按机器人和游戏事件类型配置文本模板，并提供模板渲染预览。
- 一个可恢复的机器人投递任务模型，记录来源事件、选中的机器人、状态、重试次数、下次重试时间、错误摘要和生成的消息。
- 读取 `game_issue_event` 的服务端事件扫描器，覆盖现有事件类型：
  - `ISSUE_STARTED`：期号开始。
  - `BETTING_WARNING`：临近截止提醒。
  - `BETTING_CLOSED`：停止下注。
  - `DRAW_RESULT`：开奖结果及当前游戏服务已经记录的结果消息。
- 机器人消息进入现有聊天室消息序列、outbox 和提交后 WebSocket 广播流程。
- 服务端后台接口：机器人查询、创建、修改、启停、模板查询、模板更新、模板预览、投递记录查询和失败任务重试。
- `ROBOT_READ`、`ROBOT_WRITE`、`ROBOT_TEMPLATE_WRITE` 的服务层权限检查和操作审计。
- 单元测试、H2 集成测试、MySQL 8.4 迁移验证、无在线连接验证、重复扫描验证、重启恢复验证、失败重试验证和机器人越权边界验证。

### 1.2 本阶段不包含

- Redis、消息队列、分布式锁、水平扩展、多实例广播和跨节点一致性。
- Quartz 或其他独立调度平台；使用现有 Spring 定时任务能力完成单实例扫描。
- 真实支付、充值、提现、支付回调或自动结算资金链路。
- 机器人下注、机器人钱包、机器人投注记录和模拟投注展示。
- 外部大模型、外部聊天平台或远程机器人接口。
- 机器人后台前端页面。先提供稳定的管理 API 和可重复的 HTTP 验收脚本；管理页面作为下一阶段后台运营 UI 任务单独规划。
- 历史游戏事件的批量补发工具、消息归档清理和运营报表。
- 多机器人同一事件群发。首期每个游戏事件只选择一台启用机器人，保留权重字段和选择器，为后续扩展多个机器人做结构准备。

### 1.3 完成定义

本阶段只有同时满足以下条件才可标记完成：

1. Flyway V11、V12 在 H2 测试配置和 MySQL 8.4 LTS 独立验收库中成功执行。
2. 新建机器人、启停机器人、编辑模板、预览模板、查询投递记录和重试失败任务均有可验证 API。
3. `自动轮期服务` 产生游戏事件后，即使没有任何浏览器连接，机器人消息也会落入 `chat_message` 和 `chat_outbox`。
4. 对同一事件重复扫描、重复启动调度器或重复提交请求，最终只有一条机器人消息、一个聊天室序号和一条 outbox 记录。
5. 进程在任务进入 `PENDING` 或 `FAILED` 后停止，再启动扫描器可以继续完成任务。
6. 机器人被禁用时不产生消息；机器人配置接口不能让机器人写入下注、钱包或真实用户数据。
7. 机器人消息使用现有聊天室广播链路，在线浏览器能收到，离线浏览器通过现有历史/游标接口能补齐。
8. 全量后端测试通过，且文档中明确记录已验证项、未执行项和下一阶段边界。

## 三、固定领域模型与数据契约

### 3.1 机器人身份

新增领域对象：

```java
public record ChatRobot(
        long id,
        String robotCode,
        String displayName,
        String avatarKey,
        RobotStatus status,
        int weight,
        int delaySeconds,
        Instant createdAt,
        Instant updatedAt
) {}
```

固定规则：

- `robotCode` 长度 1 至 32，只允许小写字母、数字、中划线和下划线，创建后不可修改。
- `displayName` 长度 1 至 32，作为 `chat_message.sender_name` 展示值。
- `avatarKey` 长度 1 至 64，只保存前端资源键，不保存外部 URL。
- `status` 只有 `ENABLED`、`DISABLED`。
- `weight` 范围 1 至 100；禁用机器人不参与选择。
- `delaySeconds` 范围 0 至 300。它表示事件发生后允许的最小展示延迟，不阻塞游戏轮期事务。
- 首次迁移创建一个默认机器人：`robotCode=issue-helper`、`displayName=开奖助手`、`avatarKey=robot-default`、`status=ENABLED`、`weight=100`、`delaySeconds=0`。
- 默认机器人不创建 `sys_user`，不创建权限角色，不创建钱包。

### 3.2 模板

新增领域对象：

```java
public record ChatRobotTemplate(
        long id,
        long robotId,
        String eventType,
        String templateCode,
        String templateText,
        boolean enabled,
        int version,
        Instant createdAt,
        Instant updatedAt
) {}
```

固定规则：

- `eventType` 只允许 `ISSUE_STARTED`、`BETTING_WARNING`、`BETTING_CLOSED`、`DRAW_RESULT`。
- `templateCode` 由服务端固定为 `default`，本阶段不开放任意模板代码扩展。
- 同一机器人和事件类型只有一条启用模板；更新模板采用版本递增，旧版本保留记录但置为禁用。
- `templateText` 长度 1 至 1000 个字符，按纯文本处理。
- 允许变量：`{{issueNumber}}`、`{{eventType}}`、`{{eventMessage}}`、`{{robotName}}`、`{{createdAt}}`、`{{resultNumbers}}`。
- `resultNumbers` 只在 `DRAW_RESULT` 事件中提供；其他事件使用该变量必须被拒绝。
- 未知变量、未闭合变量、HTML 标签、脚本协议、控制字符和超长内容必须在保存和预览时拒绝。
- 渲染结果长度 1 至 2000 个字符；渲染后再次执行纯文本策略检查。

默认模板：

| 事件类型 | 默认模板 |
| --- | --- |
| `ISSUE_STARTED` | `{{issueNumber}}期开始，欢迎进入聊天室。` |
| `BETTING_WARNING` | `{{eventMessage}}` |
| `BETTING_CLOSED` | `{{eventMessage}}` |
| `DRAW_RESULT` | `{{eventMessage}}` |

### 3.3 投递任务

新增领域对象：

```java
public record ChatRobotDispatch(
        long id,
        long gameEventId,
        long robotId,
        String issueNumber,
        String eventType,
        RobotDispatchStatus status,
        int attemptCount,
        Instant nextAttemptAt,
        Instant lockedUntil,
        Long messageId,
        String lastError,
        Instant createdAt,
        Instant updatedAt,
        Instant publishedAt
) {}
```

状态固定为：

| 状态 | 含义 | 可进入状态 |
| --- | --- | --- |
| `PENDING` | 已发现游戏事件，等待生成消息 | `PROCESSING`、`SKIPPED` |
| `PROCESSING` | 当前实例正在处理，带租约时间 | `PUBLISHED`、`FAILED`、`PENDING` |
| `FAILED` | 本次处理失败，等待 `next_attempt_at` | `PROCESSING`、`SKIPPED` |
| `PUBLISHED` | 已写入消息和 outbox | 终态 |
| `SKIPPED` | 机器人禁用、模板缺失或事件不支持，明确跳过 | 终态 |

固定幂等规则：

- `game_event_id` 唯一；同一个游戏事件只能有一条投递任务。
- `issue_number + event_type` 作为业务追踪字段保存，不作为跨机器人群发主键。
- 消息幂等键由 `SHA-256("robot|" + gameEventId)` 生成，写入 `chat_message.idempotency_key`；不包含模板版本，模板更新不会重复发布同一历史事件。
- `chat_robot_dispatch.message_id` 写入成功后，任务才可以进入 `PUBLISHED`。
- 任务错误只保存分类和截断摘要，不保存数据库密码、Token、Cookie、完整请求头或完整堆栈。

### 3.4 游戏事件映射

| 游戏事件 | 机器人行为 | 聊天字段 |
| --- | --- | --- |
| `ISSUE_STARTED` | 发布期号开始消息 | `message_type=ROBOT`、`sender_type=ROBOT`、`issue_number=事件期号` |
| `BETTING_WARNING` | 发布临近截止提醒 | 同上 |
| `BETTING_CLOSED` | 发布停止下注消息 | 同上 |
| `DRAW_RESULT` | 发布现有开奖结果事件消息 | 同上 |

事件映射服务必须读取 `GameIssueEventRepository.EventRecord`，不得根据字符串重新推测期号或开奖结果。`DRAW_RESULT` 的业务内容以 `event.message` 为准；本计划不修改 `自动轮期服务.resultMessage()` 的现有语义。

## 四、数据库设计与迁移任务

### 4.1 V11：机器人和模板表

文件：

`server/xupan-server/src/main/resources/db/migration/V11__创建机器人和模板表.sql`

实施内容：

```sql
CREATE TABLE chat_robot (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    robot_code VARCHAR(32) NOT NULL,
    display_name VARCHAR(32) NOT NULL,
    avatar_key VARCHAR(64) NOT NULL,
    status VARCHAR(16) NOT NULL,
    weight INT NOT NULL DEFAULT 100,
    delay_seconds INT NOT NULL DEFAULT 0,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT uk_chat_robot_code UNIQUE (robot_code),
    CONSTRAINT ck_chat_robot_status CHECK (status IN ('ENABLED', 'DISABLED')),
    CONSTRAINT ck_chat_robot_weight CHECK (weight BETWEEN 1 AND 100),
    CONSTRAINT ck_chat_robot_delay CHECK (delay_seconds BETWEEN 0 AND 300)
);

CREATE TABLE chat_robot_template (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    robot_id BIGINT NOT NULL,
    event_type VARCHAR(32) NOT NULL,
    template_code VARCHAR(32) NOT NULL,
    template_text VARCHAR(1000) NOT NULL,
    enabled BOOLEAN NOT NULL DEFAULT TRUE,
    version INT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    CONSTRAINT fk_chat_robot_template_robot FOREIGN KEY (robot_id) REFERENCES chat_robot(id),
    CONSTRAINT uk_chat_robot_template_version UNIQUE (robot_id, event_type, template_code, version),
    CONSTRAINT ck_chat_robot_template_event CHECK (event_type IN ('ISSUE_STARTED', 'BETTING_WARNING', 'BETTING_CLOSED', 'DRAW_RESULT')),
    CONSTRAINT ck_chat_robot_template_version CHECK (version >= 1)
);

CREATE INDEX idx_chat_robot_template_active
    ON chat_robot_template (robot_id, event_type, enabled, version);
```

迁移初始化：

- 插入默认机器人 `issue-helper`。
- 为默认机器人插入四条 `default`、版本 `1` 的启用模板。
- 初始化 SQL 使用 `INSERT ... SELECT ... WHERE NOT EXISTS`，确保测试重放脚本时不会产生重复默认数据。
- 初始化数据只包含演示用文本，不包含外部地址、凭据、Token 或真实业务数据。

### 4.2 V12：机器人投递表

文件：

`server/xupan-server/src/main/resources/db/migration/V12__创建机器人调度表.sql`

实施内容：

```sql
CREATE TABLE chat_robot_dispatch (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    game_event_id BIGINT NOT NULL,
    robot_id BIGINT NOT NULL,
    issue_number VARCHAR(64) NOT NULL,
    event_type VARCHAR(32) NOT NULL,
    status VARCHAR(16) NOT NULL,

    next_attempt_at TIMESTAMP NULL,
    locked_until TIMESTAMP NULL,
    message_id BIGINT NULL,

    CONSTRAINT fk_chat_robot_dispatch_message FOREIGN KEY (message_id) REFERENCES chat_message(id),
    CONSTRAINT uk_chat_robot_dispatch_event UNIQUE (game_event_id),
    CONSTRAINT uk_chat_robot_dispatch_message UNIQUE (message_id),

    ON chat_robot_dispatch (issue_number, event_type, id);
```

实施注意：

- 若现有 H2 测试方言不接受 `BOOLEAN`、`CHECK` 或外键定义，优先按现有迁移的兼容写法调整 SQL，但必须保持 MySQL 8.4 LTS 的约束语义；不能通过删除约束来绕过测试。
- `chat_robot_dispatch` 的 `game_event_id` 外键用于保证来源事件存在；不要复制事件内容作为第二事实来源。
- `message_id` 允许为空，只有机器人消息及 outbox 成功写入后才更新。
- 不新增 `sys_user` 或钱包相关迁移，不修改 V1-V10。

### 4.3 数据库验收

- H2：启动测试上下文执行 V1-V12，验证表、索引、唯一约束和默认机器人模板。
- MySQL 8.4：在独立验收库执行完整 Flyway 迁移，检查 `flyway_schema_history`、外键、索引和默认数据。
- 重复执行迁移命令时，Flyway 必须报告数据库已是最新状态，不得产生重复机器人或模板。
- 插入重复 `game_event_id` 必须失败；应用层将该异常转换为幂等成功或读取已有任务，不能向上抛出重复消息错误。

### 6.4 本地人工验收步骤

1. 以具有 `ROBOT_READ` 和 `ROBOT_WRITE` 的后台账号登录，调用 `GET /api/admin/robots`。

4. 将机器人置为 `DISABLED`，推进或插入一个测试游戏事件，确认 dispatch 为 `SKIPPED` 且聊天室没有机器人消息。

6. 在浏览器无聊天室连接时触发一个测试事件，查询数据库确认消息和 outbox 已持久化。
7. 打开聊天室，确认现有 WebSocket 收到机器人消息；刷新页面后通过历史接口仍能看到该消息。
8. 重复执行扫描或重启服务，确认消息总数不增加。
9. 检查审计记录，确认配置变更、权限拒绝和手工重试可追踪，且没有敏感信息。

### 6.5 验收数据查询

实施者在独立验收库执行等价查询，具体值使用测试事件产生的 ID：

```sql
SELECT id, game_event_id, robot_id, issue_number, event_type,
       status, attempt_count, message_id, last_error, published_at
FROM chat_robot_dispatch
WHERE issue_number = :issueNumber
ORDER BY id;

SELECT id, room_id, sequence_no, message_type, sender_type,
       sender_id, sender_name, issue_number, idempotency_key, content
FROM chat_message
WHERE message_type = 'ROBOT'
  AND issue_number = :issueNumber
ORDER BY id;

SELECT id, message_id, event_type, status, attempt_count,
       published_at, last_error
FROM chat_outbox
WHERE message_id = :messageId;
```

预期关系：一条 `game_event_id` 对应一条 `chat_robot_dispatch`，一条 `message_id` 对应一条 `chat_message` 和一条 `message_created` outbox；任务状态为 `PUBLISHED` 时三者都存在。

## 九、方案取舍与后续扩展边界

### 9.1 为什么本阶段使用数据库扫描

数据库扫描直接读取已经提交的 `game_issue_event`，天然支持服务重启恢复，不需要在轮期事务中同步等待机器人处理，也不依赖在线浏览器。单实例阶段的事件量和聊天室消息量可以由批量大小、索引和唯一约束控制，足以支撑当前最小闭环。

### 9.2 为什么本阶段不使用多实例方案

当前运行目标是单实例，现有聊天室实时链路也是单实例。引入 Redis 或分布式锁会扩大部署、故障和验收范围，但不会提升当前闭环的核心可验证性。`chat_robot_dispatch` 的唯一键、任务租约和状态恢复已经保留了后续迁移到多实例投递器所需的业务边界。

### 9.3 后续进入多实例前必须补充

- Redis 或消息队列的事件通知与消费模型。
- 跨实例任务领取和租约续期的正式协议。
- WebSocket 广播的跨节点 fan-out。
- outbox 发布器的独立消费和死信处理。
- 机器人配置缓存失效和版本一致性。
- 监控指标、告警阈值、限流和后台批量运维。
- 消息归档、重放和运营审计保留策略。

本阶段不因提前写入这些基础设施而扩大实现范围；只保持当前表字段、服务接口和状态机可迁移。
