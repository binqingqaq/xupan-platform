**目标：** 在已完成的单实例 WebSocket 和前端实时消息流代码基础上，补齐前端连接服务自动化测试，完成 MySQL 8.4 运行态、双浏览器实时聊天、断线补偿、权限失效、Nginx Upgrade、发布和回滚验证，使阶段 4 达到可审计的结项条件。

**技术栈：** Java 21、Spring Boot 4.0.8、Spring Security、Spring WebSocket、Spring JDBC、Flyway、MySQL 8.4.11、H2、JUnit、Mockito、Vue 3、TypeScript、Vite、Vitest、jsdom、Nginx、systemd。

```ts
class FakeWebSocket {
  static readonly OPEN = 1
  static readonly CLOSED = 3
  readonly sent: unknown[] = []
  readyState = 0
  onopen: (() => void) | null = null
  onmessage: ((event: MessageEvent<string>) => void) | null = null
  onclose: ((event: CloseEvent) => void) | null = null
  onerror: (() => void) | null = null

  send(payload: string) {
    this.sent.push(JSON.parse(payload))
  }

  close(code = 1000, reason = '') {
    this.readyState = FakeWebSocket.CLOSED
    this.onclose?.({ code, reason } as CloseEvent)
  }

  open() {
    this.readyState = FakeWebSocket.OPEN
    this.onopen?.()
  }

  receive(payload: unknown) {
    this.onmessage?.({ data: JSON.stringify(payload) } as MessageEvent<string>)
  }

  closeWith(code: number) {
    this.close(code, 'test close')
  }
}
```

## 7. 任务 5：执行双浏览器实时聊天主流程验收

**目标：** 证明两个正式用户在同一实例、同一房间内能实时收发数据库确认后的纯文本消息。

**证据：** 浏览器 Network 面板 WebSocket `101`、页面截图、服务端日志摘要、数据库查询结果；截图中遮挡所有凭据和带 ticket 的 URL。

**步骤：**

- [ ] **步骤 1：验证 A、B 的 WebSocket 握手。**

确认：

```text
POST /api/auth/ws-ticket?roomCode=main -> 200
GET /ws/chat/main -> 101 Switching Protocols
```

确认请求 Origin 为允许的前端来源，服务端没有把 ticket 原文写入日志；连接事件中的房间是 `main`。

- [ ] **步骤 2：验证订阅和空历史同步。**

确认连接建立后客户端发送 `subscribe`，服务端返回 `sync.required` 和 `sync.complete`，页面连接状态最终为实时可用；空历史时不出现固定用户、固定机器人或本地假消息。

- [ ] **步骤 3：A 发送普通纯文本。**

A 发送唯一文本 `ws-e2e-a-20260913-hello-01`。确认：

1. A 收到一个 `message.ack`，`deduplicated=false`。
2. B 收到一个 `message.created`。
3. A、B 展示同一个服务端 `id`、`sequenceNo`、`senderId` 和 `senderName`。
4. 数据库 `chat_message` 只有一条对应消息，`chat_outbox` 有对应持久化事件。
5. A 页面没有同时出现临时假消息和服务端确认消息。

- [ ] **步骤 4：B 回复并验证顺序。**

B 发送 `ws-e2e-b-20260913-reply-01`，A 验证实时到达；连续发送两条消息，比较页面、ACK、数据库序列号和 outbox 记录，确认序列递增且跨用户一致。

- [ ] **步骤 5：验证纯文本展示。**

发送文本 `plain-text-<b>not-html</b>` 和包含换行的文本。确认页面按文字显示，不产生 HTML 节点、不执行脚本、不改变布局结构；数据库保存的是服务端规范化后的正文。

- [ ] **步骤 6：验证同一消息幂等。**

在受控测试客户端重复提交同一个 `clientMessageId`，不得伪造发送者字段。确认服务端返回原消息且 `deduplicated=true`，房间不增加第二条消息，其他浏览器不收到第二个 `message.created`。

- [ ] **步骤 7：验证读游标。**

B 滚动到最新消息并刷新页面，确认历史通过 REST 恢复；服务端收到 `cursor.ack` 后，`chat_read_cursor` 只前进不回退。发送超过服务端最新序列的游标应收到稳定错误，不得写入非法值。

- [ ] **步骤 8：验证移动和桌面布局。**

分别使用 375px 宽度和桌面宽度检查：消息正文、输入框、发送按钮、连接状态、未读提示和错误提示不横向溢出；输入区不因长文本或失败状态改变页面结构。

## 8. 任务 6：执行断线、重连、降级和权限失效验收

**目标：** 证明网络和权限状态改变时仍以服务端序列、权限和 REST 补偿为准。

**步骤：**

- [ ] **步骤 1：验证断线前后游标补偿。**

关闭 B 的网络或阻断 B 的 WebSocket 请求；A 发送两条消息并确认数据库落库。恢复 B 网络，确认 B 重新申请新 ticket、建立新 `101` 连接、按 `afterSequence` 调用 REST 补偿，并最终展示缺失消息且没有重复。

- [ ] **步骤 2：验证主动刷新清理。**

刷新 A 页面并观察旧连接关闭、新连接建立；确认刷新前连接不会在后台继续重连，刷新后历史消息和新连接状态正确。切换路由再返回，确认没有重复 WebSocket 或重复聊天室轮询。

- [ ] **步骤 3：验证 WebSocket 降级。**

临时停止 WebSocket 转发或阻断 `/ws/`，保留 REST 可用。确认页面显示“实时连接不可用，已切换普通模式”，聊天室使用 REST after-sequence 轮询和 REST 发送；恢复 WebSocket 后状态回到实时模式，降级轮询停止。

- [ ] **步骤 4：验证 ticket 失败和重放。**

让一个一次性 ticket 过期或重复使用，确认握手不能建立可用连接；页面不无限重试、不显示 ticket 内容。使用已注销会话重新申请 ticket 应失败。

- [ ] **步骤 5：验证停用用户。**

管理员将 B 状态改为 `DISABLED`。确认 B 的 REST 房间查询、消息发送和新 WebSocket ticket 均被拒绝；已有连接不能继续发消息。恢复为 `ACTIVE` 后必须重新登录或重新建立有效会话。

- [ ] **步骤 6：验证撤销发言权限。**

管理员保留 B 的查看权限但撤销 `PERM_CHAT_MESSAGE_SEND`。确认 B 可以读取历史但发送消息收到 `CHAT_PERMISSION_DENIED`，数据库没有新增消息；重新授予权限后重新连接才允许发言。

- [ ] **步骤 7：验证禁言。**

管理员对 B 在 `main` 房间建立当前有效禁言记录。确认 B 的 WebSocket 发送和 REST 发送均收到 `CHAT_USER_MUTED`，不产生消息和 outbox；解除禁言后重新发送成功。

- [ ] **步骤 8：验证边界输入和限流。**

分别验证空内容、超过 4096 字节的 WebSocket 帧、消息发送超过 10 条/10 秒、非法游标和其他房间编码。确认错误码稳定、连接不会因普通业务失败无故关闭；协议违规和连接治理关闭必须记录关闭原因。

- [ ] **步骤 9：回收测试状态。**

在验收库中将临时用户标记为 `DISABLED`，清理当前测试房间的临时聊天数据或销毁独立验收库；保留脱敏结果。不得在正式业务库执行批量清理。

## 13. 风险处理规则

| 风险 | 发现条件 | 处理方式 |
| --- | --- | --- |
| 默认 MySQL 凭据不可用 | Spring Boot 启动出现连接拒绝或认证失败 | 不改生产配置；从受控本地密钥读取正确配置，仍不可用则记录为运行态未验证 |
| 测试用户污染正式库 | 当前数据库无法确认是独立验收库 | 停止创建用户和消息，先建立隔离库 |
| WebSocket 101 失败 | ticket、Origin、Nginx 或服务端握手失败 | 按层记录 HTTP 状态和服务日志，禁止绕过认证改成匿名连接 |
| 收到重复消息 | ACK、广播、REST 补偿同时产生重复 | 以 `messageId`/`sequenceNo` 对照数据库和前端合并逻辑，修复后重新执行全套回归 |
| 权限撤销后仍可发送 | 旧连接未重新复核当前权限 | 立即阻断结项，检查 `ChatWebSocketHandler` 的当前用户权限复核和用户状态查询 |
| Nginx reload 失败 | `nginx -t` 非 0 | 恢复备份配置并验证站点，不继续发布 |
| 服务重启后消息缺失 | 重连后 REST after-sequence 无法补偿 | 不宣称阶段完成，保留数据库消息/outbox，先定位序列、游标和历史查询问题 |
| 服务器回滚失败 | 旧 Jar 或配置无法恢复 | 保持现场、停止进一步变更，按服务器发布目录和 systemd 当前引用逐项恢复；不删除数据库历史 |
