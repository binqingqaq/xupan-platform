# 用户消息反馈与下注结算闭环实施计划

> **给实施者：** 按任务顺序执行本计划。步骤使用复选框（`- [ ]`）语法跟踪进度。

**目标：** 为聊天室建立服务端统一的用户消息反馈闭环：每条用户输入都被分类并获得可追溯反馈，确认的玩法按固定第 1 球下注并即时扣除粮草，封盘/开奖阶段拒绝下注，开奖后完成幂等结算并发布对全体用户可见的结算反馈。

**架构：** 用户原文仍先作为公开聊天室消息持久化；服务端随后使用同一套文本识别规则判定普通文本、已确认玩法、疑似但格式错误的玩法和暂未支持的命令。反馈使用现有服务端 `ROBOT` 身份写入 `chat_message`、`chat_outbox` 并通过现有 WebSocket/REST 补偿链路广播，不能由前端拼接或只发给请求用户。下注、余额流水、注单状态和反馈消息分别使用数据库事务与稳定幂等键保证可重试、不可重复扣款或重复结算。

**技术栈：** Java 21、Spring Boot 4.0.8、MySQL 8.4 LTS、Flyway、Spring JDBC、H2 测试 Profile、Vue 3/TypeScript、REST、单实例 WebSocket。

## 全局约束

- 本计划只覆盖已确认的用户消息反馈、确认玩法文本下注、粮草扣款、开奖结算反馈和相关生产安全边界；“玩法说明、历史、流水”等聊天命令暂不纳入本轮识别范围。
- 当前下注仍固定为第 1 球，前端不增加球位选择，服务端必须继续拒绝其他球位。
- 用户消息和机器人反馈对聊天室全体用户可见；机器人反馈中的 `@` 后使用用户展示名，不使用登录名、用户编码或内部 ID。
- 正确下注成功文案采用已确认格式：`@展示名  攻击成功，使用粮草金额, 剩余粮草：扣款后余额`。金额和余额使用服务端 `DECIMAL`/`BigDecimal` 结果，不由前端计算。
- 普通聊天、问候、未确认玩法和格式不正确的输入统一反馈 `@展示名, 指令格式不正确!`；不得把这类内容静默当普通聊天成功处理。
- 开奖中和封盘期间的下注必须分别返回明确的下注无效反馈；余额不足必须直接显示粮草不足，且不能生成注单、扣款流水或成功反馈。
- 下注扣款、注单保存、赔率快照和成功反馈必须有明确事务边界；网络重试、WebSocket 重连、服务重启和调度重复执行不能造成重复扣款、重复派彩或重复反馈。
- 真实业务事实只能来自 MySQL 受约束的表和 Flyway 迁移；不能以浏览器余额、内存 Map、前端消息状态或临时日志作为事实源。
- 生产配置与密钥分离；日志、机器人公开 payload 和错误反馈不得输出密码、Token、Cookie、数据库凭据或不必要的内部用户标识。
- H2 测试只能证明测试上下文行为；MySQL 8.4、本机运行态、服务器现场和生产验证必须分别记录，不能互相替代。

## 已确认规则与当前代码差距

### 已确认规则

| 场景 | 服务端行为 | 可见范围 |
| --- | --- | --- |
| 任意用户输入 | 原文作为公开用户消息保存并广播 | 全体用户 |
| 正确且已确认的玩法 | 固定第 1 球创建注单，扣除粮草，返回扣款后余额 | 原文和反馈均对全体用户可见 |
| 普通聊天、问候、未确认玩法、错误格式 | 发布 `@展示名, 指令格式不正确!` | 全体用户 |
| 余额不足 | 直接反馈粮草不足；不创建注单、不扣款 | 全体用户 |
| 当前正在开奖 | 发布“当前正在开奖，下注无效”反馈 | 全体用户 |
| 当前期已封盘 | 发布“当前已封盘，下注无效”反馈 | 全体用户 |
| 开奖后注单结算 | 更新注单、钱包和流水，并发布该用户的结算反馈 | 全体用户 |

## 验收判定

### 通过条件

- 每一条用户输入都产生可查询的处理结果；非确认玩法不会静默成功。
- 用户原文和机器人反馈对两个不同用户均可见，刷新/重连后不重复、不丢失。
- 成功下注的注单、扣款流水、赔率快照和“剩余粮草”一致；余额不足、封盘和开奖中均不产生扣款。
- 开奖后注单状态、净盈亏、钱包派彩、流水和结算反馈一致；重复开奖或重试不会重复派彩/反馈。
- 失败反馈不泄露内部异常、用户内部 ID、凭据或数据库信息。

### 未通过条件

- 只通过 WebSocket error 给当前用户，而数据库和其他用户看不到机器人反馈。
- 前端自己计算或展示余额，或者反馈中的金额与数据库流水不一致。
- 反馈投递异常导致资金事务回滚、重复扣款、重复派彩或重复消息。
- 把 H2、浏览器本地状态、演示数据或旧版机器人调度测试写成 MySQL/服务器/生产验收。
