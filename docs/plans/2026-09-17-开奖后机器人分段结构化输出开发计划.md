# 开奖后机器人分段结构化输出开发计划

## 1. 目标

在不修改 `web` 源码的前提下，让 `DRAW_RESULT` 事件由后端按摘要、历史、获胜名单顺序输出三个独立的 `ROBOT` 消息。消息结构固定为 `xupan.chat-payload.v1`，普通事件继续使用现有纯文本消息路径。

## 2. 边界判定

- 已确认：`chat_message.payload_json` 已存在；`game_issue` 保存 8 个号码、`phase` 和 `settled_at`；`game_bet` 保存当前期注单和 `WIN/DRAW/LOSE` 结算状态。
- 已确认：结构化组件只允许 `DRAW_SUMMARY`、`DRAW_HISTORY`、`WINNER_LIST`；组件关闭时不产生对应消息；开奖消息幂等键使用事件 ID 和组件名。
- 推断：历史默认取最近 10 个已结算期；名单展示采用脱敏标识并保留演示用金额字段，便于前端消费但不宣称生产隐私规则。
- 待确认：生产环境的用户脱敏算法、投注额/净盈亏是否对聊天室可见、获胜名单是否需要聚合以及最终保留期数。
- 未执行：真实 MySQL 8.4 LTS 迁移、客户端对新组件的视觉验收、生产隐私和运营规则确认。

## 3. 实现内容

1. 新增 Flyway V14 `chat_robot_draw_component`，为已有机器人和新建机器人提供默认三段配置。
2. 新增管理员接口：
   - `GET /api/admin/robots/{robotId}/draw-components`
   - `PUT /api/admin/robots/{robotId}/draw-components`
   - 更新请求为 `{"components":[{"component":"DRAW_SUMMARY","enabled":true,"order":1},...]}`。
3. `RobotGameEventAdapter` 改为按 `issueNumber` 查询 `game_issue`，不再从事件文案解析“结果:\n”。
4. `RobotDispatchService` 在同一事务内按配置生成三个 payload；摘要、历史和名单全部来自真实仓储查询；无获胜记录返回稳定空列表和明确提示。
5. 保持 `payloadJson` 原文返回，普通事件和既有 `DRAW_RESULT` 模板继续保留纯文本 fallback。

## 4. 验证

- 自动化：机器人调度、幂等键、V14 迁移、管理 Controller 和后端全量 Maven 测试。
- 重点断言：开奖文案即使不包含号码也能从 `game_issue` 生成；默认三条消息、关闭 `WINNER_LIST` 后两条消息；每条 payload 的 schema/component/data 可识别；没有中奖投注时不伪造用户。
