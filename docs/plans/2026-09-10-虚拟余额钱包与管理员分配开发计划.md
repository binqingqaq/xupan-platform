# 虚拟余额钱包与管理员分配实施计划

> **给实施者：** 按任务顺序执行本计划。步骤使用复选框（`- [ ]`）跟踪进度；本计划只覆盖虚拟余额、管理员分配和认证用户下注闭环，不提前实施聊天室、WebSocket 或机器人。

> **本轮执行状态（2026-09-10）：** 本计划的虚拟余额钱包、管理员分配、认证用户下注、手工/自动结算、前端余额和数据库验收已完成。认证基础保持已完成；聊天室 REST、WebSocket、常驻机器人和真实支付仍未实施。

**目标：** 在已经完成的用户认证与权限基础上，为每个正式用户建立服务端管理的虚拟余额账户，由后台管理员分配额度，使用户可以使用自己的虚拟余额下注，并让分配、扣款、结算和调整全部形成可审计、可幂等、不可伪造的余额流水。

**架构：** 复用现有 `demo_user_account` 和 `demo_balance_ledger` 物理表，避免改写已经执行的 V2 迁移；通过 Flyway V8 增加正式用户关联、操作人、幂等键和注单关联字段，把这组表在领域层统一封装为“虚拟钱包”。认证用户由服务端 `AuthenticatedUser.getUserId()` 定位钱包，管理员通过受保护 REST 接口分配额度，下注和结算在同一事务中操作钱包和 `game_bet`。虚拟余额不是支付系统，不接入充值、提现、转账、代理分成或真实资金清算。

**技术栈：** Java 21、Spring Boot 4.0.8、Spring Security、Spring JDBC、Flyway、MySQL 8.4 LTS、H2 测试、JUnit、MockMvc、Vue 3、TypeScript、Vite。

## 全局约束

- 总方案：`docs/plans/2026-09-10-聊天室与常驻机器人改造方案.md`；本计划是总方案阶段 2 中“虚拟余额钱包与管理员分配”部分的独立执行计划。
- 认证基础已完成并固定为当前前置条件：`V1` 至 `V7` 已存在，不能修改或重写；V8 是本计划唯一新增的数据库迁移。
- 数据库版本固定为 MySQL 8.4 LTS；所有数据库变更必须通过 Flyway，不能手工建表或直接修改共享数据库结构。
- 当前 `demo_user_account`、`demo_balance_ledger` 和 `game_bet.user_id` 已被 V2 及现有代码使用；迁移必须保留 `DEMO-USER` 和历史注单可读性。
- 正式用户的余额是平台内部虚拟演示额度。管理员分配多少，就为该用户增加多少虚拟可用余额；该金额不表示用户充值、可提现资产或平台负债。
- 不实现充值、支付、提现、转账、代理分成、真实资金账户、第三方支付回调、支付对账或真实资金结算。
- 钱包余额、注单和结算均由服务端确定；不能信任请求体、URL、聊天帧或前端状态提供的 `userId`、`userCode`、`walletId`、`balance`、`senderId` 或 `operatorName`。
- 余额流水只追加、不更新、不删除；管理员纠正必须写新的 `ADMIN_ADJUST` 流水，不能直接覆盖余额字段。
- 管理员分配、余额调整、下注扣款和结算返还必须带幂等键或服务端可推导的唯一业务键；重复请求不得重复增加或扣减余额。
- 钱包锁定、余额校验、流水插入和相关注单写入必须处于同一数据库事务内；发生任何异常必须整体回滚。
- 钱包余额统一使用 `DECIMAL(18,2)` 和 Java `BigDecimal`，金额统一使用 `RoundingMode.HALF_UP` 保留两位小数，禁止使用 `double` 或浮点比较。
- 管理员权限仍必须经过 Spring Security authority 校验并写入 `sys_operation_log`；不能使用“管理员拥有所有权限”的代码旁路跳过审计。
- 本计划完成前不修改聊天消息表、WebSocket Handler、机器人调度器；聊天新迁移继续从 `V9` 开始，机器人迁移继续从 `V11` 开始。
- 测试环境可使用 H2，但 H2 通过不能替代 MySQL 8.4 迁移、约束和事务验证。
- 生产配置不得写入密码、Token、支付密钥、数据库凭据或真实资金配置；本计划不新增任何支付密钥配置。

### 1.4 端到端验收场景

以下场景全部通过后，才算本计划完成：

```text
管理员创建正式用户 member-a
  -> 系统为 member-a 创建 0.00 虚拟钱包
  -> 管理员分配 1000.00，钱包变为 1000.00，写入 ADMIN_GRANT
  -> member-a 登录并读取 /api/me/wallet，看到 1000.00
  -> member-a 提交 15.00 结构化下注
  -> 服务端从认证上下文定位 member-a，钱包变为 985.00，写入 BET_DEBIT
  -> 注单保存 user_id = member-a 的钱包账户 ID
  -> 开奖结算产生 42.75 返还，钱包变为 1027.75，写入 SETTLEMENT_CREDIT

  -> member-b 不能读取或调整 member-a 的钱包
```

本计划采用“分配金额增加当前虚拟余额”的语义。若管理员需要把余额纠正为某个目标值，必须计算差额并使用 `ADMIN_ADJUST`，不能用覆盖字段直接设置数据库余额。

## 2. 固定设计决策

### 2.1 虚拟钱包的身份关系

- 物理表仍为 `demo_user_account`，领域名称为 `VirtualWallet`；不在 V8 直接重命名旧表。
- 每个正式 `sys_user` 最多关联一条 `demo_user_account`，通过唯一 `sys_user_id` 实现一对一关系。
- 旧的 `DEMO-USER` 可以暂时保持 `sys_user_id IS NULL`，用于兼容历史演示数据；新正式用户不得共用该记录。
- 新钱包的 `user_code` 由服务端生成，格式固定为 `USER-<sys_user.id>`，不能使用前端提供的任意账户编码；`display_name` 初始取 `sys_user.display_name`，后续展示名称变化由独立同步逻辑处理。
- `game_bet.user_id` 在本阶段仍表示 `demo_user_account.id`，这是兼容现有外键的账户 ID，不是前端可提交的用户身份。
- 认证身份唯一来自 `AuthenticatedUser.getUserId()`；所有钱包查询必须先由 `sys_user.id` 解析到 `demo_user_account.id`。

### 2.2 钱包操作类型

| `operation_type` | 金额方向 | 触发方 | 说明 |
| --- | --- | --- | --- |
| `ADMIN_GRANT` | 正数 | `ADMIN` | 管理员给成员增加虚拟额度 |
| `ADMIN_ADJUST` | 正数或负数 | `ADMIN` | 管理员更正余额，必须写明原因 |
| `BET_DEBIT` | 负数 | 服务端 | 用户下注扣款 |
| `SETTLEMENT_CREDIT` | 正数 | 服务端 | WIN 或 DRAW 结算返还 |
| `SETTLEMENT_REVERSAL` | 按业务结果 | 服务端 | 结算撤销或补偿，首期只允许后台受控调用 |

`amount` 保存带符号的实际余额变化，`balance_before` 和 `balance_after` 保存操作前后快照。`BET_DEBIT` 的绝对值必须等于 `game_bet.stake`；结算流水的金额必须由 `SettlementService` 的结构化结果计算，不能从聊天文本或前端金额读取。

### 2.3 幂等语义

- 管理员分配和调整：客户端必须传 `idempotencyKey`；同一钱包下同一键再次请求时，如果金额、操作类型和原因一致，返回原流水；如果关键参数不同，返回 `WALLET_IDEMPOTENCY_CONFLICT`。
- 下注请求：客户端必须传 `idempotencyKey`；服务端按当前钱包账户和该键查找已有注单。参数一致时返回原注单，参数不一致返回 `WALLET_IDEMPOTENCY_CONFLICT`，不能靠每次随机生成 `betCode` 识别 HTTP 重放。
- 下注扣款：首次请求服务端生成唯一 `betCode`，扣款幂等键固定为 `BET_DEBIT:<betCode>`；下注事务失败时注单和流水一起回滚。
- 结算返还：幂等键固定为 `SETTLEMENT:<betId>`；同一注单只能有一条有效结算流水。
- 幂等键唯一性必须由数据库唯一约束提供，不能只依赖内存 Map 或前端防重复点击。

### 2.4 权限矩阵

V8 追加以下权限编码：

| 权限 | `USER` | `MODERATOR` | `OPERATOR` | `ADMIN` |
| --- | --- | --- | --- | --- |
| `WALLET_READ` | 是，只读自己 | 是，只读自己 | 否 | 是，可按管理接口读取 |
| `WALLET_GRANT` | 否 | 否 | 否 | 是 |
| `WALLET_ADJUST` | 否 | 否 | 否 | 是 |
| `WALLET_LEDGER_READ` | 否 | 否 | 否 | 是 |

权限只控制接口入口；服务层仍必须校验路径用户、钱包状态、金额、幂等键和审计参数。

### 2.5 错误码

接口和业务异常使用稳定错误码，不能把 SQL 异常或完整请求内容直接返回给前端：

| 错误码 | HTTP | 条件 |
| --- | --- | --- |
| `WALLET_NOT_FOUND` | `404` | 正式用户没有钱包或目标用户不存在 |
| `WALLET_INACTIVE` | `409` | 钱包被停用或关联用户不是 `ACTIVE` |
| `WALLET_AMOUNT_INVALID` | `400` | 金额为零、精度超过两位、超过允许范围或管理员分配为负数 |
| `WALLET_INSUFFICIENT_BALANCE` | `409` | 下注或调整后会出现负余额 |
| `WALLET_IDEMPOTENCY_CONFLICT` | `409` | 幂等键已存在但请求参数不同 |
| `WALLET_OPERATION_REPLAYED` | `409` | 已完成的下注或结算再次尝试执行 |
| `GAME_BET_USER_REQUIRED` | `401` | 下注请求没有有效服务端用户身份 |
| `AUTH_PERMISSION_DENIED` | `403` | 非授权角色访问管理员钱包接口 |

- `sys_user_id` 对历史 `DEMO-USER` 可以为空；新正式用户钱包必须非空且唯一。
- `request_idempotency_key` 对 V1/V2 历史注单允许为 `NULL`；新下注必须非空，唯一约束按 `game_bet.user_id`（钱包账户 ID）和请求键生效。
- V8 不能把 `DEMO-USER` 自动绑定给第一个管理员，也不能批量猜测历史演示账户属于哪个正式用户。

### 4.2 Repository 契约

**新建：** `server/xupan-server/src/main/java/com/xupan/server/game/repository/VirtualWalletRepository.java`

Repository 必须提供以下可测试方法，所有 SQL 使用绑定参数、显式列名和 `RowMapper`：

```java
Optional<VirtualWallet> findByUserId(long userId);
Optional<VirtualWallet> findByUserIdForUpdate(long userId);
Optional<VirtualWallet> findByAccountId(long accountId);
long createForUser(long userId, String userCode, String displayName);
Optional<WalletLedgerEntry> findLedgerByIdempotencyKey(String idempotencyKey);
WalletLedgerEntry appendAdminGrant(long operatorUserId, long targetUserId,
                                   BigDecimal amount, String reason,
                                   String idempotencyKey);
WalletLedgerEntry appendAdminAdjustment(long operatorUserId, long targetUserId,
                                        BigDecimal amount, String reason,
                                        String idempotencyKey);
WalletLedgerEntry appendBetDebit(long targetUserId, long betId,
                                 String betCode, String issueNumber,
                                 BigDecimal stake);
WalletLedgerEntry appendSettlementCredit(long targetUserId, long betId,
                                          String issueNumber,
                                          BigDecimal amount,
                                          String reason);
List<WalletLedgerEntry> findLedgerByUserId(long userId, int limit);
```

事务和锁边界固定如下：

1. `appendAdminGrant`、`appendAdminAdjustment`、`appendBetDebit`、`appendSettlementCredit` 必须只在已有事务内执行；没有事务时抛出明确异常。
2. 先按 `sys_user_id` 锁定钱包行，再读取余额和幂等流水；不能先读余额后再加锁。
3. 发现已有幂等键时，比较操作类型、金额、目标用户和原因摘要；参数一致返回原流水，参数不一致抛出 `WALLET_IDEMPOTENCY_CONFLICT`。
4. 余额不足时不插入流水、不更新余额，抛出 `WALLET_INSUFFICIENT_BALANCE`。
5. 所有余额更新同时写 `balance_before`、带符号 `amount` 和 `balance_after`；插入后校验 `balance_after >= 0`。
6. Repository 不接受前端传入的 `operatorName` 作为审计身份；操作人姓名从服务端 `sys_user` 或固定 `SYSTEM` 推导。


## 5. 游戏下注与结算改造契约

### 5.1 下注事务顺序

修改：

- `server/xupan-server/src/main/java/com/xupan/server/game/service/DemoGameService.java`
- `server/xupan-server/src/main/java/com/xupan/server/game/repository/GameDataRepository.java`
- `server/xupan-server/src/main/java/com/xupan/server/game/web/DemoGameController.java`

固定顺序：

1. Controller 从 `Authentication` 取得 `AuthenticatedUser`，只把 `userId` 传给 Service；缺少该 principal 时返回 `GAME_BET_USER_REQUIRED`。
2. Service 校验当前期状态、玩法、赔率、下注金额和用户权限。
3. Service 先用当前钱包 `accountId` 和请求 `idempotencyKey` 查询已有注单；参数一致返回原注单，参数冲突抛出 `WALLET_IDEMPOTENCY_CONFLICT`。
4. 首次请求生成 `betCode`，在当前事务中使用钱包账户 ID 和 `request_idempotency_key` 写入 `game_bet`，然后调用 `appendBetDebit` 扣款；扣款失败时事务回滚注单。
5. 钱包流水的 `related_bet_id` 指向刚创建的注单，幂等键为 `BET_DEBIT:<betCode>`。
6. 返回的 `BetView` 只使用服务端保存的注单字段，不接受客户端的余额或归属字段。

`PlaceBetRequest` 新增必填 `idempotencyKey`（`@NotBlank @Size(max = 128)`）。`GameDataRepository` 必须提供按 `accountId + idempotencyKey` 查询注单的方法，并在保存方法中显式接收该键。现有 `saveBetWithOddsSnapshot` 参数 `userId` 实际代表 `demo_user_account.id`，重命名为 `accountId`，删除无参默认重载和固定 `1L` 兼容路径，防止新增调用误用默认账户。

### 5.2 手工开奖结算

修改：`server/xupan-server/src/main/java/com/xupan/server/game/service/DemoGameService.java`

每个待结算注单按 `bet.userId` 查询其钱包账户，不能使用固定账户：

1. 结构化调用 `SettlementService.settle(...)` 计算结果。
2. 在同一事务中执行 `settleBetOnce(bet.id, settlement)`。
3. 对 `WIN` 和 `DRAW` 通过 `appendSettlementCredit(bet.userId, bet.id, issue, payout, reason)` 写入钱包；`LOSE` 不增加余额，但注单结算仍必须完成。
4. 结算幂等键使用 `SETTLEMENT:<betId>`；重复开奖不能重复返还。
5. 结算异常必须回滚本次开奖事务，不能出现注单已标记结算但余额未返还的状态。

### 5.3 自动轮期结算

修改：`server/xupan-server/src/main/java/com/xupan/server/game/service/自动轮期服务.java`

- `finalizeIssue` 不再注入或调用 `DemoAccountRepository.DEFAULT_USER_CODE`。
- 自动结算读取每条注单的账户 ID，调用统一的 `VirtualWalletService`/Repository 结算方法。
- 自动轮期与手工开奖使用相同的 `SETTLEMENT:<betId>` 幂等规则；手工开奖和自动开奖不能对同一注单重复返还。
- 轮期事件 `ISSUE_STARTED`、`BETTING_CLOSED`、`DRAW_RESULT` 的唯一性语义不变；钱包流水不写入 `game_issue_event`，只通过 `issue_number` 关联。
- 自动轮期没有当前在线用户时仍应完成钱包结算；钱包操作不依赖 WebSocket 或聊天室。

### 5.4 当前余额展示

`DemoGameService.GameView.account` 在兼容阶段可以保留响应字段，但内容必须来自当前认证用户的钱包；不能继续显示固定 `DEMO-USER`。若当前接口用于后台或未带用户场景，应拆分为：

- 当前期公共数据：不包含某个用户的余额；
- `/api/me/wallet`：只返回当前认证用户余额；
- 管理员钱包接口：按权限读取成员余额。

## 11. 完成标准与移交

### 11.1 本计划完成标准

- 正式用户与虚拟钱包一对一关联，钱包余额初始为 `0.00`。
- 只有 `ADMIN` 可以给成员分配或调整虚拟余额；操作有服务端权限检查和审计。
- 用户只能查看自己的余额和流水摘要；管理员可以按权限查看成员钱包和完整流水。
- 用户下注由认证身份定位钱包，不能使用固定 `DEMO-USER` 或客户端用户字段。
- 下注扣款、注单保存、开奖结算和流水写入具备事务一致性和幂等性。
- 手工开奖和自动轮期结算使用同一钱包规则，重复结算不会重复加钱。
- 所有余额变化都有 `balance_before`、`amount`、`balance_after`、操作类型、原因、关联注单/期号和时间。
- H2、MySQL 8.4、后端全量测试和前端类型/构建验证结果均有记录。
- 没有实现真实支付；文档、界面和接口名称都不会把虚拟余额描述为现金或可提现余额。

### 11.2 移交给聊天室阶段

钱包完成后，聊天 V9/V10 只能依赖这些稳定能力：

- `GET /api/me/wallet` 返回当前认证用户的虚拟余额摘要；
- `VirtualWalletService.getForCurrentUser(userId)` 获取服务端钱包；
- 游戏下注只能调用结构化 Service，不从聊天文本扣款；
- 聊天消息可以引用 `bet_id` 和结算摘要，但不能保存或解释余额变化；
- 机器人没有 `sys_user` 钱包、不能调用管理员分配接口、不能写 `BET_DEBIT` 或 `game_bet`；
- 聊天从 V9 开始，机器人从 V11 开始，不得复用 V8 或重新设计钱包归属。

## 12. 风险和处理顺序

1. **旧演示账户身份固定：** 先完成 V8 关联和当前用户钱包查询，再修改下注；任何测试失败都不能通过继续使用 `DEMO-USER` 来绕过。
2. **历史表兼容：** 不重写 V2；使用可为空的新增字段兼容历史流水，先在 H2 和 MySQL 8.4 独立库验证约束。
3. **扣款和注单不一致：** 把保存注单、扣款、流水写入同一个 Spring 事务；任何跨事务事件只能在后续 outbox 阶段考虑。
4. **重复分配或结算：** 管理员请求使用客户端幂等键，下注/结算使用服务端业务键，数据库唯一约束是最终保障。
5. **并发余额竞争：** 钱包行必须 `FOR UPDATE` 锁定；不能只依赖 Java `synchronized`，因为多实例会失效。
6. **管理员越权：** 新接口按 `WALLET_*` 权限保护，旧 `/api/demo/admin/**` 不能保留不受控的余额旁路。
7. **虚拟余额误作真实资金：** 接口、数据库字段、前端文案和日志统一使用“虚拟余额/演示余额”，并在上线验收中明确未接入支付。
