# 后台赔率限额配置与下注校验实施计划

## 1. 计划状态

- 状态：本机实现和验证完成；服务器、生产现场和分布式并发锁未纳入本阶段。
- 日期：2026-09-24
- 所属模块：[运营后台与报表](../业务模块/06-运营后台与报表.md)、[期号玩法下注与结算](../业务模块/03-期号玩法下注与结算.md)、[聊天室与实时消息](../业务模块/04-聊天室与实时消息.md)
- 关联模块：虚拟积分钱包、玩家分类、机器人反馈。
- 目标：让后台顶部的`赔率`、`特码赔率`、`特码返水`可编辑并持久化，`限额`通过弹窗配置，并在下注入口按单个玩家当前期累计执行限额校验。

## 2. 用户已确认规则

- 后台顶部`赔率`当前只保存和展示，不参与赔率或结算计算。
- 后台顶部`特码返水`当前只保存和展示，不参与积分计算。
- `特码赔率`修改后需要保存，并作为特玩法的实际赔率。
- 顶部输入不设置确认按钮，输入完成、失焦或按回车时自动保存，下次登录保持。
- `限额`不是输入框，点击后弹出限额配置窗口，所有字段不能为空。
- 所有限额为整数，不允许小数；客户端和后端都要校验。
- 限额按单个玩家、当前期累计计算，取消注单不占用额度。
- `玩家最高注额`按单个玩家、当前期累计最高额度处理。
- `玩家最小注额`按每一笔单注最低金额处理。
- 超过限额或低于最低注额时，只拒绝对应那一项；同一组合中的其他合法项仍然可以下注。
- 机器人反馈使用明确原因、上限和剩余可下额度。

## 3. 限额口径

| 字段 | 口径 |
| --- | --- |
| 特码限额 | 单个玩家当前期`特`累计上限 |
| 单场总限额 | 单个玩家当前期所有玩法累计上限 |
| 正限额 | 单个玩家当前期`正`累计上限 |
| 角限额 | 单个玩家当前期`角`累计上限 |
| 念限额 | 单个玩家当前期`念/严`累计上限 |
| 通限额 | 单个玩家当前期`通`累计上限 |
| 车限额 | 单个玩家当前期`车`累计上限 |
| 单双限额 | 单个玩家当前期`单`和`双`共享累计上限 |
| 大小限额 | 单个玩家当前期`大`和`小`共享累计上限 |
| 番限额 | 单个玩家当前期`番`累计上限 |
| 加限额 | 单个玩家当前期`加`累计上限 |
| 玩家最高注额 | 单个玩家当前期累计最高额度 |
| 玩家最小注额 | 每一笔单注最低金额 |

`通限额`同时覆盖`通`和`无`两类排除玩法：两者都是“按剩余番值和”结算的组合玩法，且后台没有单独的无限额字段。该归并属于实现口径，若后续需要拆分必须同时修改配置表、后台弹窗、校验和文档。

## 4. 数据与接口设计

### 4.1 数据来源

- 新增 Flyway `V30`：单行配置表 `game_betting_config`，`id = 1`，保存展示字段和 13 项限额，用 `CHECK` 约束保证展示值非负、限额为正、最小注额不大于最高注额。
- `特码赔率`继续写入已有 `game_odds` 的 `SPECIAL` 行，保存的是特玩法实际赔率；`赔率`和`特码返水`只落在配置表。
- 额度占用事实来自 `game_bet`：按账号和当前期份汇总，排除 `settlement_status = 'CANCELED'`。
- 不新增第二套余额、注单或统计事实源。

### 4.2 接口

```text
GET /api/admin/player-desk/betting-config
PUT /api/admin/player-desk/betting-config/display
PUT /api/admin/player-desk/betting-config/limits
```

权限：

- 必须已认证。
- 必须具备 `USER_MANAGE`。
- 普通玩家访问返回 403。

### 4.3 校验流程

```text
下注请求
  -> 幂等重放检查
  -> 阶段检查（封盘/开奖中整批拒绝）
  -> 赔率读取和玩法参数校验
  -> 读取该账号当前期已占用额度
  -> 逐项校验最低注额、玩家最高注额、单场总限额和玩法限额
  -> 只有合法项保存注单、扣减余额并发布反馈
```

- 限额校验发生在任何写入之前，被拒项不产生注单、不扣余额、不占额度。
- 组合下注中每一项单独校验，同一批次中先通过的项已经计入额度，后续项按剩余额度判断。
- 限额拒绝使用独立的 `BetLimitExceededException` 并标注不参与回滚，避免把同一批次的其他合法项整体回滚。
- 其他失败（封盘、开奖中、余额不足、玩法参数非法）仍按整批拒绝处理，保持既有语义。

### 4.4 并发口径

限额是“先读已占用额度、再写入”的判断，同一玩家两笔请求同时进入时可能都读到旧值。当前分两条路径处理：

- 聊天室路径（玩家与托的正式下注入口）：`ChatMessageService` 的事务对 `chat_room` 取 `FOR UPDATE` 行锁并持有到提交，所以同一大厅的消息按提交顺序串行，限额判断不会读到未提交的旧值。该保护来自数据库行锁，不依赖单实例。
- 直连下注接口：`POST /api/demo/game/bets` 和 `POST /api/admin/test-players/{userCode}/bets` 没有房间行锁，改由 `PlayerBetLock` 按玩家加锁，并由控制器把加锁范围包到事务提交之外，保证同一玩家串行。该锁是实例内的，多实例部署前这两个接口仍需要数据库行锁或分布式锁。

两条路径都以 `game_bet` 的当前注单为唯一事实源，不缓存额度，也不新增额度表。

## 5. 前端行为

- 顶部状态赔率栏的`赔率`、`特码赔率`、`特码返水`改为输入框，`change`、回车和失焦触发自动保存。
- 保存前前端校验：`赔率`、`特码返水`为不小于 0 的整数；`特码赔率`为不小于 1 且最多三位小数的数字。校验失败时回滚输入并显示原因。
- `限额`改为文本按钮，点击弹出“限额配置”对话框，13 个字段全部必填且必须为正整数，最小注额不能大于最高注额。
- 对话框保存成功后关闭并提示“限额配置已保存”；失败时在对话框内显示原因，不改变已保存值。
- 配置未加载完成时输入框仍可操作，提交会先补拉配置。

## 8. 完成标准

- 后台可以读取并修改`赔率`、`特码赔率`、`特码返水`和 13 项限额，刷新和重新登录后保持。
- 限额按单个玩家当前期累计执行，取消注单不占额度；同一玩家的并发请求不会读到未提交的旧额度。
- 超限或低于最低注额时只拒绝对应项，其他合法项照常进入钱包、注单和聊天反馈链路。
- 机器人反馈包含拒绝原因、上限值和剩余可下额度。
- 文档、测试和浏览器证据能对应到当前实现，不把本机结果写成服务器或生产结论。
