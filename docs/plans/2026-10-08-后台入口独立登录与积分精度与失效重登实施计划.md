## 2. 现状事实（本次要改的东西，全部带证据）

### 2.1 权限牌：谁现在能进哪个入口

| 账号类型 | 关键权限 | 进 `/console` | 进 `/platform-admin` |
| --- | --- | --- | --- |
| `ADMIN` 超管 | `USER_MANAGE`、`PLATFORM_HOME_READ`、`AGENT_MANAGE`、`AGENT_CONSOLE_READ`、`AGENT_PLAYER_MANAGE`、`MACHINE_MANAGE`… | ✅ 靠 `USER_MANAGE` | ✅ 靠 `PLATFORM_HOME_READ` |
| `SUB_ACCOUNT` 子账号 | `PLATFORM_HOME_READ`、`GAME_CURRENT_READ`、`MACHINE_MANAGE`、`REPORT_READ`、`DRAW_HISTORY_READ`、`PLATFORM_PASSWORD_MANAGE`（V49）+ `AGENT_CONSOLE_READ`、`AGENT_PLAYER_MANAGE`（V56） | ✅ 靠 `AGENT_CONSOLE_READ` | ✅ 靠 `PLATFORM_HOME_READ` |
| `AGENT` 机器账号 | `AGENT_CONSOLE_READ`、`AGENT_PLAYER_MANAGE`（V34/V54）、`GAME_CURRENT_READ`（V57） | ✅ | ❌ → 落到 `/forbidden` |

证据：`V49__建立子账号登录与数据范围.sql:28-33`、`V56__增加机器级报网线路与子账号运营权限.sql:51-55`、`V34__建立代理组织与代理权限.sql:73-81`、`V57__补齐机器账号查看当前期权限.sql`、`web/src/consoleScope.ts:7`。

**结论：超管与子账号两个入口都放行 → 这就是"怎么敲都能进"的直接原因。**机器账号进平台后台才落 `/forbidden`。

### 2.2 会话事实：一个浏览器只有一份"后台登录态"

- 三个后台身份（超管/子账号/机器账号）都走同一个 `POST /api/auth/login`，写同一个 HttpOnly 刷新 Cookie `xupan_refresh`，有效期 30 天：
  `AuthController.java:29`（`REFRESH_COOKIE = "xupan_refresh"`）、`:131-136`（`httpOnly/secure/sameSite=Strict/path=/api/auth/maxAge=30d`）、`TokenService.java:31`。**Cookie 里没有"入口"这个维度。**
- 前端使用端只有两种：`api.ts:157` `export type AuthAudience = 'ADMIN' | 'PLAYER'`；`:470` 登录时硬编码 `setAuthAudience('ADMIN')`。
- 路由守卫把 `/console` 与 `/platform-admin` 都算作 `'ADMIN'`：`main.ts:71-74 requiredAudience()`。
- 于是"敲 `/console`"的过程是：守卫 → `restoreSession('ADMIN')` → `POST /api/auth/refresh`（浏览器自动带 Cookie）→ `GET /api/auth/me` → 权限判定 → 放行。**只要 Cookie 没过期，永远不需要再输密码**（关浏览器、开新标签页都一样）。
- 退出也是共用的：`api.logout()`（`api.ts:482-491`）清的是同一个 Cookie，所以在 `/console` 退出会把 `/platform-admin` 一起踢掉。
- 两个登录页还会"自动把人送进去"：`LoginView.vue:52-55`、`PlatformAdminLoginView.vue:41-44` 的 `onMounted` 一旦 `restoreSession` 成功就 `router.replace`，导致想看登录表单也看不到。

### 2.3 `/forbidden` 是"权限不足"页，不是"会话失效"页

- 守卫三条分支：`main.ts:96-108` —— ①无会话 → 本入口登录页（对）②`scope === 'CHAT_ONLY'` → `/forbidden` ③权限不足 → `/forbidden`。
- 真正"会话失效"的路径是 `main.ts:110-119` 的 401 监听器 → 跳本入口登录页带 `reason=expired`（已经是对的）。
- `/forbidden` 页面写死一个按钮 `router.replace('/room')`：`ForbiddenView.vue:11-13`。它来自 2026-09-23 的"管理员标签页被玩家会话覆盖"修复，当时"返回聊天室"是对的出路（见该验收记录），后来被复用成了所有权限不足的公共出口。
- 守卫跳 `/forbidden` 时**不带 `reason` 也不带 `redirect`**，所以 `LoginView.vue:20-26` 里 `reason === 'forbidden'` 的分支是死代码；重新登录也回不到原目标页。

### 2.5 玩家上下分的积分来源（搬迁的核心风险点）

`PlayerDeskAdminService.grant()/adjust()`（`:357-382`）：

```java
if (scope instanceof PlayerDeskScopeService.Scope.Machine) {
    agentConsoleService.changeScore(operator, userId, "TOP_UP", amount, key);   // 机器账号：扣自己机器积分
} else {
    walletService.grant(operator, userId, amount, reason, key);                 // 超管/子账号：不扣任何池
}
```

- 机器账号（MACHINE）：`AgentConsoleService.changeScore()` 会 `changeMachineScore(-amount)` 并 `walletService.grant(+amount)`，托（BOT）不联动（`AgentConsoleService.java:141-158`）。流水类型 `PLAYER_TOP_UP` / `PLAYER_DOWN` 已存在（`V60:41-42`）。
- 超管/子账号（GLOBAL/GROUP）：**直接给玩家钱包加分，不减任何机器或子账号积分池**。
- BY220 里没有"超管直接给玩家发分"这条链路：分只能 `子账号池/超管 → 机器（rbUpdown）→ 玩家（robot.php）`。所以**现状 GLOBAL/GROUP 的"凭空发分"是既有偏离**，一旦把工作台搬到平台后台、超管开始大量使用，就会造成"机器池 + 玩家钱包 总数对不平"。

### 2.6 积分精度三处不一致

| 路径 | 超精度（如 0.001）的行为 | 证据 |
| --- | --- | --- |
| 玩家钱包（`/api/.../wallet`、玩家上下分） | **已经正确**：`scale() > 2` → 400 `WALLET_AMOUNT_INVALID`「金额格式无效」/「金额最多保留两位小数」 | `VirtualWalletService.java:328-337` |
| 机器/子账号**目标值**（建机器、改机器积分、建子账号初始积分） | `value.setScale(2)`（无舍入模式）→ 抛 `ArithmeticException` → 全局兜底 **500**`AUTH_INTERNAL_ERROR` | `AgentLedgerService.java:308-314`、`AuthenticationExceptionHandler.java:148-156` |
| 子账号**上分/下分**、机器给玩家上下分 | `setScale(2, HALF_UP)` → **静默**把 0.001 变成 0.00，然后当作"本次不改动" | `AgentLedgerService.java:123-124,139`、`PlatformAdminService.java:612-620`、`AgentConsoleService.java:359-368` |

前端：机器管理「积分」与子账号「积分」都是 `step="0.01"`（`PlatformAdminMachines.vue`、`PlatformAdminSubAccounts.vue:206`），但子账号「上分/下分」只有 `type="number"`（`:208-209`），默认 `step=1` → **浏览器原生校验会把 0.1/0.01 直接拦下**。BY220 的 `sub/form.html:29,35` 同样没有 step，但它用 layui + `$.post` 取值，不走原生校验，所以 BY220 反而能提交——这是"照抄表单属性却换了提交机制"造成的反向差异。

BY220 精度事实：`x_admin.score` / `x_robot.score` 是 `DECIMAL(30,6)`（`local/schema-base.sql:44,534`），`rbUpdown()`（`application/common.php:3707-3724`）与 `Users.php:62-72` 全程没有 `intval/round` → **BY220 支持到 6 位小数**。保持 2 位是【已确认】的收窄，需登记为偏差。

### 3.3 权限与会话模型

- **入口权限**：`/console` 的路由门禁由"权限命中"改为"**角色命中**"：`user.roles` 含 `AGENT` 且不含 `ADMIN`/`SUB_ACCOUNT`。
- **权限收敛（迁移 V76）**：从 `ADMIN`、`SUB_ACCOUNT` 角色**撤销** `AGENT_CONSOLE_READ`（BY220 里 `robot.php` 只认 `x_robot`，`x_admin` 不含此域）。保留 `AGENT_PLAYER_MANAGE` 给两者，因为 `/platform-admin` 的玩家工作台要用它。
- **API 门禁调整**：`/api/admin/player-desk/**` 由 `USER_MANAGE | AGENT_CONSOLE_READ` 改为 `USER_MANAGE | AGENT_PLAYER_MANAGE | AGENT_CONSOLE_READ`（`SecurityConfig.java:110-111`），否则子账号撤权后会失去工作台。`/api/agent/**` 保持只认 `AGENT_CONSOLE_READ` → 收敛后只有机器账号能调。
- **会话入口维度（迁移 V75，阶段 5）**：`auth_session` 增列 `entry`（`PLATFORM` / `CONSOLE`），登录按请求头写入；刷新 Cookie 一入口一个：`xupan_refresh`（平台，沿用旧名）/ `xupan_console_refresh`（新增）/ `xupan_player_refresh`（已有）；刷新时校验 `entry` 一致，不一致返回 401 并只清该入口 Cookie；**退出只清当前入口**。
- **不复现**：BY220「登录 admin 清空整个 session 顺带踢掉 robot」——独立 Cookie 天然不会发生，登记为已确认差异。
- **超管不会失去运营入口（工头 2026-10-08 补）**：V76 只撤销 `AGENT_CONSOLE_READ`，**不动** `AGENT_PLAYER_MANAGE`；而 `ADMIN` 的 `AGENT_PLAYER_MANAGE` 来自 `V54__增加代理玩家管理权限.sql:7-15`（与本机 MySQL 实测一致），**不属于**项目里"可由子账号开关动态摘除"的那一个（被动态摘除的是子账号的 `SUB_ACCOUNT_MANAGE`，见 [子账号按 BY220 补齐验收记录](../验收记录/2026-10-07-子账号BY220补齐验收记录.md) §5「有意偏离 3」）。因此 `/platform-admin/player-workbench` 的门禁是"`USER_MANAGE` **或** `AGENT_PLAYER_MANAGE`"，超管恒有后者。

### 3.4 失效与无权限的跳转规则

| 情况 | 跳转 | 文案 | 登录后 |
| --- | --- | --- | --- |

### 3.5 积分精度与上下分口径

- 全站金额/积分统一 **2 位小数**，**超精度一律 400 明确报错**，禁止静默舍入、禁止 500。
- 抽一个共享口径（复用 `VirtualWalletService.normalizedAmount` 的既有正确实现），代理账本三处入口（机器/子账号目标值、子账号上分/下分、机器给玩家上下分）全部复用它。
- 子账号「上分/下分」输入框补 `step="0.01" min="0.01"`（前端体验层），后端校验才是防线。
- BY220 的 6 位小数收窄为 2 位，登记为已确认偏差。

**Q1=A1 的实现口径**（把"凭空发分"改成"沿机器池流转"）：

- 规则：平台侧（`GLOBAL` 超管 / `GROUP` 子账号）给**普通玩家**上分 → **扣该玩家所属机器**（`demo_user_account.agent_id`）的积分；下分 → **回补同一台机器**。托（`BOT`）不联动机器池，与 BY220 `robot.php` 一致。
- **扣哪台机器按"玩家归属"自动判定，不要求操作者另选机器**：玩家已经归属某台机器，若让操作者另选，一旦选错就会扣错池、造成跨机器串账。平台直属玩家（`PLATFORM_DIRECT`）扣平台直属机器那本账，链路一致。
  - 若使用者坚持"操作者显式选机器"，则必须校验 `所选机器 == 玩家归属机器`，否则 400；此变体请在评审时指出。
- 实现落点：在 `AgentConsoleService` 增加一个"按显式机器 + 显式操作者"的上下分方法（现方法是从操作者反查机器，平台账号查不到 `agent` 行），由 `PlayerDeskAdminService.grant()/adjust()`（`:357-382`）在非 `MACHINE` 范围时改调它；流水类型沿用已存在的 `PLAYER_TOP_UP` / `PLAYER_DOWN`（`V60:41-42`），**不需要新迁移**。
- 机器池不足时按 BY220 文案拒绝（`AGENT_SCORE_INSUFFICIENT`：您的账号剩余积分不足以完成本次上分！），且**余额与流水都不变**。
  - **文案口径（工头 2026-10-08 补）**：BY220 那句是**机器账号给自己机器上分**的自述口吻（`application/rbt/controller/Index.php:618-620`）。**机器端（`MACHINE` 范围）继续原文照抄**以保持平移；**平台侧（`GLOBAL`/`GROUP`）改用「该玩家所属机器的积分不足以完成本次上分！」**——因为 BY220 没有平台侧路径，此处"你的账号"会被误读成操作者。错误码两个路径都用 `AGENT_SCORE_INSUFFICIENT`，不改协议。
- 副作用（要写进验收记录）：机器账号不再拥有"平台代发"的豁免，平台侧上下分会真实消耗机器积分，因此超管需要先用「机器管理」给机器上分（等价 BY220 `rbUpdown`）。

## 9. 风险与回滚

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| 超管丢失日常运营入口 | 阶段 3 未完成就做阶段 4，超管将无法操作玩家 | **强制顺序**：3 → 4；阶段 4 的前置条件是阶段 3 已通过浏览器人工验收 |
| 玩家上下分账本对不平 | 现状 GLOBAL/GROUP 是"凭空发分"；搬迁后被高频使用会放大差异 | 【Q1=A1】改为按玩家归属机器扣/回积分，并补账本用例（平台侧上分 → 机器池减少、托不联动、池不足拒绝且都不变） |
| 平台上分开始消耗机器池 | A1 之后超管/子账号不能再"凭空发分"，给玩家加分前需要机器池里有分（等价 BY220 的 `rbUpdown` 前置） | 这是**预期行为**；在验收记录与业务模块基线写明"分只能沿 子账号池/超管 → 机器 → 玩家 流转"，并在机器池不足时给出 BY220 文案提示 |
| 引用面广 | `/console` 被 15 个前端文件、30 个文档引用；`AGENT_CONSOLE_READ` 被 51 处引用（含已构建的前端 bundle） | 一次性成批改；阶段 6 全文复查 `grep '/console'`、`grep 'AGENT_CONSOLE_READ'` |
| 老会话兼容 | 已存在的 30 天 `xupan_refresh` 在阶段 5 后只对平台入口有效 | 默认 `entry='PLATFORM'`，代理端提示重登一次；在验收记录写明 |
| 回滚 | 迁移 V75/V76 都是"加列/删授权" | 前向修复：再加迁移恢复授权、`entry` 列保留但不再校验；代码回滚需同时回滚前端门禁，避免"门禁严了但权限没恢复"的中间态 |
