# 统一玩家工作台与托自动行为闭环实施计划

> **给实施者：** 按任务顺序执行本计划。步骤使用复选框（`- [ ]`）语法跟踪进度。每个任务完成后先运行该任务的专项验证，再进入下一个任务。

**目标：** 将普通玩家和托集中到一个左右分栏的后台玩家工作台，并让托以明确的测试玩家身份，像普通玩家一样发送聊天指令、随机下注、接受机器人反馈、参与开奖结算并留下可审计的虚拟积分流水。

**架构：** 前端继续复用现有 Vue 路由和管理员权限，在当前测试玩家页面基础上改造成统一玩家工作台；普通玩家创建调用现有 `UserAdminService.createUser`，托创建调用现有测试玩家创建链路，统一查询层只负责拼接列表、统计和详情。托行为使用独立的持久化配置和动作表，由单实例定时调度器生成并执行动作；消息统一进入 `ChatMessageService.sendUserMessageWithOutcome`，下注、扣分、开奖、结算和机器人反馈继续使用正式业务链路。

**技术栈：** Java 21、Spring Boot 4.0.8、Spring Security、JDBC、Flyway、MySQL 8.4 LTS、H2 测试库、Vue 3、TypeScript、Vite、Vitest、现有聊天室 REST/WebSocket 和机器人 outbox 机制。

## 全局约束

- 所有金额均为虚拟积分；界面、接口、数据库字段和文档不得出现充值、提现、现金、真实资金流水或可兑换资产语义。
- 普通玩家继续使用现有 `/api/admin/users` 和 `UserAdminService.createUser` 创建逻辑，不复制一套用户认证、密码哈希或角色分配逻辑。
- 托是 `TEST` 身份和 `BOT` 玩家分类的组合，不是 `chat_robot`；托不能通过普通登录入口登录，但可以由服务端以测试玩家身份发送消息和下注。
- `test1`、`test2` 以及现有普通用户默认归类为 `NORMAL`；不能根据用户名、昵称或头像推断玩家类型。
- 总积分、普通玩家数量和托数量必须由服务端全量聚合返回，不能使用当前分页数据或前端累加作为事实源。
- 余额增加、余额扣减、重置、下注扣分和开奖派彩都必须写入现有不可变虚拟钱包流水，并带操作原因、操作人和幂等键。
- 托的每一次消息和下注动作必须有持久化动作记录；重试不能重复写聊天消息、重复下注、重复扣分或重复派彩。
- 普通聊天、玩法文本、错误指令和下注反馈必须对聊天室其他用户可见；托动作不能触发机器人反馈循环。
- 新数据库结构只能通过 Flyway 迁移增加；生产 SQL 按 MySQL `8.4 LTS` 兼容性验证，H2 只作为测试证据。
- 管理端接口继续受 `USER_MANAGE` 权限保护；托行为配置、启停、上/下分和手工触发都记录操作审计。
- 先完成一个托的完整可验收纵向流程，再扩展多个托和更复杂的随机策略；不能先做没有真实后端闭环的静态假界面。
- 不提交密码、Token、本机数据库凭据、完整访问 URL、外部真实数据或本地环境密钥。

## 已确认范围

### 统一工作台

- 页面采用截图红框区域的左右布局：左侧为统计、筛选、创建入口和玩家列表；右侧为当前选中玩家的详情与操作。
- 左侧统计展示：`总积分`、`普`、`托`。
- `总积分`为当前列表统计范围内所有玩家的积分总和；默认范围为所有未删除的 `NORMAL` 与 `BOT` 玩家，不受分页影响。
- `普`为 `player_kind = NORMAL` 的玩家数量；`托`为 `player_kind = BOT` 的玩家数量。
- 普通玩家和托共享列表、选中态、头像、昵称、状态、积分、流水和下注记录展示；托额外展示自动行为配置和最近动作。
- 旧的普通用户创建弹窗不再作为独立入口，但其后端创建规则、用户名唯一性、密码策略和角色初始化保持不变。
- 旧的测试玩家页面入口 `/admin/test-players` 保留并改造成唯一的“玩家工作台”前端入口，页面标题和导航同步更新；本期不新增第二个前端路由，避免出现两个维护入口。

### 普通玩家

- 创建普通玩家使用现有字段：`username`、`displayName`、`rawPassword`。
- 普通玩家可以通过现有登录入口登录并进入聊天室。
- 普通玩家的积分调整使用统一工作台的积分操作区，但仍调用现有虚拟钱包服务。
- `test1`、`test2` 等已有普通账号必须能在统一列表中显示，不需要重新创建或迁移用户名。

### 托玩家

- 创建托使用 `userCode`、`displayName`、可选头像；不要求可登录密码。
- 托数据库身份为 `sys_user.user_type = 'TEST'`、`demo_user_account.identity_type = 'TEST'`、`demo_user_account.player_kind = 'BOT'`。
- 托需要手动启用后才执行自动行为；创建后、停用后默认不自动发送和下注。
- 第一版支持每期固定下注单数 `betsPerIssue`，每期实际数量以数据库 `game_bet` 和动作表核对为准。
- 第一版支持在配置范围内随机生成玩法文本和积分金额，生成结果先持久化再执行。
- 第一版支持普通文本、问候、错误/未确认指令和正确下注文本；正确下注只生成当前已确认且 `BetTextParser` 能解析的玩法。
- 托发送消息必须调用 `ChatMessageService.sendUserMessageWithOutcome`，不能直接写 `chat_message`，也不能绕过 `DemoGameService.placeBetForUser`。
- 托下注沿用当前第 1 球、封盘校验、余额扣款、赔率快照、开奖结算、中奖派彩和 `BetSettlementCompletedEvent`。
- 托的机器人反馈必须进入现有 `chat_message`、`chat_outbox` 和实时广播链路，断线用户通过历史游标补齐。

### 暂不纳入

- 不实现充值、提现、支付、转账、代理分成、报网、外部链接、二维码、现金结算或真实开奖源。
- 不把托并入 `chat_robot` 表或机器人管理页面；系统机器人仍然是无钱包、无下注、无登录权限的响应者。
- 不实现复杂的概率模型、盈利控制、跨期资金策略、人工干预开奖结果或隐藏身份展示。
- 不在第一版增加多实例调度、Redis/MQ、跨节点锁；当前按单服务器、单实例设计，但动作表和租约字段必须支持重启恢复。
- 不物理删除玩家；删除按钮如需保留视觉位置，只映射为停用或归档并保留历史事实。

## 数据与接口契约

### 玩家分类

在 `demo_user_account` 增加稳定分类字段，不修改 `sys_user.user_type` 的安全含义：

```sql
player_kind VARCHAR(16) NOT NULL DEFAULT 'NORMAL'
CHECK (player_kind IN ('NORMAL', 'BOT'))
```

分类规则：

```text
sys_user.user_type = REAL  + demo_user_account.player_kind = NORMAL -> 普通玩家
sys_user.user_type = TEST  + demo_user_account.identity_type = TEST
                              + demo_user_account.player_kind = BOT -> 托
identity_type = DEMO 或无玩家钱包的系统账号 -> 不计入普/托统计
```

现有 `test1`、`test2` 通过 `user_type = REAL` 和默认 `player_kind = NORMAL` 进入普通玩家列表。V15 已存在的测试玩家记录在 V16 中回填为 `BOT`。

## 风险与处理

| 风险 | 处理方式 |
|---|---|
| 将托错误实现为 `chat_robot` | 以 `sys_user + demo_user_account + player_kind=BOT` 建模，系统机器人继续只负责响应。 |
| 前端显示的总积分与数据库不一致 | 使用独立聚合 SQL，禁止使用当前页数组累加。 |
| 随机行为重试后生成不同指令 | 动作生成后立即持久化 `source_text`，重试只执行原动作。 |
| 自动行为绕过正式下注链路 | 所有托动作调用 `ChatMessageService.sendUserMessageWithOutcome`。 |
| 机器人反馈触发托再次行动 | 托只读取自身调度配置，不消费 `ROBOT` 消息。 |
| 服务重启导致动作丢失或重复 | `PENDING/PROCESSING` 租约、唯一幂等键和动作关联 ID。 |
| 现有普通用户页面被破坏 | 保留 `/admin/users` 和旧 `/admin/test-players` 路径，统一工作台先作为门面接入。 |
| 界面复制了现实资金语义 | 统一使用“积分”、虚拟流水和测试身份文案，删除 `¥`、充值、提现等表达。 |
| 只验证 H2 就宣称上线可用 | 验收记录分开列出 H2、本机 MySQL、浏览器、服务器现场和生产验证。 |
