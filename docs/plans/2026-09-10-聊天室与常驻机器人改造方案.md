# 聊天室与常驻机器人改造实施计划

> **给实施者：** 按任务顺序执行本计划。步骤使用复选框（`- [ ]`）语法跟踪进度；本文件是聊天室、用户系统和机器人能力的统一实施入口。阶段 1 已执行完成，阶段 2 至阶段 6 尚未实施。

**目标：** 将当前前端本地演示消息改造成具备正式用户身份、角色权限、服务端持久化、多用户实时通信、消息治理和常驻机器人的可上线聊天室。

**架构：** 以 Spring Security 建立服务端身份边界，以 MySQL 8.4 LTS 保存用户、权限、会话审计、虚拟余额账本、聊天消息和机器人配置；以 REST 负责登录、余额查询、管理员分配、历史消息和管理操作，以 WebSocket 负责实时消息。单实例开发阶段可以不依赖 Redis，但正式多实例部署必须使用 Redis 完成会话共享、限流、WebSocket 跨实例广播和调度锁。

**技术栈：** Java 21、Spring Boot 4.0.8、Spring Security、Spring JDBC、Flyway、MySQL 8.4 LTS、H2 测试、Vue 3、TypeScript、Vite、WebSocket；若依仅作为模块和安全设计参考，不作为当前项目依赖。

## 全局约束

- 当前项目的事实以源代码、配置、Flyway 迁移和测试结果为准；本计划中的内容在完成代码和测试前均属于计划，不代表已实现。
- 数据库版本固定为 MySQL 8.4 LTS；所有数据库变更使用 Flyway，不能依赖手工建表。
- 保留当前首期玩法、自动轮期和演示资金的业务边界；聊天消息不写入 `game_issue_event`，机器人不拥有真实账户、不扣余额、不产生真实 `game_bet`。
- 当前下注余额是平台内部虚拟演示余额：由后台管理员给正式成员分配，分配多少即形成多少可用虚拟额度；不接入充值、支付、提现、转账、代理分成或任何真实资金通道。
- 虚拟余额必须有服务端账户和不可变流水；用户下注扣减余额，结算按现有结构化规则返还虚拟余额，所有余额变化必须能追溯到管理员分配、注单或结算。
- 所有用户显示名称、头像、消息发送者类型和权限均由服务端确定，不能信任前端传来的 `sender_id`、`sender_name`、`avatar_url` 或消息类型。
- 默认拒绝未认证请求；只有明确列出的登录、刷新、静态资源和健康检查可以匿名访问，聊天室历史也必须经过用户认证和房间权限校验。
- 生产配置不得提交密码、Token、数据库凭据、Redis 凭据或带访问作用的完整 URL。
- 若依和 `caipiaowan-main` 目录只读参考，不复制其中的密码、Token、真实数据、外部接口、支付逻辑或未经确认的业务规则。
- 新功能按可测试的纵向切片实施；每个阶段完成迁移、代码、测试、文档和 Git 状态检查后才能进入下一阶段。

## 3. 目标架构与边界

### 3.1 业务模块

```text
auth/       用户身份、登录、会话、密码和账号状态
system/     用户、角色、权限、审计和后台基础查询
chat/       房间、消息、历史、实时连接、消息治理
robot/      机器人资料、模板、触发任务和常驻调度
game/       当前已有期号、下注、结算和轮期事件
```

模块依赖方向固定为：

```text
web -> auth/system/chat/robot/game web adapters
chat -> auth（读取当前用户）
robot -> chat + game（发布消息、读取只读期号状态）
game -> 不依赖 chat（游戏领域不能反向依赖聊天文本）
system -> auth（管理用户和权限）
```

聊天消息可以关联 `issue_number`，但游戏服务不能通过解析聊天文本判断下注、扣款或结算；下注仍必须走结构化 `PlaceBetRequest` 和现有游戏领域服务。

### 3.2 认证方案

当前项目采用以下具体方案：

1. REST 使用 `Authorization: Bearer <access-token>`；访问令牌是由安全随机源生成的短时不透明令牌，服务端只接受未过期、未撤销且状态有效的令牌。
2. 刷新会话使用 HttpOnly、Secure、SameSite 受控 Cookie；数据库只保存刷新令牌的哈希、设备摘要、IP 摘要、过期时间和撤销时间。
3. 浏览器 WebSocket 不把访问令牌放在 URL 查询参数中，先调用 `POST /api/auth/ws-ticket` 获取一次性短时连接票据，再通过首帧 `AUTH` 完成认证；票据不能写入日志或浏览器持久化存储。
4. 当前单实例开发可以将短时会话和连接票据存储在 MySQL/受控内存适配器中；正式多实例部署必须切换到 Redis 共享会话和票据存储，并保留数据库登录审计。
5. 角色或权限变更后，已有访问令牌必须在权限版本不匹配时失效或重新加载权限；不能等令牌自然过期才允许已撤销权限继续生效。

本项目第一版不新增 JWT 依赖，也不把权限快照编码进客户端令牌；访问令牌原文只在登录响应和内存中短暂存在，数据库或 Redis 只保存令牌哈希。这样可以直接撤销单个会话，并在权限版本变化时立即拒绝旧令牌；后续若因跨服务需要 JWT，必须另行补充密钥轮换、签发者/受众校验和撤销策略，不能直接替换当前实现。

### 3.3 角色与权限基线

角色不是前端显示标签，权限编码才是服务端授权依据。首期固定以下角色：

| 角色编码 | 用途 | 首期权限 |
| --- | --- | --- |
| `USER` | 普通聊天和已开放的游戏用户 | `CHAT_ROOM_READ`、`CHAT_MESSAGE_SEND`、`GAME_CURRENT_READ`、`GAME_BET_PLACE`、`WALLET_READ` |
| `MODERATOR` | 聊天治理人员 | `USER` 全部权限 + `CHAT_MESSAGE_REVIEW`、`CHAT_MESSAGE_RECALL`、`CHAT_USER_MUTE`、`CHAT_USER_KICK` |
| `OPERATOR` | 游戏和机器人运营人员 | `GAME_CURRENT_READ`、`GAME_ODDS_READ`、`GAME_ODDS_WRITE`、`ROBOT_READ`、`ROBOT_WRITE`、`ROBOT_TEMPLATE_WRITE` |
| `ADMIN` | 系统管理员 | 用户、角色、权限、审计、聊天室治理、运营和虚拟钱包分配权限；所有操作仍写审计日志 |

虚拟钱包新增权限编码为 `WALLET_READ`、`WALLET_GRANT`、`WALLET_ADJUST`、`WALLET_LEDGER_READ`。其中 `WALLET_READ` 只用于当前用户查询；`WALLET_GRANT`、`WALLET_ADJUST` 和 `WALLET_LEDGER_READ` 默认只授予 `ADMIN`，不能因为前端隐藏入口而省略服务端校验。

机器人不是 `sys_user`，也不是登录角色；机器人使用 `sender_type=ROBOT` 和独立的 `chat_robot.id`。系统事件使用 `sender_type=SYSTEM`，管理员公告使用 `sender_type=ADMIN`，三者不能由普通用户伪造。

首期不做部门、岗位、数据权限树、复杂菜单路由和多租户；权限模型保留扩展接口，但先只处理“能否执行某个动作”的功能权限。

## 4. 数据模型设计

所有新表和结构变更通过下一组 Flyway 迁移创建；当前基线迁移为 `V4__增加轮期事件表.sql`，用户系统使用 `V5` 至 `V7`，其中 `V7` 是会话签发安全版本补充迁移；虚拟余额钱包使用 `V8`，聊天从 `V9` 开始，机器人从 `V11` 开始按依赖顺序递增编号。已执行迁移不得重写。

### 4.1 用户和权限表

#### `sys_user`

至少包含：

- `id BIGINT AUTO_INCREMENT PRIMARY KEY`；
- `username VARCHAR(64)` 唯一，作为登录名，不允许用昵称登录；
- `display_name VARCHAR(128)`、`avatar_key VARCHAR(255)`；
- `password_hash VARCHAR(255)`，只保存 BCrypt 或当前选定密码编码结果；
- `status VARCHAR(16)`：`ACTIVE`、`DISABLED`、`LOCKED`、`DELETED`；
- `failed_login_count INT`、`locked_until TIMESTAMP NULL`、`security_version BIGINT`；
- `last_login_at`、`last_login_ip`、`created_at`、`updated_at`；
- `CONSTRAINT uk_sys_user_username UNIQUE (username)`。

密码、访问令牌、刷新令牌、验证码和完整登录请求不得写入普通业务日志。

#### `sys_role`

包含唯一 `role_code`、展示名称、状态、说明、创建和更新时间。系统内置 `USER`、`MODERATOR`、`OPERATOR`、`ADMIN`，内置角色禁止被普通后台操作删除。

#### `sys_permission`

包含唯一 `permission_code`、展示名称、资源类型、状态和说明。资源类型至少支持 `API`、`ACTION`、`MENU`；首期授权以 `API` 和 `ACTION` 为主。

#### `sys_user_role`、`sys_role_permission`

使用联合主键或唯一联合约束，分别关联用户-角色、角色-权限，并建立反向索引。删除用户或角色前必须检查关联和审计要求，不能级联删除历史审计事实。

#### `auth_session`

保存可撤销的访问/刷新会话和设备信息：`session_id`、`user_id`、`access_token_hash`、`access_expires_at`、`refresh_token_hash`、`refresh_expires_at`、`device_label`、`ip_digest`、`user_agent_digest`、`security_version`、`revoked_at`、`last_seen_at`、`created_at`。`security_version` 是签发时的用户安全版本快照；只保存摘要，不保存完整 Token、密码和原始 User-Agent；访问令牌和刷新令牌必须使用不同随机值。

#### `sys_login_log`

保存 `username_snapshot`、`user_id`、`result`、`failure_code`、`ip_digest`、`user_agent_digest`、`created_at`。成功、密码错误、账号禁用、账号锁定和令牌撤销都必须可区分。

#### `sys_operation_log`

保存操作人、权限编码、HTTP 方法、受影响资源、结果、错误码、请求摘要、IP 摘要和时间。请求摘要必须脱敏，不能保存密码、Token、完整消息内容或金额敏感信息的无必要副本。

### 4.2 虚拟余额钱包和演示资金账本

本模块不是支付系统，也不表示真实资金。正式用户登录后可以参与演示下注，但必须先由后台管理员分配虚拟余额；用户不能自行充值、提现、转账或修改余额。

#### 兼容迁移原则

- 现有 `demo_user_account` 和 `demo_balance_ledger` 是 V2 已执行的演示账户表，不能直接删除或重命名。
- `V8__建立正式用户虚拟钱包.sql` 在 `demo_user_account` 增加可为空且唯一的 `sys_user_id` 外键；已有 `DEMO-USER` 保留为兼容演示账户，正式用户使用一对一关联的钱包记录。
- `game_bet.user_id` 继续表示余额账户记录 ID，避免破坏 V1/V2 已有注单外键；新下注必须先从当前认证用户解析到其钱包账户，禁止使用固定 `DEMO-USER` 或前端传入的用户编码。
- `demo_balance_ledger` 增加 `operator_user_id`、`idempotency_key`、关联注单/期号字段和必要索引；物理表名暂时保留，领域含义统一称为虚拟钱包流水。

#### 余额规则

- 创建正式用户时创建一条余额为 `0.00` 的虚拟钱包；没有钱包或钱包状态不是 `ACTIVE` 时不能下注。
- 管理员分配 `1000.00`，表示该成员获得 `1000.00` 虚拟可用余额；该分配写入 `ADMIN_GRANT` 流水，不能只更新余额字段。
- 用户下注写入 `BET_DEBIT` 流水并扣减余额；开奖结算写入 `SETTLEMENT_CREDIT` 或 `SETTLEMENT_REVERSAL` 流水。余额不足、封盘、重复下注和重复结算均由服务端事务拒绝或幂等处理。
- 管理员更正使用 `ADMIN_ADJUST`，必须填写原因、操作人和幂等键；不能伪装成充值，也不能绕过余额非负约束。
- 每次变化保存 `balance_before`、`amount`、`balance_after`、操作类型、操作人、原因、关联注单/期号和服务端时间；流水只追加不修改。
- 余额扣减、注单保存和结算必须在同一业务事务边界内；并发操作使用行锁或版本号，不能出现负余额或重复扣款。

#### V8 迁移验收

- 验证正式用户与钱包一对一唯一约束、钱包状态和余额非负约束。
- 验证管理员分配幂等、重复请求不重复增加余额，非管理员不能分配或调整。
- 验证下注只使用认证用户钱包，不能通过请求体、URL 或聊天消息伪造钱包所有者。
- 验证下注扣款、开奖结算、重复结算和余额不足场景的账本前后余额一致。
- 验证已有 `DEMO-USER` 和历史 `game_bet` 可读取，迁移不删除既有演示数据。

### 4.3 聊天表

#### `chat_room`

首期至少包含 `room_code`、`display_name`、`status`、`message_retention_days`、`next_sequence_no`、`created_at`、`updated_at`；`next_sequence_no` 通过事务或数据库原子更新生成房间内序号。首个房间固定为公开大厅，但表结构不能把房间编码硬编码在业务代码的每个路径中。

#### `chat_message`

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 数据库主键；作为内部定位，不直接作为客户端可信排序依据 |
| `room_id` | 房间外键 |
| `sequence_no` | 房间内单调序号，供断线补偿和排序使用 |
| `client_message_id` | 客户端幂等标识，普通用户消息按用户和房间唯一 |
| `idempotency_key` | 系统、机器人和结果消息幂等标识，普通用户消息为空 |
| `issue_number` | 关联期号，可为空 |
| `message_type` | `USER_CHAT`、`USER_BET`、`ROBOT`、`SYSTEM`、`RESULT`、`ADMIN` |
| `sender_type` | `USER`、`ROBOT`、`SYSTEM`、`ADMIN` |
| `sender_id` | 服务端确认的用户、机器人或系统标识 |
| `sender_name` | 展示名称快照，防止改名后历史展示漂移 |
| `content` | 纯文本内容，服务端限制最大长度 |
| `payload_json` | 结构化下注反馈、开奖结果或扩展内容 |
| `status` | `ACTIVE`、`RECALLED`、`DELETED` |
| `created_at`、`updated_at` | 服务端时间 |

约束和索引：`(room_id, sequence_no)` 唯一；`(room_id, id)`、`(room_id, created_at)`、`(sender_type, sender_id, id)` 索引；普通消息的 `(room_id, sender_id, client_message_id)` 唯一。机器人和系统消息使用独立的 `idempotency_key` 唯一约束，不能让空值唯一规则误伤普通消息。

#### `chat_outbox`

为持久化成功后广播增加可靠边界：保存 `message_id`、`event_type`、`payload_json`、`status`、`attempt_count`、`next_attempt_at`、`published_at` 和时间字段。单实例可以同步发布并保留 outbox，生产多实例通过 Redis 广播；WebSocket 发送失败不回滚已持久化的聊天消息。

#### `chat_user_mute`

保存禁言目标、房间、开始时间、结束时间、原因、执行人和撤销信息。禁言是服务端发送权限检查的一部分，不能只在前端禁用输入框。

### 4.4 机器人表

#### `chat_robot`

保存 `robot_code`、`display_name`、`avatar_key`、`enabled`、`weight`、`sort_order`、时间字段。它只表示聊天室展示身份，不关联余额账户，不允许写入 `game_bet.user_id`。

#### `chat_robot_template`

保存 `template_code`、`trigger_type`、`room_id`、`message_template`、`enabled`、`min_delay_seconds`、`max_delay_seconds`、`variables_json` 和时间字段。模板渲染只能使用服务端白名单变量，如 `issueNumber`、`closeInSeconds`、`drawResult`，禁止把任意用户输入当作模板指令。

#### `chat_robot_dispatch`

保存 `dispatch_key`、`robot_id`、`template_id`、`room_id`、`issue_number`、`trigger_type`、`status`、`message_id`、失败原因和时间字段；`dispatch_key` 唯一，用于服务重启、重复扫描和多实例调度幂等。

## 5. 服务端接口和协议

### 5.1 认证接口

| 方法 | 路径 | 权限 | 作用 |
| --- | --- | --- | --- |
| `POST` | `/api/auth/login` | 匿名 | 用户名密码登录，返回访问令牌并设置刷新会话 |
| `POST` | `/api/auth/refresh` | 刷新会话 | 撤销旧刷新会话或轮换后签发新访问令牌 |
| `POST` | `/api/auth/logout` | 已认证 | 撤销当前会话，写登录审计 |
| `GET` | `/api/auth/me` | 已认证 | 返回当前用户、角色、权限摘要和账号状态 |
| `POST` | `/api/auth/ws-ticket` | 已认证 | 返回一次性、短时 WebSocket 连接票据 |
| `POST` | `/api/admin/users` | `USER_MANAGE` | 后台创建用户；公共注册单独作为安全策略，不默认开放 |
| `PATCH` | `/api/admin/users/{id}/status` | `USER_MANAGE` | 启用、停用、锁定和解锁用户 |
| `PUT` | `/api/admin/users/{id}/roles` | `ROLE_MANAGE` | 更新角色关联并提升 `security_version` |

登录失败响应不能泄露“账号不存在”还是“密码错误”的可枚举差异；异常统一映射为稳定错误码，并在日志中保留内部原因。

### 5.2 虚拟余额接口

| 方法 | 路径 | 权限 | 作用 |
| --- | --- | --- | --- |
| `GET` | `/api/me/wallet` | 已认证 | 查询当前用户虚拟余额、钱包状态和最近流水摘要 |
| `GET` | `/api/admin/users/{id}/wallet` | `WALLET_LEDGER_READ` | 查询成员虚拟余额和完整流水 |
| `POST` | `/api/admin/users/{id}/wallet/grants` | `WALLET_GRANT` | 给成员分配虚拟余额；金额为正数，必须带幂等键和原因 |
| `POST` | `/api/admin/users/{id}/wallet/adjustments` | `WALLET_ADJUST` | 管理员纠正虚拟余额；必须带原因和审计，不代表支付或充值 |

分配接口只能由服务端从路径用户 ID 定位钱包，不能接受请求体中的 `walletOwnerId`、`userCode` 或余额覆盖字段。接口成功后返回服务端计算的 `balanceBefore`、`grantAmount`、`balanceAfter` 和流水 ID。

### 5.3 聊天 REST 接口

| 方法 | 路径 | 权限 | 作用 |
| --- | --- | --- | --- |
| `GET` | `/api/chat/rooms/{roomCode}` | `CHAT_ROOM_READ` | 房间摘要、当前期摘要和连接参数 |
| `GET` | `/api/chat/rooms/{roomCode}/messages?beforeSequence=&limit=` | `CHAT_ROOM_READ` | 游标分页读取历史消息 |
| `POST` | `/api/chat/rooms/{roomCode}/messages` | `CHAT_MESSAGE_SEND` | REST 兜底发送，写入后返回服务端消息 |
| `POST` | `/api/chat/rooms/{roomCode}/read-cursor` | 已认证 | 保存可选的已读游标，不作为消息可靠性的唯一依据 |
| `GET` | `/api/admin/chat/messages` | `CHAT_MESSAGE_REVIEW` | 查询和筛选消息治理记录 |

| `POST` | `/api/admin/chat/users/{id}/mute` | `CHAT_USER_MUTE` | 禁言或解除禁言 |

### 5.4 WebSocket 协议

连接地址：`/ws/chat/{roomCode}`。首帧完成认证，协议统一为 JSON，至少包含 `protocolVersion`、`type`、`requestId` 和 `payload`。

客户端到服务端：

```json
{"protocolVersion":1,"type":"AUTH","requestId":"r-1","payload":{"ticket":"one-time-ticket"}}
{"protocolVersion":1,"type":"SEND_MESSAGE","requestId":"r-2","payload":{"clientMessageId":"c-1","content":"大家好"}}
{"protocolVersion":1,"type":"ACK","requestId":"r-3","payload":{"sequenceNo":120}}
{"protocolVersion":1,"type":"PING","requestId":"r-4","payload":{}}
```

服务端到客户端：

```json
{"protocolVersion":1,"type":"AUTHENTICATED","requestId":"r-1","payload":{"userId":7,"roomCode":"main"}}
{"protocolVersion":1,"type":"MESSAGE_CREATED","requestId":"r-2","payload":{"messageId":120,"sequenceNo":120}}
{"protocolVersion":1,"type":"MESSAGE","requestId":null,"payload":{"id":120,"sequenceNo":120,"messageType":"USER_CHAT"}}
{"protocolVersion":1,"type":"ERROR","requestId":"r-2","payload":{"code":"CHAT_RATE_LIMITED","message":"发送过于频繁"}}
{"protocolVersion":1,"type":"PONG","requestId":"r-4","payload":{}}
```

协议规则固定如下：

- 未完成 `AUTH` 的连接不能发送聊天、下注或管理消息。
- 服务端只广播已经持久化的 `MESSAGE`，客户端回显使用 `MESSAGE_CREATED` 或最终消息，不把本地草稿当已发送。
- `requestId` 只用于请求响应匹配；`sequenceNo` 用于房间顺序、断线补偿和去重。
- 客户端重连后使用 `beforeSequence` 或 `afterSequence` 补偿，REST 历史和 WebSocket 推送重复到达时按 `messageId`/`sequenceNo` 去重。
- 心跳超时、连接数上限、消息大小、每用户频率、每 IP 频率和异常关闭都必须有服务端限制和可检索日志。
- 不把令牌放在 WebSocket URL、日志、错误消息或前端持久化 localStorage 中。

## 6. 核心业务流程

### 6.1 用户进入聊天室

1. 前端检查 `/api/auth/me`，未认证则进入登录流程。
2. 服务端按认证上下文确定用户和权限，读取房间摘要与最近消息。
3. 前端获取一次性 WebSocket 票据，建立连接并发送 `AUTH`。
4. 服务端校验票据、用户状态、房间权限和连接上限，返回 `AUTHENTICATED`。
5. 服务端发送当前期摘要和从历史游标补偿的消息；前端仅渲染服务端消息。

### 6.2 用户发言

1. 校验认证、房间状态、`CHAT_MESSAGE_SEND` 权限、禁言状态、长度和频率。
2. 规范化纯文本内容；拒绝 HTML、控制字符和空消息，保留必要的 Unicode 文本。
3. 检查 `(user, room, clientMessageId)` 幂等键；重复请求返回原消息，不再插入。
4. 在事务中写入 `chat_message` 和 `chat_outbox`，生成房间 `sequenceNo`。
5. 仅广播持久化后的消息；发送失败由 outbox 重试，不回滚历史事实。

### 6.3 虚拟余额分配和用户下注

1. 后台管理员创建或启用正式用户后，系统确保该用户存在 `ACTIVE` 虚拟钱包，初始余额为 `0.00`。
2. 管理员通过钱包分配接口提交正数金额、原因和 `idempotencyKey`；服务端锁定钱包、追加 `ADMIN_GRANT` 流水并更新余额，重复幂等键返回原分配结果。
3. 前端登录后从 `/api/me/wallet` 获取余额，只展示服务端结果；前端不能提交余额、钱包 ID 或其他用户 ID 作为下注身份。
4. 下注服务从认证上下文取得 `sys_user.id`，解析其钱包账户后，在同一事务内校验期号、余额和权限，再写 `BET_DEBIT` 流水和 `game_bet`。
5. 开奖结算使用同一钱包写入结算流水；机器人不使用钱包，不产生 `game_bet`，也不参与虚拟余额分配。

### 6.4 用户下注消息

1. 聊天输入可以提供快捷文本，但前端必须先转换为结构化下注请求。
2. `game` 服务按当前用户身份和现有期号/余额规则处理下注，不接受聊天发送者字段覆盖。
3. 成功、失败、封盘、赔率快照和结算结果可通过 `USER_BET`、`SYSTEM` 或 `RESULT` 消息展示。
4. 聊天消息只引用 `bet_id` 或业务结果摘要，不保存可作为结算依据的自由文本。

### 6.5 服务端常驻机器人

1. `RobotDispatchService` 由服务端定时扫描当前期状态、轮期事件和机器人模板。
2. 触发条件按 `room + issue + triggerType + sequence` 生成 `dispatchKey`。
3. 先插入 `chat_robot_dispatch`，利用唯一约束防止重复调度；再生成 `chat_message` 和 outbox。
4. 没有在线用户时仍完成数据库写入；有在线用户时由 outbox/广播层推送。
5. 服务重启后扫描 `PENDING` 或超时任务，按幂等键恢复；失败次数和最后错误必须记录。

机器人固定支持的第一批触发类型：

| 触发类型 | 消息示例 | 幂等范围 |
| --- | --- | --- |
| `ISSUE_STARTED` | `3000000期开始` | 房间 + 期号 + 触发类型 |
| `BETTING_WARNING` | `离封盘还剩30秒` | 房间 + 期号 + 秒级提醒点 |
| `BETTING_CLOSED` | `停止下注，进入开奖中` | 房间 + 期号 + 触发类型 |
| `DRAW_RESULT` | 开奖号码和结果摘要 | 房间 + 期号 + 结果版本 |
| `SETTLEMENT_RESULT` | 获胜名单或结算提示 | 房间 + 期号 + 结算版本 |
| `ROBOT_INTERACTION` | 普通互动文案 | 房间 + 模板 + 调度序号 |

机器人消息必须有明显的机器人身份标记，不能使用真实用户名称、真实余额或虚构真实用户下注来误导用户。模拟下注若未来需要，必须独立增加 `SIMULATED_ROBOT_BET` 类型和独立模拟表。

## 7. 前端改造边界

### 7.1 认证和权限

- 增加登录页、认证状态、退出登录和会话过期处理。
- 访问令牌只保存在内存；刷新由 HttpOnly Cookie 完成。
- `/room` 在认证完成后才能进入；`/admin` 根据服务端权限摘要和路由守卫显示。
- 用户前台从 `/api/me/wallet` 读取当前虚拟余额；余额只读展示，下注金额不能通过前端直接修改余额。
- 前端权限只负责隐藏入口，后端权限检查才是最终控制。

### 7.2 `UserRoom.vue`

- 删除固定参考用户、固定机器人、固定历史和本地假回复作为默认数据源。
- 使用统一 `RoomMessage` 类型映射服务端消息，按 `USER_CHAT`、`ROBOT`、`SYSTEM`、`RESULT`、`ADMIN` 渲染。
- 发送请求必须携带 `clientMessageId`，等待服务端确认后再标记成功或失败。
- WebSocket 使用退避重连、最大重试间隔、连接状态和断线补偿。
- 消息内容按纯文本渲染，禁止未经清洗的 `v-html`；服务端已经拒绝 HTML 不能替代前端安全编码。
- 历史滚动和新消息滚动分离；只有用户在底部时自动跟随新消息。
- 期号、倒计时和游戏状态继续使用现有接口或实时事件，不从机器人文本反推状态。

### 7.3 后台页面

后台按权限提供用户、角色、虚拟钱包分配、钱包流水、聊天治理、机器人资料、模板、调度失败和审计查询。余额分配页面必须展示目标成员、分配金额、分配前后余额、原因、幂等结果和操作审计；不能提供充值、提现或支付入口。首期不复制若依完整菜单树，先做能支撑聊天室上线的最小后台闭环。

## 11. 实施顺序结论

当前真正的下一部分不是先做机器人文案，也不是继续改 `UserRoom.vue`，而是进入阶段 3 的“聊天持久化和 REST 纵向切片”；阶段 2 的虚拟余额钱包与管理员分配闭环已完成：

1. 先建立 `sys_user`、角色、权限、会话和审计表。
2. 再让 Spring Security 从“全部放行”切换到默认拒绝，并打通登录、`/me`、退出和 WebSocket 票据。
3. 已建立正式用户与虚拟钱包的一对一关系，实现管理员分配、余额流水和认证用户下注。
4. 下一步实现一个普通用户发送和读取聊天消息的 REST 纵向切片。
5. 再接入单实例 WebSocket，最后接入服务端常驻机器人。

原因是没有服务端身份和钱包归属，系统无法可靠回答“谁发送的、谁在下注、谁有权分配余额、余额是否足够、是否应该禁言、机器人是否伪造用户”；先做机器人或前端，会把错误的身份和资金模型固化到后续数据库和协议中。

## 12. 当前不再需要业务确认的事项

用户已经确认按正式上线、多人聊天室、服务端常驻机器人和若依参考能力推进，因此本方案不再以“是否要认证、是否要权限、机器人是否服务端调度”为阻塞项。实施前只需要在部署阶段补齐真实环境参数和运营规则，代码阶段按本计划固定边界执行。

## 13. 最终验收标准

1. 多个真实用户使用各自账号登录，服务端能区分身份、角色、权限和会话。
2. 未登录、禁用、禁言和无权限用户无法绕过 REST 或 WebSocket 限制。
3. 用户消息写入 MySQL，刷新、换浏览器和断线重连后仍可按游标读取且不重复。
4. 两个应用实例在 Redis 广播和调度锁下能保持消息可达、机器人不重复和权限及时失效。
5. 机器人无用户在线时仍按期号事件生成历史消息，且不产生真实账户、订单或资金变化。
6. 消息撤回、禁言、踢出、审计、登录失败锁定和权限变更均有可追溯记录。
7. 当前游戏下注和结算仍由原有结构化领域服务负责，聊天室不能绕过封盘、余额和结算规则。
8. 正式用户的下注余额全部来自管理员虚拟分配，系统不存在充值、支付、提现和转账入口；所有余额变化有不可变流水。
9. 后端 `server/xupan-server` 的 `.\mvnw.cmd test`、MySQL 8.4 迁移验证、前端类型检查和生产构建通过。
10. 完成安全、故障恢复、消息保留、备份恢复、跨实例和 375px/桌面界面验收后，才能称为正式上线版本。
