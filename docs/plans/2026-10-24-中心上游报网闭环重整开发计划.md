## 1. 目标与完成标准

把 `/console` 的代理报网流程和 `/platform-admin` 的中心上游管理收敛为一套同进程内的业务闭环：超级管理员给代理子账号创建中心账号和虚拟额度；子账号名下机器使用该中心账号独立登录；单台机器只有在中心登录在线且本机自动上报已开启时，才自动将符合 BY220 报网规则的本地下注送入 Xupan 中心订单服务；中心按共享额度受理、拒绝或保持待核实；同一期开奖结果由超级管理员确认后，自动且幂等地结算本地玩家单和中心已接受镜像单。

| 验收域 | 完成标准 |
| --- | --- |
| 账号与权限 | 仅超级管理员可创建/管理中心账号、归属子账号、额度、有效期、停用、续期、密码重置和中心订单；代理机器不能越权访问其他机器或其他子账号数据。 |
| 登录与自动报单 | 同一子账号名下每台机器独立登录同一中心账号；在线与自动上报是两个独立条件，只有两者同时有效才发送新单。 |
| 订单闭环 | 每笔本地订单最多产生一个中心订单和一次风险占用；明确拒绝、待核实、重试和失败退单均可审计且不重复退款/受理。 |
| 额度 | 中心账号共享额度与机器 `agent.score` 风险补足符合基线；不从玩家钱包或共享子账号积分兜底；接受、冻结、释放、输赢和管理调整均有幂等流水。 |
| 开奖结算 | 开奖确认前逐球编辑；确认后结果锁定。一次确认使用同一期同一结果版本结算本地玩家订单和中心已接受订单，重放不重复结算。 |
| 视图 | 代理端显示共享可用额度和汇总押注，但订单详情仅限本机器；超级管理员可按中心账号/子账号/机器/期号穿透查询并对账。 |
| 工程交付 | 新库可从 Flyway 重建；本地 MySQL 8.4 定向闭环通过；安全、审计、幂等、备份/恢复和未完成验证边界有证据记录。 |

所有金额均为不可兑换的虚拟积分，不接充值、支付、提现、现实资金或第三方上游。中心订单由后端同进程调用中心服务；浏览器页面仍经正常 Xupan 应用接口。

## 2. 需求基线与已确认流程

实现以需求基线为业务目标。计划不改写其中已确认决定：

| 规则 | 执行口径 |
| --- | --- |
| 账号归属 | 一个代理子账号关联一个有效中心账号；该子账号下多个机器可共用，其他子账号不可使用。每台机器独立登录，共享账号按有效机器会话汇总在线。 |
| 有效期 | 创建默认 7 天，可自定义；续期由超级管理员明确设置新到期时间。密码安全哈希保存，明文仅创建/重置时一次展示。 |
| 自动上报 | 中心账号有效、机器所属关系正确、该机器登录在线、该机器自动上报开关开启、订单满足 BY220 报网资格且未封盘/取消，条件同时满足才发单。 |
| 共享可见性 | 同子账号机器看到共享中心可用额度和汇总押注；每台机器只看自己的订单明细。中心管理端可看完整来源链。 |
| 失败退单 | 保留 BY220 失败退单开关。明确失败后按开关决定是否返还玩家本金；待核实不立即退款。先按原订单幂等号确认中心未接受，再执行退款。保留原订单和退款流水，不物理删除订单。 |

| 结算方向 | 玩家钱包只按本地开奖结果结算一次；玩家中奖时中心承担净赢额，玩家未中奖时中心记入投注本金，平局/流局双方不产生输赢。冻结额按实际结果释放/入账。 |
| 开奖 | 管理员在确认前逐球录入/修改；确认整期开奖结果后锁定，不撤销、不改号、不冲正重结算；该确认自动触发本地玩家与中心已接受订单结算。 |

### 2.1 数字验收样例

| 阶段/结果 | 玩家本地余额 | 中心额度与流水 |
| --- | ---: | --- |

| 平局/流局 | 1,000（退回本金 100） | 释放冻结 95；可用恢复 10,000、冻结归零 |

3. 将登录、在线状态、自动上报开关独立呈现；自动上报开关按机器持久化。开关关闭或离线不自动发新单，不得显示“中心拒绝”。
4. 代理端额度/押注区显示共享中心可用余额和同子账号汇总押注；本机订单明细保持机器隔离，并展示已接受、已拒绝、未发送、待核实等不同状态和原因。
5. 对照 BY220 页面保持操作字段与顺序；移除网盘选择、网盘编码、盘口线路等不再需要的代理输入，不擅自合并其他 BY220 后台入口。

**P3 出口条件：** M01 登录后能看共享摘要及本机单；M02 登录同账号共享余额但看不到 M01 明细；其他子账号不能登录；过期/停用/登出均不能继续报新单。

### P4：订单自动上报、回执和失败恢复

> 实施状态（2026-10-26）：同进程幂等接单、报网资格、明确拒绝和失败退单保留原单已有定向 MySQL 证据；待处理/超时订单使用原账号、原幂等键恢复扫描，既有隔离 MySQL 集成测试 6/6 通过。本轮再补入恢复 CAS 失败无副作用、尝试级状态守卫及拒绝重试只计一次的独立单测 3/3；中心已撤单/退款的本地镜像转人工核对，并阻止这两种结果走人工重报。中心人工处置 CAS 竞争失败后回放同键首个结果，跨订单复用幂等键会拒绝。单测使用内存 H2/Mockito，未验证真实并发或 MySQL；处置集成用例只编译、未运行。本轮未做进程杀停/重启、人工处置与恢复集成、本地人工核对/处置工作流、失败退单开关全组合或浏览器矩阵，因此 P4 未达到出口条件。

1. 以本地已成功落库的下注为输入，在既有自动派发管线增加中心账号、有效机器会话、机器自动开关、BY220 订单资格、封盘状态等统一门槛。
2. 代理上报适配器同进程调用中心接单服务；不发起上游 HTTP，不复制中心账务规则到前端或另一个外部服务。
3. 建立稳定幂等业务键，绑定来源机器和本地订单；同单重试返回首个中心结果/中心单号，不重复建单、冻结风险或扣玩家积分；相同幂等键但载荷不同应拒绝并审计。
4. 明确 ACCEPTED、REJECTED、未发送、处理中/待核实、已退款/已取消、已结算状态的转换条件。超时或进程中断先按原键核实；状态未知时不退款、不新建键、不删除订单。
5. 明确拒绝后按失败退单开关退款；退款与本地订单状态变更原子化、幂等，钱包流水指向原订单与失败原因。失败退单关闭时保留玩家本地单并明确其仍参与本地开奖，但中心无 ACCEPTED 单不参加中心结算。
6. 设计同进程调用后的异常恢复、应用重启扫描和人工处置列表；人工重试不得对已接受订单再次占额。

**P4 出口条件：** 注单本地落库、中心成功/拒绝、中心调用中断、进程重启恢复、重复请求、两种失败退单开关及中心撤单/退款后的两种本地人工结论均有自动化证据；中心订单和本地订单可逐笔关联，并完成人工处置/恢复并发和浏览器验证。

### P5：共享额度、最大风险冻结和账本结算

> 实施状态（2026-10-26）：V92 与 `CenterOrderService` 已按本地注单快照计算最大净赔付风险，先锁中心额度再由当前机器积分补足；并发、重放、机器补足、中心拒绝及输赢/平局结算用例已有隔离 MySQL 8.4.11 证据。风险版本为 0 的历史挂单现在由同一结算器按中心订单持久化快照重算；成功确认时固化风险额和版本 1，缺字段或玩法无法解析时阻止受理并要求人工核对。新增可还原/不可还原历史挂单用例尚未执行，也未核实当前数据库是否存在此类数据。P5 还需复核数字样例、账本可重算与浏览器摘要一致性，因此阶段未封口。

1. 基于下注赔率快照计算单笔最大净赔付风险；明确金额精度、舍入时点、零风险玩法及上限，禁止使用前端传入的净风险值。
2. 在同一事务内锁定中心账号额度及当前机器 `agent.score`，计算可用中心额度和可补足机器积分；中心先占，不足再由本机补足；不足则拒绝整个中心受理。
3. 同子账号多个机器并发共享中心余额时，使用数据库锁/乐观版本/唯一约束保证总占用不超过可用额度；固定锁顺序，避免死锁。不可用内存锁作为唯一并发保护。
4. 接受时写冻结分录；输赢/和局/流局时按基线释放和入账；拒绝/撤销/退款释放冻结；每种分录按订单、事件和版本幂等。已结算中心订单不可被正常重试二次冲账。
5. 中心额度管理调整要记录原因、操作者、前后值和流水；共享机器的“中心汇总”不导致把机器积分或子账号积分混成一个钱包。
6. 实现并核对中心余额、冻结余额、未结押注、机器补足额度和流水可重算校验；报表口径与代理摘要一致。

**P5 出口条件：** 第 2.1 样例和额度不足/机器积分补足/并发竞争/重复请求均通过；全账本分录可重算余额且无负可用额度和重复消费。

### P6：开奖逐球控制与本地/中心自动结算

> 实施状态（2026-10-27）：V93、`PlatformDrawHistoryService` 和中心结算门禁已落地；V95 增加确认开奖 UPDATE/DELETE 触发器。隔离 MySQL 8.4.11 验证直接修改/删除确认结果会被拒绝，允许更新结算元数据。在 `log_bin=1`、`log_bin_trust_function_creators=0` 环境中，app-like 账号执行 V95 明确因 MySQL 1419 缺少 `SUPER` 权限而失败；新隔离 schema 上已验证 DBA 执行 V94、repair 后执行 V95/V96，以及低权限账号只读校验 V95/V96 版本。该证据确认本机受控 DBA 前置迁移方案可行，但服务器/生产迁移权限和运行验证仍未完成；P6 其他出口条件亦须单独满足。

1. 明确各彩种的球号数量、合法值和“未指定球随机生成”的唯一随机来源；逐球编辑只在开奖未确认前有效，并审计修改前后值。
2. 超级管理员确认时，以游戏、期号、唯一开奖结果版本形成不可变事实；确认接口幂等，任何并发编辑/重复提交都不能产生两个最终结果。
3. 同一开奖结果版本触发玩家本地结算与中心 ACCEPTED 单结算；不能只在 UI 上显示完成。开奖确认和结算任务要支持事务内完成，或采用有状态且可恢复的可靠任务记录，避免一侧成功另一侧静默失败。
4. 玩家钱包按本地游戏规则只结算一次；中心账按本计划 P5 的代理净输赢口径结算，使用接单赔率快照。拒绝、未发送、待核实订单不参加中心结算。
5. 复核 `PlatformDrawHistoryService`、`SettlementService`、`CenterSettlementService` 现有强制结算/批量入口/调度调用，确保同一期不会因确认、重试、旧手工入口或定时任务重复结算。
6. 结果确认后禁止改号、撤销和冲正重结算；其他历史强制结算功能要么限制到未确认/合规范围，要么在权限和审计上与已确认的不可改规则一致。

**P6 出口条件：** 同期本地玩家和中心订单共用结果版本；重复确认/恢复执行不重复写钱包、中心流水或聊天结算消息；开奖锁定在 API/服务/数据库约束层均有效；并验证部署使用的迁移账号可以创建 V95 触发器，或确认受控 DBA 前置迁移流程。

## 7. 数据迁移与兼容原则

- 以新的账号归属和额度方向为准，可重构中心相关表、服务和 DTO；不为保留错误开发期数据永久维护双轨账务。

- Flyway 只管理结构演进。业务数据转换需幂等、可检查、提供转换前后计数/金额核对；无法可信转换的历史数据应冻结并保留，而非伪造为新状态。
- 报网密码、中心密码和会话秘密不从旧明文/Token 静默继承；必要时要求代理重新登录/管理员重置并审计。
