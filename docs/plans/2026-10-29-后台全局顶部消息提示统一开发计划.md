# 后台全局顶部消息提示统一开发计划

> 状态：2026-10-29 本机源码已实施，专项测试、类型检查、独立目录构建和本机 HTTP 资源加载已验证；真实账号登录后的浏览器操作仍待验收。用户确认管理后台提示统一使用 Element Plus `ElMessage` 一类的顶部 toast，由同一个通知入口集中管理。下文第 1 至 7 节保留开发计划，第 8 节记录本机实施证据与边界。

## 1. 目标

将所有管理端的短期操作反馈统一呈现在浏览器视口顶部中央，覆盖成功、失败、警告、信息及表单业务校验提示。提示由全局通知服务统一创建、去重、计时和关闭；不使用浏览器开发者控制台 `console.log` 充当用户提示。

本需求来源于机器管理编辑积分时，所属子账号积分池不足的错误被渲染到弹窗背后的页面横幅。后端通过 `SUB_ACCOUNT_SCORE_INSUFFICIENT` 返回业务拒绝，`apiErrorMessage` 已有对应中文文案。机器积分是目标余额；机器余额上调时，后端只从所属子账号积分池划转差额。积分不足时由事务回滚，本次编辑不得部分保存。实现位置基线：`web/src/views/PlatformAdminMachines.vue`、`web/src/api.ts`、`server/xupan-server/src/main/java/com/xupan/server/agent/service/AgentLedgerService.java`、`server/xupan-server/src/main/java/com/xupan/server/platformadmin/service/PlatformAdminService.java`。

## 2. 覆盖范围与边界

| 页面/流程 | 当前提示形式 | 计划行为 |
| --- | --- | --- |
| `/platform-admin/**` 超级管理后台 | 页面级 `el-alert`、模态框 `formError`、零散 `ElMessage` | 所有用户触发的短期操作结果和业务校验统一走全局通知服务 |
| `/console` 机器代理后台 | HBY019 iframe 中的 `UIkit.notify`、页面局部 toast/反馈 | iframe 通过经验证的同源消息把通知交给父 Vue 页面，再调用同一全局通知服务 |
| 其他仍在用的管理路由 | `AdminPanel`、`UserManagement`、`RobotManagement`、`AgentManagement` 等局部反馈 | 实施时逐路由清点，将用户操作的短期结果统一迁移；已废弃路由不纳入 |
| 玩家前台与聊天室业务消息 | 玩家可见提示、聊天消息和开奖播报 | 不属于本次后台通知范围，不改业务文案或身份语义 |

- 通知位置固定在浏览器视口顶部中央，使用 Element Plus `ElMessage` 的定位与层级，确保显示在表单弹窗、遮罩及 iframe 上方。
- 所有后台用户操作的成功、失败、警告、信息与前端表单校验提示都用 toast；一次操作只显示一个结果，禁止同时留下页面横幅和 toast 两份相同消息。
- 页面加载失败、持续的服务不可用状态等需要用户持续处理的问题仍使用页面级故障区及重试入口；不要用会自动消失的 toast 代替持久故障状态。
- `ElMessageBox.confirm/prompt` 是确认或输入流程，不属于结果通知，保留现状。
- 后端业务规则、错误码、事务与审计保持不变；不得通过前端通知把服务端错误伪装为成功或吞掉异常。

## 3. 当前问题链路

1. 机器编辑提交调用 `api.updateMachine`；子账号积分池不足时，`AgentLedgerService.assignMachineScore` 返回 409 `SUB_ACCOUNT_SCORE_INSUFFICIENT`，机器配置更新事务回滚。
2. `apiErrorMessage` 已将该错误码映射为“该子帐号积分不足以为机器分配积分！”。
3. `PlatformAdminMachines.vue` 的 `catch` 将该业务错误写入页面级 `error`，因此 `<el-alert>` 出现在弹窗后面的主页面；弹窗内的 `formError` 没有承接服务端异常。
4. 进入编辑时虽清空 `error`，没有清掉之前的 `feedback`；失败时可能并列显示旧的“机器账号已更新”成功横幅。
5. `/console` 的 HBY019 源码运行在 iframe 内，使用 UIkit 通知；直接在 iframe 内调用 Element Plus 无法复用父应用的全局通知栈，需要安全消息桥。

## 4. 目标设计

### 4.1 全局通知服务

- 新增共享通知模块（建议 `web/src/services/adminNotice.ts`），统一导出 `success`、`error`、`warning`、`info` 方法；页面不得各自设置不同的全局位置、层级或生命周期。
- 由服务统一配置顶部偏移、显示时长、关闭按钮、相同消息分组和通知句柄；基准建议成功/信息约 3 秒，警告约 4 秒，错误约 5 秒。最终值可在实现时按现有 Element Plus 样式校正，不影响业务契约。
- 业务操作调用处继续通过 `apiErrorMessage` 把稳定错误码转换为中文用户文案，再交给通知服务。不得在底层 HTTP 请求拦截器无差别弹 toast，否则同一错误容易被页面和全局拦截器重复显示，后台轮询失败也会制造噪声。
- 自动轮询、静默预取、后台刷新和预期内取消不弹全局错误；只有用户可归因的操作结果才进入通知管理器。

### 4.2 iframe `/console` 通知桥

- HBY019 iframe 的通知调用改为发 `xupan-admin-notice` 消息，字段限于 `type` 和纯文本 `message`。
- `Hby019SourcePage.vue` 父页面沿用既有 `event.origin` 与 `event.source` 检查，额外校验通知类型、消息长度及纯文本，不接受 HTML、脚本或任意选项。
- 父页面将合法通知交给共享 `adminNotice` 服务。确认弹窗、玩家聊天室消息与非管理 iframe 的行为不通过此桥转发。
- 迁移 `web/public/hby019-demo/source/console.html`、`local-api-bridge.js` 等源码时，同步更新服务实际使用的 `server/xupan-server/src/main/resources/static/hby019-demo/source/` 副本、资源版本和生产 bundle；避免只改源码副本而运行页仍加载旧提示实现。

### 4.3 积分不足反馈

- 提交失败时使用 `apiErrorMessage` 显示子账号积分不足文案，通知位置在弹窗上方；弹窗保持打开，用户名、机器目标积分及其他配置继续保留供调整。
- 成功提示只在 API 成功后发送；打开新建/编辑窗口时清理前一条操作结果，避免旧成功与新错误并列。
- 保存失败不调用成功刷新路径，不关闭表单；如需刷新列表，只能在明确保持编辑内容的前提下进行。
- 服务端错误码、事务回滚、虚拟积分池划拨及审计行为不变。本需求不新增“可分配余额”查询或修改资金/积分账本逻辑。

## 5. 实施阶段

1. **清点通知出口**：盘点 `/platform-admin`、`/console` 与仍有效管理路由中的 `el-alert`、`ElMessage`、自定义 toast、UIkit notify、`alertErr/alertSuc` 及操作 catch；区分用户操作、字段校验、页面持久故障、确认对话框和后台轮询。
2. **建立通知中心**：实现并测试共享通知服务；定义 severity、顶部位置、时长、去重、关闭和多消息排队规则。
3. **迁移 Vue 管理页**：先修复机器编辑的成功/失败状态生命周期，再将其余有效管理路由的短期操作结果统一调用通知中心；删除同一操作重复的内嵌横幅。
4. **接通 `/console` iframe**：添加受源与 schema 校验的父页面通知消息，替换 iframe 内管理操作通知，并处理未挂载、超时、重复消息与父页面离开场景。
5. **发布资源与文档**：按仓库构建流程更新 `server/xupan-server/src/main/resources/static` 实际服务资源和 HTML 资源版本；同步更新本计划状态、相关业务模块和文档索引。

## 6. 验收标准

- 机器积分调高超过子账号可用积分时，只出现一次顶部居中错误 toast；编辑弹窗仍打开、输入保留；页面不显示旧成功提示；数据库中机器与子账号余额均未部分改变。
- 机器积分调整成功时只出现一次顶部居中成功 toast；表单成功关闭，列表刷新。
- 前端字段校验失败（如用户名、积分或配置校验）使用同一顶部 toast 机制，不出现对话框内/主页面重复错误横幅。
- `/platform-admin/**` 和仍有效管理路由的用户操作错误/成功全部调用共享通知服务；后台轮询失败、静默读取和确认取消不会弹不相关通知。
- `/console` iframe 发出的错误/成功经父页面校验后显示在同一通知层；伪造来源、未知类型、超长文案、HTML 内容不渲染。
- 多次重复错误按统一分组规则合并或限流；登录过期后只显示一次提示再按现有入口规则跳转；消息层级高于弹窗与遮罩，并在桌面/窄屏均不遮挡关键操作。
- 确认/输入类 `ElMessageBox` 保持原交互；玩家前台通知、聊天室开奖播报、消息身份与业务文案不变。
- 运行前端组件/服务专项测试、类型检查、生产构建；本机浏览器检查 `/platform-admin/machines` 与 `/hby019-demo/console`。真实数据库积分验证使用可回滚的专用测试数据，不操作真实用户业务账户；未执行项按本机/服务器/生产证据分别记录。

## 7. 风险与防护

- **重复提示**：同一错误不得同时由请求层、页面 catch、iframe 和父页面重复派发；通知服务只负责显示与归并，错误转中文仍由页面 API 语义层处理。
- **消息滥用**：父页面只接收当前 iframe 的同源窗口消息；只允许四种等级、纯文本和长度限制，不解析 HTML。
- **遮挡与焦点**：提示层位于弹窗遮罩之上但不抢焦点；用户仍能继续修正表单。超长错误需换行，不得溢出屏幕。
- **旧静态文件**：项目存在源码 public 页与 Spring Boot static 运行副本，验收必须检查实际 HTTP 返回资源和新构建入口，不能只依赖源码测试。
- **语义边界**：用户提示统一不意味着所有接口错误自动弹窗；后台异步轮询、播放器消息和聊天消息按各自语义处理。
