# 聊天室 WebSocket 部署运行说明

## 当前边界

当前实现是单实例 WebSocket：连接注册表和房间广播位于单个 Spring Boot 进程内。它支持多个用户和多个浏览器连接，但不支持多台应用服务器之间的实时广播，也不代表生产高可用（BY220: application/console/Websocket.php:40-46 同样是单进程 Swoole 服务与 `receive` 回调；本项目改用 Spring Boot WebSocket 属技术选型）。

> **当前部署决策（2026-09-14）：** 当前只部署一台服务器、一个 Spring Boot 实例。当前不引入 Redis、MQ、多实例任务协调、跨节点 WebSocket 广播或专门监控告警平台。正式上线后，只有当真实用户量、在线连接数或故障恢复需求证明单服务器不足时，才另行评估多服务器方案。

服务端常驻机器人基础能力和机器人管理前端代码已经完成（BY220 的系统消息角色：application/common.php:1811-1827 addMsg 写 `NickName='机器人'` 的消息）；机器人管理管理员 API、事件发布、无在线持久化、重启恢复和失败重试已在本机 MySQL 8.4.11 运行态通过，登录后的浏览器视觉操作、历史事件批量补发、消息归档和单服务器正式故障演练属于当前后续收尾。Redis/MQ 跨实例广播和专门监控平台只作为正式上线后的可选扩展。本说明不包含任何数据库密码、Token、ticket 或完整会话 URL。

## WebSocket 契约

- 票据：登录后调用 `POST /api/auth/ws-ticket?roomCode=main`，票据短期有效且只能消费一次（技术选型：本项目自定的短期票据协议，BY220 无对应实现）。
- 连接：`ws://<host>/ws/chat/main?ticket=<短期票据>`；生产 HTTPS 使用 `wss://`。
- 客户端建立连接后发送 `subscribe`，携带房间和最后接收序列。
- 发送消息使用 `message.send`，必须提供稳定的 `clientMessageId` 和纯文本 `content`（技术选型）。
- 断线补偿使用现有 REST `GET /api/chat/rooms/{roomCode}/messages?afterSequence=...`。
- 未订阅连接不能发送消息；用户身份、昵称、头像和权限不接受客户端自报。

## Nginx 反向代理

在现有站点的 API location 同级增加 WebSocket location。`proxy_pass`、域名和 TLS 参数必须结合服务器当前配置确认，不能直接覆盖整个站点配置（工程基线）：

```nginx
location /ws/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_read_timeout 75s;
}
```

修改后先执行：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

生产 Origin 通过 `XUPAN_CHAT_WS_ALLOWED_ORIGINS` 配置明确来源，禁止使用 `*`。Nginx 日志和应用日志不得记录 ticket 原文。

## 故障排查

- 页面显示“实时连接不可用，已切换普通模式”：检查浏览器 Network 中 `/api/auth/ws-ticket` 是否成功、WebSocket 是否返回 101、Origin 是否在白名单中。
- ticket 失败：确认用户登录态、会话未注销、用户为 ACTIVE、用户拥有聊天室查看权限；不要重用旧 ticket。
- 管理员与玩家标签页互相影响：确认管理员使用 `xupan_refresh`、玩家链接使用 `xupan_player_refresh`，刷新请求携带 `X-Xupan-Auth-Audience`；修复前被覆盖的旧共享 Cookie 需要重新登录一次。
- 连接成功但不能发消息：确认客户端已发送 `subscribe`，用户拥有发言权限且未被禁言；服务端消息仍应通过现有 `ChatMessageService` 落库。
- 消息重复：检查客户端是否同时启动了 WebSocket 和 REST 轮询；正常 READY 状态不应运行聊天室降级轮询，消息合并按 ID/序列去重。
- 多节点部署：当前版本不做多节点扩容。正式上线后若实际数据证明单服务器不足，再先单独完成 outbox 可靠发布、Redis/MQ 跨实例设计和跨节点广播验收，之后再接入负载均衡（工程基线）。
- 访问 `/platform-admin/player-workbench` 或 `/platform-admin/players` 得到 404：**属预期**（2026-10-08 方案 A 已删除这两个越界页面，BY220 `admin.php` 没有玩家运营面：application/admin/view/public/head.html:170-193 的菜单里没有它们）。玩家与托的运营请用机器账号进 `/console`；平台侧与玩家相关的只有在线的「在线玩家」`/platform-admin/online-players`。超管/子账号登录后的落地页是 `/platform-admin`（不再是 `/platform-admin/player-workbench`）。

## 运维可观测性与日志

生产启动使用 SPRING_PROFILES_ACTIVE=prod。应用日志默认写入 /opt/xupan-platform/logs/xupan-server.log，同时输出到 systemd journal。Logback 默认按单文件 50MB、历史 30 天、总容量 2GB 滚动，参数可通过 XUPAN_LOG_MAX_FILE_SIZE、XUPAN_LOG_MAX_HISTORY_DAYS 和 XUPAN_LOG_TOTAL_SIZE_CAP 调整。

请求日志和异常日志通过 X-Request-Id 关联；密码、Token、Cookie、ticket 等敏感字段按日志配置脱敏。健康检查地址为 /actuator/health，info 和 metrics 及具体指标需要 SYSTEM_MONITOR_READ 权限。

deploy 目录提供 xupan-server.service、xupan-healthcheck.service、xupan-healthcheck.timer 和 journald 配置示例。当前只完成模板和本机静态检查，尚未在真实服务器上安装、启用 timer、验证日志滚动或执行故障重启演练。现场操作前需要确认维护窗口和服务器变更授权（工程基线）。
