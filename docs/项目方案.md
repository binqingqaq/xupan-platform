# Xupan Platform 产品方案与首期玩法交付基线

## 1. 目标

当前阶段交付一个可在浏览器使用的“8 球番摊玩法”业务切片，复现参考页的核心信息结构和玩法交互：期号、开奖倒计时、8 个位置的 01～20 号码、玩法赔率、按球下注、开奖结果和结算明细。后台提供期号、赔率、账户、注单和开奖控制能力；真实用户、代理、支付等业务能力可以分阶段纳入，但不因此降低数据、安全、可靠性和运维要求。本项目从现在起按面向服务器正式上线、持续运行和交付使用的产品建设，不把“首期”理解为一次性演示代码。

## 1.1 正式产品交付原则（已确认）

- 业务范围允许分阶段确认和实现；生产工程基线从当前阶段开始执行。
- 数据库是业务事实源。表结构必须通过 Flyway 管理，业务数据必须考虑约束、索引、金额精度、时区、历史兼容、备份恢复、保留和幂等，不能依赖前端临时状态或内存数据。
- 安全必须前置到设计：认证授权、最小权限、密码哈希、会话与 Cookie、输入校验、敏感信息脱敏、SQL/JSON/HTML/文件/WebSocket 边界、CORS/CSRF、限流和操作审计均属于交付范围内的工程要求。
- 关键流程必须可恢复和可追溯：事务边界、并发控制、重复请求、任务重试、服务重启、开奖/下注/结算中断和失败状态都要有明确处理方式。
- 发布必须可配置、可观测、可运维：密钥与代码分离，生产配置不入库，健康检查、日志、指标、备份、恢复、迁移、回滚或前向修复策略必须有记录。
- 验收必须标明证据级别，严格区分单元测试、H2、本机 MySQL、服务器现场和生产验证；未执行内容必须标注为未验证。

演示数据、fixture 和临时实现只允许作为隔离的测试手段，不能作为正式业务事实源。任何无法满足上述基线的例外，都必须在方案、风险和验收记录中写明影响范围及收敛计划。

## 1.2 用户确认的产品合规边界（2026-09-19）

用户已确认：本项目完全合法合规，定位为上线后的自娱自乐娱乐产品；产品只使用虚拟积分，不接入充值、支付、提现、转账、代理分成或其他现实资金能力，不形成真实资金流水。系统中的余额、下注额、返还、盈亏、流水和结算记录均为虚拟积分记录，仅用于娱乐、联调、统计和审计。

后续功能设计必须保持该边界。可以保留虚拟积分的数据库持久化、内部流水、幂等和审计能力，但不得实现或暗示积分兑换现金、现实资金结算、充值入口、支付渠道、提现入口或隐藏资金通道。任何扩大到现实资金或可兑换资产的需求，都必须先重新进行范围、合规、安全和上线评审，不能直接沿用当前方案开发。

## 2. 事实基础与范围边界

方案依据：

- `docs/参考资料/汇博盈-业务参考.md` 中的参考页只读观察。
- 参考页公开 HTML 中内嵌的玩法说明和当前赔率展示。
- 当前项目已确定的 Java 21、Spring Boot 4.0.8、MySQL 8.4 LTS、Flyway 技术基线。

首期确认范围：

- 只处理一个游戏类型和一个期号流。
- 每期生成或由后台录入 8 个 01～20 的号码。
- 每个位置独立计算番、单双、大小。
- 自动轮期按当前确认规则运行：每期 300 秒，前 180 秒下注，后 120 秒开奖中；首期期号为 `3000000`。
- 开奖阶段展示 8 个 01～20 的随机预览值，最终开奖再生成 8 个随机值；允许重复，不要求去重。
- 支持番、角、车、严、加、正、通/无、单双、大小、特等玩法的结构化结算。
- 赔率存储为可修改配置，结算时保存下注使用的赔率快照。
- 页面展示当前期、封盘状态、下注列表、开奖结果、赢和输结算明细。

首期业务范围明确不做（不代表工程质量可以按演示处理）：

- 真实资金、支付、提现、充值、代理分成和第三方开奖接口。
- 真实用户账户、密码、权限后台和生产运营流程。
- 参考页的聊天机器人、跟投、飞单、历史走势算法和多游戏入口。
- 未经确认的总结果聚合规则、和局返还金额和特玩法组合金额口径。

## 3. 结算规则

对单球号码 `n`：

```text
fan = n % 4；余数 0 映射为 4
parity = fan 为 1 或 3 时为单，否则为双
size = n 在 01～10 时为小，在 11～20 时为大
```

玩法判定返回 `WIN`、`DRAW` 或 `LOSE`：

| 玩法 | 结构 | 判定 |
| --- | --- | --- |
| 番 | 一个番数 | 命中为赢，其余为输 |
| 角 | 两个番数 | 任一命中为赢，其余为输 |
| 车 | 三个番数 | 任一命中为赢，未选番为输 |
| 严 | 赢号、和号 | 赢号为赢，和号为和，其余为输 |
| 加 | 赢号、两个和号 | 赢号为赢，两个和号为和，余号为输 |
| 正 | 一个主番 | 主番为赢，相对番为输，另外两个为和 |
| 通/无 | 两个赢号、一个输号 | 赢号为赢，输号为输，剩余番为和 |
| 单双 | 单或双 | 按番的奇偶命中为赢，否则为输 |
| 大小 | 大或小 | 按实际号码 11～20/01～10 命中为赢，否则为输 |
| 特 | 一个或多个实际号码 | 号码直接命中为赢，否则为输 |

赔率结算采用可配置口径：

```text
LOSE: -stake
WIN: stake * (odds - 1) 作为净盈亏
DRAW: drawPolicy 配置，首期默认退回本金，净盈亏为 0
```

页面当前观察到的默认赔率为：番 3.850、角 1.950、念 2.900、单双/大小 1.950、正 1.950、车 1.316、两赢一输一和的无组合 1.950、三赢一输的无组合 1.475、特 18.00。实现中必须保存赔率快照，不能依赖开奖后的当前赔率。

## 4. 技术架构

首期使用单体 Spring Boot 服务，浏览器页面由同一服务的静态资源提供，减少前后端联调成本：

```text
浏览器静态页面
    -> REST API：当前期、轮期状态、玩法赔率、下注、演示后台控制
    -> Spring Boot Controller
    -> 领域服务：期号、玩法解析、结算
    -> Repository/JDBC
    -> MySQL 8.4 LTS；测试使用 H2
```

首期暂不引入 Redis、Quartz、WebSocket、MyBatis 和微服务。自动轮期使用 Spring `@Scheduled` 每秒推进，前台使用 REST 轮询；后续若确认多人实时消息需求，再评估 SSE/WebSocket。

## 5. 数据边界

首期至少需要以下实体：

- `game_issue`：期号、状态、轮期阶段、下注结束时间、开奖结束时间、最终 8 个号码、创建和更新时间。
- `game_issue_event`：轮期开始、封盘提醒、进入开奖和开奖结果等幂等机器人事件。
- `game_odds`：玩法编码、显示名称、赔率、和局策略、启用状态、版本。
- `game_bet`：期号、球位、玩法编码、玩法参数、投注额、赔率快照、结算状态、净盈亏。

金额统一使用 `BigDecimal`，数据库使用 MySQL `DECIMAL`。任何开奖结果只能在期号状态允许时写入；结算必须具备幂等保护，同一期同一注单不能重复结算。

## 6. 验收标准

1. 浏览器打开首页后能够看到当前期、8 个球位、倒计时、玩法赔率和下注区域。
2. 后台演示接口可以设置 8 个号码和当前期状态，前台刷新后显示结果。
3. 输入 `第8球/3番15` 等价的结构化下注后，能够保存下注和赔率快照。
4. 给定固定号码和固定赔率时，番、角、单双、大小、特、严、加、正、通/无、车的 WIN/DRAW/LOSE 结果与方案表一致。
5. 结算结果显示投注额、判定、赔率和净盈亏，并且重复请求不会产生重复结算。
6. `.\mvnw.cmd test` 在 JDK 21 环境通过；至少包含领域结算单元测试、Controller 参数校验测试和 Flyway/H2 上下文测试。
7. 页面在 375px 手机宽度和桌面宽度下均可操作，不出现横向滚动，输入和按钮具有清晰的焦点及禁用状态。

## 7. 风险与确认项

- 参考页的“特”玩法前端展示金额与普通玩法的金额口径不同，必须通过甲方确认或固定测试样例确认。
- 页面当前展示的是动态赔率，不应直接当成永久产品配置。
- 参考页的总结果、聊天和资金行为不属于首期结算核心，不能为了视觉相似而提前引入。
- 当前仍有部分业务能力按阶段实现，尚不能据此宣称具备完整生产运营能力；未实现的合规、资金、权限、备份恢复和现场运维能力必须明确记录，不能用本地演示或 H2 测试替代正式上线验收。

- 顶部展示演示用户、余额、当前期号、倒计时和封盘状态。

- 文本格式只作为展示和快捷输入，不直接让结算服务依赖字符串解析；提交前转换为结构化下注请求。

### 8.4 演示后台范围

- 赔率管理：修改玩法赔率并立即影响新的赔率快照。
- 演示账户：查看用户余额，增加或扣减虚拟余额并记录原因。
- 期号控制：录入 8 个中奖号码、封盘开奖、开启下一期。
- 注单核对：按期号查看下注、赔率快照、WIN/DRAW/LOSE 和净盈亏。

### 8.5 明确不纳入本阶段

## 10. 当前聊天室与常驻机器人实施记录

### 10.0 当前阶段：确认格式文本下注与固定第 1 球

本阶段在既有虚拟余额和开奖闭环上补齐正式使用所需的文本下注入口。下注文本按 `docs/参考资料/汇博盈-下注规则与文本格式分析.md` 的已确认部分建立白名单：支持番、角、三位车、严/念、加、正、通、三参数无、单双、大小、特及两位/三位省略写法。单数字无、单数字车和其他模棱两可文本暂不接受。

每笔下注固定落到第 1 球，前端不提供球位选择，服务端同时校验并拒绝其他球位。下注只允许发生在 BETTING 阶段；封盘或开奖阶段返回下注无效提示。订单保存赔率快照，开奖后按现有 WIN/DRAW/LOSE 规则幂等结算，扣款、派彩、净盈亏和余额流水均以服务端记录为准。

机器人和前端使用同一套下注文本解析结果：合法文本进入下注服务，疑似下注但格式错误时返回明确指令，不降级为普通聊天；余额、下注结果、净盈亏和流水通过现有服务端查询能力展示。实施计划见 [确认玩法文本下注与结算实施计划](plans/2026-09-17-确认玩法文本下注与结算实施计划.md)。

> **当前部署决策（2026-09-14）：** 当前版本只按一台服务器、一个 Spring Boot 实例设计、开发、验收和运行。当前不引入 Redis、MQ、多实例任务协调、跨节点 WebSocket 广播或专门监控告警平台。项目正式上线后，只有当真实用户量、在线连接数或故障恢复需求证明单服务器不足时，才另行评估多服务器方案。

### 10.11 当前变更：开奖后机器人分段结构化输出

测试玩家是明确标记的联调身份，服务于上线前后的页面、下注、开奖和结算验收；它不是伪装的真实用户，也不用于充值、支付或现实货币交易。数据库通过 `sys_user.user_type = 'TEST'` 和 `demo_user_account.identity_type = 'TEST'` 保留身份边界，测试玩家不能通过普通登录入口登录，前台展示和后台操作均保留“测试玩家”标识。
