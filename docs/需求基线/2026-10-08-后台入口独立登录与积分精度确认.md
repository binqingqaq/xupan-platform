## 2. 三题结论

### 2.1 ①积分精度：保持 2 位小数（对 BY220 的收窄）

| 项 | 结论 | 依据 |
| --- | --- | --- |
| 全站金额/积分精度 | **保持 2 位小数** | 使用者 2026-10-08 确认 |
| BY220 事实（列类型） | `x_admin.score`、`x_robot.score` 均为 `DECIMAL(30,6)` | `local/schema-base.sql:44`（`x_admin` 表自第 11 行起）、`local/schema-base.sql:534`（`x_robot` 表自第 516 行起） |
| BY220 事实（运算） | `rbUpdown()` 与子账号上下分全程**无任何取整/`intval`/`round`**，直接用传入增量做 `setInc/setDec` | `application/common.php:3707-3724`（`rbUpdown`：`setInc('score', $score)` / `setDec('score', $score)`）、`application/admin/controller/Users.php:62-72`（`up` → `setInc`，`down` → 余额校验后 `setDec`） |
| 由此得出 | BY220 实际支持到 **6 位小数**；xupan 的 2 位是**对 BY220 的收窄** | 上两行 |
| 偏离登记 | 登记为**有意偏离**（原因：虚拟积分口径统一与前端展示一致，避免 6 位小数在界面与账本口径上分叉） | 使用者 2026-10-08 确认 + 本文 §5 |
| 工程口径（必须同时满足） | 超精度（如 `0.001`）一律 **400 明确报错**；**禁止静默舍入**；**禁止 500** | 使用者 2026-10-08 确认 ①；现状三处不一致见实施计划 §2.6 |
| 前端体验层 | 子账号「上分/下分」输入框补 `step="0.01"`（后端校验才是防线） | 实施计划 §3.5；BY220 `view/sub/form.html` 本身无 `step`，但走 layui `$.post` 不做原生校验 |

> 说明：BY220 的表单属性"看起来"也只允许两位，但它用 layui 取值提交、不走浏览器原生校验，所以 BY220 实际能提交 6 位；xupan 一度"照抄表单属性却换了提交机制"，反而把 `0.1/0.01` 拦在浏览器侧。本次以**后端 400 校验**为唯一防线，前端 `step` 只做体验提示。

## 3. 追加决定（同为 2026-10-08 使用者确认）

### 3.1 A1：平台侧给玩家上下分，按玩家归属机器扣/回机器积分池

| 项 | 结论 | 依据 |
| --- | --- | --- |
| 扣谁的池 | 平台侧（`GLOBAL` 超管 / `GROUP` 子账号）给**普通玩家**上分 → **扣该玩家所属机器**的积分；下分 → **回补同一台机器** | 使用者 2026-10-08 确认（Q1=A1 + R1=做法①） |
| 谁选机器 | **操作者不选机器**，按玩家归属机器（`demo_user_account.agent_id`）自动判定 | 使用者 2026-10-08 确认（R1=做法①）；理由：玩家已归属某台机器，若让操作者另选，选错即跨机器串账 |
| 托（BOT） | **不联动**机器积分池 | 使用者 2026-10-08 确认；BY220 `application/rbt/controller/Index.php:622-624`（只有 `isrobot == 0` 的普通玩家才 `db('robot')->setDec('score', ...)`）、`:637-641`（托在机器池不足时仍可上分、不扣机器分）——即 BY220 侧上下分对托同样不动机器积分 |
| 为什么必须这样 | BY220 里分只能沿「子账号池/超管 → 机器（`rbUpdown`）→ 玩家（`robot.php`）」单向流转，**不存在"平台直接给玩家发分"** | `application/common.php:3707-3724`（`rbUpdown`：机器 `+score` 与子账号 `−score` 成对，并写 `folder_record`）；`application/rbt/controller/Index.php:610-664`（`UpDownScore`：普通玩家上分才扣机器分、下分才回补；托不扣） |
| 现状偏离 | xupan 现状 `GLOBAL`/`GROUP` 范围是"凭空给玩家钱包加分、不减任何池"，属**既有偏离**；平台后台高频使用后会造成"机器池 + 玩家钱包 总数对不平" | 实施计划 §2.5（`PlayerDeskAdminService.grant()/adjust()`） |
| 附带后果（预期行为，不是缺陷） | 平台侧上下分会**真实消耗机器积分**；给玩家加分前需先给机器上分（等价 BY220 的 `rbUpdown` 前置）；机器池不足按 BY220 文案拒绝，且**余额与流水都不变** | 使用者 2026-10-08 确认（A1）；实施计划 §3.5、§9 |

### 3.2 C1：入口级独立会话

| 项 | 结论 | 依据 |
| --- | --- | --- |
| 刷新 Cookie 拆分 | 三个：`xupan_refresh`（平台）/ `xupan_console_refresh`（代理后台）/ `xupan_player_refresh`（玩家链接） | 使用者 2026-10-08 确认（Q2=C1） |
