# 当前需求基线：自动轮期与随机开奖

> 当前状态（2026-09-24）：需求已实施，最新实现状态见 [业务模块 03 期号玩法下注与结算](../业务模块/03-期号玩法下注与结算.md)。本文保留当时的确认规则，出现冲突以模块基线为准。

## 1. 已确认规则

- 首期期号为 `3000000`，后续数字期号连续加一。
- 每期总时长 5 分钟，即 300 秒。
- 每期开始后的前 3 分钟，即 180 秒，为 `BETTING`，允许下注。
- 第 180 秒进入 `DRAWING`，自动封盘，持续 2 分钟；前台显示“开奖中”，8 个球号可以滚动变化。
- 第 300 秒生成最终开奖结果，期号进入 `SETTLED`，执行待结注单结算并发布机器人结果消息。
- 旧期结算后立即创建下一期并进入 `BETTING`，不能停留在“已结”而不创建下一期。
- 8 个球号分别在 01～20 范围内随机生成，允许重复，不要求去重。

## 2. 当前实现

- 服务端使用 Spring `@Scheduled(fixedDelay = 1000)` 推进轮期。
- 期号阶段、开始时间、下注截止时间、开奖截止时间和结算时间写入 `game_issue`。
- 机器人事件写入 `game_issue_event`，按期号和事件类型幂等。
- 最终号码使用服务端 `SecureRandom` 生成并持久化；开奖中的预览号码不覆盖最终结果。
- 前台通过 REST 轮询当前期，使用服务端时间和截止时间计算倒计时。
- 当前为演示账户和本地单实例实现，不代表真实资金或生产级开奖能力。

## 3. 已验证证据

- H2 集成测试验证 `+180s` 进入 `DRAWING`，`+300s` 结算旧期并创建下一期。
- 2026-09-10 本地 MySQL 8.4 服务重启后，接口返回 `3000000`、`BETTING`、阶段截止时间和 `ISSUE_STARTED` 事件。
- 后端完整测试 13 个通过；前端 `npm run typecheck` 和 `npm run build` 通过。

## 4. 当前不包含

- 真实第三方开奖源。
- 真实资金、支付、充值、提现和代理分成。
- 生产多实例调度锁、故障补偿和完整审计。
- WebSocket/SSE 实时通信。
- 已确认的特玩法本金口径、和局返还和总结果聚合规则。
