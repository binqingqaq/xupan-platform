## 1. 为什么需要这份基线

用户 2026-10-02 明确：要做的"中心上游"是**让自己成为代理的上级盘口**，不是接入真实外部平台。BY220 自身也没有中心上游（其 `x_rbwp` 只有 `code=k28/name=本地盘口/websiteUrl=http://127.0.0.1:9999`，且该地址无服务；`BY220_LOCAL_MODE=1` 会绕过真实登录）。

因此这是**新建一个业务域**。中心上游本质是一套账本系统，在账本建模不达标的地基上直接开发必然返工。本文档把"准入条件"固定下来：**原则逐条达标后才进入中心上游服务端开发**。

## 2. 业务定义（对齐需求文档）

### 2.1 一句话

```text
代理甲 ─┐
代理乙 ─┼→ 中心上游 API → 中心数据库 → 中心管理端（主庄）
代理丙 ─┘
```

代理仍使用自己的本地玩家与下注系统，只是在**报网设置里选择「中心上游」并填入自己的账号/Token**，订单就进入中心。

### 2.2 两层账（需求文档第 10 节）

| 层 | 关系 | 现状 |
| --- | --- | --- |
| 第一层 | 玩家 ↔ 代理/平台（本地虚拟积分结算） | **已实现** |
| 第二层 | 代理/平台 ↔ 上游（中心） | **本文档要建** |

上报的目的是**把代理/平台的风险转移一部分到上游**，不是让上游直接给玩家结算。玩家赢：本地赔玩家，中心再赔代理；玩家输：本地收玩家，中心再从代理收。

### 2.3 必须守住的业务规则

| 规则 | 依据 |
| --- | --- |
| 盘口 A/B/C/D **不是**代理身份，只是上游内部线路；代理身份靠**代理 ID / UserName / Token / 上游账号**区分 | 需求文档 §14 |
| 共用同一上游账号会导致余额混合、订单归属不明、风险共用、退款不清 → 必须禁止或明确隔离 | 需求文档 §14 |
| 报网类型最少一个，就叫「中心上游」，所有代理都选它，用**不同 Token** 区分代理 | 需求文档 §23.9 |
| 超时**不等于失败**，不能直接退款；需要查询上游状态、等待确认、人工处理或按规则重试 | 需求文档 §12.3 |
| 失败退单开：退玩家积分 → 发取消消息 → 删除或关闭本地订单；关：保留订单 → 标记失败 → 等待重试 | 需求文档 §12.4、§13.2 |
| 只有在线时自动上报才有意义；上游掉线应尝试重新登录 | 需求文档 §13.3、§13.4 |
| 管理端：最小可无界面只有 API；可运营在超管后台加「中心上游」菜单 | 需求文档 §23.7 |

### 2.4 闭环判据（需求文档 §23.10）

```text
订单已接受 + 开奖已确定 + 玩家已结算 + 代理/上游已结算
+ 流水已写入 + 订单状态已关闭 + 没有超时/退款/对账遗留
```

### 2.5 合规边界（不可突破）

中心上游的金额**只能表示虚拟积分与内部风险敞口**，不得形成真实资金链路、充值、提现、真实货币结算或可兑换资产；不接入真实外部上游。此边界为项目强制约束（见 `AGENTS.md`）。

## 3. 账本原则 9 条逐条现状

> 判定口径：**通过** = 已有代码满足；**部分** = 一层达标另一层缺失；**不通过** = 未满足。
> 证据均为本次实读代码/迁移的行号。

| # | 原则 | 状态 | 现状与证据 |
| --- | --- | --- | --- |
| 1 | 玩家余额、代理可用额度、代理冻结额度、上游未结算金额是**不同事实**，不能共用一个余额字段 | **不通过** | 玩家侧有独立 `demo_user_account.balance` + `demo_balance_ledger`；**代理侧只有单个 `agent.score` 列**（`V35__补齐BY220子账号与机器管理字段.sql:42` 仅 `CHECK (score >= 0)`），无可用额度、冻结额度、上游未结算的分离 |
| 2 | 余额变化**必须同时写流水**，不允许只改余额 | **部分** | 玩家侧✅：`demo_balance_ledger` 追加 + 唯一幂等键（`V8:16` `uk_demo_balance_ledger_idempotency`）。**代理侧❌**：`PlatformAdminService.java:124-132` 为裸 `UPDATE agent_group SET ... score=? ...`，整值覆盖且**不写任何流水** |
| 3 | 账本记录应**追加保留**，不应直接覆盖或删除历史 | **部分** | 玩家流水追加✅；代理层无流水；**审计日志只能写不能查**——`OperationAuditRepository` 仅有 `record(...)`，无任何查询方法；`PermissionCode.AUDIT_READ` 已声明但**无任何控制器/服务校验**；前端无日志页面 |
| 4 | 本地玩家注单和**上游上报订单是不同实体**，不能只靠一个状态字段区分 | **不通过** | 现在就是单字段：`game_bet.report_status`（`ReportConfigRepository.updateReportStatus`），与原则明文禁止的做法一致 |
| 5 | 金额使用精确整数或定点小数，禁止浮点误差进入账本 | **通过** | 全仓金额使用 `BigDecimal`，数据库 `DECIMAL(18,2)` |
| 6 | 上报、退款、撤单、结算、**对账**都必须有幂等键 | **部分** | 上报：状态迁移带 `allowedFrom` 条件（幂等）；退款/撤单：`CANCEL_REFUND:<betId>` 唯一键；结算：`uk_demo_balance_ledger_idempotency`；**对账：不存在** |
| 7 | 超时记录必须保存**"未知"语义**，不能写成已失败 | **通过** | `TIMEOUT` 是与 `FAILED` 并列的独立状态（`V56` 扩展 `game_bet.report_status` CHECK 并加索引）；实测超时只标记、不退款、不删单，且可重报 |
| 8 | 同一上游账号被多代理共用时必须**禁止或明确隔离** | **不通过** | `report_username` 只在 `V35`（子账号 `agent_group`）与 `V56`（机器 `agent`）建了列，**无任何唯一约束**；多台机器可共用同一上游账号 |
| 9 | Token 只保存哈希或受控密文，原文不得进入普通日志和前端持久化 | **通过** | 报网密码复用 `PlayerLinkTokenCipher`（AES-GCM），库内存 `v1.` 前缀密文，接口只回 `hasPassword` 布尔；实测按明文检索命中 0 |

**汇总：通过 3 条（5、7、9），部分 3 条（2、3、6），不通过 3 条（1、4、8）。**

## 7. 明确不做 / 暂缓

- **真实外部上游**（TT / K28 / ls8899 / wns / lx / hy 等真实第三方飞单平台）：不实现。BY220 的 `flyers_type` 指向这些真实平台，属于"外部上游模式"，按合规边界不纳入。
- **中心上游与真实资金**：永远不做。
- **`127.0.0.1:9999` 本地盘口服务**：BY220 中该地址无真实服务；本项目继续用本地模拟适配器，不新建该服务。
- **BY220 `Logi888n.php::imdex` 之类免密登录后门**：**不得平移**（该文件零密码校验直接以超管 `id=1` 写入会话；正常路由因类名不匹配 404，但一旦被重写映射即为后门）。
