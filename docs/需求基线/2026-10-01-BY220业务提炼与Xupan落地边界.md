## 1. 结论摘要

BY220 可以概括为：

```text
玩家前台 + 代理运营后台 + 平台管理后台
          + 本地游戏与本地结算
          + 可选报网/盘口客户端
          + 可选上游或中心上游二层结算
```

它的关键价值不是某一张页面或某一段 PHP 代码，而是以下业务结构：

1. 平台、管理子账号、代理机器账号、玩家、托是不同身份，不能用一个普通用户模型全部替代。
2. 玩家与平台/代理完成第一层虚拟积分结算；代理/平台与上游或中心上游之间还可以存在第二层结算。
3. 游戏、报网类型、盘口线路、上游账号是四个不同概念。
4. 本地订单状态和上游上报状态不能共用一个模糊状态字段。
5. 超时不能直接等同失败，必须先查询或确认，再决定重试、退款或人工处理。
6. 真正闭环必须同时满足：订单已接受、开奖已确定、玩家已结算、上游侧已结算、双方流水已写入、订单已关闭、没有退款和差异遗留。
7. 中心上游的本质是让多个代理通过标准 API 把订单提交到同一个中心，由中心完成认证、接单、风控、退款、结算、对账和管理。

Xupan 当前已经具备一部分相近能力：

- 管理员认证与权限。
- 普通玩家、TEST 玩家、BOT/托和服务端机器人。
- 玩家链接登录和房间聊天。
- 单游戏期号、下注、开奖、结算和虚拟积分钱包。
- 玩家前台、统一运营后台、上下分审批、下注榜、赔率与限额。
- 托自动行为和基础审计、日志、发布基线。

Xupan 当前明确不具备或只是静态占位的部分：

- 管理子账号、机器账号、代理层级和代理归属关系。
- 每个代理独立的数据隔离和运营视图。
- 代理自己的虚拟积分账户、额度、冻结和在途风险。
- 正式报网领域、盘口线路、上游账号、报网状态和自动登录。
- 本地订单与上报订单分离的双状态机。
- 第二层代理/上游账本及完整对账。
- 中心上游认证 API、中心订单、中心信用、中心结算和管理端。
- 经确认的飞单、抽水、代理分成或多游戏上游映射规则。

因此后续不能在现有玩家钱包表上直接硬加几个“报网字段”来冒充完整业务。正确路径是先确认业务规则，再建立独立领域和状态机，最后接入现有玩家、游戏、钱包和后台模块。

## 3. 角色与账号层级

### 3.1 参考账号模型

```text
平台主 / 超级管理员
  └─ 可选：管理子账号/渠道分组
       └─ 机器账号（代理运营账号）
            ├─ 玩家
            └─ 托/BOT
```

无子账号时：

```text
平台主
  └─ 机器账号（代理）
       ├─ 玩家
       └─ 托
```

### 3.2 角色能力

| 角色 | 参考定位 | 主要能力 | xupan 当前对应情况 |
| --- | --- | --- | --- |
| 平台主/超级管理员 | BY220 `admin.php` 最高管理者 | 管理代理、游戏、开奖、玩家、全局统计、强制结算、上游配置、创建子账号和机器账号 | 已有系统管理员和角色权限，但没有代理组织管理层 |
| 管理子账号 | `x_admin.type=0` 的分组或下级管理层 | 管理一组机器账号、拥有积分、控制权限、统一飞单、失效时间 | xupan 当前没有业务子账号模型；现有系统角色不能直接等同于代理子账号 |
| 机器账号/代理 | BY220 `x_robot`，登录代理后台 | 创建玩家和托、上下分、赔率/返水/封盘、查看流水和盈亏、生成玩家链接、配置报网、查看上游余额和押注 | xupan 当前只有平台管理员；玩家直接属于平台，没有代理归属 |
| 玩家 | BY220 `x_rbuser` | 聊天、下注、查分、上下分申请、查询开奖/流水/记录 | xupan 已有普通玩家、链接、聊天、钱包和下注 |
| 托/BOT | `x_rbuser.isrobot=1` | 模拟活跃、自动下注、产生玩家消息和系统反馈 | xupan 已有 TEST+BOT 身份、自动行为和链接工作前提 |
| 服务端机器人 | BY220 中的系统消息角色 | 发布系统消息而非拥有玩家钱包 | xupan 已有独立服务端机器人，不能与 BOT 玩家混为一类 |

### 3.3 xupan 落点

xupan 要实现 BY220 相近效果，至少需要补充或确认：

1. 代理是“系统角色”“组织层级”还是“业务租户”。
2. 子账号是否只是管理员分组，还是拥有独立积分和业务权限。
3. 一个代理是否拥有自己的虚拟积分账户、信用额度和在途风险。
4. 玩家、托、注单、上下分申请和报表是否必须按代理隔离。
5. 平台主、子账号、代理的操作权限和数据可见范围。
6. 代理删除、停用、转移玩家和历史保留规则。

在这些规则确认前，不应直接把 `sys_user` 当成 BY220 的全部账号模型改造。

## 4. 游戏、报网、盘口与上游

### 4.1 概念区分

| 概念 | 回答的问题 | 示例 | 是否为玩家身份 |
| --- | --- | --- | --- |
| 游戏 | 玩家玩什么 | 澳8番摊、快乐8、K28 等 | 否 |
| 玩法 | 在一个游戏中具体怎么下注 | 番、角、正、念、通、单双、大小、特等 | 否 |
| 报网类型 | 订单交给哪套协议或上游系统 | 某个适配器代码、中心上游 | 否 |
| 盘口线路 | 同一上游内走哪条账号池、区域、线路或结算池 | A/B/C/D 盘 | 否 |
| 上游账号 | 以谁的账号、Token、余额和额度向上一级提交 | 每个独立身份的账号配置 | 否 |
| 代理身份 | 订单归属于哪个代理 | 代理 ID、账号名、Token 和绑定关系 | 是运营归属，不是玩家 |

结论：

- 多个代理可以选同一个“盘口线路”，只要上游账号或 Token 独立，不天然冲突。
- 真正会导致余额混合、订单归属不明和退款不清的，是多个代理共用同一个上游账号或 Token。
- A/B/C/D 不是代理身份，不能用它替代代理 ID。
- 报网类型和盘口线路必须分开建模，不能压成一个字符串字段。

### 4.2 BY220 的报网能力

参考文档显示 BY220 已存在或存在基础结构：

- 报网配置页面。
- 上游平台配置表。
- 代理连接上游的账号和状态表。
- 自动上报开关、失败退单开关、在线状态。
- K28 和至少两类其他适配器结构。
- 本地模拟登录和本地模拟盘口。

参考文档同时明确：

- 当前真实本地盘口服务未完成。
- 玩法和上游玩法 ID 的完整映射表为空。
- 本地模式会绕过真实登录。
- 现有系统没有真正可运营的中心上游。

因此 xupan 不能把“页面存在”理解为“上游业务已闭环”。

## 5. 第一层结算：玩家与平台/代理

第一层结算只处理玩家和本地系统之间的虚拟积分：

```text
玩家下注
  -> 校验期号、玩法、余额和限额
  -> 本地生成注单
  -> 扣减玩家虚拟积分并写流水
  -> 等待开奖
  -> 按注单赔率快照结算
```

设：

```text
玩家下注金额 = S
可返还系数 = O
玩家赢时返还 = S × O
玩家赢时净收益 = S × (O - 1)
玩家输时净收益 = -S
```

玩家赢：

```text
下注时：余额 - S
结算时：余额 + S × O
该笔玩家净收益：+S × (O - 1)
平台/代理本地侧镜像盈亏：-S × (O - 1)
```

玩家输：

```text
下注时：余额 - S
结算时：不再返还本金
该笔玩家净收益：-S
平台/代理本地侧镜像盈亏：+S
```

必须保持：

- 下注扣分和结算返还都必须有流水。
- 结算使用注单保存的赔率快照，不能读取开奖后的当前赔率。
- 相同注单重复结算必须幂等。
- 和局、撤销、退款和特玩法的返还口径必须另行确认，不能从上述通用公式自行推断。
- 玩家看到的余额只由本地玩家钱包事实决定。

## 6. 第二层结算：平台/代理与上游或中心上游

第二层结算是 BY220 与当前 xupan 差距最大的部分。

```text
第一层：玩家       <-> 本地平台/代理
第二层：平台/代理  <-> 上游或中心上游
```

订单上报的目的，在 BY220 业务中是降低或转移平台/代理承担的输赢风险。订单进入上游后：

- 上游通常扣减或冻结代理在上游的额度。
- 上游接受或拒绝订单。
- 开奖后，上游与代理完成第二层输赢结算。
- 上游通常不会直接修改本地玩家余额。
- 本地玩家余额仍由本地系统负责。

### 6.1 完整参考链路

```text
玩家在本地下注
  -> 本地保存注单并扣玩家积分
  -> 转换为上游订单格式
  -> 向上游提交
  -> 上游接受/拒绝/超时
  -> 开奖
  -> 本地结算玩家
  -> 上游结算代理/平台
  -> 两边流水与订单状态对账
```

### 6.2 xupan 的边界解释

xupan 当前只能把“上游”设计为：

- 内部虚拟积分信用账户；
- 内部中心上游 API；
- 本地模拟适配器；
- 不连接任何真实外部投注服务、不形成现实资金流水。

如果未来要求接入真实外部上游、真实余额、真实信用、真实输赢或可兑换资产，必须暂停实现，重新完成范围、合规、安全和资金边界评审。

## 7. 订单与上报状态

BY220 旧系统把本地注单和上游状态混在 `x_record` 与 `flyers_status` 中：

| 旧值 | 文档含义 |
| --- | --- |
| 0/1 | 未报 |
| 2 | 已报/已接受 |
| 3 | 失败或超时 |

这个字段只能用于理解历史系统，不能照搬到 xupan。

### 7.1 建议拆成三条业务状态链

以下为正式建模建议，不是已经从 BY220 复制的事实：

#### A. 本地玩家注单状态

```text
ACCEPTED -> SETTLED
ACCEPTED -> CANCELED
ACCEPTED -> VOIDED
```

可选扩展：

- `PENDING_ACCEPTANCE`
- `PARTIALLY_SETTLED`
- `REFUNDED`

xupan 必须明确当前游戏是否允许部分结算、撤单和作废。

#### B. 上报/上游提交状态

```text
NOT_REPORTED
  -> PENDING_SUBMISSION
  -> SUBMITTED
  -> ACCEPTED
  -> REJECTED
  -> TIMEOUT_UNKNOWN
  -> VOIDED
  -> REFUNDED
  -> RECONCILED
```

关键规则：

- `SUBMITTED` 只表示请求已经发出，不表示上游接受。
- `TIMEOUT_UNKNOWN` 不表示失败，不能直接退款。
- `REJECTED` 是明确拒绝，可按规则进入保留、重试或退款。
- `ACCEPTED` 后仍要等待开奖和上游结算，不能直接标记闭环。

#### C. 综合结算状态

```text
PENDING
  -> PLAYER_SETTLED
  -> UPSTREAM_SETTLED
  -> CLOSED
  -> DIFFERENCE
```

只有玩家侧和上游侧都结算、流水一致、订单关闭且无差异，才算真正闭环。

### 7.2 必须保留的关联标识

正式模型至少需要保留：

- 本地注单唯一标识。
- 客户端或业务幂等键。
- 上报请求唯一标识。
- 上游返回的订单号。
- 报网类型、盘口线路和上游账号配置 ID。
- 上报次数、最近请求时间和最近响应时间。
- 上游状态原文和标准化状态。
- 玩家结算记录和上游结算记录。
- 退款、撤单、作废和人工处理的审计记录。

## 8. 自动上报、失败退单与自动登录

### 8.1 自动上报

BY220 文档显示，自动上报至少依赖：

- `flyers_online = 1`
- `flyers_auto = 1`

任一不满足就不自动提交。

正式规则还必须回答：

- 是下注成功后立即上报，还是异步队列上报。
- 同一注单允许重试多少次。
- 重试间隔和退避规则。
- 网络超时后先查询还是直接重试。
- 上游明确拒绝后是否重试。
- 关闭自动上报时，订单如何补报和人工处理。
- 多代理并发上报时如何隔离账号、Token、额度、余额和日志。

### 8.2 失败退单

BY220 文档显示：

```text
开启失败退单：
  上游失败
    -> 本地退回玩家积分
    -> 发送注单取消消息
    -> 删除或关闭本地订单

关闭失败退单：
  上游失败
    -> 本地订单保留
    -> 标记失败
    -> 等待人工或系统重试
```

xupan 不应删除业务订单。正式实现应改为：

```text
确认失败/超时后按规则处理
  -> 若允许退款：退玩家虚拟积分，写退款流水，订单标记 REFUNDED/VOIDED
  -> 若不退款：保留失败状态和重试/人工处理入口
  -> 全过程保留审计和历史状态
```

必须先确认“什么失败才能退款”：

- 上游明确拒绝可以退款吗？
- 请求超时但上游可能已接单，能否退款？
- 已接单后能否撤单？
- 开奖后能否退款？
- 一期多笔组合注单中的部分失败如何处理？

### 8.3 自动登录和在线状态

BY220 在代理掉线后尝试重新登录，并通过轮询/长连接维护上游在线状态。xupan 后续至少要拆出：

- 连接状态：在线、离线、登录中、认证失败、被禁用。
- 业务状态：可接单、封盘、额度不足、人工停用。
- 最近心跳和重登时间。
- 失败原因、重试次数和人工干预记录。

不能只用“在线/离线”一个布尔值表达全部状态。

## 9. 中心上游业务

中心上游可以理解为：

```text
代理甲 ─┐
代理乙 ─┼─> 中心上游 API -> 中心订单/账本/风控 -> 中心管理端
代理丙 ─┘
```

代理仍使用自己的本地玩家系统，只是在报网设置中把订单提交给中心。

### 9.1 必需能力

| 领域 | 业务能力 |
| --- | --- |
| 代理认证 | 代理账号、Token、登录状态、权限、Token 轮换和吊销 |
| 代理账户 | 虚拟余额、信用额度、冻结金额、可用额度、代理等级 |
| 订单接收 | 接单、校验期号、玩法、限额、余额、赔率和封盘状态 |
| 订单状态 | 待处理、已接受、已拒绝、超时、已撤单、已退款、已结算 |
| 结算中心 | 按开奖结果结算、更新代理账户、写代理流水、处理退款和差异 |
| 风控 | 单笔、单期、玩法、代理和全局风险限制 |
| 日志审计 | API 请求、登录、下注、重试、退款、结算和人工操作 |
| 数据隔离 | 每个代理的订单、余额、额度和报表不得互相泄露或混用 |

### 9.2 管理端业务视图

主庄/中心运营方需要看到：

- 总览：今日流水、盈亏、在途订单、待结算订单、异常订单、在线代理数。
- 代理管理：账号、余额、额度、可用额度、在线状态、开放游戏、限额、盈亏。
- 实时订单：代理、玩家、游戏、期号、玩法、金额、赔率、状态。
- 风险：代理风险、玩法风险、每期总敞口、各结果预计盈亏。
- 财务：上下分、结算、退款、流水、对账、调整金额。
- 日志：登录、API、下注、超时、重试、退款、结算。

这些指标中的金额和盈亏，在 xupan 中只能表示虚拟积分和内部虚拟风险敞口。

### 9.3 中心上游成熟度

```text
最小可用：
  API + 中心订单 + 代理 Token + 成功/失败/超时

可运营：
  + 中心账本 + 代理余额/额度 + 风控 + 退款 + 结算 + 管理页面

高可靠：
  + 幂等 + 队列/重试 + 锁 + 对账 + 监控告警 + 多租户隔离
```

BY220 当前只到“服务结构/原型概念”，没有真正中心的订单、余额、额度、风控、结算和对账闭环。

## 10. 部署模式

BY220 文档列出四种模式：

| 模式 | 链路 | xupan 当前处理意见 |
| --- | --- | --- |
| 独立本地模式 | 玩家 -> 本系统 -> 本地虚拟积分结算 | 可优先实现 |
| 内部中心上游模式 | 多个内部代理 -> 中心上游 API -> 中心虚拟账本 | 可作为目标业务，但必须先确认代理和二层账规则 |
| 外部上游模式 | 本系统 -> 外部上游 | 不纳入当前实现；任何真实外部资金或投注承接必须先合规评审 |
| 混合模式 | 不同代理选择本地、中心或外部 | 只有在三类模式都定义清楚后才考虑 |

不能因为 BY220 页面里存在“报网类型”选择，就直接在 xupan 开放外部上游或真实资金链路。

## 13. 数据与账本原则

1. 玩家余额、代理可用额度、代理冻结额度和上游未结算金额是不同事实，不能共用一个余额字段。
2. 余额变化必须同时写流水，不允许只改余额。
3. 账本记录应追加保留，不应直接覆盖或删除历史。
4. 本地玩家注单和上游上报订单是不同实体，不能只靠一个状态字段区分。
5. 金额使用精确整数或明确精度的定点小数，禁止浮点误差进入账本。
6. 所有上报、退款、撤单、结算和对账操作必须有幂等键。
7. 超时记录必须保存“未知”语义，不能写成已失败。
8. 同一上游账号被多个代理共用时必须禁止或明确建立归属隔离方案。
9. Token 只保存哈希或受控密文，原文不能进入普通日志和前端持久化。
10. 订单、流水、结算和审计必须能通过同一业务链路追溯。

## 14. 建议的业务实现顺序

这里只给出业务能力顺序，不替代后续实施计划。

### 阶段 0：规则确认

先确认：

- 代理层级和目标边界。
- 中心上游是否确认要做。
- 外部上游是否永久不做，还是待合规评审。
- 第一层和第二层账本的解释。
- 订单、上报、退款、撤单、超时和结算状态。
- 风控、限额和信用的业务口径。

### 阶段 1：代理组织与归属

- 平台主、子账号、代理机器账号。
- 代理拥有玩家和托。
- 代理级权限、数据隔离和报表。
- 保留现有管理员、玩家和 BOT 能力。

### 阶段 2：本地核心收敛

- 将现有单游戏本地下注、扣分、结算和玩家钱包整理为稳定领域。
- 明确本地注单状态和审计。
- 明确上下分、退款和撤单对钱包的影响。

### 阶段 3：内部报网域与本地模拟上游

- 报网类型、盘口线路、上游账号配置。
- 本地模拟适配器。
- 上报订单、上报尝试和上报状态。
- 自动上报、超时、重试和人工处理。
- 失败退款和订单作废。

### 阶段 4：第二层账本与对账

- 代理/平台在上游的虚拟余额、信用、冻结和可用额度。
- 上游侧结算、退款和流水。
- 本地订单与上游订单对账。
- 差异处理和人工调整审计。

### 阶段 5：中心上游

- 代理认证和 Token。
- 中心代理账户和信用。
- 中心接单、风控、退款、结算和状态机。
- 中心管理端和对账。
- 中心 API 的幂等、错误码、超时和审计。

### 阶段 6：外部接入评审

只有用户明确要求，且通过合规、安全、资金边界和运维评审后，才能讨论任何真实外部上游。默认状态是禁止接入。

## 15. 必须由用户后续确认的问题

以下问题不能由实现者自行假设：

1. xupan 是否真的要引入代理和子账号，还是只需要做出相近界面？
2. 代理层级有几级，是否支持子账号下多个代理？
3. 代理是否拥有独立的虚拟积分余额和可分配额度？
4. 玩家和托是否必须归属某个代理，历史数据和现存玩家如何迁移？
5. “中心上游”是否确认为内部虚拟积分 API？是否允许任何真实外部上游？
6. 第二层结算是否只用于虚拟积分审计，还是要影响用户侧展示的盈亏？
7. 计划支持多少游戏和玩法，是否需要上游玩法 ID 和赔率映射？
8. 多个代理能否共用同一上游账号或 Token？如果共用如何保证订单和余额归属？
9. 自动上报是同步还是异步，重试次数、间隔、优先级和人工处理规则是什么？
10. 什么状态下允许退款，什么状态下必须人工处理，什么状态下绝对不能退款？
11. 超时订单的查询、等待、重试和关闭时限。
12. 撤单窗口和封盘时间如何计算。
13. 代理余额、信用额度、冻结金额和可用额度的公式。
14. 对账频率、差异容忍度和差异处理权限。
15. 平台、子账号、代理、运营和审计分别能看到哪些数据。
16. 审计、订单、流水、连接日志和敏感配置的保留期限。
17. 旧 BY220 是否需要数据迁移；如果要，如何清洗其错误状态、重复数据和敏感配置。

## 17. 本文提炼后的最终判断

BY220 与 xupan 的关系应定义为：

```text
BY220：
  提供业务发现、页面行为、旧流程证据和待验证原型

xupan：
  提供正式领域模型、清晰状态机、虚拟积分账本、幂等、审计、对账和生产化基础
```

真正需要实现的不是 BY220 的旧字段，而是它背后的业务能力：

```text
账号层级
  -> 代理归属
  -> 玩家/托运营
  -> 游戏下注
  -> 第一层玩家结算
  -> 可选内部报网
  -> 第二层虚拟积分结算
  -> 中心上游
  -> 对账、风控和审计
```

分界线必须始终明确：

> 可以采纳 BY220 的业务结构、交互范围和状态思路；不能直接复制旧代码、旧数据库、旧状态编码、敏感配置和未确认的外部资金能力。所有金额和结算在 xupan 中仅解释为虚拟积分。
