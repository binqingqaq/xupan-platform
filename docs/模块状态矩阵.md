## 1. 状态定义

| 状态 | 含义 |
| --- | --- |
| 待确认 | 业务规则、范围或口径尚未由用户确认 |
| 已规划 | 已有方案或计划，但尚未形成可验收实现 |
| 开发中 | 当前工作区或分支正在实现 |
| 代码完成未验证 | 代码存在，但缺少对应自动化或运行态证据 |
| H2 已验证 | 测试数据库迁移、单元或集成测试通过 |
| 本机 MySQL 已验证 | 本机 MySQL 8.4 LTS 迁移或接口链路通过 |
| 服务器已验证 | 已在目标服务器现场验证 |
| 生产已验证 | 已在正式生产环境验证 |
| 暂不纳入 | 当前阶段明确不做，不代表需求已完成 |

## 3. 当前优先级

### P0：影响后续所有功能

- 继续维护身份、权限、虚拟积分和数据库事实源边界。
- 新功能必须更新模块归属、依赖关系和验收证据。
- 对“代码完成”“本机 MySQL 通过”“服务器通过”“生产通过”保持严格区分。

### P1：适合作为下一批业务功能

- 玩家前台实际操作体验和业务页面联动。
- 期号、玩法、下注、开奖、结算的完整可视化运营流程。
- 报表和对账的本机 MySQL 现场验收。
- 统一后台中仍是占位或兼容入口的运营模块收敛。
- 上下分确认、声音提醒和最近上下分记录。

### P2：暂不抢先实现

- Redis、多实例、MQ、分布式调度。
- 现实资金和支付相关能力。
- 未确认的抽水、飞单、代理和资产兑换规则。

## 4. 使用方式

新需求进入时，先在本表找到所属模块：

1. 如果模块不存在，先在《产品总览与模块地图》中增加模块。
2. 如果模块存在但规则不清，先标记为“待确认”，不要直接写代码。
3. 如果模块存在且规则明确，建立跨模块影响清单，再创建实施计划。
4. 开发和验收结束后，只更新实际证据对应的状态，不提前提升环境等级。
