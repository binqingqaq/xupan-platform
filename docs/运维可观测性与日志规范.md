# 运维可观测性与日志规范

## 1. 文档定位

本文档定义 xupan-platform 当前单服务器、单 Spring Boot 实例的日志、健康检查、运行指标和故障排查边界。

本阶段采用应用日志、systemd/journald、Spring Boot Actuator 和数据库业务记录组合的轻量方案。它用于支持开发验收和单服务器维护，不等同于集中式监控平台，也不代表多节点高可用。

## 2. 四类证据边界

| 类型 | 主要位置 | 解决的问题 | 不能替代的内容 |
| --- | --- | --- | --- |
| 应用运行日志 | journald、生产滚动日志 | 请求状态、异常堆栈、调度器和 WebSocket 失败 | 业务事实和资金流水 |
| 健康与运行指标 | /actuator/health、/actuator/info、/actuator/metrics | 进程、JVM、HTTP、数据库和队列是否异常 | 单条业务操作的完整审计 |
| 业务审计 | sys_login_log、sys_operation_log | 谁在什么时间执行了什么管理操作 | JVM 崩溃和线程堆栈 |
| 业务状态 | chat_robot_dispatch、chat_outbox、chat_message 等 | 机器人、消息和重试当前处于什么状态 | 应用是否已经停止或磁盘是否已满 |

## 3. 统一日志字段

HTTP 访问日志至少包含：

- timestamp：日志时间。
- level：日志级别。
- logger：产生日志的类或组件。
- requestId：一次 HTTP 请求的关联标识。
- httpMethod：请求方法。
- path：请求路径，不带 query string。
- status：HTTP 状态码。
- durationMs：请求耗时。
- userId：只有已认证且确实需要时记录内部 ID，不记录 Token 或完整用户对象。

业务日志按需增加 eventId、messageId、roomCode、connectionId、robotId、dispatchId 等内部标识。消息正文、密码、Cookie、Access Token、Refresh Token 和 WebSocket ticket 不属于允许字段。

## 4. 日志级别

- INFO：服务启动和停止、低频生命周期变化、正常完成的关键后台任务。
- WARN：权限拒绝、参数拒绝、业务跳过、自动重试、连接被策略关闭等可预期异常。
- ERROR：未预期的 5xx、数据库访问失败、调度器扫描失败、广播失败、JVM fatal error。
- DEBUG：本地诊断细节。生产默认关闭，不得用 DEBUG 绕过敏感信息脱敏规则。

登录失败、参数校验失败和普通业务拒绝必须保持低噪声；不能因为用户输入错误写出完整异常堆栈。通用 500 必须记录异常类型、请求路径、requestId 和堆栈。

## 5. requestId 规则

1. 每个 HTTP 请求都必须有 requestId。
2. 请求未提供合法 UUID 时由服务端生成新的 UUID。
3. 响应通过 X-Request-Id 返回同一个值。
4. MDC 使用 requestId 作为线程上下文。
5. 请求结束后必须清理 MDC，防止线程池复用造成串线。
6. 错误响应中的 requestId 必须能够在 journald 或滚动日志中搜索到。
7. WebSocket 消息帧不复制 HTTP 请求体；握手和连接日志使用 connectionId，不记录 ticket 原文。

## 6. 日志存储和保留

本地开发和测试默认使用控制台日志，不把日志文件写入 Git 工作区。

生产环境：

- systemd 标识为 xupan-server，标准输出和错误输出进入 journald。
- 应用可同时写入 /opt/xupan-platform/logs/xupan-server.log。
- 单文件目标上限为 50 MB，历史保留 30 天，总容量上限为 2 GB。
- 日志目录由 xupan:xupan 持有，目录权限使用 0750。
- journald 需要设置磁盘上限和最长保留时间；应用不能自行覆盖系统级 journald 配置。
- 删除日志前先确认不再被进程写入，并保留故障期间的必要证据。

日志保留策略是可验证配置，不以一次启动成功作为验收结论。

## 7. 第一版运行指标

Spring Boot Actuator 提供 JVM、HTTP、数据库连接池和应用基础指标。项目自定义指标包括：

- xupan_robot_dispatch_pending：待处理机器人 dispatch 数量。
- xupan_robot_dispatch_failed：失败机器人 dispatch 数量。
- xupan_chat_connections：当前 WebSocket 连接数。
- xupan_chat_outbox_pending：待广播 outbox 数量。

指标端点只对拥有 SYSTEM_MONITOR_READ 权限的管理员开放。/actuator/health 可以用于反向代理探测，但不显示敏感数据库详情。

## 8. 常用排查顺序

### 8.1 页面或 API 无法访问

1. 检查 systemd：systemctl status xupan-server。
2. 查看最近日志：journalctl -u xupan-server -n 200 --no-pager。
3. 检查健康：curl -fsS http://127.0.0.1:8080/actuator/health。
4. 检查 Nginx 状态和错误日志。
5. 如果返回 500，使用响应中的 requestId 搜索应用日志。

### 8.2 服务反复重启或疑似崩溃

1. 检查重启次数：systemctl show xupan-server -p NRestarts。
2. 查看时间窗口：journalctl -u xupan-server --since "-30 min"。
3. 检查 /opt/xupan-platform/logs/hs_err_pid*.log。
4. 检查磁盘空间、MySQL 连接和 Flyway 启动错误。
5. 未确认原因前不要反复重启或删除日志。

### 8.3 机器人没有发消息

1. 查看 chat_robot_dispatch 的 status、attempt_count、last_error 和 next_attempt_at。
2. 查看 xupan_robot_dispatch_pending 和 xupan_robot_dispatch_failed。
3. 用 dispatchId、eventId 和 messageId 关联应用日志与业务表。
4. 确认失败重试是否已经达到 max-attempts。

### 8.4 聊天室不实时

1. 检查 ws-ticket 请求是否成功。
2. 检查 WebSocket 是否返回 101。
3. 检查 xupan_chat_connections 和广播失败日志。
4. 检查消息是否已经写入 chat_message 和 chat_outbox。
5. 不使用旧 ticket 重复验证，也不在日志中搜索或记录 ticket 原文。

## 9. 当前告警边界

当前阶段先实现本地可发现和可查询能力：

- 健康端点失败。
- systemd 服务不为 active。
- 服务连续重启。
- 数据库或 Flyway 启动失败。
- 机器人 FAILED 持续增加或 PENDING 长时间不下降。
- 日志目录或 journald 使用量接近上限。

短信、邮件、钉钉、企业微信、Webhook、Prometheus 和 Grafana 等外部告警渠道需要单独确认，不在当前实现中伪造为已接入。

## 10. 验收要求

- HTTP 500 响应的 requestId 能在应用日志中定位同一次请求。
- 未登录、普通用户和监控权限管理员访问 Actuator 的结果符合权限设计。
- 数据库指标查询失败不会静默返回正常的零值。
- 日志滚动和保留策略可以通过真实文件或配置检查确认。
- systemd 崩溃自动恢复、journald 查询、JVM fatal error 路径和健康检查均在真实运行环境独立记录证据。
- 文档区分本地自动化、真实 MySQL、服务器 systemd、浏览器人工操作和外部告警渠道，不把未执行内容写成完成事实。
