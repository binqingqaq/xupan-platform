## 1. 模块边界

本模块只处理虚拟积分，不处理现实资金。系统中的余额、下注额、返还、盈亏和流水不能兑换现金，也不代表充值、支付、提现、转账或代理分成。

## 3. 核心流程

```text
机器账号在 /console 上分或下分（平台侧 A1 分支代码保留但已无 UI 入口）
  -> AGENT_CONSOLE_READ + AGENT_PLAYER_MANAGE（机器账号；平台侧为 USER_MANAGE / AGENT_PLAYER_MANAGE）
  -> 金额校验（统一 2 位小数，超精度 400）
  -> 玩家状态校验
  -> 判定玩家归属机器（demo_user_account.agent_id；操作者不选机器，R1=做法①）
  -> 先校验机器积分池：不足则在写任何余额之前拒绝（机器池 / 玩家钱包 / 流水三样都不变）
  -> 普通玩家：扣/回该机器积分池 → 事务更新玩家余额
  -> 托（BOT）：不联动机器池
  -> 写入 PLAYER_TOP_UP / PLAYER_DOWN 流水和幂等标识
  -> 返回服务端最新余额
```

```text
玩家聊天申请上分/下分
  -> 创建 player_point_request(PENDING)
  -> 不改变余额
  -> 机器账号在 /console「上下分确认」同意（/api/admin/player-desk/point-requests/{id}/approve）
       -> 与手动上下分走同一条链路（changeScoreForAgent）
       -> 先扣/回玩家归属机器积分池；机器池不足则拒绝且三样都不变
       -> MACHINE 范围扣机器账号自己那台（2026-10-08 修掉原先完全不扣池的老问题）
       -> 事务锁定钱包 → 写钱包流水（reason 为「代理上分/下分：<玩家名>」）
       -> 申请标记 APPROVED
  -> 机器账号拒绝
       -> 不改变余额
       -> 申请标记 REJECTED（审批原因落 review_reason）
```

```text
下注
  -> 校验玩家身份和期号
  -> 托自动下注先按可用余额与剩余额度压降金额
  -> 锁定/校验余额
  -> 保存注单和赔率快照
  -> 扣减虚拟积分
  -> 写流水
```

```text
托随机上分申请（自动模式）
  -> 按配置概率触发
  -> 已有待审批申请则跳过
  -> 直接创建 player_point_request(PENDING)
  -> 不产生聊天消息，等待管理员在「上下分确认」处理
```

```text
结算
  -> 读取注单快照和开奖结果
  -> 幂等判定 WIN/DRAW/LOSE
  -> 更新注单状态和净盈亏
  -> 派彩或退回虚拟积分
  -> 写流水
```

## 4. 必须保持的规则

### 4.1 业务规则（BY220 对照）

- 余额变化不能只改余额字段，必须有流水（BY220 的申请落在 `x_folder`：BY220: local/schema-base.sql:102；积分流水落在 `x_money_log`：BY220: local/schema-base.sql:261；写流水入口 BY220: application/common.php:1872）。
- 软删除玩家保留历史钱包和流水，但不能继续上下分或下注。
- 与 BY220 的差异：BY220 删玩家是**物理删除并把玩家分数退回机器**（BY220: application/rbt/controller/Index.php:235）。
- 本项目改为软删除且不退分，是对上述行为的偏离，尚未取得使用者确认：未对齐核对。
- BOT 使用同一套钱包事实，不能用独立内存余额（BY220 的托与玩家共用 `x_rbuser.score`：BY220: local/schema-base.sql:397）。
- 待审批申请不是余额事实；当前余额仍以钱包表和服务端流水为准（BY220 的申请与余额是两张表：BY220: local/schema-base.sql:102、BY220: local/schema-base.sql:397）。
- 拒绝申请保留 `REJECTED` 审计事实，但不产生钱包流水（BY220 拒绝入口 BY220: application/rbt/controller/Index.php:298）。
- 托的自动下注在余额不足时只降额，不自动触发上分；上分申请由独立概率控制（BY220 托仅在余额低于 `tuoMin` 时另发上分申请：BY220: application/console/Websocket.php:561）。
- **金额精度（2026-10-08）**：全站金额/积分统一 **2 位小数**；超精度（如 `0.001`）一律 **400**（`SUB_ACCOUNT_SCORE_INVALID` / `MACHINE_SCORE_INVALID` / `WALLET_AMOUNT_INVALID`），**禁止静默四舍五入、禁止 500**；`0.01` / `0.1` 正常可用。共享口径 `com.xupan.server.web.MoneyAmounts`（调用方传入的原始值/目标值走 `requireTwoDecimals`，减法算出的差额走 `rounded(HALF_UP)`）。**BY220 实为 `DECIMAL(30,6)`（支持 6 位小数、`rbUpdown` 无取整）→ 2 位是对 BY220 的收窄**：`xupan 扩展（使用者确认 2026-10-08）`，依据 [后台入口独立登录与积分精度确认](../需求基线/2026-10-08-后台入口独立登录与积分精度确认.md) §2.1。
- **平台侧上下分沿机器池流转（A1，2026-10-08；URL 层已不可达）**：平台侧（超管 `GLOBAL` / 子账号 `GROUP`）给**普通玩家**上下分必须扣/回**该玩家归属机器**的积分池；**托（BOT）不联动**；机器池不足时在写任何余额之前拒绝，机器池 / 玩家钱包 / 流水三样都不变。理由：BY220 里分只能沿「子账号池/超管 → 机器（`rbUpdown`）→ 玩家（`robot.php`）」单向流转，**不存在“平台直接给玩家发分”**。**副作用（预期行为，不是缺陷）**：平台侧上下分真实消耗机器积分，给玩家加分前需先给机器上分（等价 BY220 的 `rbUpdown` 前置）。**2026-10-08 现状**：平台侧 UI 入口（`/platform-admin/player-workbench`）已删除，且 `/api/admin/player-desk/**` 已收紧为仅 `PERM_AGENT_CONSOLE_READ`，**该分支在 URL 层已不可达（死代码，保留未删）**；是否独立清理见 [缺口表 §4.1 D2](../对齐基线/BY220对齐缺口表.md)。`xupan 扩展（使用者确认 2026-10-08）`，依据 [后台入口独立登录与积分精度确认](../需求基线/2026-10-08-后台入口独立登录与积分精度确认.md) §3.1（Q1=A1 + R1=做法①）。
- **池不足文案分两路**：机器端照抄 BY220「您的账号剩余积分不足以完成本次上分！」（BY220: application/rbt/controller/Index.php:620）；**平台侧**用「该玩家所属机器的积分不足以完成本次上分！」。错误码两路都是 `AGENT_SCORE_INSUFFICIENT`。

### 4.2 工程不变量（工程基线）

- 重试、重复请求和服务重启不能重复扣分或派彩（工程基线）。
- 报表读取钱包流水，不能再建第二套统计余额（工程基线）。
- 审批使用稳定幂等键，重复或并发审批不能重复加减积分（工程基线）。
- **已知遗留**：审批路径的钱包流水 `reason` 由“审批原因”改为共享服务生成的「代理上分/下分：<玩家名>」（审批原因仍落 `player_point_request.review_reason`），**重放修复前已落库的 `POINT-REQUEST:<id>` 钱包流水会因 reason 不一致返回 409 `AGENT_SCORE_IDEMPOTENCY_CONFLICT`**（运维中间态）；一次审批现在写**两条审计**（原 `USER_MANAGE` 审批行 + `changeScore` 内部 `AGENT_PLAYER_MANAGE` 行）。**审批路径的运行态未单独验收，由 H2 覆盖**（工程基线）。

## 8. 流水保留期限（使用者确认 2026-10-09）

- 玩家虚拟钱包流水和已结注单保留 3 年（1095 天），再由每日分批清理任务清理；已结注单关联的改单和钱包流水一并删除，独立旧钱包流水也按期限清理。
- `agent_ledger` 超过 3 年清理。中心账本只清理非中心订单引用流水；中心订单相关流水和 `center_reconciliation_disposition` 按现有对账追溯规则保留。未结算注单、被上游/中心对账引用的注单和流水不清理。
- 清理幂等流水后，超过期限的历史幂等键不再提供永久防重保证；现有余额不被清理任务改写。
