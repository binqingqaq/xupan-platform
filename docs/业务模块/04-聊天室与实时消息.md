# 业务模块 04：聊天室与实时消息

> 当前状态：单实例 REST/WebSocket 闭环已形成；玩家历史窗口已限制为最近4小时；生产高可用不在当前基线内。

## 1. 模块职责

负责大厅房间、历史消息、发送者归属、消息顺序、客户端幂等、禁言、已读游标、outbox、WebSocket 广播、断线补偿和机器人反馈。

## 2. 事实源

- `chat_room`：房间和权限。
- `chat_message`：用户、BOT、ROBOT 消息和序号。
- `chat_outbox`：待投递、失败、重试和广播事实。
- `chat_read_cursor`：用户已读位置。
- `chat_user_mute`：禁言状态。
- `player_point_request`：聊天上下分指令产生的待审批业务申请，不是聊天消息的替代记录。

浏览器本地状态只能做缓存或交互状态，不能作为消息事实源。

## 3. 消息流程

```text
用户/系统产生消息
  -> 服务端恢复发送者身份
  -> 纯文本和容量校验
  -> 房间权限/禁言校验
  -> 写 chat_message、序号和 outbox
  -> 事务提交后广播
  -> 客户端 ACK/游标推进
  -> 断线后 REST 补偿
```

下注和结算反馈必须复用正式消息服务，不能由前端拼接假消息。

### 3.1 历史窗口与新消息提示

- 玩家大厅初始加载最近消息，向上滚动时按 `beforeSequence` 分页加载。
- 只展示服务端时间最近4小时内的消息，达到边界后停止继续加载。
- 加载更早消息时保持当前阅读位置，不能因内容插入跳动到底部。
- 用户不在消息底部时，新消息只增加未读数量，不强制滚动。
- 右下角显示 `▼ N条新消息` 浮动提示；点击后回到最新聊天节点并清空未读数。
- 4小时之前的数据仍保留在数据库，不作为当前大厅历史窗口展示。

`上金额`和`下金额`属于聊天触发的业务指令：

- 用户原文和机器人“待审批”反馈必须持久化到聊天室。
- 指令只创建 `PENDING` 申请，不直接修改钱包。
- 余额变化只能由后台审批服务调用钱包服务完成。
- 审批结果和上下分记录不得通过删除聊天消息表达。

`说明`和`玩法`属于聊天触发的展示类指令：

- 消息按普通用户消息持久化并对全体房间用户可见，**不产生机器人反馈**。
- 玩法说明弹窗只在发送者本机打开，其他用户只看到`说明`这条消息，不弹窗。
- 服务端把`说明`与`玩法`识别为同一类指令，避免落入「指令格式不正确」分支。

### 3.2 托的自动消息边界

- 托在自动模式下**不发送闲聊消息**（「你好、吃了吗」这类内容不再自动生成）。
- 托下注成功后仍由系统机器人发布「攻击成功，使用粮草…」反馈，作为下注痕迹，和真实玩家下注一致。
- 托的随机上分申请直接写入后台审批队列，不产生聊天消息。
- 工作台「手动发送测试消息」保留，用于人工验证。

## 4. 实时能力边界

- WebSocket 使用一次性 ticket、Origin/权限检查、心跳、连接上限和限流。
- 当前是单 Spring Boot 实例，不承诺 Redis 会话共享、跨实例广播或分布式调度。
- REST 历史查询和游标补偿是 WebSocket 不可用时的降级路径。
- 入站帧、出站 envelope 和机器人 payload 有配置化字节上限，超限不能静默截断。
- 机器人或结算反馈失败不能回滚已经完成的钱包和注单事实。

## 5. 当前证据和风险

已有 H2、MySQL、浏览器、本地 WebSocket 和历史服务器运行态证据；聊天上下分申请、4 小时历史分页、新消息浮动提示、`说明`指令和托自动模式不发送闲聊均已接入当前工作区。公网 HTTP 下 Secure Cookie 刷新恢复、正式 HTTPS、现场大消息和生产监控仍需补验。

## 6. 新需求入口

任何聊天功能必须说明消息是否公开、是否持久化、是否需要 outbox、是否允许重试、是否影响房间序号和断线补偿，以及普通玩家、TEST、BOT、ROBOT 的可见性。
