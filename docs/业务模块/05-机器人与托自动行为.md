# 业务模块 05：机器人与托自动行为

> 当前状态：服务端机器人和 TEST/BOT 自动行为均已形成基础闭环；托改为“链接是工作前提 + 期内随机时间下注 + 自动模式不聊天”后，玩法/金额档位等约束仍按专项计划推进；长周期和生产验证待补。

## 1. 两类机器人必须分开

| 类型 | 身份 | 作用 | 是否有钱包/注单 |
| --- | --- | --- | --- |
| 服务端机器人 | `chat_robot`、`ROBOT` 消息 | 发布期号、开奖、结算和系统消息 | 没有 |
| BOT 玩家/托 | `TEST` + `BOT` + `BOT_SERVICE` | 像玩家一样聊天、下注、扣积分和结算 | 有虚拟积分和正式注单 |

两者不能合并，不能让服务端机器人伪造普通用户，也不能让 BOT 绕过正式下注和钱包链路。

## 2. 服务端机器人流程

```text
游戏事件提交
  -> RobotDispatchScheduler 扫描
  -> 选择启用机器人和模板
  -> 创建唯一 dispatch
  -> 租约认领
  -> 渲染文本/结构化消息/图片
  -> 写入 chat_message 和 outbox
  -> 成功、跳过或失败重试
```

需要保证事件类型、模板版本、dispatch 幂等、失败退避和审计可追溯。

## 3. BOT 行为流程

```text
管理员配置 AUTOMATIC/MANUAL
  -> 期号进入 BETTING 时按“每期注单”生成 test_player_action = PENDING
  -> 每条动作带 scheduled_at（投注窗口内随机分布）
  -> 调度器只执行已到期动作，“立即执行”忽略计划时间
  -> 校验 BOT ACTIVE 且存在可用链接
  -> 按可用余额与剩余额度压降金额
  -> 统一进入 ChatMessageService
  -> 解析并正式下注
  -> 关联消息、注单和流水
  -> SUCCEEDED/SKIPPED/FAILED
```

动作必须具备唯一幂等键、租约、重试次数、失败原因和关联事实。

### 3.1 工作前提与停止条件

- 托只有在“用户 ACTIVE + 账户 ACTIVE + `player_kind=BOT` + 存在未拉黑且未过期的 `PLAYER_FULL` 链接”时才工作；**链接是托能否工作的前提**。
- 拉黑、链接过期、停用、删除都会让托停止；已排队的待执行动作按 `SKIPPED` 收尾，原因码为 `LINK_INVALID`、`PLAYER_INACTIVE` 或 `ISSUE_CLOSED`。
- 恢复链接（拉白或刷新）后从后续动作继续；当期已经跳过的动作不会补下。
- 手动模式（未打开自动）等同普通玩家，不产生任何自动注单或消息。

### 3.2 下注计划与金额

- 不再在开盘瞬间集中下注：每期按配置单数生成计划，`scheduled_at` 均匀分布在投注窗口内（只保留期初 3 秒缓冲，封盘前最后时段同样参与）；计划持久化，服务重启后继续执行。
- 活跃比例按 A+B 口径：先按概率决定本期是否参与，参与时本期注单数按比例收缩（至少 1 单且不超过配置值）。
- 下注范围档位：`随机 / 30-300 / 300-1000 / 1000-3000 / 3000-10000 / 10000-30000`；`随机`在全局 30-30000 之间取值并偏向小额，同时单笔不超过当前余额的 20%。
- 下注金额整十：`随机 / 关 / 开`；金额一律为整数，不出现小数。
- 下注指定玩法：从「角/正/番/车/念/加/通/无/单双/大小/特」中按配置集合随机选择，参数由生成器随机且保证可解析；`随机`等于全选。
- 全局托风控：`所有托每期总注单`和`所有托每期总积分`达到上限后，其余动作记 `SKIPPED(BOT_ISSUE_CAP)`；深夜时段可用全局覆盖活跃比例。
- 随机上分申请：按概率触发，命中且没有待审批申请时直接写入后台审批队列，不在聊天室发消息。
- 自动模式不再发送闲聊消息；下注成功后仍由系统机器人发布“攻击成功，使用粮草…”反馈，作为下注痕迹。
- 金额从配置区间随机后，依次被可用余额和剩余额度压降；压降后低于最小注额时记 `SKIPPED(INSUFFICIENT_BALANCE)`，不会再把余额不足记成失败重试。
- 下注被限额或封盘拦截时不产生注单，动作记 `SKIPPED(LIMIT_EXCEEDED)`，避免“成功但没有注单”的假成功。

## 4. 与其他模块的联动

- 期号：决定自动动作是否执行、当前能否下注。
- 钱包：BOT 下注必须扣虚拟积分，结算必须写流水。
- 聊天：BOT 消息对全体房间用户可见，复用正式消息服务。
- 玩家身份：停用或删除 BOT 后，执行前二次检查 ACTIVE 与链接可用性。
- 报表：BOT 动作、注单、流水分别进入同一业务日查询。

## 5. 当前证据和风险

已有 H2、前端测试、本机 MySQL 跨期调度和动作执行观察；链接前提、期内随机时间、不自动聊天、余额降额、档位与整十、玩法集合、活跃比例、全局上限与随机上分申请已由 `TestPlayerBehaviorServiceTest` 和 `BotBetTextGeneratorTest` 覆盖（后端全量 `285/285`）。全局托上限在极端并发下可能少量超出，多实例强一致控制尚未实现；真实开奖结算周期、服务器重启恢复、多用户可见性、失败队列长期积压和生产告警仍未完成。

## 6. 新需求入口

新增机器人消息、托行为或自动调度时，必须先说明它属于服务端机器人还是 BOT 玩家，并写清是否产生注单、积分流水、公开消息和可重试动作。
