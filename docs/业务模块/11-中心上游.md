## 1. 模块负责什么，不负责什么

**负责**：

- 代理把自己的注单上报给"上级盘口"（中心），中心完成认证、接单校验、风控、额度占用、第二层结算和对账（上报概念对应 BY220 飞单 BY220: application/common.php:1499、盘口表 BY220: local/schema-base.sql:431；"中心"这一侧 BY220 没有，属 `xupan 扩展（使用者确认 2026-10-02）`）。
- 中心侧的代理身份、Token、额度三层与追加式账本。
- 中心管理端（`/platform-admin/center`）：账户、实时订单、财务流水、风险、对账。

**不负责**：

- 玩家与代理之间的**第一层**结算（属 [03 期号玩法下注与结算](03-期号玩法下注与结算.md) 与 [02 虚拟积分与钱包](02-虚拟积分与钱包.md)）。
- 本地机器账号、代理组织与报网配置界面（属 [09 代理组织与代理后台](09-代理组织与代理后台.md)）。
- 子账号、机器管理菜单（属 [10 BY220 式超级管理后台](10-BY220式超级管理后台.md)）。
- 真实外部上游平台接入：**永远不做**。

### 1.1 两层账

```text
第一层：玩家  ↔ 代理/平台          本地虚拟积分结算（已实现）
第二层：代理  ↔ 中心上游（本模块）  上报订单、中心接单、第二层结算
```

上报的目的是把代理的一部分风险转移到上游，**不是**让上游直接给玩家结算：玩家赢 → 本地赔玩家，中心再赔代理；玩家输 → 本地收玩家，中心再从代理收。

### 1.2 术语（易混淆，必须区分）

| 术语 | 含义 |
| --- | --- |
| `agent`（本地机器） | BY220 `robot.php` 的机器账号；本地表 `agent` |
| `center_agent`（中心代理身份） | 中心侧的一个代理身份，有独立 `upstream_account` 与 Token；与本地机器是**多对一** |
| 盘口 A/B/C/D | **不是代理身份**，只是上游内部线路；代理身份靠 代理 ID / UserName / Token / 上游账号 区分 |
| `report_type = 'CENTER'` | 本机器把订单报给中心上游 |

## 2. 参与者、状态和权限

### 2.1 参与者

| 参与者 | 入口 | 能做什么 |
| --- | --- | --- |
| 代理侧（本地机器） | 报网适配器 `ReportAdapter`，`report_type='CENTER'` | 上报订单、查看本机器上报结果 |
| 中心入站面 | `/api/center/**`，**代理 Token 认证**（非会话） | `GET /me`、`POST /orders`、`GET /orders`（只见自己） |
| 超级管理员 | `/api/admin/center/agents/**` | 创建中心代理、启用/停用、拨额度、设信用上限、触发结算、订单/账本/对账查询 |

### 2.2 权限码（版本沿革：V62 引入；V 编号是 Flyway 文件标识，不是"当前版本号"）

| 权限码 | 含义 | 默认授予 |
| --- | --- | --- |
| `CENTER_AGENT_MANAGE` | 中心代理账户、额度、Token 管理 | 仅 `ADMIN` |
| `CENTER_ORDER_READ` | 中心订单与对账查看 | 仅 `ADMIN` |

V62 刻意**不授予** `SUB_ACCOUNT` / `AGENT` / `USER` / `MODERATOR`：中心是"代理的上级盘口"，代理自己能看的是本机器的报网状态，不是中心的全量账户与全量订单。`SecurityConfig` 中 `/api/center/**` 放行后由控制器自校验 Token 并自行返回 401。

### 2.3 订单状态机

中心侧 `center_order`（迁移沿革：V63 建表、V64 修正可空性与拒绝单约束）：

```text
PENDING → ACCEPTED / REJECTED / TIMEOUT
ACCEPTED → SETTLED（开奖后第二层结算）
ACCEPTED → CANCELLED（流局/取消）
需退单的已接受订单 → REFUNDED
结算结果 settle_result ∈ {AGENT_WIN, AGENT_LOSE, VOID}
```

本地侧 `report_upstream_order`（V58，一次上报尝试一行、追加保留）：

```text
PENDING / ACCEPTED / REJECTED / TIMEOUT / CANCELLED / REFUNDED / SETTLED
```

两侧靠 `idempotency_key` / `agent_order_no`（中心侧口径 `agent_order_no = 'BET-' || 本地 bet_id`）一一对应，这样才能逐笔对账。

**关键语义（需求 §12.3）**：`TIMEOUT` 表示**状态未知**，与 `FAILED` 并列而非等价；超时**只标记、不退款、不删单**，必须支持查询上游状态、等待确认或按规则重报。

### 4.1 接单校验（顺序按"越便宜越先判"）

期号格式（`^[0-9]{6,12}$`）→ 玩法白名单（从 `PlayType` 枚举派生，**不手写字符串**）→ 金额 → 赔率 → 单期敞口。

风控当前为**基础档**（档位取值属工程基线，见下表）：

| 规则 | 当前取值 | 性质 |
| --- | --- | --- |
| 单笔上限 | 100,000 | **全局常量**，不区分代理 |
| 单期敞口上限 | 500,000 | **全局常量**，不区分代理 |
| 可用额度校验 | 不足即拒，不做透支 | 按账户 |
| 拒绝留痕 | `reject_code` / `reject_reason` 落库 | ✅ |

校验失败返回**"已拒绝"的订单行**而不是只抛错，这样代理侧能看到拒绝原因、中心侧留下可对账的记录。**代理级敞口上限与异常行为识别未实现**，属阶段 C。

### 4.2 对账差异分类

| 类别 | 含义 |
| --- | --- |
| `MISSING_IN_CENTER` | 本地有上报记录，中心没有对应订单 |
| `MISSING_IN_LOCAL` | 中心有订单，本地没有上报记录（脏数据或串号） |
| `STATUS_MISMATCH` | 两侧状态语义不一致（如本地 ACCEPTED 而中心 REJECTED） |
| `AMOUNT_MISMATCH` | 两侧金额不一致（最危险，必须逐笔查；处置要求属工程基线） |

对账同时做双方账本自检（`balanced` / `inconsistent` 计数），不是"看一眼总数差不多"。

对齐口径（**长期规则，不得由实现细节漂移**）：中心侧 `agent_order_no = 'BET-' || 本地 bet_id`，
由 `CenterReconciliationService.ORDER_NO_PREFIX` 与 `CenterOrderGateway` 共同保证。
改动任一侧的订单号生成规则都会让对账整体失效，属于破坏性变更，必须先改这里再改代码（工程基线）。

### 4.3 结算与对账口径（P1-C4 固化）

以下口径从"实现细节"上升为**模块规则**（工程基线），后续任何改动都必须先改本节：

| 口径 | 规则 | 依据 |
| --- | --- | --- |
| 两层账方向 | 玩家赢 → 本地赔玩家、中心赔代理（`AGENT_WIN`）；玩家输 → 本地收玩家、中心从代理收（`AGENT_LOSE`）；流局 → `VOID` | 需求 §10 |
| 结算范围 | 只处理 `status = ACCEPTED` 的订单，结算后置 `SETTLED`；重复调用不重复赔钱 | 原则 6 幂等 |
| 额度流转 | 接单 可用→冻结；开奖 冻结→上游未结算；结算 上游未结算→可用 | 原则 1 三层 |
| 结算金额 | 由 `SettlementService` 按玩法判定，与第一层**同一套判定逻辑**，不另写一份 | 避免两层口径漂移 |
| 未结算不计入敞口 | `acceptedExposure` 只累计 `ACCEPTED`，`PENDING/REJECTED/TIMEOUT` 不构成敞口 | 风控正确性 |
| 业务日边界 | 与第一层一致：`Asia/Shanghai` 06:00 切换 | 跨模块一致性 |
| 对账差异保留 | 差异**不自动修复**，先人工确认；`center_order_disposition` 记录处置过程 | 阶段 C 决策 |
| 舍入 | 全链路 `BigDecimal` + `HALF_UP`；与 BY220 的 bcmath 截断存在末位差异，**未与旧系统逐笔对账** | 原则 5 + 已知差异 |

### 4.4 订单处置口径（P1-C2 / C-3）

「超时 ≠ 失败」（需求 §12.3）在本模块的落地方式（工程基线）：超时单不会自动转终态，必须由人工查证后
通过处置接口明确落定。四个动作及其额度后果：

| 动作 | 允许的起始状态 | 终态 | 额度后果 |
| --- | --- | --- | --- |
| `CONFIRM_ACCEPTED` | `TIMEOUT` / `PENDING` | `ACCEPTED` | **新增**占用：可用 → 冻结 |
| `CONFIRM_FAILED` | `TIMEOUT` / `PENDING` | `REJECTED` | 无（从未占用，故**不退款**） |
| `REFUND` | `ACCEPTED` | `REFUNDED` | 冻结 → 可用 |
| `CANCEL` | `ACCEPTED` | `CANCELLED` | 冻结 → 可用 |

- 每次处置**追加**一行 `center_order_disposition`（谁、何时、按什么理由、从什么状态到什么状态），
  不只改 `center_order.status`——否则事后无法解释一笔退款是谁批的。
- `idempotency_key` 唯一：重复提交只生效一次，不二次改状态、不二次退额度。
- 处置引起的额度回流一律经 `CenterAgentService.moveInternal` 写账本，
  保证 `countInconsistentBuckets` 恒为 0。

### 4.5 对账差异的处置与保留策略（C-2 ② / C-4 ③）

**处置 ≠ 修复。** 规划要求"差异应先人工确认再自动化"，因此处置只写
`center_reconciliation_disposition`，**绝不修改订单、额度或账本**。
自动改账会在真相未明时改写账本事实，比差异本身更危险。

| 结论 | 含义 |
| --- | --- |
| `ACKNOWLEDGED` | 已知悉，暂不处理 |
| `ACCEPTED` | 接受该差异（例如舍入造成） |
| `FIXED` | 已在源头修复 |
| `IGNORED` | 判定为脏数据，忽略 |

**保留与清理策略**（长期规则的权威口径）：

| 规则 | 说明 |
| --- | --- |
| 只追加不删除 | 处置记录是"差异为什么被认可"的凭据（账本原则 3）。**代码不提供删除方法** |
| 处置会过期 | `expires_at` 默认 **7 天**；到期后差异重新回到待处置列表——避免"标一次已知就永远不再看" |
| 撤销是状态迁移 | 撤销写 `revoked_at`/`revoked_by`，记录保留，判断历史可追溯 |
| "生效"的唯一定义 | 未撤销 **且**（无到期时间 或 未到期）。对账、列表、生效判定三处共用这同一口径 |
| 差异事实不被隐藏 | 已处置的差异**仍然出现在对账结果里**，只是带 `disposed=true` 标记——事实不能因为被标记就消失 |
| 长期增长的处理 | 通过 `GET …/reconciliation/retention` 观察生效/失效数量，由人工判断归档时机；**不通过删数据解决** |

唯一键是 `(difference_type, bet_id)` 语义：同一笔注单可能在不同类型差异之间变化
（例如先 `STATUS_MISMATCH` 后 `AMOUNT_MISMATCH`），因此处置必须按"类型 + 注单"定位，
不能只按注单定位（该唯一键口径属 `xupan 扩展（使用者确认 2026-10-02）` 的模块内部规则，依据：[阶段 C 验收记录](../验收记录/2026-10-03-上线可用收口与阶段C实施验收记录.md) §2.2 C-4）。

## 5. 成功、失败、重复执行和服务重启

| 场景 | 处理 |
| --- | --- |
| 重复上报 | `(center_agent_id, agent_order_no)` 唯一；重复直接返回首次结果，**不重复扣额度** |
| 接单被拒 | 落 `REJECTED` 订单行；本地按机器 `report_withdraw` 决定是否退玩家本金 |
| 中心拒绝 → 本地退单 | 同一事务内幂等退款（`CANCEL_REFUND:<betId>`）+ 物理删除注单 + 中心留痕 |
| 超时 `TIMEOUT` | **只标记，不退款，不删单**；可重报 |
| 结算重复调用 | 只处理 `status=ACCEPTED`，结算后置 `SETTLED`，因此重复调用不重复赔钱 |
| 中断恢复 | 本地 `findPendingAttempts` 作为恢复入口 |
| 代理停用 | 中心侧同样落 `REJECTED`（`CENTER_AGENT_DISABLED`），避免"本地有、中心无"的对账差异 |

### 5.1 部署形态（用户 2026-10-03 确认）与已知缺陷

**部署形态：不拆进程。** 用户 2026-10-03 明确确认：本项目部署一套，中心上游逻辑就在同一套进程内运行，**不拆独立进程、不对外提供 HTTP 接单入口**（`xupan 扩展（使用者确认 2026-10-03）`，依据：[阶段 C 验收记录](../验收记录/2026-10-03-上线可用收口与阶段C实施验收记录.md) §1）。据此：

- **`TIMEOUT` 查证路径当前不是欠债**：同进程调用永不产生网络超时，该场景在当前架构下**不会发生**。这与"未实现"是两回事，必须在文档中区分。
- **若将来改为独立进程**，以下三项立刻变为前置：超时语义、超时后查询中心订单状态、幂等重试（且不允许"超时即退款"）。
- 单实例滚动重启仍需要**定时任务互斥**（与拆不拆进程无关），见[规划 §4 P0-1](../plans/2026-10-02-上线可用收口与阶段C至D实施规划.md)。

**必须与本模块实现的缺陷**（与部署形态无关）：

1. **上报重报头部阻塞**：`ReportUpstreamOrderRepository.findSubmittableBets` 用 `ORDER BY b.id LIMIT 50`，且重报状态集合含 `REJECTED`/`TIMEOUT`。累积 50 笔长期失败单后，批次被永久占满，**新注单再也排不上上报**，且无告警。修法（`next_retry_at` + 退避 + 重试上限）见[规划 §4 P0-2](../plans/2026-10-02-上线可用收口与阶段C至D实施规划.md)。BY220 的 `flyers_status = 3` 轮询很可能有同样问题，因此**加退避与上限属对 BY220 的偏离，需用户确认**。
