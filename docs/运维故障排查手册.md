# 运维故障排查手册

## 1. 适用范围

本文用于单服务器、单 Spring Boot 实例部署的日常排障。当前不包含 Redis、MQ、多实例协调和专门告警平台。

排查时先记录发生时间、访问地址、用户操作、HTTP 状态码和 requestId。不要把密码、Token、Cookie、WebSocket ticket 或完整带参数 URL 写入工单。

## 2. 服务是否存活

在服务器上执行：

    sudo systemctl status xupan-server --no-pager
    curl --max-time 5 -i http://127.0.0.1:8080/actuator/health

健康检查必须同时满足 HTTP 200 和返回 JSON 中 status 为 UP。项目提供的 xupan-healthcheck.sh 只负责检测，不负责自动重启。

如果服务未运行，先查看最近日志：

    sudo journalctl -u xupan-server -n 200 --no-pager
    sudo journalctl -u xupan-server --since "30 minutes ago" --no-pager

## 3. 按 requestId 追踪一次请求

浏览器开发者工具或接口响应中的 X-Request-Id 是排查入口。应用访问日志、异常日志和错误响应使用同一个 requestId。

    sudo journalctl -u xupan-server --since "30 minutes ago" | grep "requestId=目标值"
    sudo grep -R "requestId=目标值" /opt/xupan-platform/logs/

如果只有 4xx，先区分登录失效、权限不足、参数校验失败和资源不存在；如果是 5xx，再结合同一 requestId 的 ERROR 堆栈查找根因。

## 4. 登录、权限和管理后台

- 登录失败：检查账号状态、密码错误次数、刷新会话和服务端时间。
- 返回 401：确认登录 Cookie 是否存在且未过期；先重新登录，再复现并记录新的 requestId。
- 返回 403：确认账号具有目标权限。系统监控接口需要 SYSTEM_MONITOR_READ，机器人管理接口需要对应 ROBOT 权限。
- 访问 /forbidden：先确认是否是预期的前端权限跳转，不要仅凭页面元素判断后端权限。

生产环境下 /actuator/health 可用于存活检查；/actuator/info、/actuator/metrics 和具体指标接口需要 SYSTEM_MONITOR_READ。

## 5. 机器人调度异常

先检查指标和应用日志：

    curl --max-time 5 -u 用户名:密码 http://127.0.0.1:8080/actuator/metrics/xupan_robot_dispatch_pending
    curl --max-time 5 -u 用户名:密码 http://127.0.0.1:8080/actuator/metrics/xupan_robot_dispatch_failed
    sudo journalctl -u xupan-server --since "30 minutes ago" | grep -E "robot|dispatch|template"

重点判断：

- PENDING 持续增长：检查事件是否已提交、调度器是否运行、模板是否启用。
- FAILED 增长：检查模板校验、数据库写入和消息持久化异常。
- 无在线用户但消息应保留：检查 chat_message、chat_outbox 和 dispatch，不以 WebSocket 在线数判断是否投递成功。
- 重复消息：检查 dispatch 唯一键、消息幂等键和是否存在手工重复重试。

数据库排查只读示例：

    SELECT status, COUNT(*) FROM chat_robot_dispatch GROUP BY status;
    SELECT COUNT(*) FROM chat_outbox WHERE published_at IS NULL;

## 6. 聊天室和 WebSocket

- 页面提示实时连接不可用：检查 /api/auth/ws-ticket 是否成功、WebSocket 是否返回 101、Origin 是否在白名单。
- 连接成功但不能发消息：确认客户端已发送 subscribe，且账号有聊天室发言权限。
- 消息重复：检查是否同时启用了 WebSocket 和 REST 降级轮询；按消息 ID 和序列号判断是否真的重复。
- 消息延迟：查看 xupan_chat_connections、xupan_chat_outbox_pending，并检查应用日志中的消息持久化和发布记录。

当前版本是单实例实时通信。不要把单实例连接数指标解释为多节点全局在线人数。

## 7. 重启、崩溃和 JVM 错误

确认影响后执行受控重启：

    sudo systemctl restart xupan-server
    sudo systemctl status xupan-server --no-pager
    curl --max-time 5 http://127.0.0.1:8080/actuator/health

重启后重点查看：

    sudo journalctl -u xupan-server -b --no-pager
    sudo find /opt/xupan-platform/logs -maxdepth 1 -name "hs_err_pid*.log" -print

出现 hs_err_pid 文件时，不要直接删除。保留文件、记录生成时间和服务版本，再分析 JVM 崩溃信号、线程、内存和本机资源。

## 8. 日志空间

生产应用日志默认写入 /opt/xupan-platform/logs/xupan-server.log，并按 50MB 单文件、30 天历史、2GB 总容量滚动。检查空间和日志文件：

    df -h /opt/xupan-platform/logs
    du -sh /opt/xupan-platform/logs
    ls -lh /opt/xupan-platform/logs

日志滚动参数可通过 XUPAN_LOG_MAX_FILE_SIZE、XUPAN_LOG_MAX_HISTORY_DAYS 和 XUPAN_LOG_TOTAL_SIZE_CAP 调整。调整前应确认磁盘余量和保留要求。

## 9. 当前未执行事项

本手册描述的是可执行操作，不代表服务器级演练已完成。本轮尚未在真实服务器上执行 systemd 模板安装、健康检查定时器启用、日志轮转现场验证、kill/restart 故障演练和外部告警联动。
