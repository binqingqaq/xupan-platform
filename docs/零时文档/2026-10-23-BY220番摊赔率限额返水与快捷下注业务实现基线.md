## 2. PeiLv=95的倍率口径

普通玩法的中奖总返还倍率 = 1 + (95/100) × 玩法系数。1表示返还原下注积分；输时返还0，和局返还原下注积分（1倍）。以下倍率均为中奖时含原下注积分的总返还，不含另外核算的返水。

| 玩法规则 | 系数 | 中奖总返还倍率 | 下100积分：中奖返还 / 净增加 |
| --- | ---: | --- | --- |
| 单、双、大、小、角、正/堂、两号码无、加 | 1 | **1.950** | 195 / 95 |
| 番 | 3 | **3.850** | 385 / 285 |
| 严/念 | 2 | **2.900** | 290 / 190 |
| 通、三号码无 | 0.5 | **1.475** | 147.5 / 47.5 |
| 车/推及三号码数字别名 | 1/3 | **1.316666…** | 131.666666… / 31.666666…；最终写库精度依字段处理 |
| 数字特码 | 不用PeiLv | **T = tePeilv** | 100T / 100(T−1) |

车/推的显示与结算精度不同：页面调用 getPeilv($rb,0.333)，95时为 number_format(1.31635,3)，显示 **1.316**；结算用下注积分 / 3 × 95/100，加回原下注积分后为 **1.316666…**。不能把页面的0.333当成结算中的精确1/3。

特码直接按tePeilv返还，**不再加1**。仅作说明，若另外假设tePeilv=18，每个中奖特码返还18倍，100积分返还1800、净增加1700；这不是由95推导的，也未修改或假定当前机器配置为18。

公式与入账证据：[页面赔率公式](/D:/codes/liuhecai/_github-by220-cp/application/common.php:4566)、[xzjs入账](/D:/codes/liuhecai/_github-by220-cp/application/common.php:3667)、[车/推结算](/D:/codes/liuhecai/_github-by220-cp/application/common.php:4256)、[特码结算](/D:/codes/liuhecai/_github-by220-cp/application/common.php:4185)。

## 6. 两条下注路径与不能隐去的差异

### 6.1 两条入口

- WebSocket消息处理调用sendMsg()，普通玩法由getWfArr()解析后查rbwf.name。还需满足开盘、期号、余额、限额和身份条件。
- 本地玩家页在localhost或127.0.0.1时POST到Index::send()；该函数使用独立硬编码玩法白名单，没有沿用rbwf查询。
- 两条路径的普通结算使用jiesuan()，它又有自己的数组和分支。“配置存在”“入口接收”“正确结算”需要逐层对齐。

证据：[Web调用sendMsg](/D:/codes/liuhecai/_github-by220-cp/application/console/Web.php:115)、[本地HTTP发送](/D:/codes/liuhecai/_github-by220-cp/application/chat/view/index/index.html:1407)、[rbwf名称查询](/D:/codes/liuhecai/_github-by220-cp/application/common.php:2444)、[HTTP白名单](/D:/codes/liuhecai/_github-by220-cp/application/chat/controller/Index.php:238)。

### 6.2 当前差异

1. **rbwf缺24个三号码“无”写法。** 12无3、21无3等不在表中，但HTTP白名单和jiesuan包含，正确规则倍率1.475。只导出rbwf会漏掉源码玩法。
2. **严/念24个配置名与getWfArr查找名不一致。** 表中存1严2、1念2等；输入1念2/100会查12念，表中没有。HTTP路径支持1念2/100及12念100，结算均为2.900。不能将本地rbwf路径写成正常打通。
3. **3通21缺HTTP和结算白名单。** 表中有，getWfArr按3通21/100解析后能查到；但jiesuan的$tong数组在相应位置重复了3通12、缺3通21。该字符串没有中奖或和局分支，不能标为有效1.475玩法。逻辑等价的正常名称是3通12、12无3、21无3。
4. **无号码“特”不构成数字特码。** 当前“特”条目不能代替01特～20特。普通解析后备分支能让特/100查到该表名，但结算没有具体号码匹配；属于错误输入校验缺口，不计为可用特玩法。
5. **输入语法不能任意拼接。** 本文示例：1番100、1通23/100、4无3/100、1加34/100、1念2/100、12念100。1番/100不等同于1番100，解析会将/100作为金额，不能统一加斜线。
6. **13角、24角采用带斜线示例。** getWfArr与HTTP的$jiao不同，HTTP对13角100与13角/100的判断不同；本表采用13角/100、24角/100，不把名称存在推成任意语法都能用。
7. **紧凑严/念带斜线有单笔/批量差异。** 12念/100等落入$yanlian分支时，单笔路径错误提示后仍继续调用xiazhu，批量路径会return；本表只采用明确支持的12念100，不把异常语法计为新玩法。
8. **通用x_play里的“中”不是当前rbwf命令。** 本次147项和HTTP白名单均无“中”，此前按另一套分类数7/8类不适用于本次聊天下注全量统计。
9. **有番结果范围，不代表输入校验天然严密。** getFan只有1～4，但入口另有白名单和解析逻辑；132456番100不能当成合法的多个“番”投注组合。异常输入是否拒绝要看入口，不能只用“中奖不可能”代替“下注会拒绝”。

### 6.3 rbwf究竟配置什么

当前x_rbwf只有id与name两列，**没有逐项启停字段，也没有逐项赔率字段**。普通赔率来自机器PeiLv，下注时快照进注单peilv，结算再应用玩法系数。之前说“数据库只影响启用哪些项”不够准确：名称是否存在本身就是接单白名单条件，还会受到解析名称转换影响。

本地147项来源可在local/bootstrap_betting.php的$names及去重插入逻辑找到。本次只读取该文件，未运行；该脚本会删除并重建rbwf，不能作为只读查询工具。

## 10. 配置创建、修改、保存与生效流程

### 10.1 BY220 代理顶部的实际请求链

1. 页面状态刷新把 `data.PeiLv`、`data.tePeilv`、`data.teFanshui` 回填到顶部输入；编辑过程中用 `centerConfig.changepeilv` 暂停覆盖。
2. 输入框获得焦点后选中文字；失焦事件读取 `parseFloat(value)` 和 `data-type`。
3. 三类顶部输入实际都调用 `index/UpdatePeiLv`，请求为 `newPeiLv=<值>, tar=<字段名>`。其中 `tar` 分别为 `PeiLv`、`tePeilv`、`teFanshui`。
4. `UpdatePeiLv()` 调用 `rbUpdate([$data['tar'] => $data['newPeiLv']])`；`rbUpdate` 按当前 session 机器账号更新 `robot`，并刷新 `rbInfo`。
5. 后续后台状态读取展示新值；下一笔下注重新读取机器配置并保存快照。玩家页赔率是模板渲染值，本次未发现对已打开快捷面板执行实时赔率重算的对应机制，不能宣称修改后所有已打开页面立即刷新。

**实际校验边界：** `UpdatePeiLv` 中原本关于 P≥95 的判断已注释，也没有固定 `tar` 白名单；`UpdatePeiLv2` 中关于 T≤19 的判断也已注释。`UpdateFanShui2` 是另一个函数，检查数值和 `>1`，没有下界检查，而且截图顶部失焦并不调用它。因此不能写“顶部特码返水后端保证 0≤R≤1”，更不能仅用输入框样式推断校验已完善。

Xupan 的实现要求是保留字段含义、机器归属和可修改结果，并使用受约束的字段白名单、数值校验、授权和审计。最终可输入范围、精度和修改生效提示按第 17 节显式收敛，不复制任意字段写入接口。

## 11. 限额的实际口径、检查顺序与边界

### 11.1 不是简单按玩法大类加总

正常 WebSocket 番摊链路的总额查询条件为：`gameType + type=3 + wid(玩家昵称) + rid(机器账号) + qihao + isTuo=0`。玩法限额再加 `getWfArr()` 生成的文本匹配条件；特码则拆出每个具体号码单独累计。

因此：

- 配置归机器所有，消耗额度却按该机器名下的单个玩家统计。玩家甲使用了额度，不会直接占用同机玩家乙的这个累计；机器乙有独立配置。
- 当前普通限额查询没有按 `qiuNum` 再拆桶；不能擅自把它改为“每球都获得一份新额度”。
- `isTuo=0` 排除了历史托注单的额度统计；托的新单及不同入口行为须另外验收，不能说普通玩家与托完全一致。
- 原代码用昵称 `wid` 而不是稳定玩家ID累计，重名／改名有风险。Xupan 用内部玩家ID实现身份隔离属于工程约束，须记录这个兼容差异。
- `fan=500` 的常规含义是某个番的匹配注单累计最多500，不是“1番+2番+3番+4番合计最多500”。同样不能把所有 NONE 玩法用一个总桶替代原规则。

### 11.2 玩法与限额归类

### 11.3 单笔普通下注的检查与结果

1. 入口确认玩家、所属机器、期号、状态和封盘条件，解析玩法与金额，检查玩法配置／白名单。
2. 从机器配置取得本玩法限额，从历史注单取得当前玩家本期已占额度。
3. 检查余额；比较本次 `money` 与 `zuidi`、`zuigao`。这是本次指令金额，不能改成玩家当期累计上限。
4. 普通玩法检查 `本次money + 该匹配组历史额 ≤ 对应玩法限额`；特码在前置步骤按各号码检查，后续普通类型检查用 `isTe` 跳过。
5. 检查 `本次money + 当前玩家本期历史总额 ≤ total`。
6. 全部通过后扣虚拟积分、写注单及参数快照，产生下注成功反馈；失败给出原因及适用的剩余可下额度。

源代码使用 `<` 判断“限额小于已用+本次”才拒绝，所以恰好达到限额可接单。普通玩法 `$xian>0` 还是前置解析门槛之一；0 不能无依据地解释为“不限额”。机器表单里保存0与实际可正常接单是两件事。

例如：机器配置 `zuidi=10、zuigao=200、fan=500、total=1000`。玩家本期已有 `1番450`、全部玩法合计900。下表每行都是从这个初始状态独立判断，不连续累计上一行的下注：

| 新指令 | 按源码正常限额口径判断 |
| --- | --- |
| `1番5` | 低于最小注额10 |
| `1番201` | 超过本次最高注额200 |
| `1番60` | 该番只剩50，拒绝 |
| `1番50` | 该番累计500，总额950，可通过这些限额检查 |
| `2番100`（该番未用额） | 不与1番共用fan匹配组，总额1000，恰好可通过 |
| `2番101`（该番未用额） | 本期总额1001，超总限额 |

上述案例只说明限额判断，实际仍需满足玩法启用、余额、开盘、期号等全部条件。

### 11.4 特码多选与批量指令

特码 `1/2特100` 表示每号100，共200。若 `te=300` 且号码1已下250、号码2已下0，继续该指令时号码1会达到350，必须在号码级检查被拒绝；不能因为本次总额200小于300就放行。重复号码由相应入口检查拒绝。

逗号／换行多条普通指令走批量解析和 `xiazhu3()` 预检查，先收集注单、计算 `totalM`，再扣分写入。源码用 `$moneyData[$ma]` 累计本批同名玩法，但旧的 `$zongxiaList` 在预检查阶段没有随全部待接单金额一起增长。因此不能宣称当前 BY220 批量总限额检查完全正确；不同别名属于同一规则时，也可能绕过按 `$ma` 的本批合并。特码组合与多个单号同时出现亦应纳入批内占额检查。

后续 Xupan 必须明确批量是整批接收还是逐项接收，并在约定结果下保证余额、同规则额度和单号额度不会超限。选择部分成功属于用户可见流程，不能靠现有实现习惯自行决定。

### 11.5 撤单、并发和零值的实施要求

- BY220 玩家撤单路径退回注额并删除相应 `record`，后续累计查询自然不再包含该注单。Xupan 即使使用取消状态，也应让相应额度恢复且只退一次。
- 旧代码多次先查额度再扣分，不能用这些片段证明多请求并发时不会超限。Xupan 必须在同一事务／并发控制边界内完成额度占用与余额扣减。
- 下调限额后已有注单保留；新单按新限额检查，余额和赔率历史不回写。已占额超过新上限时，新单拒绝，剩余额展示不得为负数。
- 新机器0值、关闭玩法与不限额必须有明确语义；当前 BY220 的正值门槛和 Xupan 表单0默认值不相容，见第17节。

## 12. 特码赔率、特码返水、余额与报表的完整关系

### 12.1 特码中奖返还和返水统计是两个输出

设玩家起始余额1000，提交 `12特100`，该笔快照 `tePeilv=18`、`teFanshui=0.01`。假设该游戏、玩法和号码已配置可接单，全部限额检查通过：

| 阶段 | 玩家余额 | 注单／报表 |
| --- | ---: | --- |
| 下注前 | 1000 | 尚无本单 |
| 扣除本次下注100 | 900 | 新建待结算注单，保存T=18、R=0.01 |
| 开奖计算值等于12 | 2700 | 中奖返还1800；净赢1700；单边特码返水统计1 |
| 若计算值不是12（另一种结局） | 900 | 未中奖不返还；净亏100；本单单边特码返水统计0 |

BY220 `jiesuan()` 的特码中奖分支令 `$score=单价×tePeilv`、`$ying=0`，`xzjs()` 加余额时只加 `$score+$ying`。`getRecordData()` 另行计算返水；这条链路没有把该返水加入玩家余额。因此上例中奖后的余额为2700，不是2701。

R=1 时，100积分的**中奖特码单号**统计返水100；R=0.01时统计1；R=0时统计0。R不是固定返多少积分，也不改变T=18，更不改变开奖号。

可以确定的用途是：为代理／超级后台按注单、玩家及机器核算和显示返水金额。根据这段代码，不能继续宣称“系统已自动发放返水”，也不能编造一个现有的“人工结算返水”按钮或审批流程。若以后增加自动发放，属于新增行为，需要另行确认。

### 12.2 多号码时按中奖单价计算

`1/2特100`：总下注200，但每号单价100。若开1，中奖返还 `100×18=1800`，该组合净赢 `1800−200=1600`；R=0.01时单边特码返水是 `100×0.01=1`，不是总注额200×0.01=2。实现若把组合拆成单号订单，须确保总扣分、中奖返还及返水汇总与这一结果等价。

### 12.3 单边与双边报表不同

`getRecordData()` 同时返回两套数：`recordFan` 和 `recordFans`。`resetOrder()` 把它们分别汇总成 `totalFanShui`、`totalFanShuis`，注单明细为 `dtfanshui`、`dtfanshuis`。代理记录页按 `liushuiMode==2` 选择后者，否则选择前者。

| 场景 | 单边返水 `recordFan` | 双边返水 `recordFans` |
| --- | --- | --- |
| 普通中奖注单 | 以 `yingScore` 为基数乘普通返水F/100 | 以 `getShuangs()` 的结果为基数乘F/100 |
| 普通未中奖注单 | 0 | 根据玩法基数乘F/100；和局除外 |
| 特码中奖注单 | **中奖单号单价 × R** | **`totalYing` × F/100**；这里用普通返水快照F，不用R |
| 特码未中奖注单 | 0 | 基数取该单 `totalYing`；正常未中奖默认0时结果0 |
| 和局／未结算 | 不满足中奖条件，不计单边返水 | 和局与未结算不进入相应计算条件 |

所以“改特码返水后，当前报表数字没变”不必然表示保存失败：若报表正在显示双边口径，显示的公式可能根本不用 R。也可能查询的是修改前已保存快照的旧注单。

**精度差异：** BY220 这里使用 BCMath 并指定两位：特码为 `bcmul(单价,R,2)`；普通／双边先 `bcdiv(F,100,2)` 再相乘。这是中间步骤就截断，例如F=1.5会先得到0.01，不能直接等同数学上的1.5%。当前 Xupan 的 BigDecimal 算法采用另一套精度与 HALF_UP，见第14、17节。后续必须明确保留还是修正，不能只比较整数示例就宣称完全一致。
