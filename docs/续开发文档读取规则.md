# 续开发文档读取规则

本文规定续开发时如何使用仓库文档，避免把历史计划、旧验收或过时快照当成当前需求。

## 开始任务时

1. 查看 `git status --short --branch` 和当前提交；确认用户未提交改动的边界。
2. 阅读根目录 `AGENTS.md` 与 [文档索引](文档索引.md) 的入口说明。
3. 只读本任务对应的需求基线、业务模块和对齐缺口；再检查对应源码、迁移和测试。
4. 只有索引把某份计划列为“当前执行中”时，才把它作为实施输入。查看相关最新验收记录时，先确认其提交、环境和证据范围。

不要把 `docs/` 全目录、全部计划、全部验收记录或整个历史项目记忆作为默认上下文。索引、模块矩阵和交接文件用于定位；具体行为仍须按下方规则核实。

## 不同问题看不同证据

| 要回答的问题 | 依据 |
| --- | --- |
| 现在要求系统怎么做 | 用户最近明确确认的决定；其未覆盖处按 BY220 对应源码和已确认需求基线。已确认的合规、技术约束或有意偏离优先于 BY220。 |
| 代码现在实际上怎么做 | 当前分支源码、配置、Flyway 迁移及测试；运行行为只由对应环境的实测证明。 |
| 某次改动当时做了什么、测了什么 | 对应计划和验收记录；它们是有提交/环境范围的时间点材料，不自动说明当前状态。 |
| 某能力是否仍待做 | 当前文档索引的活动事项，并与源码、模块基线和之后的验收记录交叉核对。 |

如果业务规则与当前代码不同，先把它记为实现偏差或待确认，不得把代码现状反推为需求。如果 BY220 与用户已确认的规则冲突，使用已确认规则，并记录偏离依据。

## 文档生命周期

- **长期规则**：只放稳定、跨任务有效的协作和业务边界；阶段、测试数字、当前待办不写入 `AGENTS.md`。
- **当前入口与状态**：由 `docs/文档索引.md` 指向；需标注核对日期和代码提交。未重新核对的模块行必须标明未核对，不能沿用旧状态冒充当前结论。
- **业务基线与需求决定**：业务模块写当前规则；新的用户决定若改变旧决定，应注明生效日期、被替代文件/条目和影响范围，并更新索引与模块基线。旧决定保留为追溯材料。
- **实施计划**：只服务于一个明确实施范围。完成后补计划状态和验收链接，并从活动事项移至已结项计划；取消或被替代时写清原因和替代项。
- **验收记录**：保留当时的原始证据和未执行边界，不因后续状态变化而改写成当前结论。
- **历史/参考/交接**：默认只用于追溯或比较。除非索引明确标为当前有效，否则不能直接作为需求或实施指令。

## 更新后检查

改动需求或实现后，按影响范围同步更新模块基线、活动计划、验收记录和索引。已完成的事项不得同时留在活动清单；测试数字、迁移版本和“未完成”结论须绑定具体提交及验证环境。无法确认时写“待核实”，不要猜测，也不要为消除不确定性批量删除历史文档。
