## D1 全局赔率/限额的路径归属

- **BY220 是什么**：全局赔率/限额属 `admin.php` 的**「设置」**（`changed/config`），该菜单在 `head.html:186` 的 `user_uid == '1'` 块内 → **仅超管可写**。
- **我方现状**：`PUT /api/admin/player-desk/betting-config/**` 仍是 `PERM_USER_MANAGE`（超管）；`/player-desk/**` 其余已收紧为仅机器账号。即**行为是对的，路径归属错了**（"全局设置"挂在"玩家工作台"下），且形成"读=机器账号 / 写=平台管理员"的不对称。
- **选项 A**：保留现状 + 在缺口表登记"路径归属待清理"（**不改代码**）。
- **选项 B**：把**全局**赔率/限额迁到归属正确的设置端点（对齐 `changed/config`），机器级配置留在 `/player-desk`。
- **我的建议：A（现在）**。理由：行为已与 BY220 一致，迁端点属于重构、会牵动前端与权限矩阵；**B 值得做，但应作为独立批次**，不要混进正在验收的行为改造里。

## D2 A1 平台侧上下分分支已成死代码

- **BY220 是什么**：超管对玩家**零操作**——`admin/controller/*` 查 `db('user')` 零命中。
- **我方现状**：`PlayerDeskAdminService` 的 grant/adjust 与 `PlayerPointRequestService` 的 approve 里，`scope.global()` → `changeScore(...)` 那一支**在 URL 层不可达**（只有 MACHINE 能进 `/player-desk/**`）。代码保留、已注释标注。
- **选项 A**：保留死代码（可回退、零风险）。
- **选项 B**：删掉该分支，使 `grant/adjust/approve` **恒走机器池路径**，逻辑更简单。
- **我的建议：B（作为独立清理，不在本批）**。理由：BY220 平台侧本就没有这个入口，删掉能让"超管不碰玩家"在代码层也成立；但**必须独立成批**（触及共享服务与审批链路，不适合与正在验收的改造混在一起）。

## D3 机器级显示/线路/注册类开关（6 个只做了 1 个）

- **BY220 是什么**：`setType`（`rbt/Index.php:125-130`）把机器行 6 个开关**整包写入 `x_robot`**：`ls`(流水显示)/`dj`(倒计时)/`vip`(会员订单)/`log`(开放注册)/`ltype`(提示音)/`url`(房间域名)；另有 `UpdateHideMsg`（`:245-250`，机器级 `hideMsg`）。
- **我方现状**：只做了 `ls`→`agent.rebate_mode`。`link_domain`(V56:24)、`registration_open`(V56:26/46) **列已落库但无接口无界面**（`文档索引` 亦记"阶段 5 未执行"）；`dj` 只是前端本地 ref（页面自标"阶段 4 接入"）；`vip`/`ltype`/`hide_message` **连消费点都没有**（grep 零命中）。
- **选项 A**：按 BY220 **逐个**补结构化端点（**绝不可照抄 `setType` 的"整包写入"形态**）。
- **选项 B**：**明确不做**，登记为有意偏离。
- **我的建议：A，但分批**——**先做 `url` + `log`**（这两项在需求基线 `2026-10-02` 里本来就被列为"阶段 5 未执行"，有既存依据）；`dj` 是纯展示可后置；**`vip`/`ltype`/`hideMsg` 建议归入 B**（无消费点、BY220 里也近乎装饰）。

## D4 玩家/托级三个业务开关（追 / 吃单 / 飞单）

- **BY220 是什么**：托「追」`zhui`（`rbt/Index.php:132-142`，先过机器级门禁 `:136`）、普玩家「吃单」`chi`（`:144-149`，参与下注榜分组 `:359-382` 与飞单分流 `common.php:1135`）、玩家/托「飞单」`isFeidan`（`:158-163`，门禁 `common.php:1504`）。
- **我方现状**：三者 grep **零命中**。`agent.chase_enabled` 列存在但**没有任何业务逻辑读它**；飞单只有**机器级** `report_auto`/`report_withdraw`。
- **选项 A**：按 BY220 逐个补齐（改变"注单是否飞上游 / 是否被代理吃下 / 是否连续追投"）。
- **选项 B**：明确不做，登记为有意偏离。
- **我的建议：A 的一部分**——**先补 `isFeidan`（玩家/托级是否飞单）与 `chi`（吃单）**，因为报网已实现、这两项直接影响注单流向；**`zhui`（追号）建议先归 B**（它会引入新的连续下注语义，风险最大）。**这三项属业务规则、不得由 Agent 自行补**，请逐项拍板。

## D5 「拉黑」的粒度

- **BY220 是什么**：写**玩家级列** `x_rbuser.isBlack`（`rbt/Index.php:151-156`），拦截点 `common.php:1287`/`:2012`、托遴选 `Websocket.php:442-443`。
- **我方现状**：拉黑 = **撤销指定链接** `linkId`（`PlayerLinkAuthenticationService:228-240`，同时撤销该玩家全部会话）；按钮只在"当前链接 active"时出现 → 等价性依赖"同玩家通常只有 1 条有效链接"。
- **选项 A**：撤销时改走 `revokeAllByUserId`（**玩家级效果，最小改动**）。
- **选项 B**：新增独立的**玩家级黑名单**判定（与链接解耦）。
- **我的建议：A**。理由：BY220 要的是"这个玩家进不来"，A 就能达到该效果且改动最小；B 会引入与链接并行的第二套判定，增加状态维度。**但若你确认"同一玩家可能持有多条有效链接"，A 也必须做**（那就是真缺口）。

## D6 代理后台的「撤单 / 未结订单」

- **BY220 是什么**：撤单入口**在代理后台的下注榜行上**——`AllowDel`（`rbt/Index.php:430-448`）＝封盘窗口拒绝 ＋ 退余额 ＋ **物理删除注单**；未结订单有**机器维度**页 `GetUncalculated`（`:603-608`，`isTuo=0`/`status=0`）＋ `ShowUnCalculated`（`:337-340`）。
- **我方现状**：①`/console` 撤单按钮**被禁用**（`BetBoardPanel.vue:141` 标"暂未开放"）；②超管侧 `DELETE /api/admin/unsettled-orders/{id}` **只认 `player_kind='NORMAL'`** → **托的注单撤不掉**；③该入口**无机器维度**；④**无封盘窗口（`fengpan`）拒绝判定**；⑤`/console` **没有未结订单页/端点**。
- **选项 A**：按 BY220 分三步补齐（先补封盘窗口判定与机器维度 → 再开放 `/console` 入口 → 再定托能否撤）。
- **选项 B**：保持现状（按钮继续禁用），仅保留超管侧能力。
- **我的建议：A，但分三步且不要一次做完**。当前那个"诚实的禁用按钮"好过做一个不完整的入口；**在拍板前不要动它**。**动注单+退款，属高风险区**。

## D7 `/console` 的「网盘」选择

- **选项 A**：改为从 `report_network` 拉启用网盘做**下拉选择**。
- **选项 B**：保持自由文本。
- **我的建议：A**。理由：手输网盘编码容易写错且没有约束；A 是纯前端改动。**同时建议不暴露 `api_key_ciphertext`**（无真实上游、存了也不用），`search_code`/`api_version` 是否暴露请你定。

## D11 托行为的细粒度参数（**全是 xupan 扩展**）

- **BY220 是什么**：托只有 `isauto`、`tuoMin/tuoMax`（**固定 5 档**）、`zhui`、`chi`、`isBlack`、`isFeidan`；自动下注金额就是 `rand(tuoMin, tuoMax)`（`Websocket.php:481`）——**没有**整十/玩法白名单/活跃比例/每期注单/随机上分这些维度。
- **我方现状**：`test_player_behavior` 独有 `bets_per_issue`、`stake_round_ten`、`activity_percent`、`play_random`/玩法白名单、`topup_probability_percent`/`topup_min`/`topup_max`、`chat_enabled`/`messages_per_issue`，以及 `stake_range_code` 多出的 **`RANDOM`** 档（30–30000 + "单笔 ≤ 当前余额 20%"）。
- **选项 A**：**保留为 xupan 扩展**，并按 §4 格式登记（确认日期 + 依据文件）。
- **选项 B**：**收敛回 BY220 的粗粒度**（只留 `isauto` + 固定 5 档）。
- **我的建议：A，但你需要做两件事**——①**给一个确认日期**（现在 §4.1 明确写着"需求基线里找不到你对这些参数的确认"）；②**逐项确认数值口径**（整十开/关/随机、活跃比例、每期注单、随机上分概率/区间）。理由：这些参数**直接决定托产出多少虚拟积分、多频繁**，属"业务规则而非工程细节"；保留可以，但**不能没有你的确认就长期悬着**。

## D12 代理后台「实时/状态」的形态

- **BY220 是什么**：`needhandle`（`rbt/Index.php:505-601`）**一次长轮询响应**返回登录态＋机器配置＋当期＋注单榜＋成员；网盘信息读 **session 缓存**（`:922-926` 只读 `rbWpinfo`，不读库）。
- **我方现状**：多个 REST 端点 ＋ WebSocket ＋ 注单榜 3 秒轮询 ＋ **每次读库**（无 session 缓存层）。
- **选项 A**：登记为**技术栈决定的差异**（我方读库在多进程/多节点下更可靠、不会与库不同步）。
- **选项 B**：照 BY220 改回单包心跳 + session 缓存。
- **我的建议：A**。理由：B 会把"库是唯一事实源"这条工程基线打破（session 缓存会与库不同步），**得不偿失**。**未核项**（与拍板无关，登记备查）：BY220 `:510` 的"`logtime` 超 5 小时"与"机器到期强制下线"分别对应我方哪一处判定。
