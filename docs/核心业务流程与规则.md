# Xupan Platform 核心业务流程与规则

> 当前基线日期：2026-09-23
>
> 本文描述当前已经形成的跨模块流程和规则，重点回答“一个业务动作会联动什么”。新增功能应先判断是否影响这些流程。

玩家链接的详细状态、操作影响和验证边界以 [玩家链接生命周期与影响矩阵](玩家链接生命周期与影响矩阵.md) 为专项基线；本文只保留跨模块流程摘要。

## 1. 参与者与身份边界

| 参与者 | 认证方式 | 能做什么 | 明确不能做什么 |
| --- | --- | --- | --- |
| 管理员 | 密码登录、管理员会话 | 管理用户、玩家、赔率、期号、积分和机器人 | 不能绕过权限直接改数据库事实 |
| 普通玩家 | 管理员签发的链接兑换、`PLAYER_LINK`/`PLAYER_FULL` | 进入完整玩家前台，查看余额、聊天并参与已开放游戏能力 | 不能进入管理后台，不能使用管理员权限 |
| TEST 玩家 | 明确的 `TEST` 身份 | 用于联调、手工下注和可审计测试 | 不能伪装成普通真实用户，不能通过普通登录入口登录 |
| BOT 玩家 | `TEST` 身份 + `BOT` 分类 + 玩家链接/服务端行为 | 可通过链接进入完整玩家前台，也可由服务端自动或手动执行聊天、下注和反馈链路 | 不能进入管理后台，不作为独立系统机器人使用 |
| 服务端机器人 | 独立机器人身份、`ROBOT` 消息 | 发布开奖、结算、系统事件和运营消息 | 不能创建玩家注单、扣减玩家积分或伪造普通用户发言 |

## 2. 管理员创建普通玩家并登录

```text
管理员登录
  -> 进入玩家工作台
  -> 创建普通玩家
  -> 服务端生成内部编号和会员编号
  -> 持久化昵称、状态、身份和账户
  -> 管理员生成玩家访问链接
  -> 链接 Token 只以受控响应返回，服务端保存密文/哈希
  -> 玩家兑换链接
  -> 创建 PLAYER_LINK / PLAYER_FULL 会话
  -> 进入 /room
```

必须满足：

- 会员编号由数据库序列产生，不能由前端生成。
- 链接只能绑定 ACTIVE 的普通玩家。
- 链接登录不获得管理员权限。
- 完整原始链接不能写入普通日志或历史详情。
- 刷新链接才产生新 Token；拉黑/拉白不应无故改变链接。
- 链接过期、撤销、玩家软删除或安全版本变化后，旧会话必须失效。
- 管理员和玩家链接刷新会话必须分 Cookie 保存，同一浏览器不同标签页可以共存。
- 刷新请求必须声明管理员或玩家使用端，服务端校验刷新会话的认证模式。

## 3. 玩家软删除与历史保留

```text
管理员确认删除
  -> 按不可变 userId 定位
  -> 事务更新用户和钱包账户为 DELETED
  -> 提升安全版本
  -> 撤销玩家会话和访问链接
  -> 停用 BOT 行为（若存在）
  -> 写身份审计
  -> 默认列表隐藏，显式 includeDeleted 才能查历史
```

删除不物理删除：钱包、积分流水、注单、结算、聊天和审计历史必须保留。重复删除应返回幂等结果，不重复产生业务流水或行为副作用。

待补充规则：链接撤销和过期元数据的保留期限、清理任务、审计保留期限。

## 4. 上分、下分与虚拟积分流水

```text
管理员操作
  -> 权限校验
  -> 校验玩家状态和金额
  -> 事务锁定/更新余额
  -> 写 demo_balance_ledger
  -> 保存前余额、变化额、后余额、操作人、原因和幂等标识
  -> 返回最新余额
```

规则：

- 所有金额只表示虚拟积分。
- 余额变化必须有流水，不能只更新余额字段。
- 前端显示的余额不是事实源，服务端返回结果为准。
- 上分、下分、下注扣分和结算返还必须能在流水中区分。
- 不新增充值、支付、提现、转账、代理分成或现金兑换语义。

### 4.1 聊天上下分申请与后台审批

```text
玩家发送“上100”或“下100”
  -> 服务端识别玩家身份
  -> 持久化公开用户消息
  -> 创建 status=PENDING 的 player_point_request
  -> 发布“待审批”机器人反馈
  -> 管理员后台待处理队列显示申请
       -> 同意
            -> 二次确认
            -> 事务更新钱包
            -> 写 demo_balance_ledger
            -> 申请变为 APPROVED
       -> 取消
            -> 不改余额
            -> 申请变为 REJECTED
```

必须满足：

- 申请创建时不改变余额，只有管理员审批通过才产生积分变化。
- 待处理申请持久化，刷新页面、重新登录和服务重启后仍可查询。
- 同意和拒绝只能有一个终态；并发审批不能重复加减积分。
- 审批使用稳定幂等键，钱包流水保留操作人、原因和前后余额。
- 最近上下分记录只显示当天实际生效的管理员上分和下调。
- 拒绝申请保留审计状态，但不进入最近上下分记录。

## 5. 期号、下注、开奖与结算

```text
期号创建/推进
  -> BETTING
  -> 下注请求
       -> 身份/权限
       -> 当前期和封盘状态
       -> 玩法文本白名单解析
       -> 余额校验
       -> 保存注单与赔率快照
       -> 扣减虚拟积分并写流水
       -> 发布下注反馈
  -> CLOSED / DRAWING
  -> 生成或录入开奖结果
  -> 按赔率快照计算 WIN/DRAW/LOSE
  -> 幂等更新注单、余额和流水
  -> 发布结算反馈
```

当前记录的基础规则：

- 当前轮期方案为每期 300 秒，前 180 秒允许下注，后 120 秒进入开奖阶段。
- 下注固定进入第 1 球，服务端拒绝其他球位输入。
- 订单必须保存下注时的赔率快照，不能用开奖后的当前赔率重算历史注单。
- `LOSE` 净盈亏为负投注额；`WIN` 按赔率计算净盈亏；`DRAW` 采用配置的和局策略，当前默认返还本金、净盈亏为 0。
- 结算必须幂等，同一注单不能因重复请求或任务重试重复扣款/派彩。
- 特玩法金额、总结果聚合和部分和局口径仍需单独确认，不能从参考页面截图直接推断。

### 5.1 下注榜与开奖只读视图

```text
管理员打开 /console
  -> 读取当前期
  -> 按 demo_user_account.player_kind 聚合普通玩家 / 托
  -> 排除 CANCELED 注单
  -> 返回数量、总积分和当前期明细
  -> 读取最近 18 个已结算期
  -> 返回 8 个位置的番值和当前期阶段倒计时
```

规则：

- 下注榜只读，不改变注单、钱包、期号或开奖状态。
- 普通玩家和托由持久化分类决定，不按昵称或用户名推测。
- 取消注单不计入当前期数量、总积分和明细。
- `上期` 当前明确保持空白，不生成假数据。
- 当前期明细中的 `×` 只为后续撤单预留，当前禁用；解除禁用必须另立计划，补齐幂等、退款、流水、审计和开奖竞态。
- 倒计时使用服务端时间校准，不能只信任浏览器本地时间。

### 5.2 玩家快捷下注与偏好

```text
玩家点击“快捷”
  -> 读取当前服务端赔率和当前期
  -> 在 74 项赔率中多选
  -> 输入或选择金额
  -> 按固定顺序拼接逗号分隔组合文本
  -> 发送到聊天室
  -> 聊天室在同一事务中创建全部注单并扣减虚拟积分
  -> 任一注单失败时整批不生效
```

规则：

- 快捷面板赔率来自当前项目服务端赔率，不使用参考站固定值。
- 快捷金额按玩家保存到 `player_quick_bet_preference`，同一玩家的所有链接共享。
- 快捷金额只是界面偏好，不是余额、流水或资金事实。
- `X` 删除金额输入的最后一位；`重置`只清空赔率选择。
- `1车`表示覆盖另外三个番值；`2无3`表示 `2` 中、`3` 输、其余番值和。
- 批量下注继续复用正式聊天、钱包、注单和结算链路，不建立第二套下单事实源。

### 5.3 赔率与限额配置

```text
管理员修改顶部赔率/特码赔率/特码返水
  -> 失焦或回车自动保存
  -> 配置写入游戏配置表和特码赔率表
  -> 重新登录或刷新后保持

管理员点击限额
  -> 弹窗填写 13 项整数限额
  -> 服务端校验正整数和最小/最高注额关系
  -> 保存为当前全局配置

玩家下注
  -> 读取该玩家当前期已占用额度
  -> 逐项校验最低注额、玩家最高注额、单场总限额和玩法限额
  -> 只拒绝超限项
  -> 合法项继续扣分、生成注单并发布反馈
```

规则：

- `赔率`和`特码返水`当前只保存和展示，不参与赔率和积分计算；`特码赔率`是特玩法的实际赔率。
- 限额按单个玩家、当前期累计计算；`CANCELED` 注单不占额度。
- `玩家最小注额`是单笔最低金额；`玩家最高注额`和`单场总限额`按当前期累计判断。
- `单双限额`覆盖`单`和`双`，`大小限额`覆盖`大`和`小`，`通限额`覆盖`通`和`无`。
- 校验在写入前完成，组合下注只拒绝超限那一项，机器人反馈给出原因、上限和剩余可下额度。
- 前端弹窗校验只是即时反馈，服务端校验才是最终事实。
- 聊天室下注路径由 `chat_room` 数据库行锁保证“读额度-写注单-提交”之间没有并发插入，同一大厅消息按提交顺序串行。
- 直连下注接口没有房间行锁，使用实例内 `PlayerBetLock` 按玩家串行并覆盖到提交；多实例部署前这些接口仍需数据库行锁或分布式锁。

## 6. 聊天、下注反馈与实时通信

```text
用户发送文本
  -> 服务端识别发送者身份
  -> 持久化原始用户消息
  -> 判断普通聊天/问候/下注/错误格式
  -> 下注形态进入正式下注服务
  -> 机器人反馈作为公开聊天消息持久化
  -> outbox / WebSocket 广播
  -> 断线客户端按游标补偿
```

规则：

- 用户原文和机器人反馈对聊天室可见。
- 错误格式、普通聊天和未确认玩法不能静默吞掉，应返回明确错误反馈。
- 反馈消息不能替代注单、钱包、结算和审计事实。
- WebSocket 是单实例实时能力；REST 历史查询和短轮询/重连补偿是降级路径。
- 消息、outbox、发送 ACK 和结算反馈需要幂等键，失败重试不能重复展示业务结果。

## 7. BOT 自动/手动行为

```text
管理员配置 BOT
  -> 选择 AUTOMATIC 或 MANUAL
  -> 动作持久化为 PENDING
  -> 调度器或立即执行入口认领动作
  -> 条件校验 BOT 仍为 ACTIVE
  -> 统一进入正式聊天/下注服务
  -> 保存 SUCCEEDED / SKIPPED / FAILED
  -> 关联聊天消息、注单和错误信息
```

必须保持：

- BOT 是测试玩家身份，不是独立服务端机器人。
- 自动行为不能绕过余额、期号、玩法解析和权限规则。
- 动作需要唯一幂等键、租约、重试次数和失败原因。
- 玩家停用或软删除后，执行前必须再次检查 ACTIVE 状态。
- BOT 的下注、扣分、结算、聊天和报表都应留下可查询事实。

## 8. 积分记录与业务日对账

```text
管理员打开普通玩家积分记录或托积分记录
  -> 选择业务日期
  -> 服务端按 Asia/Shanghai 06:00 计算业务日范围
  -> 读取钱包流水、已结算注单和 BOT 动作
  -> 按玩家聚合汇总
  -> 展示注单、流水和动作明细
```

当前规则：

- 每天早上 06:00 切换业务日。
- 总盈亏取该业务日已结算注单的 `net_profit` 合计。
- 普通玩家和 BOT 使用同一套报表结构，但入口名称不同。
- 抽水、飞单和代理分成暂不建模、不展示、不计入统计。
- 报表读取现有业务表和钱包流水，不建立第二套事实源。
- 报表接口继续受 `USER_MANAGE` 权限保护，普通玩家不能查询后台报表接口。

## 9. 数据事实归属

| 业务事实 | 唯一写入责任 | 读取方 | 禁止做法 |
| --- | --- | --- | --- |
| 用户和玩家状态 | 身份/玩家工作台服务 | 管理后台、认证、报表 | 前端直接修改状态 |
| 玩家链接和会话 | 链接认证/会话服务 | 登录和权限过滤器 | 日志保存原始 Token |
| 余额和积分流水 | 钱包服务 | 玩家、下注、结算、报表 | 只改余额不写流水 |
| 期号和开奖结果 | 游戏期号/开奖服务 | 前台、下注、结算、机器人 | 页面临时生成最终结果 |
| 注单和结算 | 下注/结算服务 | 钱包、聊天、报表 | 用聊天消息代替注单 |
| 聊天消息 | 聊天服务 | 玩家房间、WebSocket、机器人 | 浏览器本地假消息作为事实 |
| BOT 动作 | BOT 行为服务 | 调度、工作台、报表 | 直接调用页面逻辑绕过正式链路 |
| 上下分申请 | 聊天/积分申请服务 | 管理后台审批、钱包服务 | 审批前修改余额或只靠前端保存待处理状态 |
| 运营报表 | 报表查询服务 | 管理后台 | 前端自行聚合作为唯一结果 |

## 10. 新需求的流程影响检查

任何新功能开发前，至少回答：

1. 它属于哪个模块？
2. 它会读取或写入哪些业务事实？
3. 它影响管理员、普通玩家、TEST、BOT 或机器人中的哪些身份？
4. 它是否改变期号、下注、结算、余额、聊天或报表流程？
5. 重复请求、服务重启、调度重试和玩家删除后如何处理？
6. 需要哪些 Flyway 约束、索引、审计和权限？
7. H2、本机 MySQL、服务器、生产分别如何验收？

如果这些问题无法回答，需求处于“待确认”，应先补规则，不应直接通过页面改动推进。
