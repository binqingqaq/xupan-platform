## 1. 参与者与身份边界

| 参与者 | 认证方式 | 能做什么 | 明确不能做什么 |
| --- | --- | --- | --- |
| 管理员 | 密码登录、管理员会话 | 管理子账号、机器、赔率、期号、报表、订单、平台设置和机器人；**与玩家相关的只有「在线玩家」的只读列表 + 强制下线 + 发消息**（BY220: application/admin/controller/Users.php:22 online()、:257 userClose2()、:276 sendMessage()；菜单 application/admin/view/public/head.html:170-193） | 不能绕过权限直接改数据库事实；**不碰玩家积分与资料**（BY220 `admin/controller/*` 查 `db('user')` 零命中） |
| 普通玩家 | 管理员签发的链接兑换、`PLAYER_LINK`/`PLAYER_FULL` | 进入完整玩家前台，查看余额、聊天并参与已开放游戏能力（BY220: application/chat/controller/Index.php:14 index、:1412 login、:1445 codelogin；链接生成 application/rbt/controller/Index.php:992 getUserLink） | 不能进入管理后台，不能使用管理员权限 |
| TEST 玩家 | 明确的 `TEST` 身份 | 用于联调、手工下注和可审计测试 | 不能伪装成普通真实用户，不能通过普通登录入口登录 |
| BOT 玩家 | `TEST` 身份 + `BOT` 分类 + 玩家链接/服务端行为 | 可通过链接进入完整玩家前台，也可由服务端自动或手动执行聊天、下注和反馈链路（BY220: 托是玩家行上的 `isrobot`——application/rbt/controller/Index.php:118 SetAuto、:125 setType；**本项目另设 TEST/BOT 身份维度，与 BY220 的 `isrobot` 口径不一致，未对齐核对**） | 不能进入管理后台，不作为独立系统机器人使用 |
| 服务端机器人 | 独立机器人身份、`ROBOT` 消息 | 发布开奖、结算、系统事件和运营消息（BY220: application/common.php:1811-1827 addMsg 写 `NickName='机器人'` 的系统消息） | 不能创建玩家注单、扣减玩家积分或伪造普通用户发言 |

## 2. 代理（机器账号）创建普通玩家并登录

```text
机器账号登录 /console（BY220 robot.php）
  -> 进入机器端玩家/托工作台
  -> 创建普通玩家
  -> 服务端生成内部编号和会员编号
  -> 持久化昵称、状态、身份和账户
  -> 创建工作台内生成玩家访问链接
  -> 链接 Token 只以受控响应返回，服务端保存密文/哈希
  -> 玩家兑换链接
  -> 创建 PLAYER_LINK / PLAYER_FULL 会话
  -> 进入 /room
```

> **2026-10-08 方案 A 更正**：BY220 里建玩家、上下分、上下分申请审批、流水、链接、改名、托参数全部属于**代理后台 `robot.php`（`/console`，机器账号）**（`application/rbt/controller/Index.php:677 AddMember`、`:610 UpDownScore`、`:252/258/298`、`:992 getUserLink`）；**平台侧「玩家工作台」是上一批越界新增，已删除**。超管后台不碰玩家。

必须满足：

- 会员编号由数据库序列产生，不能由前端生成。
- 链接只能绑定 ACTIVE 的普通玩家。
- 链接登录不获得管理员权限。
- 完整原始链接不能写入普通日志或历史详情。
- 刷新链接才产生新 Token；拉黑/拉白不应无故改变链接。
- 链接过期、撤销、玩家软删除或安全版本变化后，旧会话必须失效。
- 管理员和玩家链接刷新会话必须分 Cookie 保存，同一浏览器不同标签页可以共存。
- 刷新请求必须声明管理员或玩家使用端，服务端校验刷新会话的认证模式。

## 3. 玩家软删除与历史保留

```text
管理员确认删除
  -> 按不可变 userId 定位
  -> 事务更新用户和钱包账户为 DELETED
  -> 提升安全版本
  -> 撤销玩家会话和访问链接
  -> 停用 BOT 行为（若存在）
  -> 写身份审计
  -> 默认列表隐藏，显式 includeDeleted 才能查历史
```

删除不物理删除：钱包、积分流水、注单、结算、聊天和审计历史必须保留。重复删除应返回幂等结果，不重复产生业务流水或行为副作用。**与 BY220 不一致（未对齐核对）**：BY220 代理后台删玩家是**物理删除** `rbuser` 行并把该玩家积分退回机器（`application/rbt/controller/Index.php:235-243 DelMember`），本项目改为软删除+历史保留，但未在 `docs/需求基线/**` 登记为有意偏离或已确认差异。

待补充规则：链接撤销和过期元数据的保留期限、清理任务、审计保留期限。

## 4. 上分、下分与虚拟积分流水

```text
管理员/子账号操作
  -> 权限校验
  -> 校验玩家状态和金额（统一 2 位小数，超精度 400）
  -> 判定玩家归属机器（demo_user_account.agent_id；操作者不选机器，R1=做法①）
  -> 校验机器积分池：不足则在写任何余额之前拒绝（池 / 钱包 / 流水三样都不变）
  -> 普通玩家：扣/回该机器积分池；托（BOT）不联动
  -> 事务锁定/更新余额
  -> 写 demo_balance_ledger
  -> 保存前余额、变化额、后余额、操作人、原因和幂等标识
  -> 返回最新余额
```

规则：

- 所有金额只表示虚拟积分。
- 余额变化必须有流水，不能只更新余额字段。
- 前端显示的余额不是事实源，服务端返回结果为准。
- 上分、下分、下注扣分和结算返还必须能在流水中区分。
- 不新增充值、支付、提现、转账、代理分成或现金兑换语义。
- **平台侧上下分沿机器池流转（A1，2026-10-08 实现）**：平台侧（超管 `GLOBAL` / 子账号 `GROUP`）给**普通玩家**上分扣**该玩家归属机器**的积分池、下分回补同一台机器；**托（BOT）不联动**；机器池不足在写任何余额之前拒绝。理由：BY220 里分只能沿「子账号池/超管 → 机器（`rbUpdown`）→ 玩家（`robot.php`）」单向流转，**不存在“平台直接给玩家发分”**（`application/common.php:3707-3724`、`application/rbt/controller/Index.php:610-664`）。**副作用（预期行为）**：平台侧上下分真实消耗机器积分，给玩家加分前需先给机器上分。
- **金额精度（2026-10-08 实现）**：全站金额/积分统一 **2 位小数**；超精度（如 `0.001`）一律 **400**（`SUB_ACCOUNT_SCORE_INVALID` / `MACHINE_SCORE_INVALID` / `WALLET_AMOUNT_INVALID`），**禁止静默四舍五入、禁止 500**；共享口径 `com.xupan.server.web.MoneyAmounts`。**BY220 实为 `DECIMAL(30,6)`（6 位小数、`rbUpdown` 无取整）→ 2 位是对 BY220 的收窄，属使用者已确认的有意偏离。**
- **池不足文案分两路**：机器端照抄 BY220「您的账号剩余积分不足以完成本次上分！」；平台侧用「该玩家所属机器的积分不足以完成本次上分！」。错误码两路都是 `AGENT_SCORE_INSUFFICIENT`。

### 4.1 聊天上下分申请与后台审批

```text
玩家发送“上100”或“下100”
  -> 服务端识别玩家身份
  -> 持久化公开用户消息
  -> 创建 status=PENDING 的 player_point_request
  -> 发布“待审批”机器人反馈
  -> 管理员后台待处理队列显示申请
       -> 同意
            -> 二次确认
            -> 与手动上下分走同一链路（AgentConsoleService.changeScoreForAgent）
            -> 平台侧先扣/回玩家归属机器积分池；池不足则拒绝且池/钱包/流水三样都不变
            -> MACHINE 范围扣机器账号自己那台（2026-10-08 修掉原先完全不扣池的老问题）
            -> 事务更新钱包
            -> 写 demo_balance_ledger
            -> 申请变为 APPROVED
       -> 取消
            -> 不改余额
            -> 申请变为 REJECTED
```

必须满足：

- 申请创建时不改变余额，只有管理员审批通过才产生积分变化。
- 待处理申请持久化，刷新页面、重新登录和服务重启后仍可查询。
- 同意和拒绝只能有一个终态；并发审批不能重复加减积分（BY220: application/rbt/controller/Index.php:258-296 AcceptUpDownScoreReq、:298-322 DenyUpDownScoreReq 以 `folder.status` 0→1/3 单向迁移，非 0 一律返回 `Data=1` 拒绝重复处理）。
- 审批使用稳定幂等键，钱包流水保留操作人、原因和前后余额。
- 最近上下分记录只显示当天实际生效的管理员上分和下调。
- 拒绝申请保留审计状态，但不进入最近上下分记录。
- **审批与手动上下分走同一条机器池链路（2026-10-08 实现）**：`/api/admin/player-desk/point-requests/{id}/approve` 原先直接 `walletService.grant`、不扣池（计划未覆盖的漏网路径），已改为走 `AgentConsoleService.changeScoreForAgent`；**`MACHINE` 范围审批原先完全不扣机器分的老问题一并修掉**。
- 审批产生的钱包流水 `reason` 为共享服务生成的「代理上分/下分：<玩家名>」（BY220: application/rbt/controller/Index.php:258-289 审批同意后写玩家积分并更新 `record.afterScore`）；审批原因仍落在 `player_point_request.review_reason`。**已知遗留**：重放修复前已落库的 `POINT-REQUEST:<id>` 钱包流水会因 reason 不一致返回 409 `AGENT_SCORE_IDEMPOTENCY_CONFLICT`（运维中间态）；一次审批现在写**两条审计**（原 `USER_MANAGE` 审批行 + `changeScore` 内部 `AGENT_PLAYER_MANAGE` 行）。**审批路径的运行态未单独验收，由 H2 覆盖。**

## 5. 期号、下注、开奖与结算

```text
期号创建/推进
  -> BETTING
  -> 下注请求
       -> 身份/权限
       -> 当前期和封盘状态
       -> 玩法文本白名单解析
       -> 余额校验
       -> 保存注单与赔率快照
       -> 扣减虚拟积分并写流水
       -> 发布下注反馈
  -> CLOSED / DRAWING
  -> 生成或录入开奖结果
  -> 按赔率快照计算 WIN/DRAW/LOSE
  -> 幂等更新注单、余额和流水
  -> 发布结算反馈
```

当前记录的基础规则：

- 当前轮期方案为每期 300 秒，前 180 秒允许下注，后 120 秒进入开奖阶段。
- 下注固定进入第 1 球，服务端拒绝其他球位输入。
- 订单必须保存下注时的赔率快照，不能用开奖后的当前赔率重算历史注单（BY220: application/common.php:1101-1134 addDan 在写注单时同时落 `peilv`/`tePeilv`/`fanshui`）。
- `LOSE` 净盈亏为负投注额；`WIN` 按赔率计算净盈亏；`DRAW` 采用配置的和局策略，当前默认返还本金、净盈亏为 0。
- 结算必须幂等，同一注单不能因重复请求或任务重试重复扣款/派彩（BY220: application/admin/controller/History.php:101-114、:136-149 只取 `status=0` 的注单结算并把 `history.js` 置 1，重跑不重复结算）。
- 特玩法金额、总结果聚合和部分和局口径仍需单独确认，不能从参考页面截图直接推断。

### 5.2 玩家快捷下注与偏好

```text
玩家点击“快捷”
  -> 读取当前服务端赔率和当前期
  -> 在 74 项赔率中多选
  -> 输入或选择金额
  -> 按固定顺序拼接逗号分隔组合文本
  -> 发送到聊天室
  -> 聊天室在同一事务中创建全部注单并扣减虚拟积分
  -> 任一注单失败时整批不生效
```

规则：

- 快捷面板赔率来自当前项目服务端赔率，不使用参考站固定值。
- 快捷金额按玩家保存到 `player_quick_bet_preference`，同一玩家的所有链接共享。
- 快捷金额只是界面偏好，不是余额、流水或资金事实。
- `X` 删除金额输入的最后一位；`重置`只清空赔率选择。
- `1车`表示覆盖另外三个番值；`2无3`表示 `2` 中、`3` 输、其余番值和。
- 批量下注继续复用正式聊天、钱包、注单和结算链路，不建立第二套下单事实源。

### 5.3 赔率与限额配置

```text
管理员修改顶部赔率/特码赔率/特码返水
  -> 失焦或回车自动保存
  -> 配置写入游戏配置表和特码赔率表
  -> 重新登录或刷新后保持

管理员点击限额
  -> 弹窗填写 13 项整数限额
  -> 服务端校验正整数和最小/最高注额关系
  -> 保存为当前全局配置

玩家下注
  -> 读取该玩家当前期已占用额度
  -> 逐项校验最低注额、玩家最高注额、单场总限额和玩法限额
  -> 只拒绝超限项
  -> 合法项继续扣分、生成注单并发布反馈
```

规则：

- `赔率`和`特码返水`当前只保存和展示，不参与赔率和积分计算；`特码赔率`是特玩法的实际赔率。
- 限额按单个玩家、当前期累计计算；`CANCELED` 注单不占额度。
- `玩家最小注额`是单笔最低金额；`玩家最高注额`和`单场总限额`按当前期累计判断。
- `单双限额`覆盖`单`和`双`，`大小限额`覆盖`大`和`小`，`通限额`覆盖`通`和`无`。
- 校验在写入前完成，组合下注只拒绝超限那一项，机器人反馈给出原因、上限和剩余可下额度（BY220: application/rbt/controller/Index.php:712 ChangeLimit、:966 tuoMinMax 为机器级限额配置；「只拒绝超限那一项」属本项目工程增强，见 docs/需求基线/2026-10-02-BY220同业务现代技术栈重建定位.md §4）。
- 前端弹窗校验只是即时反馈，服务端校验才是最终事实。
- 聊天室下注路径由 `chat_room` 数据库行锁保证“读额度-写注单-提交”之间没有并发插入，同一大厅消息按提交顺序串行。
- 直连下注接口没有房间行锁，使用实例内 `PlayerBetLock` 按玩家串行并覆盖到提交；多实例部署前这些接口仍需数据库行锁或分布式锁。

## 6. 聊天、下注反馈与实时通信

```text
用户发送文本
  -> 服务端识别发送者身份
  -> 持久化原始用户消息
  -> 判断普通聊天/问候/下注/错误格式
  -> 下注形态进入正式下注服务
  -> 机器人反馈作为公开聊天消息持久化
  -> outbox / WebSocket 广播
  -> 断线客户端按游标补偿
```

规则：

- 用户原文和机器人反馈对聊天室可见。
- 错误格式、普通聊天和未确认玩法不能静默吞掉，应返回明确错误反馈。
- 反馈消息不能替代注单、钱包、结算和审计事实。
- WebSocket 是单实例实时能力；REST 历史查询和短轮询/重连补偿是降级路径。
- 消息、outbox、发送 ACK 和结算反馈需要幂等键，失败重试不能重复展示业务结果。

当前已确认的聊天指令：

| 输入 | 服务端行为 | 机器人反馈 |
| --- | --- | --- |
| `查` | 读取当前余额 | 公开回复剩余粮草 |
| `流水` | 读取当前业务日汇总 | 公开回复流水、盈亏和期数 |

## 7. BOT 自动/手动行为

```text
管理员配置 BOT
  -> 选择 AUTOMATIC 或 MANUAL
  -> 期号进入 BETTING 时按「活跃比例 × 每期注单」生成计划
  -> 每条动作带 scheduled_at，在投注窗口内随机分布
  -> 调度器只执行到期动作，立即执行忽略计划时间
  -> 条件校验账号 ACTIVE 且链接未拉黑、未过期
  -> 按可用余额、剩余额度和全局托上限压降或跳过
  -> 统一进入正式聊天/下注服务
  -> 保存 SUCCEEDED / SKIPPED / FAILED
  -> 关联聊天消息、注单和错误信息
```

必须保持：

- BOT 是测试玩家身份，不是独立服务端机器人。
- **链接是托工作的前提**：拉黑、链接过期、停用、删除后停止工作，已排队动作按 `LINK_INVALID`、`PLAYER_INACTIVE` 或 `ISSUE_CLOSED` 收尾。
- 活跃比例按 A+B：先按概率决定本期是否参与，参与时本期注单数按比例收缩（至少 1 单、不超过配置值）。
- 金额来自下注范围档位（`随机`时全局 30-30000 且不超过余额 20%），按整十规则取整，只使用整数。
- 玩法从配置集合（最多 11 类）随机选择，参数随机但必须能被解析器接受（BY220: application/common.php:454 wfuser 是玩法文本解析器；「11 类」是本项目托行为的配置集合，见 docs/验收记录/2026-09-24-托玩家自动行为改造验收记录.md）。
- 全局风控：所有托每期的总注单数和总积分达到上限后，其余动作记 `SKIPPED(BOT_ISSUE_CAP)`。
- 余额不足时只降额，不自动触发上分；上分申请由独立概率控制并进入后台审批队列。
- 自动行为不能绕过余额、期号、玩法解析和权限规则。
- 动作需要唯一幂等键、租约、重试次数和失败原因。
- 玩家停用或软删除后，执行前必须再次检查 ACTIVE 状态与链接可用性（BY220: application/rbt/controller/Index.php:151 SetBlack 拉黑/拉白开关；「执行前二次检查」属本项目工程增强，见 docs/需求基线/2026-10-02-BY220同业务现代技术栈重建定位.md §4）。
- BOT 的下注、扣分、结算和报表都应留下可查询事实；自动模式不再产生闲聊消息。

## 8. 积分记录与业务日对账

```text
管理员打开普通玩家积分记录或托积分记录
  -> 选择业务日期
  -> 服务端按 Asia/Shanghai 06:00 计算业务日范围

  -> 按玩家聚合汇总
  -> 展示注单、流水和动作明细
```

当前规则：

- 每天早上 06:00 切换业务日。
- 总盈亏取该业务日已结算注单的 `net_profit` 合计。
- 普通玩家和 BOT 使用同一套报表结构，但入口名称不同。
- 抽水、飞单和代理分成暂不建模、不展示、不计入统计。
- 报表读取现有业务表和钱包流水，不建立第二套事实源。
- 积分记录报表的入口在 `/console` 机器端玩家/托工作台（BY220: application/rbt/controller/Index.php:388 GetScoreHis、:395 GetScoreHisDetail、:1062 Getalltongji）；接口层放行集合仍为 `USER_MANAGE | AGENT_PLAYER_MANAGE | AGENT_CONSOLE_READ`（**收紧为仅 `AGENT_CONSOLE_READ` 属未执行的待确认项**），普通玩家不能查询后台报表接口。
