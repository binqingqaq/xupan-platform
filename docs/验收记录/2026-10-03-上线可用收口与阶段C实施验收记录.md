## 5. 明确的技术选择与理由

| 选择 | 为什么不选另一个 |
| --- | --- |
| MySQL `GET_LOCK` 而非 ShedLock / 锁表 | 不新增表结构、不引入额外依赖；锁随连接释放，进程崩溃不留死锁。代价是必须独占一条连接，已在代码中注明并实现 |
| 进程内限流而非 Redis / Bucket4j | 用户已确认单实例单进程部署，进程内状态不会不一致；代价是重启后计数清零，对"防枚举"可接受 |
| `MANUAL` 状态而非无限重试 | 不引入新状态就会让失败单永远留在候选池，头部阻塞会复现——这正是原缺陷的成因 |
| 风控命中单独建表而非只读 `reject_code` | `reject_code` 只保留最终原因；"同一代理连续被拒 30 次"这类信号需要计数与时间序列，逐单扫描代价高 |
| 处置流水追加而非只改状态列 | 处置含人为判断，必须留"谁、何时、按什么理由、从什么状态到什么状态"，否则事后无法解释一笔退款是谁批的 |
| 风险命中 FK 用 `ON DELETE CASCADE` | 命中是代理的**从属事实**；而额度账本刻意**不设级联**，因为账本是不允许随代理消失的凭据 |
