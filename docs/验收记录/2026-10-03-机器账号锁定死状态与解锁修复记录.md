# 机器账号锁定死状态与解锁修复记录（2026-10-03）

> 触发方式：使用者在本机边玩边验，实测「机器管理里新建的账号登不进 `/console`」。
> 结论：**不是密码错，也不是机器账号不能进后台**，而是登录账号被置成了 `LOCKED` 且 `locked_until` 为空，
> 该组合在现有认证逻辑下**永远不会自动解锁**，而机器管理只显示 BY220 的机器状态，于是既看不出被锁、也没有解锁入口。
> 本文记录根因、修复、证据与仍未处理的遗留项。

## 1. 现象（使用者实测）

| 序号 | 操作 | 实际结果 |
| --- | --- | --- |
| 1 | 用「机器管理」建的机器账号登录 `/console` | 提示「用户名或密码错误」 |
| 2 | 在「机器管理 - 编辑机器账号」里改密码并保存，再登录 | 仍然「用户名或密码错误」 |
| 3 | 用超管 `admin` 登录 `/console` | 可以进 |

第 3 条容易误导：`/console` 并没有「只允许机器账号」的限制，`ADMIN` 角色本身持有
`AGENT_CONSOLE_READ` / `AGENT_MANAGE` 等全套权限，所以超管能进属于正常，与第 1 条的失败原因无关。

## 2. 根因（代码级）

1. **锁定即死锁**：`UserAccount#canLogin` 对 `LOCKED` 的判断是
   `lockedUntil != null && !now.isBefore(lockedUntil)`；当 `locked_until` 为空时永远返回 `false`
   （`server/xupan-server/src/main/java/com/xupan/server/auth/domain/UserAccount.java`）。
2. **错误被伪装**：`AuthenticationService` 在 `canLogin` 为假时统一返回 `AUTH_INVALID_CREDENTIALS`，
   对外文案就是「用户名或密码错误」（`.../auth/service/AuthenticationService.java`），所以从界面无法区分「密码错」和「被锁」。
3. **改密码不解锁**：机器管理「编辑」只覆盖 `sys_user.password_hash`
   （`.../platformadmin/service/PlatformAdminService.java#updateMachine`），完全不碰 `status`，
   所以重置密码后依旧登不上。
4. **锁定状态的来源**：`UserRepository#updateManagedStatus` 把账号置为 `LOCKED` 时会同时清空 `locked_until`，
   而管理端（用户管理/子账号/机器状态）确实允许写 `LOCKED`，于是产生「永久锁死」形态。
   本机遗留机器账号 `localadmin`（`sys_user.id=66`）实测就是 `status=LOCKED`、`locked_until=NULL`、`failed_login_count=0`。
5. **界面看不见**：机器管理列表的「状态」列取的是 BY220 语义的 `agent.status`（正常/停用），
   与登录账号的 `sys_user.status` 是两套值，账号被锁时列表仍显示「正常」。

## 3. 修复内容

### 3.1 后端

- `PlatformAdminService.MachineRow` / `SubAccountRow` 新增 `accountStatus`（来自 `sys_user.status`），
  机器列表、机器详情、子账号列表的 SQL 都补上 `sys_user` 连接与字段。
- `PlatformAdminResourceController.MachineResponse` / `SubAccountResponse` 同步输出 `accountStatus`，
  前端因此可以区分「机器停用」与「登录账号被锁」。
- 解锁复用 BY220 口径的既有接口（不新增业务动作）：
  `PATCH /api/admin/machines/{id}/status {"status":"ACTIVE"}`、
  `PATCH /api/admin/sub-accounts/{id}/status {"status":"ACTIVE"}`。
  该路径会调用 `updateManagedStatus`，顺带清空 `locked_until`、失败次数并递增 `security_version`，即完成解锁。
- 审计摘要追加可判定信息：锁定状态下执行状态变更时写 `unlockAccount=true`，便于事后在操作审计里核对。

### 3.2 前端

- 「机器管理」「子账号」列表：`accountStatus === 'LOCKED'` 时状态列显示红色「已锁定」，
  操作区把「停用/启用」替换为「解锁」，避免超管误点成停用后仍看不出账号被锁。
- 类型定义补充可选字段 `accountStatus`，不影响旧响应解析。

## 5. 同日追加：删除改为**完全物理删除**（使用者两次确认，对齐 BY220）

最初发现的问题是「软删除不释放用户名，删掉后无法重建同名机器账号」：
删除 `localadmin` 后同名重建返回 `USER_USERNAME_EXISTS`，当时只能改名成 `localadmin2`。
使用者第一次确认「完全对齐 BY220、不要保留」，第二次进一步明确**此前刻意保留的三处也全部删掉**
（原话：那些也不是什么有用数据，有用流水后续再跑就有了，一直保留会干扰）。因此最终语义是：

### 5.1 最终删除范围

| 入口 | 删除内容（物理删除，BY220 对应） |
| --- | --- |
| 机器管理 - 删除 | 名下**玩家/托**（含余额、注单、余额流水、行为/动作、链接与偏好、玩家账号与登录账号）→ 上报订单 → 机器积分流水 → 彩种配置 → `agent` 行 → 机器登录账号（BY220 `Rb.php` 删 `x_robot` + `x_rbuser` + `x_record` + `x_rbfly`） |
| 子账号 - 删除 | **连带名下所有机器**（同上整套）→ 子账号积分流水 → `agent_group` 行 → 子账号登录账号（BY220 `Users.php` 删 `x_admin` 并删其 `x_robot`） |
| 设置 - 删除全量账号 | 全部玩家/托、全部机器（保留平台直属主机器行）、全部子账号、其余登录账号；**保留执行者本人**（BY220 `Gd.php::userDels` 保留根管理员与主机器） |

- **不再有任何拦截**：`MACHINE_HAS_PLAYERS`、`MACHINE_HAS_REPORT_ORDERS`、`SUB_ACCOUNT_HAS_MACHINES` 三个拦截全部取消。
- 删除后同名登录名与机器编码/子账号编码立即可复用（实测删除→重建→再删除→再重建均成功）。
- 实现集中在 `AccountPurgeService`（新增），按「先删引用方再删被引用方」的顺序清理，避免外键报错。

### 5.2 仍然保留的两类数据（并说明原因）

1. **审计行**：`sys_operation_log`、`sys_login_log` 等历史行**保留**，只把「操作者/创建人」外键置空
   （`V69` 已把 `chat_user_mute.operator_user_id`、`player_access_link.created_by`、
   `game_bet_edit_record.operator_user_id`、`player_admin_notice.sender_user_id` 放开为可空，
   共 20 处引用在删除账号时置空）。理由：审计是项目基线要求，删掉就没有追责依据；
   行内摘要本来就有用户名文本。另新增兜底：若账号被删后仍有待写审计（事务提交后回调），
   `OperationAuditRepository` 会退化为「无操作者」写入并记 WARN，而不是丢掉这条审计。
2. **公共聊天室消息**：`chat_message` 保留（`sender_name` 是发送时的快照），删账号不影响已发出的聊天内容。

### 5.3 迁移

- `V69__机器与子账号物理删除与账本归属快照.sql`（先行版本）：新增两个归属快照列、放宽
  `ck_agent_ledger_target`、放开 4 个操作者引用列的可空性。
- `V70__账号物理删除收敛与移除账本快照.sql`（最终版本）：清掉 V69 短暂采用「解除归属」时留下的孤儿流水、
  恢复「每条代理层流水必须挂在机器或子账号上」的原约束、删除两个不再需要的快照列。
  操作者引用列的可空性**保留**（第 5.2 条需要）。

### 5.6 只有本机 MySQL 才会暴露的三个缺陷（H2 全部测不出来，已修）

这轮是「H2 全绿、真实库才炸」的典型，三处都写进了回归用例：

1. **WS 票据顺序**：`purgeLoginAccount` 原先先删 `auth_session` 再删 `auth_ws_ticket`，被
   `fk_auth_ws_ticket_session` 挡住（H2  fixture 里这些账号没有 WS 票据）。已改为先删票据
   （按 `user_id` 以及 `session_id` 归属双条件），并在用例里先给玩家造一条 WS 票据。
2. **执行者自己的玩家档案**：本机 `admin`（`sys_user.id=1`）同时挂着一行 `demo_user_account`（早期测试留下），
   全量删除把执行者一起删掉，随后写审计时 `fk_sys_operation_log_user` 失败。
   已改为全量删除**跳过执行者自身的玩家档案**，用例里也补了「执行者也有玩家档案」的前置数据。
3. **通知收件人可以是后台账号**：`player_admin_notice.recipient_user_id` 指向 `codex_preview_admin`，
   原先按「玩家数据」拦截并抛错。已改为删除账号时一并删除「收件人是该账号」的通知行。
   顺带把这类顺序错误从笼统的 400 改成带表名的 409 `PURGE_ORDER_INVALID`，便于定位。

## 6. 影响范围与回滚

- 新增响应字段 `accountStatus`（向后兼容）；「删除」与「删除全量账号」都从软删除改为**物理删除**，
  是**行为变更且不可恢复**：账号、玩家/托、注单、余额流水、机器积分流水都会真的消失，
  这与项目此前的「账本不可变、审计保留」口径不同，是使用者明确要求对齐 BY220 的结果，已登记在案。
- 审计行保留但操作者可能为空；公共聊天记录保留。
- 回滚方式：还原 `AccountPurgeService`、`PlatformAdminService`、`PlatformSettingsService`、
  `OperationAuditRepository`、两个 `.vue` 页面与类型定义，并按前向修复原则再加迁移还原 `V70`/`V69`；
  已经物理删除的数据无法恢复。
