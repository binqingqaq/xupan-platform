# 2026-09-24 管理员自助重置密码锁等待修复验收记录

> 验收对象：后台「用户管理 → 重置密码」，目标用户与当前登录管理员为同一人时的链路
>
> 证据等级：本机后端 H2/Flyway、本机 MySQL 8.4 运行态；不是服务器或生产验收。

## 1. 现象

- 在用户管理里给当前登录的管理员重置密码，弹窗一直停在「确认重置」的禁用状态。
- 约 50 秒后请求失败，刷新页面后仍只能用旧密码登录，密码实际没有改变。

## 2. 根因

后端日志给出直接证据：

```text
未预期 HTTP 异常 httpMethod=POST path=/api/admin/users/1/password
exceptionType=org.springframework.dao.CannotAcquireLockException
SQL [INSERT INTO sys_operation_log ...
HTTP request completed httpMethod=POST path=/api/admin/users/1/password status=500 durationMs=50827
```

链路分析：

1. `UserAdminService.resetPassword` 在业务事务里先 `SELECT ... FROM sys_user WHERE id = ? FOR UPDATE`，并对目标行执行 `UPDATE sys_user SET password_hash = ...`，因此**持有操作人自己那行 `sys_user` 的排他锁**。
2. 同一步紧接着写操作审计。`OperationAuditRepository.record` 当时标注 `@Transactional(propagation = REQUIRES_NEW)`，审计 INSERT 会**挂起业务事务、另开一个连接和事务**。
3. `sys_operation_log.operator_user_id` 有外键指向 `sys_user(id)`，插入子表记录时 InnoDB 需要对父行加共享锁；父行正被业务事务排他锁定 → 审计事务等待自己。
4. MySQL 无法检测这种跨连接的自等待，等待到 `innodb_lock_wait_timeout`（默认 50 秒）后抛 `CannotAcquireLockException`，业务事务整体回滚 → 密码没有改、旧会话也未撤销。

同一类问题也会出现在「管理员上传自己的头像」「管理员修改自己的角色」等任何「改自己这行 + 写审计」的操作上；`findActiveAdminUserIdsForUpdate` 会锁住全部管理员行，因此自助改角色同样会命中。

## 3. 修复

`OperationAuditRepository` 不再用方法级 `REQUIRES_NEW`，改为显式管理审计事务：

- 存在业务事务时，登记 `TransactionSynchronization`，在业务事务**完成（提交或回滚）之后**用独立事务写审计；此时业务事务的行锁已经释放，外键检查不会再自等待。
- 没有业务事务时直接写，行为与之前一致。
- 审计仍保留「业务回滚也要留失败记录」的语义：`afterCompletion` 在提交和回滚两种结果下都会执行。
- 审计写入失败不再回滚业务操作（之前会把业务一起拖垮）；失败会在日志里以 `TransactionSynchronization.afterCompletion threw exception` 记录。

## 6. 已知边界

- 审计摘要仍受敏感词校验约束：如果审计摘要包含 `password`、`token`、`secret` 等词，审计写入会抛错并被事务完成回调记录到日志，此时业务操作已提交、审计行缺失。当前代码里摘要为 `username=xxx`，正常用户名不会命中。
- 审计写入发生在业务事务完成之后，与业务操作之间有一个极短的进程内窗口；进程在窗口内崩溃会丢审计行，这是为消除自锁而接受的取舍。
