## 0. 项目本质（用户再次确认，2026-10-02）

`xupan-platform` 不是另做一个相似产品，而是用现代技术栈重建 BY220 的同业务系统。

```text
BY220 业务流程
  -> 保持基本一致
  -> 替换技术栈
  -> xupan-platform
```

三大业务面必须同时存在并保持一致：

| 业务面 | BY220 对应 | xupan 目标 |
| --- | --- | --- |
| 玩家前台/下注 | 玩家访问链接进入、期号、开奖、聊天、下注 | 现有玩家前台按 BY220 流程收敛 |
| 代理后台 | `robot.php` | `/agent`，代理创建玩家和托并执行代理操作 |
| 超级管理后台 | `admin.php` | `/platform-admin`，平台超级管理员的全部业务菜单 |

为什么要做 xupan-platform：

- 不是因为业务要变。
- 而是因为 BY220 的 PHP、ThinkPHP、旧前端和旧运行方式不适合继续作为长期技术底座。
- 所以应当保留 BY220 的业务结果和操作习惯，替换底层技术和工程实现。

如果 BY220 已有页面或流程，未经用户确认不得改掉、合并或重新设计。只有合规、安全、数据库和现代工程约束造成的差异可以单独记录。

## 1. 总原则

用户要求：

> BY220 的业务规则和界面逻辑直接严格平移到 xupan，先照着 BY220 有的界面实现一遍，不要开发者自行改流程、改菜单或重新发明业务。

“平移”指：

- 业务名称、菜单结构、操作路径、字段含义、操作顺序和状态结果与 BY220 一致。
- 使用 xupan 的 Java 21、Spring Boot、Vue、MySQL 8.4 重新实现。
- 不是复制 PHP 代码、模板、数据库配置、密码、Token 或外部地址。
- 若受虚拟积分合规、安全或技术栈限制必须调整，先记录偏差并取得用户确认。

## 4. 子账号规则

BY220 `子账号`不是代理账号，也不是玩家账号。

核对源码：

- 菜单：`application/admin/view/public/head.html`
- 控制器：`application/admin/controller/Sub.php`
- 列表：`application/admin/view/sub/list.html`
- 表单：`application/admin/view/sub/form.html`
- 数据表：`x_admin`，典型 `type=0`

当前已观察到的字段和操作用于今后严格实现，包括：

- 用户名、密码、积分、失效日期。
- 子账号权限 `subxiugai`。
- 机器人权限 `rbxiugai`。
- 统一飞单、飞单账号、飞单密码、飞单网盘、飞单盘口。
- 添加、编辑、删除、刷新。
- 子账号状态、网盘/盘口信息展示。

xupan 实现时必须先建立字段映射，不能只做“渠道组”名称后结束。

当前 xupan 已通过 `agent_group.sys_user_id` 建立登录账号映射，并限制子账号只能访问自己的机器和报表范围；菜单按最小权限裁剪。
BY220 子账号在 `Sub.php` 中被 `isAdmin()` 拒绝，而当前项目也禁止子账号进入子账号管理；其余可见菜单以实际权限复核结果为准。

- 登录链接、二维码和复制链接。
- 下注榜、流水、盈亏、账变。
- 玩家密码、昵称、用户名和状态操作。
- 赔率、特码赔率、返水、单边/双边、封盘、取消、各类限额（`PeiLv/tePeilv/FanShui/teFanshui/ls/fengpan/cancel/zuidi/zuigao/total/...`）。

当前进度（2026-10-02）：

- `/console`（代理后台唯一入口）已具备下注榜、上下分确认、最近上下分记录、玩家工作台（创建玩家/托、上下分、链接、昵称、头像、软删除、托行为、积分记录）、全局赔率与限额；**仍是管理员权限、全局范围**。

## 10. 完成判定

只有当某一 BY220 页面满足以下条件时，才能标记完成：

1. 菜单名称和位置一致。
2. 页面主要结构一致。
3. 操作按钮和流程一致。
4. 字段含义一致。
5. 数据结果和状态变化一致。
6. 权限边界一致。
7. 已记录必要偏差。
8. 已完成本机运行态验证。
